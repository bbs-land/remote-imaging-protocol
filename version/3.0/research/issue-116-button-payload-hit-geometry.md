## Exact positional payload consumers

Shared splitter `0x2a3e9–0x2a4d3` finds the first literal `<>` using `0x65965` / original strstr, saves/splits it at `0x2a460–0x2a479`, then finds/splits at most one more delimiter at `0x2a494–0x2a4ae`. It assigns outputs in fixed order: icon filename, label, entire remaining host source. No type-dependent shifting, quote/backslash escape or third delimiter scan is present. Without a delimiter, all text occupies the icon slot. Empty/missing trailing slots point to the shared empty string RVA `0x79594`. Extra `<>` pairs belong to the host remainder; thus `<><><>` has host `<>`, not three absent blocks.

Renderer `0x2a66e` calls that splitter on field +0x32, then checks icon-name source length <128 (`0x2a6af`) and label source length <256 (`0x2a6f5`). It prepares the filename through the existing ordinary expansion path (`0x2a76a -> 0x4b0e4`) and uses the earlier ICON→CLIPBOARD→PLAIN precedence for face rendering. Non-ICON types still have the icon **position**; a nonempty first slot does not become their label. Their image source ignores it, but it remains subject to the common filename field validation/preparation. Blank that slot for non-ICON content rather than defining an alternate shorthand.

Constructor `0xac19–0xac2a` copies the full incoming text then extracts the already documented ID prefix. Its next helper `0xac39 -> 0x65611` reverses the text (`0x65c90 -> 0x75ab0`), trims trailing ASCII whitespace (`0x654e9`, ctype bit 8), then reverses again: this removes **leading whitespace from the remaining whole payload**, after ID recognition. It does not trim every block or the host remainder. Empty text after that step rejects at `0xac44`; the splitter also rejects empty input at `0x2a429–0x2a43b`. Zero _logical_ text fields are represented by `<>` or `<><>`, not by an absent string. ICON needs a nonempty usable filename under the existing image-loading rules.

The earlier #112 example used `!|1U0A0A2I140000Style B` and incorrectly called its first-slot text a label. Its numeric argument decoding and style-state proof were correct, but did not validate positional payload interpretation. Correct it to `!|1U0A0A2I140000<>Style B`; append a correction to that derivation rather than silently claiming the old example was fully validated. #112's state/current/protection answer is unchanged.

## Validation versus deferred execution

The inherited sentence “If the host command string ... cannot be parsed ... completely ignored” does not specify validation timing or data-dependent syntax. Existing host execution first preprocesses angle syntax, then segments HCL/templates, then performs two ordinary response passes, enforcing the adopted 4096-byte working-prefix rule at its defined entry/replacement points. A provider can change which later ordinary bytes exist; inactive branches and clipped suffixes may never reach those consumers. Do not invent a whole-raw-host syntax pass that executes or rejects them ahead of time.

Source action `0x2c297` extracts host text through `0x2a383` and invokes `0x4ab3e` only at action time, consistent with the normal gesture contract. There is also a conditional constructor host-action call at `0xb2d4`; it must not be misrepresented as evidence that the original constructor never executes any host action. The explicit documentary rule says drawing a selected button must not send its host command. Do not investigate or require the obsolete conditional branch in place of that rule.

**Explicit portable validation completion:** definition-time preflight checks the numeric/style/required-image/clipboard/field-count constraints, raw payload slot structure/lengths and geometry only; the third slot remains opaque stored HCL source. It neither evaluates nor rejects that source on a speculative provider/preprocessor/HCL/dollar pass. Creating/preselecting a button never executes its click host providers, delays, assignments, playback or transmissions. Rendering the distinct filename/label slots retains their already adopted ordinary-consumer semantics. Activation runs the existing host stages in the then-current environment and field callback context. It checks only what each adopted stage actually reaches, with its existing skipped-header rules, insertion/clipping and error behavior; do not add an ordinary-suffix pre-scan. A later syntax/provider failure does not delete the existing button or roll back already completed effects. This clarifies the old blanket sentence rather than promising that every original constructor path has those properties.

Pure preflight rejection happens before painting or adding a resident field and leaves prior fields/style intact. Missing required ICON input, invalid numeric/style fields and raw slot bounds can reject there; existing later image/font/render failures keep their documented behavior, not an invented transaction/rollback guarantee. No new host-source byte cap replaces the adopted wire/storage/response limits. A host that appears malformed in raw storage can legitimately be clipped or discarded before that syntax is reached.

## Geometry source facts and explicit input policy

Dynamic plain corners are **ordered in WORLD before conversion**, by original calls `0xaafe / 0xab0e -> 0x3112e`. Complete fixed style size clears the far inputs before that branch, matching #27; an incomplete size uses both command dimensions, not a per-axis hybrid. The converted anchor and existing viewport origin produce device face bounds; stored dimensions use far-minus-near, with no +1. Button field +0..+0x0c holds face geometry; +0x10..+0x1c holds interaction geometry. Initial BEVEL inflates the latter at `0x2aedd–0x2aee2`; the already documented RECESS is excluded from the persistent field. Earlier effect units, size, bitmap and clipboard choices remain adopted.

Original pointer hit helper `0xe749` called with margins (1,1) tests `L-1 <= x < R+1`, `T-1 <= y < B+1`; for integer points this includes one pixel before the near edge and the stored far boundary. Original hover `0x4035` instead uses `L <= x <= R`, `T <= y <= B`. These differ from each other and from the far-minus-near drawing extent. They therefore cannot be silently presented as one uniform pixel-extent convention. No boundary input is executed to reproduce those differences.

**Explicit portable hit/clipping completion:** use positive, half-open device rectangles for both clicks and hover: `L <= x < R`, `T <= y < B`. The stored far value remains the extent boundary; do not decrement it for storage or add 1 to dimensions. This consistently follows the resolution-independent rectangle/drawing extent convention and intentionally does not claim native near-edge tolerance or inclusive-hover parity.

For dynamic plain buttons, order both non-omitted WORLD corner pairs, convert once with existing viewport origin rules, then reject a nonpositive device face width/height; do this **before** effect expansion so a degenerate line is not made into a field by bevel. Both far coordinates zero with incomplete fixed size are an omitted/empty definition, not a new full-viewport shorthand. Both fixed dimensions present ignore the transmitted far corner under the prior rule. This safe positive-area guard is completion; old degenerate recovery or raster normalization is not required.

Mouse fields and mouse-active buttons use the PORT0 viewport as their effective creation destination, regardless of an unrelated current offscreen/other port; nonmouse decorations keep their current-port destination. Original `0xa9bf -> 0x3445b` is an early **current** viewport deactivation check, not proof of a PORT0-specific policy. The explicit documented screen-port ownership takes priority over treating that check as a universal destination rule. Do not investigate unrelated-current-port acceptance bugs.

Complete the effective-destination rule explicitly: reject new mouse geometry if PORT0's viewport is inactive or its positive intersection with the physical screen is empty. Form interaction bounds from the existing face/effect geometry, exclude the persistent recess, and intersect with PORT0 viewport and screen as half-open extents. Empty or merely touching intersection creates no resident field and no painting/hover/click/host action for that definition. Partial clipping preserves the existing face/effect dimensions rather than stretching/recentering it; only allowed painting/input is clipped. The input rectangle has no halo across a clip boundary. Reactivation does not resurrect a definition that was skipped.

The stored global hit rectangle and creation eligibility are snapshots. Later viewport movement/deactivation does not silently relocate/reclip/delete existing fields or retarget a held gesture; explicit field deletion/reset/restore and global input controls retain their own rules. This completion uses stable field ownership from #113 and does not add a new PORT/TW deferred-query loop. Nonmouse geometry has no mouse/hover entry. Preflight failure does not consume the 128-region limit or change earlier overlap order.

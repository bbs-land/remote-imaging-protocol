## Wrapper and serializer trace checkpoint

Extended `run/riptel-macro-probe DLL`: **392,029 checks pass**. Original registration confirms all four main callbacks and all 20 numbered aliases including RESTORE0. Original wrappers run with only manager boundaries captured (`0x23bd3` save, `0x23ca6` restore, `0x23d0b` push, `0x211f6` pop, `0x23d6e` delete). Matrices cover no argument/BASE/base/PUSH-or-POP/numeric 0..9, normal and failed manager returns, all aliases and alias-argument rejection, invalid count/selectors, plus four ordinary action-expansion cases. Callback results are always NULL/empty actions; invalid syntax sets variable error. These tests establish dispatch, **not actual snapshot effects**, which remain to be probed.

Ordinary SAVE/RESTORE addresses only family **6 (screen)**. Numbered aliases issue exactly the same operations for their literal slot, accepting no arguments. Base restore does not delete. Numeric restore calls restore then delete **regardless of restore return status**. SAVEALL/RESTOREALL order is **3 TW → 2 PORT → 5 mouse fields → 6 screen → 4 palette → 0 buttons → 1 graphics styles → 7 environment**, different from the inherited recipe. Numeric RESTOREALL attempts all eight restores first, then all eight deletes in the same order. Base/all/PUSH/POP wrappers continue through all operations even when every captured manager result is zero. There is no wrapper rollback or all-or-nothing success check. Need validate real screen protection/consume behavior below these boundaries.

Original save/restore function tables at `.data` `0x7de30/0x7de50` select screen **0x236fb/0x2391a**, style **0x217f7/0x218bf**, port **0x219a9/0x22226**, palette **0x22f02/0x22fcb**, buttons **0x21345/0x21622**, TW **0x22c0c/0x22d71**, mouse **0x230a8/0x23274**, environment **0x234d2/0x235da**. Eight backup-family records have stride **0xb17** through context +0x3e; each stream record has stride **0x87**, filename at +0, file descriptor +0x81, flags +0x85; numbered protection is bit **4**. Screen operations must not confuse that protection with port or palette-entry protection.

Screen serializer `0x236fb` writes **768 raw RGB bytes from the current palette entry**, then `0x237ce` captures the physical screen DC from **port record zero +0x6c**, regardless of current port. Its capture dimensions are client rectangle width/height from port-system +0x32..+0x3e; BitBlt is (0,0), SRCCOPY. It calls generic bitmap serializer `0x21f91` with include-palette flag **1**, so the stream contains **another 768-byte current palette copy after the bitmap metadata/pixels**. Do not miss that nested palette because the outer serializer already saved one. Metadata is type/width/height/stride as low words, then planes/depth as bytes, raw bitmap bytes, then palette; no viewport, current-port index, status bar, styles or button table is serialized.

Screen restore `0x2391a` reads the outer palette, copies it directly into the **currently selected palette's RGB bytes** with memmove `0x6b9a0` and uploads via original `0x3e2e7`. There is no saved palette index or entry-protection check. The generic bitmap reader `0x22968` with flag 1 then repeats that target overwrite/upload from the nested copy. `0x23a00` presents the bitmap to **port zero's DC** at (0,0), SRCCOPY, at saved bitmap dimensions. It changes no viewport record or selected port and has no style/button/status restoration. Helper `0x3e254` selects/realizes palettes across DCs; it is not a status-bar setter. Native palette/port/status scope assertions remain next.

Original stream open `0x2148a` creates a generated client-work-directory file, using original filename producer `0x212e8`: **`%03hu%05hu.$$$`** (instance number, incrementing counter), checked for collisions with GetFileAttributesA. It does not use RIPTERM*.SAV. Open flags are 0x8302 for writing / 0x8100 for reading, mode 0x180. Re-save unlinks the previous file. Original close `0x21543` closes but normally retains the file, while delete `0x212a1` closes if necessary, unlinks, clears filename/flags. Need native virtual-file service captures to validate lifecycle and avoid actual temporary disk files.

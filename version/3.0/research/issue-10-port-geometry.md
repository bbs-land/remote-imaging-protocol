## Initial static derivation

Dispatch physical slot **115**, level 2 `P`, has seven numeric fields `[1,XY,XY,XY,XY,4,4]` and handler **0x466ec**. It converts both corners with original world-to-device helper **0x31084**, subtracts lower minus upper at **0x467a0–0x467b5** with **no +1**, and calls original port initializer **0x3326f** at **0x467e1** with those differences as width/height. Offscreen initialization calls CreateCompatibleBitmap at **0x335f5** using those same widths/heights, sets origin to zero, bounds/viewport right and bottom to width/height, and stores width/height words at entry+0x13/+0x15 (**0x3370c–0x33753**). This strongly indicates a 640×480 allocation for the issue's example, not 641×481 or a physical 1280×960 bitmap. Execute the complete routine and actual query callbacks before publishing query results.

World conversion **0x31084** reads context+0x0e; state offsets +0x24/+0x28 are world width/height and +0x2c/+0x30 are device width/height. Each coordinate is multiplied by device extent and unsigned-divided by world extent. The 1280,960 endpoint therefore becomes 640,480 exactly.

Dispatch physical slot **113**, level 2 `C`, has twelve numeric fields and handler **0x46372**. After coordinate conversion it checks all four source coordinates for zero at **0x4656e–0x46591**, choosing the complete source viewport. It checks **all four destination coordinates first** at **0x465ba–0x465dd**, choosing the complete destination viewport. Only otherwise does it check both destination end coordinates for zero (**0x465df–0x46613**) and synthesize an end using the source rectangle's width/height. Neither branch establishes the final clipping behavior alone.

Original copy compositor **0x134d0** decides scaling by comparing **pre-trim** widths/heights at **0x13533–0x13555**. In the equal-size path it trims each rectangle via **0x13456**, passing the other rectangle as an adjustment target. In the scaling path it passes a null adjustment target and trims each independently. It then calls **0x136a9** (BitBlt, no scale) or **0x13763** (StretchBlt) without recomputing the branch. Trim helper **0x13456** clips right/bottom and subtracts the trimmed amounts from the counterpart's end when supplied. This indicates initial verbatim copies retain one-to-one dimensions under clipping; verify the concrete case natively before updating the inherited blanket clip-then-fit prose.

The viewport diagram arithmetic is independent: screen port origin (25,25) + port-relative viewport origin (40,40) + viewport point (50,50) = **(115,115)**. The point is (90,90) relative to the port. Both 2.0 and 3.0 Markdown copies contain 125; original text remains historical evidence and must be preserved.

## Native allocation and copy checkpoint

New [`run/riptel-port-probe`](../../../run/riptel-port-probe) / [implementation](../../../run/lib/riptel-port-probe.c), registered in deno.json and the script catalogue, passes **1,203 preliminary checks** on the unchanged fingerprinted DLL. The native i386 wrapper uses the same preferred-base mapper and compiler flags as the previous probes; no GUI runs. Reproduce with `run/riptel-port-probe /path/to/ripscrip.dll`.

The original **0x466ec / 0x3326f / 0x31084** path executes; controlled Win32 providers capture actual CreateCompatibleBitmap width/height and supply successful DC/object/palette/fill calls. Original port existence/protection helper is bypassed to an unprotected fresh slot; switch-port only sets the current index, and pixel-budget accounting is a controlled dimension product. Budget availability is ample. State invalidation/drawing synchronization are inert; exact hooks/imports are listed in `main()`. Allocations are observed, not performed by Windows.

At world 1280×960/device 640×480 the issue's exact decoded DEFINE_PORT arguments `[1,0,0,1280,960,3,0]` allocate **640×480**, store width/height 640/480 and switch to port 1. The offscreen boundary/viewport is `[0,0,640,480)`; its last addressable pixel is (639,479). A second definition with endpoint 2560,1920 allocates **1280×960**: offscreen allocations are **not clamped** to the display. The difference is the command's extent-boundary arithmetic, not an offscreen clipping correction.

Original **0x46372 / 0x134d0 / 0x13456 / 0x136a9 / 0x13763** executes for copies; controlled SetRect/OffsetRect/IsRectEmpty have their usual rectangle behavior, while BitBlt/StretchBlt capture final arguments. No raster filter is modeled. For a 4×1 source and 2×1 destination viewport, destination `(1,0,0,0)` reaches **BitBlt destination (1,0), size 1×1, source (0,0), size 1×1** in all five modes. Thus it copies only the first source pixel. Changing destination to all zeros reaches **StretchBlt destination (0,0), size 2×1, source (0,0), size 4×1**, also in all five modes. The all-zero/full-viewport case takes precedence.

An independent geometry matrix covers source widths 1..8, destination viewport widths 1..8, every in-bounds destination X, and explicit equal-size versus fit-to-end rectangles. The original decision is made **before clipping**: equal dimensions remain BitBlt with matching trimmed source/destination widths, unequal dimensions remain StretchBlt with independently trimmed extents. A vertical 1×4-to-1×2 at Y=1 fixture confirms symmetric one-to-one clipping. These checks observe the exact branch and rectangle arguments; no claim about exact RIPtel pixels under scaling is needed.

## Unexpected original PORTW/PORTH query defect

The shipped registration instructions push **0x2f642 for PORTH** and **0x2f863 for PORTW**, at the registration sequence around **0x2614b–0x2617d** (the name pointer operand is 0x26157 / 0x2616f respectively). Both callbacks call common argument decoder **0x2f743**. That decoder returns **AX=1 for valid arguments**, including count zero (current port, PORT, WORLD defaults) and valid CUR/PORT/DEVICE forms with one to three arguments. It returns zero on invalid input.

The actual callback tests are inverted: PORTH at **0x2f668–0x2f67d**, PORTW at **0x2f889–0x2f89e** branch to the numerical calculation on **zero**; on normal valid success they set the variable engine error word at +0x436 to 1 and return NULL. The native probe first calls the original common decoder to verify AX=1 and decoded current port 1, then calls each original callback for counts 0/1/2/3 and confirms **NULL plus error word 1**, without a captured host error report. This is not a fixture expectation silently reversed: the initial expected-640 assertion failed, and the exact original branch explains it. No query helper, callback, validation or world conversion is hooked.

Consequently do not publish numeric PORTW/PORTH output as shipped behavior for the example. The stored physical dimensions are 640/480; the normal inverse conversion would be world 1280/960, but valid original callbacks fail instead of returning those numbers. The query parameter decoder also establishes three arguments (port, PORT/VIEW, WORLD/DEVICE), relevant later to issue #25; do not assume the inherited two-argument summary is a safe alternate form. Invalid arguments can reach calculation with uninitialized decoded state through the inverted gate; do not execute them as an oracle.

The existing macro probe now also executes original registration and the complete ordinary variable-expansion path for these names. Captured original registration confirms **PORTW=0x2f863 / PORTH=0x2f642** among 179 registrations. On the same 1280×960/world and 640×480 port fixture, `A$PORTW$B`, `A$PORTH$B`, `A$PORTW(CUR,PORT,DEVICE)$B` and `A$PORTH(CUR,PORT,WORLD)$B` all remain **unchanged**, return expansion status 1, set variable error +0x436 to 1 and produce no captured host error report. The expanded macro probe passes **66,218 checks**. Thus the original ordinary macro path retains the failed expression; it does not emit 640/480/1280/960 or replace it with an empty numeric reply. Host command-specific error/reply handling is separate. Keep this defect even if a modern generic implementation chooses to repair it; no primary instruction was changed to make the anticipated numeric answers pass.

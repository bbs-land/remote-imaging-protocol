## Original wire and geometry checkpoint

Original byte-parser cases now confirm **both radius descriptors are XY**, at bases36/64 and all supported coordinate widths **2..5**, with maximum-width radius values. `run/riptel-polygon-probe` passes **215,495 checks**. An initial fixture tried width1, which the original shared environment setter 0x3e989 rejects (it accepts 2..5); corrected the fixture to the actual supported range. No fixed-width-radius fallback exists in these U/u descriptors.

Extended `run/riptel-fill-probe` passes **3,463,098 checks**. It executes original U **0x1f108–0x1f2f8** and u **0x1c0fe–0x1c347**, original normalization **0x3112e**, world conversion **0x31084**, port/viewport offset **0x34231**, final bounds helper **0x2530b**, pen/brush/ROP selection and both filled passes. The only new service is stdcall **RoundRect IAT 0x96478**, capturing complete bounds and ellipse dimensions; the original calls remain otherwise intact. Same controlled GDI/context/color/protection boundaries as #12/#33. No Windows rasterization is performed.

Each raw opposing axis pair is normalized **unsigned** before conversion. Both corners use normal X/Y world-to-device conversion, then the handler adds **one to each converted far coordinate** and adds stored viewport origin. Radius is converted **as X only**, `r=floor(rad×device_width/world_width)`; it is not a fixed device input and no Y/aspect-ratio conversion follows. The corner ellipse request is **width=2×r, height=2×(int16_t)(r&65535)**, in both U and u. The high-radius Y sign/truncation difference is a shipped defect, not an alternate intended radius unit. For ordinary r<32768 the requested diameters are equal device values, independent of world Y scale. On world640×350/device640×480, rad20 gives a **40×40 device corner ellipse**, while corner Y coordinates use floor(y×480/350).

No original U/u branch compares the radius against rectangle dimensions or rejects oversized/zero radius. Every radius 0..65535 is captured for both handlers against an 8×6 rectangle. Further matrices cover four profiles (640×350→640×480, 1280×960→640×480, 640×480→320×480, 640×480→1280×960), both handlers, both N states, all four corner orderings, zero width/height/both and radius values0/1/3/4/8/9/20/32767/32768/65535/65536. Controlled RoundRect success/failure produces identical RIP behavior: its return is ignored, no RIP error/rollback occurs, and a requested border pass is still issued after a failed fill call. Zero source extent becomes a **one-unit API box** due to far+1; it is not skipped at RIP level even with N0. Negative signed coordinates are not a wire numeric form; do not generalize a raw unsigned DWORD's wrap into signed wire support. Actual GDI edge/corner raster behavior still needs a separately sourced boundary below before publication.

U always selects the current pen and NULL_BRUSH; it is independent of N. u N0 uses current fill and NULL_PEN; u N1 uses the same combined/separate-pass rule as #33 and retains the current write ROP. No inset/shrink of the fill geometry occurs when N is disabled: the exact RoundRect request is unchanged apart from pen/brush selection. This is stronger evidence than the inherited generic fill-between statement, but a literal pixel grid must distinguish API bounds from actual GDI scan conversion.

## GDI boundary reconciliation

The boundary answer combines the directly executed **original RIP request**, Microsoft's diameter/current pen/brush/exclusive-far contract, and the explicitly identified **published Windows-conformance observations**, not Wine's renderer as an RIP implementation oracle. The current source dataset has ordinary (non-todo) compatible-mode assertions for unchanged bounds, corner exclusion, magnitude-equivalent negative ellipse sizes, oversize per-axis fitting and square-corner radius0. The older path test introduced in 0b38f167677f5611296214d021ff11a41bc55075 contains matching expected paths: RoundRect(30,50,55,35,-30,-30) yields the bounded ellipse at x30..54/y35..49; zero ellipse dimension gives a four-line rectangle; zero API width/height contributes no compatible path. The associated source adjustment clamps each absolute ellipse diameter to the **post-compatible-adjustment geometric span**, independently. These records corroborate the platform construction; we did not rerun them on original Windows and do not claim pixel parity. Microsoft's documented RoundRect API alone did not supply the oversize detail.

For the default compatible geometry, original far+1 is undone at the platform contour's exclusive-far adjustment: contour spans are converted R-L and B-T. Fit ellipse diameter independently to those spans. Ordinary equal diameters therefore remain circular until an axis saturates; oversized values can become an ellipse rather than a common circle clamped by the smaller axis. Conversion precedes fitting. A converted zero radius requests a rectangle; the original signed Y-diameter defect can also create a zero dimension at r65536. Invalid signed wire numerals remain outside the command grammar, while reversed unsigned corners are normalized by the original driver.

The literal grid now distinguishes **strictly interior sample points**, straight contour samples and unspecified curved-edge pixels. It does not invent exact NULL_PEN scan conversion or promise that every contour integer pixel is painted/erased when N changes. Original u forwards the same fill geometry with N0 and N1; no extra inset or shrink occurs. K uses the same far+1 request construction, so the inherited fill-between shorthand cannot add a second inset. U stays an outline even under N0. All four issue questions now have explicit wire, request, construction and inference boundaries; fine device rasterization remains outside the request's stated requirement.

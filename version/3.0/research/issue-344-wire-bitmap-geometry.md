## Rectangle preparation

1. The original `1b` handler `0xc569` loads four decoded coordinates. `0xc648–0xc652` bypasses axis ordering only when both **supplied** far coordinates equal zero. Otherwise `0xc65c` and `0xc66c` call `0x3112e` independently, using the unsigned ordering of each axis. This preserves a natural-size anchor from the both-zero spelling and treats a single supplied zero as an ordinary coordinate during ordering.
2. Calls `0xc67d` and `0xc68e` apply `0x31084` to the two ordered or preserved corners. Its unsigned divisions at `0x3109c` and `0x310b1` truncate the two projections to the ordinary device frame. At `0xc86f–0xc879` a second both-zero test uses the **projected** far pair. If both equal zero, the call at `0xc957` receives the viewport-adjusted near corner, two zero far arguments and geometry selector 0. A nonzero projected far on either axis takes the other branch, adds viewport origin to both corners at `0xc932–0xc949`, and supplies selector 1.
3. Renderer `0x4a410` reads the bitmap and calls `0x49340` at `0x4a49e`. The helper reads decoded image dimensions through `0x4e38e` and `0x4e348` and projects them only when the selector is nonzero. The far X test `0x4938a` and far Y test `0x493a0` each replace a zero far coordinate by near plus the corresponding prepared dimension. The tests use the actual absolute far arguments from the wrapper. Thus a single viewport-relative zero can be canceled by a nonzero origin, while the both-zero branch explicitly passes two zero sentinels regardless of that origin. Source coordinate arguments and renderer extents use low words at the renderer boundary. The portable examples use representable, nonwrapping geometry.

For example, at scale 1/2, WORLD (0,6) to (1,10) projects to relative (0,3) to (0,5). With origin (0,0) the far X stays zero and an 8-pixel bitmap width contributes 4 device units. With origin (5,7) both far components are nonzero and the resulting rectangle has zero width. WORLD (0,0) to (1,1) at the same scale sends both zero sentinels and uses the native 8×6 bitmap at the viewport origin. The corresponding examples include equal endpoints and reversed axes. [Geometry vectors](../ripscrip/4.0-icons-and-bitmaps.md#destination-geometry).

## Initial rendering and follow-on stages

The renderer subtracts the near coordinates from the resolved far coordinates at `0x4a4a3–0x4a4b5` and handles palette adoption and preparation. At `0x4a53f–0x4a591` it publishes the unclipped rectangle before choosing opaque or keyed paint. It does not widen that published rectangle when a lower paint helper changes dimensions.

- **Opaque paint.** `0x4a5c0` passes width and height to `0x4e42b`. At `0x4e497–0x4e4c2` a zero width causes both dimensions to be computed as their decoded source dimensions times the supplied height divided by 100, truncating. For instance, a zero-wide published rectangle of height 50 can send a 40×30 paint request for an 80×60 bitmap. Positive width with zero height passes the zero height to the ordinary stretch call. `0x4e7a8` calls StretchDIBits. `0x4e7ae–0x4e7c1` displays its own diagnostic on `GDI_ERROR`, but `0x4e806` returns success regardless of that draw status. A zero scan-line result also reaches success. The original API return boundary therefore separates backend paint/diagnostics from the wrapper's load-failure branch. [StretchDIBits documentation](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-stretchdibits).
- **Keyed paint.** The unchanged requested extents reach mask `0x493c0`, background capture `0x48f20` and source temporary `0x49000` through calls at `0x4a662`, `0x4a688` and `0x4a6a9`. Any marked failure in these or the final compositor reaches renderer failure, and backend results determine those branches. The opaque percentage rule can also be reached inside the source temporary's drawing helper. The adopted empty-draw protocol performs no image pixel writes on a collapsed logical rectangle after normal resource and palette processing.
- **Duplication.** On renderer success, `0xc9c8` copies the published rectangle. `0xc9f9` passes it unchanged to the shared clipboard helper, which adds one to each extent for allocation. `0xca63` instead requests exactly width and height for a different explicit port following the established protection and deletion order. In native Windows, `0x335f5` passes those requested dimensions to CreateCompatibleBitmap. A zero requested dimension can produce a 1×1 monochrome bitmap, while the logical port bounds remain empty. The portable rule treats this zero-sized explicit creation as a failed replacement after the usual deletion. In either native route, `0x134dd` and `0x1350a` reject empty source/destination rectangles in the compositor before blitting. No copy pair follows. The clipboard can still allocate using its nonzero plus-one extents, with prior pointer/state effects and no restoration of a deleted target. [CreateCompatibleBitmap documentation](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createcompatiblebitmap) · [Clipboard lifecycle](../ripscrip/4.0-icons-and-bitmaps.md#capture-failure-and-geometry).
- **Wallpaper.** `0xcae4` passes the same published seed and the then-current viewport to `0x3ea2e` after duplication. Its `0x3f0a6` reconciler checks the far-minus-near extents at `0x3f0d9–0x3f0e7`, after far-edge trim. A nonpositive dimension reports the wallpaper-size diagnostic and exits before the tiling loops. This does not invoke the image-load marker.

## Failure and placeholder boundaries

Lookup result 1 at `0xc7bc` calls the marker helper `0x383b0` via `0xc7e9`. Result 2 takes the separate deferral path. The image-renderer failure return at `0xc95f–0xc962` also calls the marker via `0xc99b`. Both marker calls rebuild coordinates from the translated wire request before far-coordinate substitution, then finish without duplication or wallpaper. Decode failure can display a native bitmap-read diagnostic inside the renderer at `0x4a46f`. A successful render status with zero logical coverage or a later duplicate/wallpaper failure does not enter these marker paths.

`0x383b0` attempts the `BROKEIMG.BMP` resource, with an internal `BROKEIMG` fallback. `0x38570–0x3857b` requires both caller extents positive before drawing a decorated box and placing the marker one pixel inside its near corner. With a nonpositive extent, `0x385c1–0x385e3` draws the marker at the caller's near corner using its own device size. Successful marker display can additionally reach the missing-file popup setting at `0x387c3`. Failure to prepare or present the marker itself reaches a separate fallback dialog at `0x38618`. Portable renderers can use the same placement with their own diagnostic and marker presentation. These are local effects with no new wire response.

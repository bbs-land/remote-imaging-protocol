## Existing original-font evidence and initial leads

The [issue #3 derivation](issue-3-extended-font-style.md) already establishes original placement renderer **0x40ed0**, normal text adapter **0x42870**, font initializer **0x3ff90**, face lookup **0x3fb50**, realization **0x40170**, bitmap glyph engine **0x523f0** and advance query **0x4efd0**. Its native geometry fixture controls the font engine/bitmap output, so it cannot prove the font rasterizer's fill or hollow policy. Its separate isolated Wine oracle used the real Marin bytes and unmodified font engine for orientation only. Do not silently promote either into evidence for the remaining questions.

First static leads: renderer **0x41485 / 0x41580 / 0x41e98** reads input bytes with zero extension and calls glyph engine per character. Glyph presentation **0x40660** calls SetBitmapBits then BitBlt with ROP **0xb8074a**. The renderer's later loop/bitmap clearing and complete write-mode producer still require tracing before concluding coverage aggregation or XOR behavior. Cache lookup **0x55a30** subtracts the realized font's first character from the supplied code and indexes the cache; trace the uncached record consumer too and verify there is no earlier translation.

## Native renderer, compositor and slot checkpoints

Expanded `run/riptel-font-probe DLL` passes **194,204 checks** on FreeBSD 15.1 / clang 19.1.7. It preserves original placement renderer **0x40ed0**, restored bitmap presenter **0x40660**, wire write-mode setter **0x2102c**, cache slot arithmetic **0x55a30**, and file-offset lookup **0x505e0**. Previous #3 numeric/geometry checks remain. New byte cases use controlled font realization/advance/rasterization for all bytes **1..255**, twice per input, with both Marin and SYMBOL face names. The original renderer passes each byte **zero-extended and unchanged** to the glyph and advance engines. A reference **W (87)** advance query precedes text metrics; a first fixture incorrectly expected only input-byte requests and was corrected after capturing `87,1,1,1,1,1` and tracing the original call. This is not a codepage translation.

Cache tests control **0x52340 / 0x523c0** only to provide an owned realized-font descriptor: first 32, count 224, 224 distinct cached glyph sentinels. Original **0x55a30** is invoked for **all 65,536 unsigned word values** and returns exactly slot `code−32` for 32..255, NULL outside. Original **0x505e0** reads a patterned relative-offset table and adds glyph base directly, for every slot 0..223. An initial offset fixture passed its cached-font record as argument three instead of two and faulted at 0x505eb; reading the actual stack offsets and correcting the argument order fixed it. Debug builds were scoped with Python TemporaryDirectory and core dumps disabled; no core or debug binary remains.

The ordinary renderer reads a byte at **0x41580**, calls rasterizer **0x523f0** once for that glyph at **0x41ed7**, paints its shadow/foreground before advancing, and clears its working glyph bitmap to all ones at **0x42635–0x4264d** before the next character. This is **per-glyph presentation**, not a whole-text coverage union. Presenter **0x40660** uploads the bitmap with SetBitmapBits, then calls BitBlt with fixed **0xb8074a** at **0x40793–0x407af**. Its ternary truth table is `S ? D : P`: the black ink mask replaces with the selected brush, white mask preserves destination. That operation cannot implement XOR; current ROP2 does not replace a BitBlt's explicit ternary ROP.

Native original-presenter tests store every wire write mode **0..4** through original **0x2102c** (style +4), capture two overlapping bitmap copies for each of the **256 byte masks**, and verify the same fixed ROP. Controlled GDI boundaries are SetBitmapBits **IAT 0x963bc**, SetRect **0x96618**, BitBlt **0x963e4**, plus invalidation **0x13c69** and style activation **0xe6e9**. The small mask compositor used to check resulting replacement/retention is an explicit service model, not Windows rasterization. Original typeface/coordinate/placement and presentation decisions remain original. Thus ordinary FastFont glyph ink is copied per glyph even after selecting XOR; overlapping ink does not cancel. Full actual GDI color realization is outside the fixture.

## Hollow-width static derivation lead

Original realization **0x52030** rounds tenths-of-a-point size as `(size+5)/10`; original **0x51eb0** stores that whole point size at realized record +4, horizontal percentage separately at +0x2a, and hollow flag at +0x2c. Original **0x56950 → 0x56340** constructs the outline rasterizer representation. For an ordinary, non-bold hollow face, **0x564cc–0x56555** reads **byte 0x13 of the cached metrics header**, multiplies by whole point size and selected device DPI, divides by **7200**, and clamps the filter index to **0..4**. Every recovered RFF has metrics bytes **+0x12=4 / +0x13=2**, formerly described only as constant u16 0x0204. At 72 DPI this gives `min(4,floor(points/50))`, matching all measured indices. These bytes are active strength coefficients in the RIPtel consumer, not merely an inert signature.

The filter table is original **0x85120 / 0x85160**, pointing to masks **0x84f60,0x84f70,0x84f80,0x84f90,0x84fa0,…**; their first five heights/diameters are 1..5. It is a device bitmap stamp, not a current line-style pen. Device-registration **0x4f150** stores first DPI at display +4, second DPI at +6 and orientation flags at +2; **0x564df** chooses +6 when orientation bit 0 is set, otherwise +4. The horizontal style percentage participates in coordinate transforms later in **0x5656d onward**, after filter selection, and is absent from that diameter formula. Bold face handling has separate coefficient/clamps and remains to test; do not generalize the ordinary-face formula prematurely.

## Completed adapter and filter-scope validation

Final native probe passes **194,714 checks**, adding all bytes 1..255 through original ordinary-text adapter **0x42870**, for Marin and SYMBOL names. It forwards the exact original byte-string pointer to renderer **0x40ed0** unchanged. Combined with the renderer and both cache/file consumers above, byte `c` selects raw slot `c−32` for 32..255, including every high byte; there is no CP437→Windows ANSI, Unicode or special SYMBOL remap in this path. This is byte-index behavior, not a universal Unicode character identity for the artwork in each face.

The unmodified-engine probe additionally passes **1,440 filter-selection cases**: DPI profiles (72,144), (144,72), (36,72), four engine orientations, five hollow width styles, four face modifiers (normal/bold/italic/bold-italic), six point sizes. Display changes use original **0x4f230** with the actual instance ID; realization and cache construction remain original. For orientation 0/2 the strength computation uses **X DPI**; for 1/3 it uses **Y DPI**. Italic does not change filter diameter. Bold uses coefficient **4** from metrics byte +0x12, clamps the computed index to **1..7**; non-bold uses coefficient **2** from +0x13 and clamps to **0..4**. In both cases the ordinary non-overflow computation is `floor(P * selected_DPI * coefficient / 7200)`. Horizontal percentage is absent. Exact historical arithmetic first multiplies coefficient and DPI in a **16-bit word**, then helper **0x543a1** performs unsigned word-product/division and returns AX. All recovered fonts have strength bytes 4,2; all eight original extracted RFF files match their checkout LFS OIDs/content.

The first anisotropic test treated **0x40170's byte-count result as signed int16**, rejecting a valid count above 32767. Reading it as unsigned AX/uint16 corrected the fixture and all 1,440 cases pass. This is an ABI fixture error, not a font-engine failure.

Actual glyph rendering also captures engine +0x60c after hollow E: selected stamp RVAs are **0x84f60 / 0x84f70 / 0x84f70 / 0x84f80 / 0x84fa0 / 0x84fa0**, with heights/nominal diameters 1,2,2,3,5,5 and offsets (0,0),(1,1),(1,1),(1,1),(2,2),(2,2). Thus the formula does select the actual glyph renderer's stamp, not merely an unrelated metric record. Original **0x53850** draws that stamp through **0x55e80**, while the one-pixel path uses **0x562d0**. The masks are device-space footprints; observed raster run widths and asymmetric synthetic edges are not a reason to substitute an unproved circular pen or constant line-style width.

The table's first eight records have nominal diameters 1..8. At diameter 1..3 they are full squares; diameter 4 has two-pixel corner rows and four-pixel middle rows; diameter 5 has three-pixel corner rows and five-pixel middle rows. Larger bold stamps are likewise defined by the original bitmap table, not a continuously scaled em pen. Pixel-exact reproduction of those stencils/scan stepping is outside the issue's requested geometry scope.

# 4.2 Mouse Fields & Pointer

[◀ Prev: 4.1 JPEG Images](4.1-jpeg-images.md) · [Contents](README.md) · [Next: 4.3 Buttons ▶](4.3-buttons.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

[Mouse fields](../../glossary.md) - host-defined rectangular hot regions that transmit a [host command](../../glossary.md) when clicked - the commands that delete them, and control of the mouse pointer shape.

_The 1.54 record is [4.1 in the v1.54 reference](../../1.54/ripscrip/4.1-mouse-fields.md); the 2.0 record is [4.2 in the v2.0 reference](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md), which added world-coordinate placement, the region-selective [RIP_KILL_ENCLOSED_MOUSE_FIELDS](#rip_kill_enclosed_mouse_fields), and [RIP_SET_MOUSE_CURSOR](#rip_set_mouse_cursor)._

Two global rules apply to all mouse regions (fields and buttons alike):

- Up to 128 mouse fields, 128 mouse buttons, or any combination may exist simultaneously, but combined their total number cannot exceed 128 - they share the mouse field [data table](7.1-data-tables.md#mouse-field-table). _(v1.54)_
- When the user clicks the mouse on the screen, all mouse regions (whether mouse fields or mouse buttons) are scanned from most recent to the least recent ("last in, first out"): if regions overlap, the newest one wins the click. _(v1.54, revised v2.A3)_

Mouse fields exist only on the screen (port #0) - they cannot be placed on offscreen [drawing ports](7.0-drawing-ports.md). The corpus confirms both rules operate as documented in the shipping 3.0 driver. _Evidence: 2.00a4; corpus._

**Portable hit/eligibility completion:** Stored resident hit bounds are positive global device rectangles with exclusive far edges: `L <= x < R`, `T <= y < B`. Press, movement feedback, release and hover use that same predicate. New fields are clipped to active PORT0's viewport and screen; an inactive effective viewport or empty intersection creates no field/painting and consumes no region slot. Later viewport changes do not reclip or resurrect definitions. The [full extent/eligibility policy and edge examples](4.3-buttons.md#face-extents-and-input-eligibility) distinguish these explicit completion choices from the old nonuniform native edge tests, and cover button face/effect bounds and degenerate geometry.

## Left-button Gesture Commitment

A field's **click host command** commits once, on a left-button release inside the same field that acquired the preceding press. A press alone gives temporary depression feedback; it does not expand/transmit that click command. Releasing outside cancels activation. Dragging outside removes temporary depression and dragging back inside restores it; a final release inside activates once. Pressing outside every field and releasing inside one does not activate it. Simple `1M` fields and mouse-active `1U` buttons share this rule; `clk=0` suppresses simple-field visual inversion, not the press/release requirement. Keyboard/hotkey activation and the existing persistent radio/checkbox selection rules are separate. _Evidence: original RIPtel 3.1 press/release/move dispatch and simple/ordinary-button action paths; [derivation](../research/issue-113-mouse-gesture-identity.md)._

Keyboard buttons use a [separate explicit profile](4.3-buttons.md#keyboard-activation): byte matching/default/wildcard priority and translated key-down commitment do not require a pointer hit. A winning keyboard activation cancels an outstanding pointer capture safely; unmatched input does not. It never synthesizes pointer coordinates or transfers the held gesture to a replacement field.

Only the newest hit field acquires the **press**. Release does not perform a new winner scan. Hover queries are independent actions and can run during pointer movement, including while a click is held; the rule above delays the region's click command, not those separate hover actions. The existing coordinate, clipping, 128-region and rendering rules remain adopted.

**Explicit portable completion for mutation and lifetime:** The original stable-table event path establishes press ownership but uses live indices; it does not supply a complete safe rule across deletion, compaction, restore or callbacks that change their own definitions. For this reference, capture a stable **field instance/generation**, its hit rectangle and its **unexpanded** host definition. The public `ID=n:` value is metadata, not a unique object handle. Apply the following state rules, without requiring any old invalid-index behavior:

| Event or operation | Required gesture result |
| --- | --- |
| Left press hits a field | Capture that newest hit instance; arm feedback while inside; no click-command execution yet |
| Left press hits no field | Keep the entire held gesture unowned; movement/release cannot acquire a field |
| Movement while captured | Update temporary depression from whether the point is inside the captured rectangle; retain ownership |
| Release inside a surviving captured instance | Clear capture, then execute its click action once; expand variables at commitment, not at press |
| Release outside, or release without capture | Clear capture/temporary feedback; no click action |
| Append a new overlapping field, even with the same public ID | Retain the captured instance; the new field cannot steal the held gesture |
| Change a button-style definition | Retain the already created field/capture; the style definition governs subsequent button creation |
| Delete or replace the captured instance | Cancel capture; a replacement with the same ID, rectangle or table index does not inherit it |
| Delete only other fields, including enclosed-field deletion | Retain capture if its instance survives, even if storage indices change |
| `1K` / `$MKILL$` or outer SOFT deletes all fields | Cancel capture and clear hover membership |
| Apply a restored/replaced mouse-field table | Cancel capture and clear hover membership; restored definitions never resume a saved held gesture |
| Save definitions only | Retain capture; saving does not simulate input |

A repeated down indication while the same physical button remains held does not start another gesture. After cancellation, require release and a fresh press before another activation. A table restore is an input boundary when it starts applying live mouse definitions, including the MOUSE part of a whole-state restore; cancellation still holds if later restore work fails. A rejected request that never applies a table does not create that boundary. Remove temporary depression before applying deletion's specified painting; this adds no scene erase to `1K` and does not override enclosed deletion's fill/clear flags.

Clear capture **before** running a committed command. Its own clear/reset flag, scene playback or nested deletion cannot make the same release activate twice, retarget the action or undo an already committed command. This completion governs click-host dispatch and momentary depression; it does not invent rollback timing for persistent radio/checkbox group selection. No new TW/PORT deferred-click dispatch is implied; the [separate query-mode contract](5.5-file-transfer-and-queries.md#rip_query) remains unchanged.

### Hover and Callback Context

Identified fields have independent hover membership. On movement, process **exits before entries**, newest first within each pass. Overlapping identified fields can each run the shared exit/entry handler; this is separate from the single winner chosen for a click press. A field without a valid ID does not run the shared mode-5/mode-6 hover query. The identified field being entered or exited supplies `$FIELDID$` during its handler. _Evidence: original two-pass hover consumer and temporary FIELDID writes; [derivation](../research/issue-113-mouse-gesture-identity.md)._

**Handler-independent membership:** each stable field starts outside. Every delivered movement updates its geometric inside/outside membership, whether entry-only, exit-only, both handlers, or neither is configured. Membership is per instance, not public ID; duplicate-ID fields remain independent. Unidentified fields still do not invoke the shared queries. Enabling, replacing or removing a handler does not change membership or synthesize a transition. Thus a field entered while entry is absent stays inside when entry is later enabled; another movement at the same point sends no entry. Movement outside can still invoke a configured exit even if no entry callback ever ran. _Evidence: membership writes precede identity/handler-pointer checks in the original consumer; [derivation](../research/issue-132-hover-handler-lifetime.md)._

**Explicit traversal/commitment completion:** snapshot the movement point, existing field-instance tokens, hit rectangles and old memberships. Form exits and entries from that snapshot, newest first within each pass. Before each candidate's turn, verify the original instance still lives and the traversal's interaction boundary remains valid; skip removed tokens, defer newly created fields until a later movement. Commit that instance's new membership **before** considering its applicable current handler. An absent handler means no host callback, not a deferred callback. Then read the **current** shared exit/entry definition and, if present and the ID is valid, atomically own its source bytes, numeric FIELDID and host continuation. Each such transition commits at most one callback. Do not hold field/table locks over providers/prompts.

The applicable handler is selected **per callback**, not copied once for the movement. An earlier exit can replace the handler used by a later exit or entry. Clearing it suppresses later uncommitted callbacks but does not suppress their membership updates. Once a callback commits, removing/replacing the handler, deleting its field or a full reset cannot alter its owned source/FIELDID or replay it. Resume a suspended callback once at its saved stage; use the then-current handler for later candidates. Completed membership/effects are not rolled back by host failure, and no automatic retry occurs. Serialize movement traversals while a callback is suspended; queued movements run afterward from their own point/snapshot. Definition/deletion/reset/focus/cancellation notifications may still apply during suspension. These safe ownership/serialization choices complete the original live-pointer/live-index paths.

Deletion of unrelated fields retains surviving memberships. Deletion/reset/restore never synthesizes an exit into a removed field. New/restored fields get fresh tokens and outside membership even if their numeric IDs/geometry match removed fields. Held click capture stays independent; no hover action acquires another field's press. A focus/disable/reset/restore boundary invalidates remaining uncommitted callbacks from the old traversal, while a callback already committed keeps its owned source/FIELDID under existing host-stage rules.

#### Hover Handler and Membership Lifetime

The handler slots and field membership have distinct ownership. Full drawing reset's separate releases and the original corpus `TELKILL.FN` sequence (`1K`, then mode 5 `$OFF$`, then mode 6 `$OFF$`) support that distinction. The local focus/disable and fresh restored-interaction choices below are explicit portable completion, not claims about original desktop event timing.

| Operation | Field membership / press | Shared mode-5/6 definitions |
| --- | --- | --- |
| Define/replace/remove either handler | Retain all live membership and press; synthesize no input | Change only that mode |
| Delete some fields, including enclosed deletion or HEADER mouse-only deletion flags | Remove deleted memberships/cancel their captures; retain survivors | Retain both |
| `1K` / `$MKILL$` (all live fields) | Remove all membership and cancel capture; no removed-field exits | Retain both, even when no fields remain |
| Outer SOFT / drawing reset / HARD; HEADER global bit 2 / bit 1 | Delete live fields and clear membership/capture | Clear both; no hover source executes as part of reset |
| HEADER without full reset | Apply only its actual operations; field deletion follows rows above; input lock follows disable row | Retain unless a requested operation restores/replaces them |
| Local focus loss or disabling pointer-event delivery, including an input lock | Cancel capture, clear membership and invalidate remaining traversal candidates; no synthetic exits | Retain both and field definitions |
| Refocus / enable / unlock | No synthetic movement, click or entry; next delivered movement can enter at the same point | Retain |
| Save mouse definitions / mouse-family backup | No live interaction change | Save owned copies of both; execute neither |
| Apply a mouse-family backup restore, including MOUSE in RESTOREALL | Cancel old capture/traversal; restored fields have fresh tokens/outside membership, never a saved held press | Replace with saved handler definitions, including saved absence; restoration does not execute them |
| Replace only field definitions without restoring a mouse-family backup | Same fresh interaction boundary | Retain current definitions |
| Reject/no-op restore before applying anything | Retain interaction state | Retain |
| Cursor-shape change, drawing/refresh, pure table/style selection | Retain membership/capture unless it separately performs one of the operations above | Retain |

An applying mouse-family restore begins its boundary even if later restore work fails; no all-or-nothing rollback is added. Restore handler values according to the portions actually applied, preserving the existing backup-manager/error rules. New entries wait for a following movement. The [grouped mouse-backup contract](7.2-data-backup-areas.md#grouped-mouse-snapshots-and-template-publication) also defines saved persistent selection/owner maps and pure reconciliation with current global template publications; restored public IDs never revive old association continuations. The [definition edges and source bound](5.5-file-transfer-and-queries.md#resident-hover-definitions) govern new mode-5/6 definitions; changing a window selector does not create another handler namespace.

#### Hover State and Callback Vectors

Assume older field A and newer B overlap at P, both start outside, and Q is outside both. The normal half-open hit and ID grammar apply. Each listed movement is delivered explicitly; merely defining a handler or refocusing sends no movement.

| Setup and sequence | Callbacks / final membership |
| --- | --- |
| Neither configured: move P; enable entry E; move P again | Zero; A/B remain inside, so no delayed entry |
| Continue above: move Q; move P | No exit while exit absent; then E(B), E(A), once each |
| Entry-only: Q→P→Q | E(B), E(A); both end outside, no exit callback |
| Exit-only: Q→P→Q | Zero on entry, then X(B), X(A); both end outside |
| Both configured: Q→P→Q | E(B), E(A), X(B), X(A) |
| Both explicitly `$OFF$`: Q→P→Q; then enable both, move Q again | Zero; both stay outside; enabling is not a transition |
| A/B both public ID 7: Q→P | Two E callbacks, each FIELDID 7; independent stable instances, not one ID-keyed membership |
| E(B) removes entry before A's turn | E(B) only; A/B both commit inside. Reenable E and move P: zero |
| E(B) replaces E with F before A's turn | E(B), F(A); source was not frozen for the movement |
| X(B) replaces entry with F while moving from both-inside P to a point outside A/B but inside preexisting C that does not contain P | X(B), X(A), then F(C); exits still precede entries |
| E(B) suspends; redefine E as F; resume | Old committed E(B) completes once, then F(A); no replay or rollback |
| E(B) deletes A and creates replacement A2 with the same ID/rectangle | E(B) only this movement; next movement at P invokes current entry for A2 once, not again for surviving B |
| E(B) executes `1K` | E(B)'s committed source may finish once; no A callback or removed-field exits; handlers remain for later new fields |
| E(B) performs full SOFT | Same committed-source ownership, but fields and both handlers are cleared; a new field gets no callback until a handler is defined and a later transition occurs |
| Inside P, lose focus/disable; refocus/enable; move P | No callbacks at boundaries; current entry B then A on the new movement; no held press inherited |
| Save fields/handlers E/X while inside; change handlers; apply saved mouse backup; move P | Restore E/X, fresh outside instances; E(B), E(A), even for the same IDs/geometry |

For definition edges, `!|1<ESC>5Z00$FIELDID$` stores the single global entry source (Z is ignored). `!|1<ESC>6000$oFf$` removes exit only. `<ESC>` denotes **one actual byte 27**, not six printable characters. A fully framed empty `!|1<ESC>5000` reports nonfatally and preserves entry; so does a 1024-byte source under the explicit bound, while 1023 accepted bytes are stored intact. A stored `$NAME$` whose later value is `$OFF$` invokes NAME only during a committed host callback, never during definition, and does not remove that handler. Pure membership updates, absent-handler transitions, definition/removal, deletion, backup save and reset invoke zero hover host providers. All these are documentary/profile vectors, not original-client executions.

The [identity grammar and FIELDID lifetime](5.0-host-commands.md#identity-grammar-and-fieldid-lifetime) define numeric IDs, unrecognized prefixes, callback snapshots, nesting and use after deletion/reset. FIELDID is not a persistent last-click value or the identity of whichever field currently lies under the pointer.

### Gesture Examples

Assume older field A spans device `(10,10)` to `(60,60)`, ID 7, and newer field B spans `(20,20)` to `(80,80)`, ID 8. All following points are away from boundaries:

| Input sequence | Click action |
| --- | --- |
| Press `(30,30)`, release `(30,30)` | B once; B won the overlapping press |
| Press `(15,15)`, move `(100,100)`, move back `(15,15)`, release there | A once; depression disappears outside and returns inside |
| Press `(15,15)`, release `(100,100)` | None |
| Press `(100,100)`, release `(30,30)` | None |
| Press `(15,15)`, append a new field over that point, release there | A once |
| Press `(15,15)`, delete A, create another field with ID 7, release there | None; the new instance does not inherit the press |
| Press `(30,30)`, delete only A, release there | B once despite index compaction |
| Press `(30,30)`, restore even an identical field table, release there | None |
| Press `(30,30)`, execute `1K` or SOFT, release there | None |

With entry/exit queries defined, moving from outside to `(30,30)` runs entry with FIELDID 8, then 7. Moving back outside runs exit with FIELDID 8, then 7. Between those callbacks FIELDID is unavailable. Capture acquired earlier by A or B does not change that hover order. These are protocol/policy examples, not results from executing original client events.

## RIP_MOUSE

_Defines a rectangular hot mouse field_

|               |                                                        |
| ------------- | ------------------------------------------------------ |
| **Level**     | 1                                                      |
| **Command**   | `M`                                                    |
| **Arguments** | `num:2 x0:XY y0:XY x1:XY y1:XY clk:1 clr:1 res:5 text` |

**Format:** `!|1M <num> <x0><y0><x1><y1> <clk><clr><res><text>` **Example:** `!|1M000G7Y8ICC1000000ID=2:$-=RETURN=>NEWSPAPR.RIP$$>TWEATHER.RIP$`

**Attributes used:** Viewport, Port (NO; screen ports only), Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_mouse)) · HLP (`RIP_Mouse`; `$FIELDID$` variable, mouse-field entry/exit queries) · corpus (100 uses in 31 files) · SyncTERM (ripper.c:16381)

This command ties together three things:

- A region on the screen
- A mouse-click event
- A string of text to be transmitted by the terminal.

This command defines a rectangular region on the screen that functions as a "hot" mouse area. If the user clicks the [left] mouse button while pointing inside the region, then the terminal must transmit the `<text>` string to the Host. The (x0,y0) parameter MUST be the upper-left corner, and (x1,y1) MUST be the lower-right corner of the region.

The `<num>` parameter used to be used in the older RIPscrip v1.0 specification but is now obsolete. For upwards compatibility, it should be set to "00". _(v1.54)_

The `<clk>` parameter, if 1, indicates that the region should be visibly inverted while the mouse button is down. This offers visual feedback. If `<clk>` is 0, the region will not be inverted while clicked.

The `<clr>` parameter, if 1, will physically zoom the text window to full screen size and clear the screen. This is useful if the `<text>` parameter instructs the host to enter an area of the System that doesn't support RIPscrip graphics.

The `<text>` parameter is a Host command that gets sent when the field is clicked. You may use a caret (^) or a backquote (`` ` ``) to represent control characters, (e.g., ^M for carriage return, `` `G ``, ^C, etc.). Mouse fields may use Data text variables, active text variables, pick lists, control characters and local file playback directives. At no time are templates permitted in simple mouse fields. See the section on [host commands](5.0-host-commands.md) for more details about these types of features of RIPscrip. _(v2.A3)_

Mouse fields are always created relative to port #0 (the screen port). Under no circumstances are mouse fields allowed in offscreen drawing ports - you can't have a clickable mouse area in a region that cannot be clicked (ie, off the screen). If the current drawing port is an offscreen port, or even a port other than port #0, then the mouse field is defined relative to screen port #0 for the purposes of defining its position. The same applies to mouse-based buttons (see the [RIP_BUTTON](4.3-buttons.md#rip_button) command). _(v2.A3)_

Mouse fields that extend partially outside of a viewport are truncated to fit inside the viewport. _(v2.A3)_

When this command is stored in-memory, it is converted to global screen coordinates (for internal storage only). This makes it so that if you have mouse regions defined in multiple different viewports, that each field will be properly inverted at the right location regardless of the currently defined viewport. _(v1.54)_

NOTE: All Mouse Fields are scanned in "last in, first out" order. This means that the last-most received Mouse Field will be the first one scanned for a mouse click. You are limited to a maximum of 128 Mouse Regions or Mouse Buttons (128 total). _(v1.54)_

### 3.x extensions to the `<text>` parameter

The 3.x corpus reveals two undocumented extensions to the `<text>` parameter. Both live at the host-command layer - they are documented in full in chapter 5 and only summarized here:

- **`ID=n:` prefix** - assigns a numbered mouse-field identity, readable back through the `$FIELDID$` [text variable](5.1-text-variables.md) and used by the `.MSE` overlay scenes' entry/exit queries to drive hover status lines and cursor changes (the example above, from NEWSPAPR.RIP's navigation, is field ID 2). The prefix is not transmitted to the host. The mechanism - and RIPtel's canonical nine-field menu built on it - is documented in [5.0 Host Commands](5.0-host-commands.md#mouse-field-identities---idn). _Evidence: HLP (`$FIELDID$` - "current mouse field ID"); corpus (NEWSPAPR.RIP, MENU.MNU/MENU.MSE)._
- **Inline conditionals and macros** - `<<if $RETURN$!="">>$<<RETURN>>$<<else>>$NULL$<<endif>>` as a host command (BUTTONS.RIP), and [`$GOTOURL(WEBURL)$`](5.0-host-commands.md#launching-web-urls---gotourlname) launching a web URL from a variable (TELLISTS.MNU/.MSE - 1997-era web integration). The conditional/macro layer is [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md). _Evidence: corpus (BUTTONS.RIP, TELLISTS.MNU, TELLISTS.MSE)._

Hover is configured separately with [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query) **mode 5 for entry and mode 6 for exit**. The corpus uses these handlers for `.MSE` status-line updates and `$MCURSOR(n)$` pointer changes. The [callback rules above](#hover-and-callback-context) distinguish independent hover membership from press ownership. _Evidence: HLP, corpus (MENU.MSE), original hover/query dispatch and [#51 derivation](../research/issue-51-deferred-query-order.md)._

## RIP_KILL_ENCLOSED_MOUSE_FIELDS

_Added in RIPscrip v2.A0._

_Destroys any Mouse Fields inside a region_

|               |                                   |
| ------------- | --------------------------------- |
| **Level**     | 1                                 |
| **Command**   | `k`                               |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY flags:4` |

**Format:** `!|1k <x0> <y0> <x1> <y1> <flags>` **Example:** `!|1k0K142S3C0003`

**Attributes used:** Fill Style (see below), Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_kill_enclosed_mouse_fields)) · HLP (`RIP_KillEnclosedMouseFields`) - not observed in the RIPtel demo corpus, not in SyncTERM

This command removes selected simple mouse fields and mouse-active buttons, with optional screen painting. Nonmouse decorations have no resident field to select. **Explicit portable completion:** the inherited terminology and old corner/margin predicates do not establish a complete contract for the adopted half-open geometry. The following classification, clipping/paint and failure rules complete it; [source findings and differences](../research/issue-120-selective-field-deletion.md) remain separate from policy.

### Selector Coordinates and Region Predicates

Interpret the numeric corners in the **current ENV's WORLD**, order each axis before WORLD→device conversion, then use the resulting rectangle as **absolute screen coordinates**. Add no PORT0/current-viewport/port origin. Do not clip the selector to a viewport or screen before classifying fields. The unrelated current/offscreen port and PORT0's activation do not gate logical deletion. Later viewport changes do not relocate stored global field snapshots. _Evidence: original wire ordering/conversion and metadata deletion consumers; [derivation](../research/issue-120-selective-field-deletion.md#primary-sources-and-bounded-findings)._

**Portable empty/flag validation:** Validate the flag mask first. If either converted selector dimension is nonpositive, the whole operation is a no-op, including flag 4 and optional painting. Positive WORLD spans that collapse during conversion are empty. All-zero corners are not a full-screen shorthand. Accept only the documented flag mask **0..255**; reject any bits outside `0xff` before deletion/painting instead of truncating them.

Let S be the nonempty selector and F each field's **stored, already clipped half-open hit rectangle**, including its adopted persistent bevel bounds but not an extra face/recess expansion. Use these three mutually exclusive classes:

| Region bit | Exact predicate |
| --- | --- |
| `1`: contained C | All F edges lie within S, allowing equality: `SL <= FL`, `ST <= FT`, `FR <= SR`, `FB <= SB` |
| `2`: crossing P | F and S have positive-area intersection, **and F is not contained**; a field covering S is included |
| `4`: outside O | No positive-area intersection; touching edges/corners count as outside |

Positive intersection means `max(FL,SL) < min(FR,SR)` and `max(FT,ST) < min(FB,SB)`. Equal rectangles are contained, not crossing. Thus bit 2 excludes fully contained fields; it means crossing the selector boundary, resolving the draft's “non-intersecting” containment wording. Region bits form a **union**, with each field selected once: 3=C+P (all overlapping), 5=C+O, 6=P+O (not-contained), 7=all. With no region bits, **nothing is deleted or painted**, even with paint/128 bits.

Apply type exclusions after region classification: bit **8** excludes simple `1M` fields; bit **16** excludes mouse-active `1U` buttons. Both bits exclude all fields from deletion. A type exclusion never changes a rectangle's class or the meaning of a whole-selector paint request.

### Painting and Failure Ordering

**Explicit portable painting policy:** With at least one region bit, use the following rules. They clarify the primary text's “64 overrides 32” and “whole bounding rectangle” intent; the old brush/current-DC/complement paths are not asserted as exact oracles.

| Paint bits | Without 128 | With 128 |
| --- | --- | --- |
| Neither 32 nor 64 | Delete only; no painting | Delete only; no painting |
| 32 | Paint each selected field's stored hit rectangle with palette index 0 | Paint S interior once with palette index 0 |
| 64 | Paint each selected field's stored hit rectangle with current fill | Paint S interior once with current fill |
| Both 32 and 64 | Same as 64 | Same as 64 |

Flag **128 replaces per-field painting** with one selector-interior paint. It applies even with zero matching fields, an empty field table or exclusions 8+16, provided a region bit and 32/64 are set. With region bit 4 it still paints **S**, not its outside complement. Painting can cover surviving fields without changing their logical definitions; its extent is not another deletion predicate.

Painting addresses the **physical screen only**, clipped to its canvas, with no current-port/viewport clipping or PORT0-activation gate. Use opaque **COPY**, no border; ignore but preserve current W, draw color, line settings and graphics cursor. Bit 32's “black (color 0)” means current palette **index 0**, so remapping that entry to red makes the cleanup red; it is not the outer SOFT reset's literal RGB-black rule and does not use STYLE background. Bit 64 uses the existing Fill Style/Fill Color and pen-background semantics: mask one selects fill, zero selects background. Its [8×8 pattern phase](2.3-shapes-and-fills.md#fill-pattern-origin-and-scaling) stays anchored at physical screen `(0,0)` in device pixels, with no WORLD magnification or restart for each field. Ordinary solid/empty-mask meanings remain adopted.

Validate flags/selector and snapshot eligible **instance tokens and hit rectangles**, plus the current paint color/pattern bindings, before mutation. Remove selected temporary depression and cancel capture only if its instance is selected, then delete the entire selection set while retaining survivor order, capture identity and existing hover/FIELDID lifetime rules. Paint **after deletion** from the snapshot list (newest first for individual rectangles), or S once with 128. A paint failure does not restore definitions or transfer/cancel a surviving capture; attempt remaining requested regions without logical rollback. This is deterministic failure completion, not a native transaction guarantee. No deletion or painting executes a field's click/hover host action. The [gesture lifetime rules](#left-button-gesture-commitment) also govern deletion during a running callback.

### Literal Selection and Paint Vectors

Assume DEVICE 800×600, current WORLD 1600×1200, base 36/coordinate size 2 and initially active full PORT0. Create these six fields (IDs are labels for the examples, not storage handles):

```text
!|1K
!|1B00000200ZK000F000F080700000F07000000
!|1M000U1E1E1Y0000000ID=1:A
!|1U0K142S3C0000ID=2:<>B
!|1M00281O3W2S0000000ID=3:C
!|1U0A0U323M0000ID=4:<>D
!|1M002S1E3C1Y0000000ID=5:E
!|1U4G4G50500000ID=6:<>F
```

The selector below is WORLD `(20,40)..(100,120)`, hence DEVICE **S=`[10,50) × [20,60)`**, regardless of a later PORT0 viewport-origin change or an unrelated current port:

```text
!|1k0K142S3C0003
```

| Field    | Type   | Stored DEVICE hit rectangle     | Class |
| -------- | ------ | ------------------------------- | ----- |
| A / ID 1 | Simple | `[15,25) × [25,35)`             | C     |
| B / ID 2 | Button | Equal to S                      | C     |
| C / ID 3 | Simple | `[40,70) × [30,50)`             | P     |
| D / ID 4 | Button | `[5,55) × [15,65)`, covering S  | P     |
| E / ID 5 | Simple | `[50,60) × [25,35)`, touching S | O     |
| F / ID 6 | Button | `[80,90) × [80,90)`             | O     |

Every row below starts from that six-field fixture, before optional painting. “+8/+16/+24” means add type-exclusion bits to the region mask:

| Region bits | No exclusion | +8 (exclude simple) | +16 (exclude buttons) | +24 |
| --- | --- | --- | --- | --- |
| 0 | None | None | None | None |
| 1 | A B | B | A | None |
| 2 | C D | D | C | None |
| 3 | A B C D | B D | A C | None |
| 4 | E F | F | E | None |
| 5 | A B E F | B F | A E | None |
| 6 | C D E F | D F | C E | None |
| 7 | A B C D E F | B D F | A C E | None |

Reversing the literal selector to `!|1k2S3C0K140003` gives the same result. An equal/collapsed selector does nothing even with mask 7; a nonempty selector wholly beyond the screen can still select all fields through bit 4, while its own selector paint clips to nothing. PORT0 inactivity does not suppress this cleanup.

| Decimal flags / four-digit base-36 field | Result on the fixture |
| --- | --- |
| 35 / `000Z` | Delete A B C D; palette-index-0 paint on their stored hit rectangles |
| 67 / `001V` | Delete A B C D; patterned COPY on their stored hit rectangles |
| 99 / `002R` | Same as 67; 64 wins 32 |
| 161 / `004H` | Delete A B; paint S once with index 0 |
| 164 / `004K` | Delete E F; paint S interior once, not the outside complement |
| 194 / `005E` | Delete C D; paint S once with current fill |
| 185 / `0055` | Delete none (both types excluded); still paint S once with index 0 |
| 160 / `004G` | No region bits: no deletion or painting |
| 256 / `0074` | Unsupported bit: reject before any change |

For each flags field, use the same coordinate prefix, e.g. `!|1k0K142S3C004H`. If palette index 0 is red, STYLE background and pen background are blue, and fill is green, 32 paints red despite an XOR W setting. With custom mask rows `80 00 00 00 00 00 00 00`, whole-selector fill makes `(16,24)` green and `(17,24)` blue by the absolute pattern phase. If painting fails after selecting A–D, those four definitions remain deleted; capture on surviving E stays E through compaction, whereas capture on deleted A is canceled and cannot pass to a newly created ID-1 field. These are explicit protocol/policy vectors, not original raster executions.

## RIP_SET_MOUSE_CURSOR

_Added in RIPscrip v2.A1._

_Sets the mouse cursor (pointer) to various shapes_

|               |                        |
| ------------- | ---------------------- |
| **Level**     | 1                      |
| **Command**   | `c`                    |
| **Arguments** | `cursor_style:2 res:4` |

**Format:** `!|1c <cursor_style> <res>` **Example:** `!|1c06`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_set_mouse_cursor)) · HLP (`RIP_SetMouseCursor`; also the `$MCURSOR(n)$` variable) · corpus (2 uses in FXSHWIMG.FN) - not in SyncTERM

This command allows you to alter the current mouse cursor shape that is shown on the screen. This feature lets you change the cursor to another shape to give the user of the terminal an idea that something is going on. For example, changing the cursor to the shape of an hourglass or a watch could give the idea that they should wait for a moment because something is going on.

The `<cursor_style>` parameter selects the **same logical number** as [`MCURSOR`](5.1-text-variables.md#mcursor). **Canonical RIPscrip 3.0 range: 0..7.** The inherited documentary table establishes 0..6; both original cursor-handle arrays and the original color/monochrome resources establish 7 as the unavailable/prohibited symbol. [Exact tables, resource fingerprints and source/policy boundary](../research/issue-125-cursor-number-mapping.md).

| Style | Logical presentation | Portable equivalent |
| --- | --- | --- |
| 00 | Default left-leaning arrow | Normal selection pointer |
| 01 | Wristwatch / clock | Busy/wait cursor; may use the same native stock shape as 06 |
| 02 | Crosshair | Precision crosshair |
| 03 | I-bar | Text-selection I-beam |
| 04 | Pointing finger | Link/pointing-hand cursor |
| 05 | Raised open hand / palm | Raised-hand equivalent |
| 06 | Hourglass | Busy/wait cursor |
| 07 | Slashed circle: unavailable / prohibited | Not-allowed cursor |

**Presentation completion:** retain the selected logical number separately from the native cursor handle. Exact original artwork, color, size, animation and hotspot pixels are not protocol requirements; native/accessibility equivalents are permitted. When the backend cannot supply a requested shape, show the default arrow while retaining that number, so a later refresh or environment activation still knows the requested style. A native watch and hourglass can share artwork without merging stored values 1 and 6. This fallback is an explicit portable policy consistent with the original missing-handle arrow path.

Value **7 is an ordinary visible shape selection**, not a hidden/no-change/default sentinel. It stores 7 and replaces the displayed shape just like other values; it does not hide the pointer, disable input, cancel/transfer capture, change hover membership, alter keyboard bindings or synthesize a movement/click. A not-allowed symbol conveys appearance only; input enable, HEADER lock and the adopted gesture rules remain separate. Native cursor constants need a translation table; their numeric values are not RIP numbers.

**Explicit accepted-range completion:** reject values outside 0..7 before changing cursor state or presentation, as a nonfatal command/variable error; retain earlier state. This applies to both wire and variable forms. The wire field uses current Base Math; MCURSOR uses its documented decimal argument grammar and defaults to zero when omitted. The original wire outer guard admits 8/9 to a shared setter that does not store them; that legacy refresh path is not an additional logical style or a portable range extension.

**State ownership (RIPtel 3.1):** the number is stored in the current environment, not in the graphics style. This wire command checks current environment protection; style protection is irrelevant. [`MCURSOR`](5.1-text-variables.md#mcursor) performs the same state change without that protection check. Style switching does not restore a mouse number; environment switching selects the stored number for the next refresh. _Evidence: [original handlers/setter and native cases](../research/issue-24-drawing-state-ownership.md#ownership-and-switching-observations)._

A [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) resets the mouse cursor to the default pointer. [`RIP_HEADER`](1.1-protocol-and-command-hierarchy.md#rip_header) has selective cursor behavior: resets can restore defaults, input lock selects the wait cursor, and environment flag 32768 selects the arrow. A zero-flags header does not unconditionally reset the cursor.

FXSHWIMG.FN brackets its slow JPEG display with `!|1c06` / `!|1c00` - hourglass on, arrow back - omitting the reserved digits entirely, which the shipping driver's truncation-tolerant parser accepts. Most corpus cursor changes go through the `$MCURSOR(n)$` variable inside [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query) commands instead ([5.1 Text Variables](5.1-text-variables.md)), typically wired to field entry/exit for hover pointer changes. _Evidence: corpus (FXSHWIMG.FN, DEMO-01.COL, MENU.FN)._

### Cursor Mapping Vectors

Assume Base Math 36, current environment unprotected and input otherwise enabled. `!|1c070000` and `$MCURSOR(7)$` both store 7 and show not-allowed; a backend without that shape shows arrow but still stores 7. `!|1c040000` / `$MCURSOR(4)$` select pointing finger; `!|1c060000` / `$MCURSOR(6)$` select hourglass. `!|1c000000`, `$MCURSOR(0)$` and argumentless `$MCURSOR$` select arrow; argumentless MCURSOR is not a getter.

With stored style 3 and current ENV protected, wire `!|1c070000` leaves 3; `$MCURSOR(7)$` changes it to 7 under the existing bypass rule. Protecting graphics STYLE alone blocks neither. `!|1c080000` and `$MCURSOR(8)$` reject without changing a previous 7. ENV A storing 7 and ENV B storing 3 retain those independent values across environment selection; graphics STYLE/PORT selection does not substitute another cursor number.

A press captured on an existing field remains captured after selecting cursor 7; a valid inside release still follows its adopted action contract. Selecting 0 afterward changes appearance without enabling any independently disabled/locked input. These are logical state/presentation vectors, not original client/UI executions.

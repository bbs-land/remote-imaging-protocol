# 4.2 Mouse Fields & Pointer

[◀ Prev: 4.1 JPEG Images](4.1-jpeg-images.md) · [Contents](README.md) · [Next: 4.3 Buttons ▶](4.3-buttons.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

[Mouse fields](../../glossary.md) - host-defined rectangular hot regions that transmit a [host command](../../glossary.md) when clicked - the commands that delete them, and control of the mouse pointer shape.

_The 1.54 record is [4.1 in the v1.54 reference](../../1.54/ripscrip/4.1-mouse-fields.md); the 2.0 record is [4.2 in the v2.0 reference](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md), which added world-coordinate placement, the region-selective [RIP_KILL_ENCLOSED_MOUSE_FIELDS](#rip_kill_enclosed_mouse_fields), and [RIP_SET_MOUSE_CURSOR](#rip_set_mouse_cursor)._

Two global rules apply to all mouse regions (fields and buttons alike):

- Up to 128 mouse fields, 128 mouse buttons, or any combination may exist simultaneously, but combined their total number cannot exceed 128 - they share the mouse field [data table](7.1-data-tables.md#mouse-field-table). _(v1.54)_
- When the user clicks the mouse on the screen, all mouse regions (whether mouse fields or mouse buttons) are scanned from most recent to the least recent ("last in, first out"): if regions overlap, the newest one wins the click. _(v1.54, revised v2.A3)_

Mouse fields exist only on the screen (port #0) - they cannot be placed on offscreen [drawing ports](7.0-drawing-ports.md). The corpus confirms both rules operate as documented in the shipping 3.0 driver. _Evidence: 2.00a4; corpus._

**Portable hit/eligibility completion:** Stored resident hit bounds are positive global device rectangles with exclusive far edges: `L <= x < R`, `T <= y < B`. Press, movement feedback, release and hover use that same predicate. New fields are clipped to active PORT0's viewport and screen; an inactive effective viewport or empty intersection creates no field/painting and consumes no region slot. Later viewport changes do not reclip or resurrect definitions. The [full extent/eligibility policy and edge examples](4.3-buttons.md#face-extents-and-input-eligibility) distinguish these explicit completion choices from the old nonuniform native edge tests, and cover button face/effect bounds and degenerate geometry.

## Left-button Gesture Commitment

A field's **click host command** commits once, on a left-button release inside the same field that acquired the preceding press. A press alone gives temporary depression feedback; it does not expand/transmit that click command. Releasing outside cancels activation. Dragging outside removes temporary depression and dragging back inside restores it; a final release inside activates once. Pressing outside every field and releasing inside one does not activate it. Simple `1M` fields and mouse-active `1U` buttons share this rule; `clk=0` suppresses simple-field visual inversion, not the press/release requirement. Keyboard/hotkey activation and the existing persistent radio/checkbox selection rules are separate. _Evidence: original RIPtel 3.1 press/release/move dispatch and simple/ordinary-button action paths; [derivation](../research/issue-113-mouse-gesture-identity.md)._

Keyboard buttons use a [separate explicit profile](4.3-buttons.md#keyboard-activation): byte matching/default/wildcard priority and translated key-down commitment do not require a pointer hit. A winning keyboard activation cancels an outstanding pointer capture safely; unmatched input does not. It never synthesizes pointer coordinates or transfers the held gesture to a replacement field.

Only the newest hit field acquires the **press**. Release does not perform a new winner scan. Hover queries are independent actions and can run during pointer movement, including while a click is held; the rule above delays the region's click command, not those separate hover actions. The existing coordinate, clipping, 128-region and rendering rules remain adopted.

**Explicit portable completion for mutation and lifetime:** The original stable-table event path establishes press ownership but uses live indices; it does not supply a complete safe rule across deletion, compaction, restore or callbacks that change their own definitions. For this reference, capture a stable **field instance/generation**, its hit rectangle and its **unexpanded** host definition. The public `ID=n:` value is metadata, not a unique object handle. Apply the following state rules, without requiring any old invalid-index behavior:

| Event or operation | Required gesture result |
| --- | --- |
| Left press hits a field | Capture that newest hit instance; arm feedback while inside; no click-command execution yet |
| Left press hits no field | Keep the entire held gesture unowned; movement/release cannot acquire a field |
| Movement while captured | Update temporary depression from whether the point is inside the captured rectangle; retain ownership |
| Release inside a surviving captured instance | Clear capture, then execute its click action once; expand variables at commitment, not at press |
| Release outside, or release without capture | Clear capture/temporary feedback; no click action |
| Append a new overlapping field, even with the same public ID | Retain the captured instance; the new field cannot steal the held gesture |
| Change a button-style definition | Retain the already created field/capture; the style definition governs subsequent button creation |
| Delete or replace the captured instance | Cancel capture; a replacement with the same ID, rectangle or table index does not inherit it |
| Delete only other fields, including enclosed-field deletion | Retain capture if its instance survives, even if storage indices change |
| `1K` / `$MKILL$` or outer SOFT deletes all fields | Cancel capture and clear hover membership |
| Apply a restored/replaced mouse-field table | Cancel capture and clear hover membership; restored definitions never resume a saved held gesture |
| Save definitions only | Retain capture; saving does not simulate input |

A repeated down indication while the same physical button remains held does not start another gesture. After cancellation, require release and a fresh press before another activation. A table restore is an input boundary when it starts applying live mouse definitions, including the MOUSE part of a whole-state restore; cancellation still holds if later restore work fails. A rejected request that never applies a table does not create that boundary. Remove temporary depression before applying deletion's specified painting; this adds no scene erase to `1K` and does not override enclosed deletion's fill/clear flags.

Clear capture **before** running a committed command. Its own clear/reset flag, scene playback or nested deletion cannot make the same release activate twice, retarget the action or undo an already committed command. This completion governs click-host dispatch and momentary depression; it does not invent rollback timing for persistent radio/checkbox group selection. No new TW/PORT deferred-click dispatch is implied; the [separate query-mode contract](5.5-file-transfer-and-queries.md#rip_query) remains unchanged.

### Hover and Callback Context

Identified fields have independent hover membership. On movement, process **exits before entries**, newest first within each pass. Overlapping identified fields can each run the shared exit/entry handler; this is separate from the single winner chosen for a click press. A field without a valid ID does not run the shared mode-5/mode-6 hover query. The identified field being entered or exited supplies `$FIELDID$` during its handler. _Evidence: original two-pass hover consumer and temporary FIELDID writes; [derivation](../research/issue-113-mouse-gesture-identity.md)._

**Explicit mutation completion:** Snapshot field-instance tokens for a movement event. Skip tokens deleted before their turn; newly created fields become eligible on the next movement event. Deletion of unrelated fields retains surviving hover membership. Deleting fields, SOFT or applying restored definitions does not synthesize an exit callback into removed fields; restoration begins with no remembered hover membership. A following movement can produce new entries, even if the restored geometry matches the old geometry. These rules prevent storage compaction or callback-created fields from changing the current traversal. Held click capture remains independent of hover traversal.

The [identity grammar and FIELDID lifetime](5.0-host-commands.md#identity-grammar-and-fieldid-lifetime) define numeric IDs, unrecognized prefixes, callback snapshots, nesting and use after deletion/reset. FIELDID is not a persistent last-click value or the identity of whichever field currently lies under the pointer.

### Gesture Examples

Assume older field A spans device `(10,10)` to `(60,60)`, ID 7, and newer field B spans `(20,20)` to `(80,80)`, ID 8. All following points are away from boundaries:

| Input sequence | Click action |
| --- | --- |
| Press `(30,30)`, release `(30,30)` | B once; B won the overlapping press |
| Press `(15,15)`, move `(100,100)`, move back `(15,15)`, release there | A once; depression disappears outside and returns inside |
| Press `(15,15)`, release `(100,100)` | None |
| Press `(100,100)`, release `(30,30)` | None |
| Press `(15,15)`, append a new field over that point, release there | A once |
| Press `(15,15)`, delete A, create another field with ID 7, release there | None; the new instance does not inherit the press |
| Press `(30,30)`, delete only A, release there | B once despite index compaction |
| Press `(30,30)`, restore even an identical field table, release there | None |
| Press `(30,30)`, execute `1K` or SOFT, release there | None |

With entry/exit queries defined, moving from outside to `(30,30)` runs entry with FIELDID 8, then 7. Moving back outside runs exit with FIELDID 8, then 7. Between those callbacks FIELDID is unavailable. Capture acquired earlier by A or B does not change that hover order. These are protocol/policy examples, not results from executing original client events.

## RIP_MOUSE

_Defines a rectangular hot mouse field_

|               |                                                        |
| ------------- | ------------------------------------------------------ |
| **Level**     | 1                                                      |
| **Command**   | `M`                                                    |
| **Arguments** | `num:2 x0:XY y0:XY x1:XY y1:XY clk:1 clr:1 res:5 text` |

**Format:** `!|1M <num> <x0><y0><x1><y1> <clk><clr><res><text>` **Example:** `!|1M000G7Y8ICC1000000ID=2:$-=RETURN=>NEWSPAPR.RIP$$>TWEATHER.RIP$`

**Attributes used:** Viewport, Port (NO; screen ports only), Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_mouse)) · HLP (`RIP_Mouse`; `$FIELDID$` variable, mouse-field entry/exit queries) · corpus (100 uses in 31 files) · SyncTERM (ripper.c:16381)

This command ties together three things:

- A region on the screen
- A mouse-click event
- A string of text to be transmitted by the terminal.

This command defines a rectangular region on the screen that functions as a "hot" mouse area. If the user clicks the [left] mouse button while pointing inside the region, then the terminal must transmit the `<text>` string to the Host. The (x0,y0) parameter MUST be the upper-left corner, and (x1,y1) MUST be the lower-right corner of the region.

The `<num>` parameter used to be used in the older RIPscrip v1.0 specification but is now obsolete. For upwards compatibility, it should be set to "00". _(v1.54)_

The `<clk>` parameter, if 1, indicates that the region should be visibly inverted while the mouse button is down. This offers visual feedback. If `<clk>` is 0, the region will not be inverted while clicked.

The `<clr>` parameter, if 1, will physically zoom the text window to full screen size and clear the screen. This is useful if the `<text>` parameter instructs the host to enter an area of the System that doesn't support RIPscrip graphics.

The `<text>` parameter is a Host command that gets sent when the field is clicked. You may use a caret (^) or a backquote (`` ` ``) to represent control characters, (e.g., ^M for carriage return, `` `G ``, ^C, etc.). Mouse fields may use Data text variables, active text variables, pick lists, control characters and local file playback directives. At no time are templates permitted in simple mouse fields. See the section on [host commands](5.0-host-commands.md) for more details about these types of features of RIPscrip. _(v2.A3)_

Mouse fields are always created relative to port #0 (the screen port). Under no circumstances are mouse fields allowed in offscreen drawing ports - you can't have a clickable mouse area in a region that cannot be clicked (ie, off the screen). If the current drawing port is an offscreen port, or even a port other than port #0, then the mouse field is defined relative to screen port #0 for the purposes of defining its position. The same applies to mouse-based buttons (see the [RIP_BUTTON](4.3-buttons.md#rip_button) command). _(v2.A3)_

Mouse fields that extend partially outside of a viewport are truncated to fit inside the viewport. _(v2.A3)_

When this command is stored in-memory, it is converted to global screen coordinates (for internal storage only). This makes it so that if you have mouse regions defined in multiple different viewports, that each field will be properly inverted at the right location regardless of the currently defined viewport. _(v1.54)_

NOTE: All Mouse Fields are scanned in "last in, first out" order. This means that the last-most received Mouse Field will be the first one scanned for a mouse click. You are limited to a maximum of 128 Mouse Regions or Mouse Buttons (128 total). _(v1.54)_

### 3.x extensions to the `<text>` parameter

The 3.x corpus reveals two undocumented extensions to the `<text>` parameter. Both live at the host-command layer - they are documented in full in chapter 5 and only summarized here:

- **`ID=n:` prefix** - assigns a numbered mouse-field identity, readable back through the `$FIELDID$` [text variable](5.1-text-variables.md) and used by the `.MSE` overlay scenes' entry/exit queries to drive hover status lines and cursor changes (the example above, from NEWSPAPR.RIP's navigation, is field ID 2). The prefix is not transmitted to the host. The mechanism - and RIPtel's canonical nine-field menu built on it - is documented in [5.0 Host Commands](5.0-host-commands.md#mouse-field-identities---idn). _Evidence: HLP (`$FIELDID$` - "current mouse field ID"); corpus (NEWSPAPR.RIP, MENU.MNU/MENU.MSE)._
- **Inline conditionals and macros** - `<<if $RETURN$!="">>$<<RETURN>>$<<else>>$NULL$<<endif>>` as a host command (BUTTONS.RIP), and [`$GOTOURL(WEBURL)$`](5.0-host-commands.md#launching-web-urls---gotourlname) launching a web URL from a variable (TELLISTS.MNU/.MSE - 1997-era web integration). The conditional/macro layer is [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md). _Evidence: corpus (BUTTONS.RIP, TELLISTS.MNU, TELLISTS.MSE)._

Hover is configured separately with [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query) **mode 5 for entry and mode 6 for exit**. The corpus uses these handlers for `.MSE` status-line updates and `$MCURSOR(n)$` pointer changes. The [callback rules above](#hover-and-callback-context) distinguish independent hover membership from press ownership. _Evidence: HLP, corpus (MENU.MSE), original hover/query dispatch and [#51 derivation](../research/issue-51-deferred-query-order.md)._

## RIP_KILL_MOUSE_FIELDS

_Destroys all previously defined hot mouse regions_

|               |          |
| ------------- | -------- |
| **Level**     | 1        |
| **Command**   | `K`      |
| **Arguments** | \<none\> |

**Format:** `!|1K` **Example:** `!|1K`

**Attributes used:** Base Math (N/A) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_kill_mouse_fields)) · HLP (`RIP_KillMouseFields`; also the `$MKILL$` variable) · corpus (8 uses in 8 files) · SyncTERM (ripper.c:16370)

This command will "forget" all Mouse Regions. Use it at the beginning of each Scene, so that one scene's Mouse Regions don't get used in another.

The corpus's TELKILL.FN ("Kill all mouse fields and entry/exit queries") wraps it as a reusable subroutine scene. _Evidence: corpus (TELKILL.FN)._

## RIP_KILL_ENCLOSED_MOUSE_FIELDS

_Added in RIPscrip v2.A0._

_Destroys any Mouse Fields inside a region_

|               |                                   |
| ------------- | --------------------------------- |
| **Level**     | 1                                 |
| **Command**   | `k`                               |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY flags:4` |

**Format:** `!|1k <x0> <y0> <x1> <y1> <flags>` **Example:** `!|1k00003G2H`

**Attributes used:** Fill Style (see below), Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_kill_enclosed_mouse_fields)) · HLP (`RIP_KillEnclosedMouseFields`) - not observed in the RIPtel demo corpus, not in SyncTERM

This command will destroy any Mouse Fields or Mouse Active Buttons that are contained inside the given rectangle or that intersect the rectangle. The exact operation of this function is dependent on the setting of the `<flags>` parameter. The `<flags>` parameter can combine any of the following flags to determine the exact mode of operation:

**Region Specific Flags**

| Flags | Description                                              |
| ----- | -------------------------------------------------------- |
| 1     | Kill only fields completely contained (non-intersecting) |
| 2     | Kill only fields that intersect bounding rectangle       |
| 4     | Kill fields entirely outside bounding rectangle          |

> If 1, 2 and 4 are not present, then NO fields are deleted. One of these flags must be supplied for any mouse fields to be deleted.

**What Types of Fields not to Destroy**

| Flags | Description                              |
| ----- | ---------------------------------------- |
| 8     | Don't destroy simple Mouse Fields        |
| 16    | Don't destroy active Mouse Button fields |

> If 8 and 16 are not present, then all types of mouse fields are destroyed.

**What to do With the Affected Region(s)**

| Flags | Description |
| --- | --- |
| 32 | Clear the affected field(s) to black (color 0) |
| 64 | Fill the affected field(s) with current fill color and fill pattern (64 overides 32 in the case that both of 32 and 64 are present). |
| 128 | Perform the 32/64 operations on the whole bounding rectangle (based on Region Specific Flags). |

> If 128 is omitted but 32 or 64 are used, then the mouse field's affected are cleared with the appropriate method. If 128 is present as well, then instead of clearing the individual mouse fields with the given method, the entire region specified by the Region Specific Flags is affected (ie, the entire interior of the bounding rectangle is cleared, etc). If 32, 64 and 128 are omitted, then the affected region/fields are left on the screen visually, but their mouse field definitions are destroyed internally. If 128 is used, but 32 and 64 are omitted then nothing is done visually either.

The demos always clear all fields at once with [RIP_KILL_MOUSE_FIELDS](#rip_kill_mouse_fields) instead. _Evidence: corpus (absence)._

## RIP_SET_MOUSE_CURSOR

_Added in RIPscrip v2.A1._

_Sets the mouse cursor (pointer) to various shapes_

|               |                        |
| ------------- | ---------------------- |
| **Level**     | 1                      |
| **Command**   | `c`                    |
| **Arguments** | `cursor_style:2 res:4` |

**Format:** `!|1c <cursor_style> <res>` **Example:** `!|1c06`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.2-mouse-fields-and-pointer.md#rip_set_mouse_cursor)) · HLP (`RIP_SetMouseCursor`; also the `$MCURSOR(n)$` variable) · corpus (2 uses in FXSHWIMG.FN) - not in SyncTERM

This command allows you to alter the current mouse cursor shape that is shown on the screen. This feature lets you change the cursor to another shape to give the user of the terminal an idea that something is going on. For example, changing the cursor to the shape of an hourglass or a watch could give the idea that they should wait for a moment because something is going on.

The `<cursor_style>` parameter is an ID number that specifies which cursor style should be activated. The possible values for this parameter are: _(v2.A4)_

| Style | Description                                    |
| ----- | ---------------------------------------------- |
| 00    | Standard "left-leaning" arrow cursor (default) |
| 01    | Wrist watch cursor                             |
| 02    | Cross-hair cursor                              |
| 03    | I-bar cursor (for text editing)                |
| 04    | Pointing finger cursor                         |
| 05    | Hand held up cursor                            |
| 06    | Hourglass cursor                               |

**State ownership (RIPtel 3.1):** the number is stored in the current environment, not in the graphics style. This wire command checks current environment protection; style protection is irrelevant. [`MCURSOR`](5.1-text-variables.md#mcursor) performs the same state change without that protection check. Style switching does not restore a mouse number; environment switching selects the stored number for the next refresh. _Evidence: [original handlers/setter and native cases](../research/issue-24-drawing-state-ownership.md#ownership-and-switching-observations)._

A [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) resets the mouse cursor to the default pointer. [`RIP_HEADER`](1.1-protocol-and-command-hierarchy.md#rip_header) has selective cursor behavior: resets can restore defaults, input lock selects the wait cursor, and environment flag 32768 selects the arrow. A zero-flags header does not unconditionally reset the cursor.

FXSHWIMG.FN brackets its slow JPEG display with `!|1c06` / `!|1c00` - hourglass on, arrow back - omitting the reserved digits entirely, which the shipping driver's truncation-tolerant parser accepts. Most corpus cursor changes go through the `$MCURSOR(n)$` variable inside [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query) commands instead ([5.1 Text Variables](5.1-text-variables.md)), typically wired to field entry/exit for hover pointer changes. _Evidence: corpus (FXSHWIMG.FN, DEMO-01.COL, MENU.FN)._

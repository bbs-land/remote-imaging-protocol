# 5.0 Host Commands

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

The **Host Command Language (HCL)**, as the RIPscrip 3.0 White Paper names it - the action language that mouse regions, buttons, hotkeys and query expressions speak back to the host, divided into five areas: control characters, pop-up picklists, local playback directives, template directives, and text variables. A [host command](../../glossary.md) is, at its simplest, raw text transmitted to the host when a button or mouse field is clicked; every HCL directive is something the terminal interprets _before_ (or instead of) transmitting.

_Evidence: WP; 2.00a4._

## Where Host Commands Run

_Evidence: 2.00a4; SyncTERM (ripper.c:11884-12001); HLP._

A host-command string may be attached to:

- **Buttons** (`1U`) - the command block of the Text Parameter segment, executed when the button is clicked. Template groups are associated with buttons; the [shipped common processor](5.2-templates-and-conditionals.md#shipped-processing-order) also accepts template-enabled blocks without a button association.
- **Mouse fields** (`1M`) - the host command executed when the field is clicked.
- **Queries** (`1` + ESC) - the query text itself is a host-command string, executed or deferred per the mode digit (below); full entry at [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query).
- **Keystroke macros / hotkeys** - hotkey-triggered buttons execute their command block exactly as if clicked.

### What Can Go Where

The following chart records the inherited 2.00a4 design. For shipped RIPtel behavior, use the [consumer/pass contract](5.2-templates-and-conditionals.md#shipped-processing-order): its common host processor can accept template-enabled blocks without a button association, and angle preprocessing is separate from these ordinary host features.

| Context | Templates | Data Text Vars | Active Text Vars | Pick Lists | Ctrl Chars | Local Playback |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| Button host commands | Y | Y | Y | Y | Y | Y |
| Simple mouse fields | N | Y | Y | Y | Y | Y |
| Query commands | N | Y | Y | Y | Y | Y |
| Button labels | N | Y | N | N | N | N |
| `RIP_TEXT_XY` / `RIP_TEXT` | N | Y | N | N | N | N |

In the original 2.x chart, the first three rows (Button Host Commands, Simple Mouse Fields, Query Command) are grouped as "Host Related Commands" and the last three rows (Button Labels, RIP*TEXT_XY, RIP_TEXT) are grouped as "Text Output Related Commands". \_Evidence: 2.00a4.*

RIPtel’s ordinary host response expansion makes **two passes**, while its angle preprocessor has distinct rescan rules. Template insertion and local-file playback must not be collapsed into one unlimited recursive expansion model; see the [exact processing order and shipped defects](5.2-templates-and-conditionals.md#shipped-processing-order). SyncTERM’s separate `handle_command_str` recursion cap of 64 is implementation evidence for SyncTERM, not a recovered RIPtel limit.

RIPtel additionally exposes a **Command Mode** menu option that executes any typed HCL string directly - TeleGrafix's own recommended way to test host commands interactively. _Evidence: HLP._

## Control Characters

_Evidence: original RIPtel 3.1 response executor 0x4acd9, ordinary conversion 0x4b394 and [native notation derivation](../research/issue-53-host-control-brackets.md#original-stages-and-first-native-checkpoint); inherited 2.00a4/HLP conventions._

RIPtel 3.1 converts caret (`^`) and backquote (`` ` ``) pairs during the **second ordinary host-response pass**, after bracket-template segmentation. For the shipping default ASCII locale, the conversion rules are:

| Following character | Result |
| --- | --- |
| `A`..`Z` or `a`..`z` | Uppercase the letter, then subtract 0x40: bytes 1..26 |
| `[` / backslash / `]` / `_` | Bytes 27 /28 /29 /31 |
| The same prefix as the first character | One literal prefix: `^^`→caret, doubled backquote→backquote |
| Caret after a backquote | Byte 30 (RS); `^^` instead means literal caret |
| Any other non-NUL ASCII character | Preserve both bytes unchanged |
| End of text immediately after the prefix | Preserve the trailing prefix unchanged |

Thus `^m` and `^M` both produce CR, `^?` sends the two literal bytes 5e 3f rather than DEL, and **`^@` sends 5e 40 rather than NUL**. The inherited “following character minus @” formula applies only to the accepted letters/punctuation above. Invalid/unrecognized pairs and trailing prefixes do not reject the response. A decoded literal prefix is skipped rather than decoded again: `^^M` sends literal `^M`. Non-ASCII character classification depends on the CRT locale and is not specified by this ASCII contract.

**Individual control characters**

| Sequence     | Transmitted byte | Conventional meaning         |
| ------------ | ---------------- | ---------------------------- |
| `^G`         | 07               | Bell                         |
| `^H`         | 08               | Backspace                    |
| `^L`         | 0c               | Form feed                    |
| `^M` or `^m` | 0d               | Carriage return              |
| `^C`         | 03               | Break, host-dependent        |
| `^[`         | 1b               | Escape                       |
| `^S` / `^Q`  | 13 /11           | Pause/resume, host-dependent |

**Special keystroke notation** uses the same ordinary conversion; there is no atomic whitelist of key strings. Only the first `^[` becomes ESC; subsequent raw bytes retain their values unless the earlier template parser recognizes a complete directive.

| Sequence | Transmitted bytes (hex) | Conventional key |
| --- | --- | --- |
| `^[[A` / `^[[B` | 1b 5b 41 /1b 5b 42 | Up /Down |
| `^[[C` / `^[[D` | 1b 5b 43 /1b 5b 44 | Right /Left |
| `^[[H` / `^[[K` | 1b 5b 48 /1b 5b 4b | Home /End |
| `^[[L` | 1b 5b 4c | Control-Home |
| `` `[[A `` | 1b 5b 41 | Same bytes as `^[[A` |
| `^[[Z` | 1b 5b 5a | Unlisted example; still converted and transmitted |

The unclosed bracket+Mega-letter forms above also produce a **nonfatal `Invalid MegaNum` diagnostic** while the earlier stage looks for a closing template delimiter. RIPtel nevertheless transmits the bytes shown; malformed template syntax is not universally rejected before partial execution. Remote host interpretation of those escape sequences is separate from the bytes sent.

> **NOTE:** `^M` is notation for a byte, not two transmitted characters. RIPscrip wire commands themselves (for example [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query)) use a real ESC byte, not the `^[` host-command notation.

### Literal Dollars and Brackets

The earlier blanket claim that every raw `$` or `[` must start a directive, attributed to a SyncTERM source comment, does **not** describe shipping RIPtel 3.1. Its bracket stage searches for **complete recognized template delimiters** before ordinary dollar/control expansion. It neither tests for a preceding ESC nor treats special-key sequences atomically. See [template processing order](5.2-templates-and-conditionals.md#shipped-processing-order) and the [original derivation](../research/issue-53-host-control-brackets.md).

| Host-command source | Result with template 3=`THREE`, template A(10)=`TEN` |
| --- | --- |
| Lone raw `[` | Transmit literal byte 5b; no template action or diagnostic |
| `^[[A` | Transmit ESC+`[A`; nonfatal incomplete-template diagnostic |
| `^[[A]` | Invoke template A; transmit ESC+`TEN` |
| Raw ESC followed by `[A]` | Invoke template A; transmit ESC+`TEN` |
| `^[x[3]` | Invoke template 3; transmit ESC+`xTHREE` |
| `[3]` | Invoke template 3; transmit `THREE` |
| `\[3]` | Still invoke template 3; backslash does not hide a delimiter from the earlier scan |
| `[3` | Transmit literal `[3`; nonfatal `Invalid MegaNum` diagnostic |
| `x[A:]TAIL` | Transmit x, store TAIL as template A |

An emitted ESC does **not** suppress bracket interpretation. Complete directives in the original source are processed earlier; an expression that returns the literal string `[3]` after segmentation is not restarted through that stage and can transmit those bytes literally. Unrecognized bracket syntax such as `[?]` also passes as ordinary text. These facts do not create a universal quote for an otherwise valid bracket directive.

Backslash handling is stage-specific. In the full two-pass host path, `\$SHIFT\$` transmits literal `$SHIFT$` without evaluating SHIFT, whereas quoting only its opening dollar (`\$SHIFT$`) still lets the earlier pass evaluate the variable. Both forms are verified through the original pipeline. These examples are **host-command input bytes**; preserve the separate [wire quoting rules](1.1-protocol-and-command-hierarchy.md#escaping-in-text-parameters) when carrying them inside RIP commands. Caret/backquote doubling quotes only its own prefix and is unrelated to bracket segmentation.

For each executed host response, the [response/embedding byte-limit policy](5.2-templates-and-conditionals.md#response-and-embedding-byte-limit) caps working text at 4096 bytes before ordinary expansion and after each replacement, including direct responses without templates. Clipping precedes later callback evaluation; discarded suffix actions do not execute or return when decoding frees space. This is an explicit timing/storage policy completing the inherited final-size bound.

## Query Deferral Modes

_Evidence: SyncTERM (ripper.c:14996-15013); 2.00a4; corpus (MENU.MSE, DEMO-01.COL); HLP._

The query command `1` + ESC ([RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query)) takes a mode, window number and reserve. Each field has a full-width form and a one-byte period spelling for zero. The [wire command entry](5.5-file-transfer-and-queries.md#rip_query) defines where query text begins. The following modes describe RIPtel 3.1.

| Mode | Effect |
| --- | --- |
| `0` | Execute the command text immediately upon receipt |
| `1` | Store a floating viewport expression; clicks do not execute it |
| `2` | Store a floating text-window expression; clicks do not execute it |
| `3` | Store an expression on the numbered viewport; clicks do not execute it |
| `4` | Store an expression on the numbered text window; clicks do not execute it |
| `5` | Store a mouse-field entry expression; execute on pointer entry |
| `6` | Store a mouse-field exit expression; execute on pointer exit |

Modes 1–4 retain the storage/copy/reset machinery, but the original driver has no click-dispatch loop for them and the original client adds none. There is **no shipping numbered/floating click order or same-click live/snapshot mutation rule** to implement for RIPtel 3.1. The inherited A4 numbered-viewport→numbered-text-window→floating-viewport→floating-text-window sequence and contrary A1 sentence are explicitly separated as historical intent in [RIP_QUERY](5.5-file-transfer-and-queries.md#rip_query). This finding does not change earlier-version references. _Evidence: original query definition, event dispatch, client forwarding and [72,972 native query checks](../research/issue-51-deferred-query-order.md#event-path-and-native-checkpoint)._

Sending exact case-insensitive `$OFF$` in a stored-query mode cancels that mode/target's stored expression. The [resident-hover definition rules](5.5-file-transfer-and-queries.md#resident-hover-definitions) specify mode-5/6 empty text, C-string sentinel matching, ignored numeric selectors, source bounds and per-callback source commitment; [membership/lifetime](4.2-mouse-fields-and-pointer.md#hover-and-callback-context) remains independent of handler availability. “Resident” covers stored strings, including floating/numbered and entry/exit queries; it does not split the historical ordering into two classes.

The RIPtel corpus makes constant use of mode 0 as an immediate command carrier - nearly every `.DEF` configuration file is a stack of `!|1<ESC>0000$-=NAME=value$` lines that silently set variables. MENU.MSE also contains:

```text
!|1^[5000$MCURSOR(4)$$>menu.ent$
!|1^[6000$MCURSOR(0)$$>menu.ext$
```

TeleGrafix comments describe mouse entry/exit status-line and cursor changes. Original pointer-movement dispatch confirms the numbering: **5=entry, 6=exit**. These are working hover paths, separate from the stored-but-unexecuted click modes 1–4. _Evidence: corpus; original hover 0x4035, native positive controls and [derivation](../research/issue-51-deferred-query-order.md#event-path-and-native-checkpoint)._

## Mouse-Field Identities - `ID=n:`

_Evidence: corpus (DEMO-01.COL, MENU.MSE, MENU.ENT); HLP._

RIPscrip 3.x lets a [mouse field](4.2-mouse-fields-and-pointer.md)'s host command begin with an identity prefix, `ID=` followed by a number and a colon:

```text
!|1M000G7Y8ICC1000000ID=2:$-=RETURN=>NEWSPAPR.RIP$$>TWEATHER.RIP$
!|1M000GCG8GGU1000000ID=3:$>N2_HORO.RIP$
```

The prefix is not transmitted; it assigns the field a numeric identity that the pre-defined data variable `$FIELDID$` ("current mouse field ID" - RIPTEL.HLP) reports back. Combined with entry/exit queries this produces per-field behavior from a _single_ shared handler. RIPtel's main menu is the canonical example: nine fields carry `ID=1:` through `ID=9:`, the entry query plays MENU.ENT, and MENU.ENT draws a status line with:

```text
!|@HSKA$&MSG<<FIELDID>>$
```

- the `<<FIELDID>>` [macro expansion](5.2-templates-and-conditionals.md#the-3x-macro-layer---name) composes the variable name `MSG1`…`MSG9`, and the `$&…$` dereference (below) prints whichever hover text the `.DEF` file assigned to that field.

### Identity Grammar and FIELDID Lifetime

The definition-time prefix grammar is ASCII **`[iI][dD]=[0-9]{1,5}:`**, with the decimal numeric value restricted to **0..32767 inclusive**, independent of Base Math. It must begin at byte zero of the command's text payload. Leading zeroes are allowed and count toward the five-digit maximum; signs, whitespace, hexadecimal/base-36 digits, missing digits or a missing colon do not match. For simple `1M`, this is the start of its host text. For `1U`, it is the start of the **full text payload before button label/host-command splitting**, not a later embedded host segment. _Evidence: shared original RIPtel 3.1 prefix parser and both constructor calls; [derivation](../research/issue-113-mouse-gesture-identity.md#exact-id-prefix-grammar)._

Recognize and remove **one** valid prefix before normal label/host processing. A nonmatching or out-of-range prefix assigns no identity (`-1`) and leaves the **entire text unchanged** for its normal processing; looking like an invalid ID prefix alone does not reject the enclosing definition. A valid prefix can leave an empty remainder, subject to the enclosing command's other rules. The number is not a macro expression. It is metadata, not the obsolete `1M` slot number or a unique gesture handle; duplicate IDs are allowed and do not merge/replace field instances. ID 0 is valid and differs from no identity.

| Text payload | Stored identity | Remainder after identity parsing |
| --- | --- | --- |
| `ID=0:GO` | `0` | `GO` |
| `id=00007:GO` | `7` | `GO` |
| `ID=32767:GO` | `32767` | `GO` |
| `ID=32768:GO` | `-1` | Unchanged |
| `ID=000001:GO` | `-1` | Unchanged; six digits |
| `ID=+7:GO` or `ID=-7:GO` | `-1` | Unchanged |
| `ID= 7:GO` or `ID=7 :GO` | `-1` | Unchanged |
| ` ID=7:GO` | `-1` | Unchanged; leading space |
| `ID=0x7:GO`, `ID=:GO` or `ID=7GO` | `-1` | Unchanged |
| `ID=7:ID=8:GO` | `7` | `ID=8:GO`; no second prefix parse |

`$FIELDID$` returns the current field's identity as a decimal integer **during synchronous field callback expansion**:

| Evaluation context | FIELDID result |
| --- | --- |
| Shared entry handler, RIP_QUERY mode 5 | Entering field's ID |
| Shared exit handler, RIP_QUERY mode 6 | Exiting field's ID |
| A committed region/button click host command | Captured field's ID, or `-1` if it has no identity |
| Synchronous variable expansion/local file playback called by that handler | Inherit its field context |
| Between handlers, ordinary unrelated expansion, or later queued work | Unavailable: recognized-variable evaluation failure; no numeric substitution |

Unidentified fields skip the shared entry/exit queries; their ordinary click action can still evaluate FIELDID to `-1`. Outside callback context, unavailable FIELDID follows normal macro error handling and does not prompt as an unknown user variable. It does not default to zero/−1, retain the last click's ID or become available merely because the pointer remains over a field. _Evidence: original FIELDID getter, temporary click/hover context writes and [derivation](../research/issue-113-mouse-gesture-identity.md#fieldid-and-hover-scope-evidence)._

**Explicit portable lifetime completion:** Snapshot the numeric identity for each synchronous handler. Nested field callbacks push their own context and restore the caller's identity on return; nested ordinary expansion/playback inherits the current one. Deleting/resetting/restoring the handler's field during that handler cancels future gesture/hover work under the [mutation rules](4.2-mouse-fields-and-pointer.md#left-button-gesture-commitment), but its current identity remains valid until return. After the outermost handler returns, no identity remains. Mouse backups carry definitions, not an active callback stack or held gesture. This is a deliberate lifetime policy for mutation/nesting; the original live-index implementation does not establish those safety guarantees.

For example, entry for ID 7 reads `7`; a nested field callback for ID 8 reads `8`; after it returns the outer handler reads `7` again. If the outer handler executes `1K`, it still reads `7` until it returns, after which FIELDID is unavailable. A later unrelated query does not inherit `7`. The exact identity grammar and normal temporary scope are source-derived; the snapshot/nesting/deletion behavior in this example is the explicit portable completion.

## Setting & Reading User Variables from Host Commands

_Evidence: HLP; corpus (NEWSPAPR.RIP, MENU.DEF, SHOWFONT.FN); 2.00a4; SyncTERM (ripper.c:7774-7789)._

The full reference syntax for a user-defined [text variable](../../glossary.md) inside a host command is unchanged in shape from 2.0, and RIPTEL.HLP documents it completely:

```text
$[directives][x,y:]NAME[(MODE[,CONV])][,width][@question][=default]$
```

| Element | Meaning |
| --- | --- |
| directives | Boolean prefix flags in any order; repeated flags are ignored (see the authoritative directive contract below) |
| `x,y:` | Pop-up dialog position in [world coordinates](../../glossary.md); omit either value (keep the comma) to center on that axis - `$,:NAME$` centers both |
| `(MODE[,CONV])` | Data mode `ANY` / `ALPHA` / `NUMBER` / `ALPHANUM`, optional conversion `TONAME` / `TOUPPER` / `TOLOWER`; conversion-only form (`(TONAME)`) is legal, conversion _before_ mode is a syntax error |
| `,width` | Data-entry field width in columns |
| `@question` | Custom prompt (no `$` allowed inside) |
| `=default` | Default response |

The six directive characters are `*`, `+`, `=`, `#`, `-` and `&`. Prefix `=` selects session memory; `+` selects persistent storage and wins when both occur. **`%` is invalid**, rather than a memory alias: a read of the original help bytes and parser dispatch corrects the earlier transcription/synonym hypothesis. See the authoritative [directive and storage contract](5.1-text-variables.md#directive-characters-in-3x), including repeated flags and mixed-prefix examples.

Transparency is conditional. `-` with a default assigns without prompting; without a default it can prompt. `&` retrieves an existing value without prompting, but prompts if both value and default are missing. The [complete prompt/effect matrix](5.1-text-variables.md#prompt-and-effect-matrix) specifies replacement bytes and storage for all sixteen cases. Cancellation inserts `NONE` for ordinary prompting and no bytes for transparent prompting; successful empty output uses the explicitly chosen `NULL` policy. Neither sentinel is implicitly stored.

Limits per RIPTEL.HLP: variable names up to **20 characters** (letters, digits, underscore; must start with a letter; auto-uppercased), questions and defaults up to **100 characters**, values up to **255 characters**. SyncTERM's reconstruction differs on the name limit: its `rip_user_var` struct allows only 12 characters (`ripper.c:7774-7789`). These limits and the existing argument/evaluation rules are unchanged by the directive correction. The [source derivation](../research/issue-87-user-variable-directives.md) records the original artifact/offsets and separates documentary rules from explicit edge policies.

### The Set-Syntax: `$-=NAME=value$`

_Evidence: corpus (122 distinct occurrences; NEWSPAPR.RIP, MENU.DEF, TELLISTS.MSE)._

The single most common HCL construct in the RIPtel corpus - 122 distinct forms - is the silent assignment:

```text
!|1^[0000$-=MAIN_STORY=story01.txt$|!     Filename containing main story
!|1^[0000$-=MAIN_AUTHOR=Jeff Reeder$|!    Author of main story
!|1^[0000$-=RETURN=>TELDEMOS.RET$
```

This is not new syntax but a _composition_ of the directive characters above: `-` (set without prompting) + `=` (memory table) + `=value` (default supplying the value). Nothing is prompted, nothing is transmitted - the variable is simply defined. MENU.DEF confirms the decomposition by writing the same two directives in the opposite order: `$=-MSG1=Visit your favorite Telnet sites$`. Whole `.DEF` files are nothing but these lines, turning scene scripts into configurable applications.

### The Dereference: `$&NAME$`

_Evidence: corpus (SHOWFONT.FN, NEWSPAPR.RIP, MENU.ENT); 2.00a4._

The `&` directive was defined in 2.0 as _transparent retrieval to the host_, subject to the missing-value/default cases above. The 3.x corpus shows its far more powerful role: **inline interpolation into command arguments**. A `$&NAME$` expands to the variable's value wherever it appears - including inside the argument block of drawing commands:

```text
!|@I064$&FONT_NAME$:                    (text argument of RIP_TEXT_XY)
!|y0000010X000000001S1a000000Marin
!|@4L2L$&MAIN_TITLE$                    (headline drawn from a variable)
!|1R00000000$&MAIN_STORY$               (RIP_READ_SCENE filename from a variable)
```

Even the outline-font _name_ argument of `y` (RIP_EXTENDED_FONT_STYLE) can be `$&FONT_NAME$`. Together with the set-syntax this is the parameter-passing mechanism of the whole RIPtel demo: a scene sets variables, then calls a generic `.FN` "function" scene that dereferences them.

### Defining Variables from the Wire - RIP_DEFINE (`1D`)

[RIP_DEFINE](5.5-file-transfer-and-queries.md#rip_define) defines a variable directly from the wire. It can silently set new or existing names when allowed by the record's confirmation policy. The policy and value may be saved together to the persistent store.

Host requests to delete variables are a separate operation. RIPtel help describes a deletion confirmation and a data-security message for protected variables. See [User Defined Variables and Data Security](5.1-text-variables.md#user-defined-variables-and-data-security).

## Launching Web URLs - `$GOTOURL(NAME)$`

_Evidence: corpus (TELLISTS.MSE); HLP._

New to the 3.x era - and pure 1997 - is web integration from a mouse field. `$GOTOURL(NAME)$` launches the URL held in user variable `NAME` in the system browser. RIPtel's Telnet Site Listings screen wires six fields this way:

```text
!|1M000ZACBSE41000000ID=1:$-=WEBURL=http://duke.usask.ca/~scottp/free.html$$GOTOURL(WEBURL)$
!|1M00CDACNAE41000000ID=2:$-=WEBURL=http://library.usask.ca/hytelnet$$GOTOURL(WEBURL)$
```

Each click silently sets `WEBURL` with the set-syntax, then invokes the launcher - a two-step idiom that keeps `$GOTOURL$` itself generic.

## Things to Take Special Care With Host Commands

_Evidence: 2.00a4._

Special care must be taken when executing host commands or query commands that contain local file playback or active text variables. Either of these operations could instruct the terminal to destroy all mouse fields by performing a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) command (`$RESET$`), a [RIP_KILL_MOUSE_FIELDS](4.2-mouse-fields-and-pointer.md#rip_kill_mouse_fields) command (`$MKILL$`), a restore mouse fields text variable (`$RMF$`) or other such things.

If a situation like this happens, care should be taken to preserve the currently processed host buffer. If it is a mouse field's host command that is being processed, you wouldn't want your application destroying the very buffer that you're processing before you're done processing it. In the case of RIPterm, a sub-string search is done on the host buffer before any processing, for the following strings:

```text
$RMF$    ... Restore Mouse Fields
$>       ... Beginning segment of a Local RIP playback command
$APP     ... Instruction to execute an external application
$RESET$  ... Performs a RIP_RESET_WINDOWS command
$MKILL$  ... Destroys the contents of the internal mouse table
```

If any one of the above strings is found, the terminal physically backs the host buffer up into another location - one that won't be destroyed by the execution of the above commands - and processes the copy instead. In this way, the application can destroy the mouse table to its heart's content but the processing of the buffer will not be affected.

## RIP_SET_REFRESH

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.0-host-commands.md#rip_set_refresh)); HLP (`RIP_SetRefresh`; `$REFRESH$`/`$NOREFRESH$` variables, "refresh expressions", DLL export `RIP_RefreshSend`) - not observed in the RIPtel demo corpus, not in SyncTERM._

_Sets a sequence to send host to refresh display_

|               |                        |
| ------------- | ---------------------- |
| **Level**     | 2                      |
| **Command**   | `R`                    |
| **Arguments** | `res:4 refresh_string` |

**Format:** `!|2R <res> <refresh_string>` **Example:** `!|2R0000^m`

**Attributes used:** [Base Math](../../glossary.md) (current setting)

This command sets a host command sequence in the terminal that can be sent to the host to refresh the current display screen. This refresh option would be chosen by the user to redisplay the screen in case line noise or some kind of corruption caused the screen to become distorted or corrupted. It can only be altered (or cleared) by another RIP_SET_REFRESH command or via a reset. To completely clear a refresh state, call this command with a `$OFF$` text variable as its host command or use the text variable `$NOREFRESH$`.

The host command portion of this sequence can contain any kind of host command information including control characters, [pick lists](5.4-popup-lists.md), text variables or many other things (but not [templates](5.2-templates-and-conditionals.md)).

Local demo scenes have no host to refresh from - hence the command's absence from the RIPtel corpus - but the 3.0 driver's refresh machinery is well attested in HLP (`$REFRESH$`/`$NOREFRESH$` variables, "refresh expressions", the `RIP_RefreshSend` DLL export). _Evidence: HLP._

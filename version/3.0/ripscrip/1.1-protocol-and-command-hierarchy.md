## RIPscrip Protocol - Syntax and General Structure

_Evidence: 2.00a4; corpus; SyncTERM (ripper.c:18516-18608)._

RIPscrip is organized into 10 levels of graphical commands (low Level-0 to high Level-9). Level-0 commands are the building blocks of RIPscrip. The basic graphics primitives of the system are all Level-0, including the commands Line, Rectangle, Circle, Color, Font, etc. Each level of RIPscrip gets progressively higher-level in concept. For example, Level-1 commands use Mouse Regions, Icons, and Formatted Text Regions.

The basic syntax rules are as follows:

1. A RIPscrip command line starts at the beginning of a line of text. A RIPscrip command line moved to the middle of a line of text is treated as literal text. This prevents people inserting mischievous things in teleconference messages, or similar pranks. The only exceptions to this rule is stated below under item 6, "continuation of long lines", and item 12 "alternate RIPscrip starting sequences".

2. A RIPscrip command line begins with an exclamation mark `!` (ASCII code 33 decimal).

3. Every RIPscrip command is preceded by the universal RIPscrip delimiter, vertical-bar `|` (ASCII code 124 decimal).

4. Individual RIPscrip commands may be combined on the same line providing they are separated by the vertical bar delimiter. There are some exceptions to this ([RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode), and a few others). See individual command descriptions for exceptions. _(v2.A1)_

5. RIPscrip commands or command lines may be split across multiple lines with a backslash `\` (ASCII code 92 decimal) just before each split. This helps RIPscrip commands conform to right margins and escape word wrapping.

   An example:

   ```text
   !|c02|L02030405|P0901020102010201020102\
   0102010201020102
   ```

6. RIPscrip must allow for normal text to be intermixed with RIPscrip commands. If unrecognized text appears after a RIPscrip command, on the same line, the text is ignored (the command is not ignored). A line that does not begin with `!|` is considered raw text and is routed to the TTY text window (see "8" below).

7. RIPscrip makes provisions for multiple Graphical Windows and multiple Text Windows. A Graphical Window is where all RIPscrip graphics appear. A Text Window is where raw text appears. Raw Text includes ANSI color and cursor movement codes (a subset of VT-100 terminal emulation), and possibly other terminal emulations like VT-100, VT-102, VT-220, etc.

8. The vertical bar (`|`) of a RIPscrip command can be followed by a level number. If the 1st character after (`|`) is a numeric digit (1-9), then that's the RIPscrip Command Level. If the very 1st character is NOT a digit 1-9, then it is the command type character and the command is a Level-0 command. If the 1st character is a digit 1-9, and the second character is also a digit, then that defines a sub-level of a RIPscrip level. For example:

   ```text
         !|L     RIPscrip Level-0 Command "L"
        !|1L     RIPscrip Level-1 Command "L"
       !|15L     RIPscrip Level-1, sub-level 5 Command "L"
   ```

   Each of the above examples are unique commands not to be confused with each other. You may continue the sub-levels up to a maximum level of 9 (e.g., `!|123456789<cmd>`").

9. Every RIPscrip command includes a command type character. In Level-0 commands, this character immediately follows the vertical bar. At all other levels, it follows the level digits. The command type character may be any of the following characters:

   ```text
   ABCDEFGHIJKLMNOPQRSTUVWXYZ
   abcdefghijklmnopqrstuvwxyz
   @#$&*()[]{}<>:;'",.?-_=+!
   ```

10. Following the command type character are 0 or more parameters. If the command requires a text-string, it is always the LAST parameter. Numeric parameters DO NOT have any delimiters (commas, dashes, spaces, etc.). A variable width numeric parameter may be used as the last parameter. This allows for maximum efficiency.

    If a RIPscrip command does not have a string parameter, but does have numeric parameters, the last parameter may be shortened to get a bit more efficiency out of it. If the last parameter is more than one digit long and the left-most digits are zeros, they may be omitted. At least one digit must remain though after all of the shortening is done (eg, "0001" can be shortened to "1" but "0000" cannot be shortened to "", it can only be shortened to "0"). _(v2.A3)_

    For example, the [RIP_COLOR](2.0-color-modes-and-palettes.md#rip_color) command, used to set the current drawing color, requires one parameter - a color number. If we were going to set color 1 (usually dark blue), then the command would appear formally as follows: _(v2.A3)_

    ```text
    !|c01
    ```

    Under this shortening clause, you could omit the "0" and make the command appear like this: _(v2.A3)_

    ```text
    !|c1
    ```

    This allows you to shave one byte off of the command. If you were trying to set color number zero (normally black), then you could still shorten the parameter, but you still have to leave at least one digit there (0), so the command would appear like this: _(v2.A3)_

    ```text
    !|c0
    ```

    There is an additional optimization that can be used for commands that have no string parameter, and have a reserved parameter as the LAST parameter for that command. In this case, the reserved parameter may be omitted completely, and the value should be assumed to be zero (`0'). Please take note that the previous paragraphs still apply! You can omit the reserved parameter AND shorten the last transmitted parameter so as to squeeze out as many unnecessary characters from the command as possible. _(v2.A2)_

    Numbers are normally represented in base-36 (unless altered by a RIPscrip command). This compacts numbers down to roughly 3/5 of their decimal form. This numbering system, technically called "Hexa-Tri-Decimal" or "MegaNums" is unlike Hexadecimal which uses 0-9 and A-F. MegaNums take advantage of the entire alphabet, using characters 0-9 and A-Z. _(v2.A0)_

    See [1.2 Math & Coordinates](1.2-math-and-coordinates.md) about Base Math variations. _(v2.A0)_

11. An exclamation mark (`!`) or vertical bar (`|`) character can appear in a RIPscrip text parameter by preceding it with a backslash (`\`). This is known as "quoting" a special character. A literal backslash is represented with a double-backslash (`\\`). Also, in some situations you need to quote specific characters so that they are not misinterpretted. For example, in a button host string, the characters `[`, `]`, `(`, and `$` are used as special host command characters and will need to be quoted (eg, `\[`, `\]`, `\(` and `\$` respectively). See rule #14 below for more details on quoting these special sequences. _(v2.A3)_

12. A RIPscrip sequence CAN begin in a column other than column #0, if the exclamation mark prefix is replaced with a Ctrl-A (Start Of Header [SOH] - ASCII character 1) character, or Ctrl-B (STX - ASCII character 2) character. Since 99.9% of all BBS' do not allow users to enter most control characters, users will be unable to begin RIPscrip sequences in the middle of a command line. Only the host should be able to do this. This prevents people from cluttering teleconference, or other areas of a host with spurious RIPscrip sequences.

    Let's take an example, where we have a piece of raw text and then a RIPscrip command immediately following the text before the carriage return (in this example `<STX>` stands for the STX character): _(v2.A3)_

    ```text
    This is raw text<STX>|c01|@1010hello world
    ```

    In the above example, the text "This is raw text" would be sent to the active text window, then the RIPscrip sequences would be processed - set the color to blue (01), then print the text "hello world" on the screen at (10,10) in meganums or (36,36) in decimal. _(v2.A3)_

13. If the last couple of bytes on a RIPscrip text line are backslashes, special care must be taken to make sure that they are not interpreted as a line-continuation. If a literal backslash is desired as the last position on the line, it must be specified as a double-backslash (eg, `\\`). If a line-continuation is used then there would have to be three backslashes used on the line as in the following example: _(v1.54)_

    ```text
    !|@2233this is a text line with a literal \\\
    used in the message
    ```

    This would text output at (22,33) [meganum] the message: _(v1.54)_

    ```text
    this is a text line with a literal \used in the message
    ```

14. Some character sequences in text parameter strings can be misinterpreted as RIPscrip command sequences (eg, `$`, `<>`, `((`, `))`, `[`, `]`, `[]`, etc). To avoid syntax confusion these sequences can be "escaped" to indicate that they are actually literal sequences, not to be confused with a RIPscrip command sequence identifier. For example, the sequence: _(v2.A1)_

    ```text
    $Name$
    ```

    would normally be interpreted as a RIPscrip text variable that requires the user's response. If however, you wanted this sequence to be interpretted as literal text, you should perform the following escape sequences:

    ```text
    \$Name\$
    ```

    This makes it so a RIPscrip terminal doesn't misinterpret the dollar signs as text variable delimiters.

15. Extraneous information. If too much data is encountered for a particular RIPscrip command, or too little information is found (aside from a short last parameter) then the command is considered "hopelessly corrupted" and discarded. The RIPscrip parser should synchronize to the next vertical bar delimiter to begin the next command. _(v2.A1)_

## Command Syntax - Parser-Exact Behavior

_Evidence: DLL; [primary traces, artifact identity, native buffer/RIP/ANSI probes and controlled-service limits](../research/issue-7-framing-identification.md)._

These sections describe the original RIPtel 3.1 driver’s input pipeline. The original outer buffer consumer tries RIP framing first when RIP emulation is enabled; unconsumed/fallback bytes then enter the text path, where ordinary ANSI parsing remains available. Column-flow interception and disabled text/ANSI paths can consume text separately; the following ANSI examples assume the normal ANSI-enabled text path.

### Introducers

In idle RIP framing, SOH (0x01) or STX (0x02) can introduce a sequence between raw-text bytes. `!` (0x21) is accepted when the preceding byte is CR, LF or form feed and ANSI is idle, or when the client’s beginning-of-line callback returns true. Every introducer must then be followed by `|`; otherwise both the failed introducer and the following byte go through the raw-text fallback. A stray exclamation therefore remains ordinary text.

The client predicate is explicit: RIPtel supplies client-maintained line state. SyncTERM’s separate display-cursor-column rule is not established as this driver’s universal rule. SOH/STX acceptance is an idle-framing rule, not a promise to interrupt an already buffered RIP argument or reset pending ANSI. The [priority examples](#esc-priority-and-resumption) distinguish these states.

### Levels and Sublevels

The original parser accepts **up to nine consecutive digits `1`..`9`** after the initial/chaining pipe. All those digits form the level key; the next non-level digit/byte is the opcode. A **third digit is another level digit**, unlike SyncTERM’s two-digit parser. `0` is never a level digit at any position: `!|0X` attempts level-zero opcode `0`, not a level-zero form of command X. A tenth level digit discards the current command.

The complete shipped dispatch table defines commands at level zero and single-digit keys 1, 2, 3 and 9 only. Recognizing a deeper key syntactically does not define commands for it: `!|123L…` is an unknown level-123 command, not opcode `3` under level 12. Unknown commands scan to a pipe or line ending. Opcode bytes need not be printable; ESC is the actual opcode in level-1 query, level-2 directory-switch and level-9 block-mode commands.

**Shipped stale-prefix defect:** after a multilevel prefix, its second byte can remain in the parser’s reused key buffer. Level-zero lookup checks that stale byte and can skip all level-zero records even after a pipe or new line. Checked input `!|123L00000000|c01` plus CRLF dispatches neither command. A subsequent `!|1K|c01` plus CRLF dispatches both: the one-digit prefix clears the stale second byte. A full parser reset also clears it. Implementations that clear unused key bytes correct this defect; do not mistake the defect for a two-digit depth limit or reinterpret a third digit as an opcode.

### Parameters

_Evidence: 2.00a4 rules 9-10._

Zero or more parameters follow the command character, with no delimiters between numeric fields. Numeric parameters are fixed-width [MegaNums or UltraNums](1.2-math-and-coordinates.md) per the current base math. A text parameter, if present, is always last. For a command without a text parameter, drop leading zeros from its last transmitted numeric field to shorten it (`!|c01` → `!|c1`). Keep at least one digit in that field. A trailing _reserved_ field may be omitted when the command's receive rules allow it. Omission supplies `0`. The [delimiter](#numeric-collection-and-dispatch) finalizes a short field or an allowed omission. A [period at the start of a numeric field](#period-as-a-zero-field) supplies zero in one byte.

### Chaining, Continuation, and Line Endings

_Evidence: DLL, original byte parser; [checked streams](../research/issue-7-framing-identification.md#distinguishing-streams-and-stages)._

An unquoted pipe dispatches/finishes the buffered command and starts the next command on the same line. **CR, LF and form feed terminate commands**; LF is not unconditionally swallowed inside a command. CRLF is accepted as a physical line ending. Thus `!|Tleft` LF `right` CRLF draws `left`, then routes `right` CRLF as raw text; it does not concatenate the two words.

A backslash at a physical line ending continues the current parsing state across CR/LF/form-feed bytes. In a string, `abc\` CRLF `def` becomes `abcdef`. A literal trailing backslash is doubled; two backslashes preserve the literal and allow the line to terminate, while a third continues it. These rules apply to the framing state, before macro/host interpretation.

### Escaping in Text Parameters

_Evidence: DLL, text escape branch RVA `0x3aa63–0x3aae2`; [framing capture and original-host-stage checks](../research/issue-7-framing-identification.md#distinguishing-streams-and-stages)._

Framing does **not** globally remove every backslash. Within a RIP string, quoting SOH, STX or `|` removes the backslash and inserts that byte as data. Other quoted bytes retain both the backslash and the following byte in the string passed to the command consumer. In particular, `\$`, `\[`, `\]`, `\(`, `\!` and `\\` survive framing; continuation at a line ending is the separate rule above.

The subsequent consumer interprets its own text/macro/host syntax. In the ordinary dollar-code scanner, enabled backslash processing removes one quote and skips interpretation of the following character. Host response processing makes [two ordinary passes](5.2-templates-and-conditionals.md#shipped-processing-order), deferring backslash removal in the first and applying it in the second. The preprocessor and command-block parsers have their own scans, so quoting is stage-specific.

Checked host text `\$SHIFT\$` transmits literal `$SHIFT$` and never queries SHIFT. Quoting only the opening dollar, `\$SHIFT$`, is insufficient in this two-pass path: the first pass evaluates SHIFT and the second removes the remaining quote; with Shift down the output is `1`. Preserve the quotes through framing and quote both dollar delimiters for the literal-variable example. SyncTERM’s global `\X` collapse before command consumption is a distinct implementation behavior.

### ESC Priority and Resumption

_Evidence: DLL, original buffer consumer `0x57a2`, RIP parser `0x39e90`, ANSI parser `0x37b7c`, autosense `0x355d9`; [native derivation](../research/issue-7-framing-identification.md)._

ESC does not globally preempt all unfinished input. RIP framing runs before ordinary ANSI handling while enabled. In a pending RIP text argument, ESC is data; in numeric fields it can corrupt the command; in the opcode position it can be a valid level-1/2/9 opcode. Only bytes routed to the text path are candidates for ANSI interpretation.

ANSI recognizes a new ESC sequence while idle. ESC received during its pending ESC/CSI sequence is handled by that state rather than universally restarting at ESC; the checked unsupported ESC final clears the pending sequence, leaving subsequent `[`/`!` as ordinary text. CAN (0x18) and SUB (0x1a) explicitly cancel a pending ANSI sequence. Starting RIP with SOH while ANSI is pending does not itself clear ANSI state.

Disabling RIP skips RIP framing but leaves the normal ANSI path available. `ESC[2!` can therefore re-enable RIP, including for the next byte in the same buffer. Enable changes the emulation flag; it does **not** reset parser state or reinterpret bytes received while disabled. If an API/menu action disables RIP during a buffered string, re-enabling resumes that string with the disabled interval omitted. Send a new command at a valid framing boundary (for example CRLF then `!|`, or idle SOH followed by `|`); enable is not an implicit scene reset.

In this table, ESC/SOH/LF/CRLF denote the named literal bytes, not their printed spellings. Initial state is enabled, idle and at a line boundary unless specified; commands are captured at original dispatch, independently of rendering.

| `!\|123` | Prefix `123` buffered; no opcode yet |
| `!\|1234567891L…` | Tenth level digit discards the command |
| `!\|123L00000000\|c01` CRLF | Unknown deep key; stale-prefix defect also suppresses color |
| Following that with `!\|1K\|c01` CRLF | Kill-mouse-fields and color both dispatch; one-digit prefix clears stale byte |

### Raw Text and Error Handling

A line with no accepted introducer is raw text, routed to the current text path (or consumed by active [column flow](3.1-column-text-system.md)). A malformed numeric field discards the command. The parser resumes at the next pipe or line ending. Recovery after multilevel prefixes remains subject to the [stale-prefix defect](#levels-and-sublevels).

#### Numeric collection and dispatch

While collecting an ordinary numeric field, apply the command's documented radix and its [receive alphabet](1.2-math-and-coordinates.md#working-with-meganums-and-ultranums-by-hand). A lowercase letter therefore discards an unfinished MegaNum command, and a dash discards an unfinished command in either radix. Framing bytes follow their framing rules. A [leading period](#period-as-a-zero-field) completes the field with value zero. After a numeric prefix switches into text collection, use the command's text grammar for the remaining bytes. Lowercase letters and dashes can occur in filename text.

For an ordinary fixed-field numeric command such as `L` or `f`, consuming the declared fields ends numeric collection. The parser keeps those values pending across receive chunks and ignores surplus bytes, including further numeric digits, until the command delimiter. A pipe dispatches the pending command and starts the next command on the same line. A terminating CR, LF or form feed dispatches it and closes the line. The handler runs once when the delimiter arrives. The earlier ALPHA 4 draft calls for rejecting surplus bytes. The 3.0 behavior here follows the original fixed-field collector. [Source trace and staged captures](../research/issue-237-fixed-numeric-dispatch.md).

An opcode with zero numeric arguments and no text argument enters the same delimiter wait as soon as the opcode is recognized. For example, bodies `#extra`, `(extra`, `)extra`, `*extra`, `eextra` and `>extra` each dispatch once with zero arguments at the following CR. The [comment opcode](#rip_comment) has a text argument, so `!extra` instead passes `extra` to its text consumer. [Descriptor and state derivation](../research/issue-270-coordinate-and-fixed-field-edges.md#zero-argument-commands).

While still collecting a field, a delimiter can finalize a nonempty shortened final number under the [parameter rules](#parameters). A space within unfinished numeric fields instead discards the command. An ordinary counted polygon (`P`) is a variable-argument command. Its count defines the number of vertices, while numeric collection continues to the delimiter under the existing [polygon limits](2.3-shapes-and-fills.md#polygon-counts-and-wire-limits). A space after the listed vertices can therefore discard that polygon.

With Color Map mode and XY width 2, feed `!|` followed by one body below and then feed CR separately. The body alone produces zero dispatches. #### Period as a zero field

When the ordinary numeric collector expects the first byte of a field, a period (`.`, byte `0x2e`) supplies the entire field with value zero. This applies in both bases and to any current field width. Advance by one argument using one input byte. If another field follows, its first byte comes immediately after the period and uses that next field's own width and radix. If this completes a fixed numeric-only command, retain the decoded arguments until the delimiter.

A period after any digits in an unfinished field is malformed input and discards the command. At that point a delimiter could end a permitted short final field. A period after all fixed numeric-only fields are complete belongs to the ignored surplus. [Original collector trace and supplied captures](../research/issue-240-period-zero-field.md).

## Description of RIPscrip Command Levels

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4._

As previously described, RIPscrip is composed of ten different levels of commands. The distribution of commands over different levels is done in a rather organized fashion based on command type. Each level of command in general, is progressively higher level in concept. For example, level 0 commands are the most basic building blocks of RIPscrip (eg, graphical primitives, protocol setup, etc). Level one commands are simple user interface objects. Level 2 commands are higher level still in that they deal with context swapping issues. At the highest level, level-9, we deal with binary transfer modes like file transfer protocols, etc. A more formal definition of the currently used levels are:

| Level | Description |
| --- | --- |
| 0 | Lowest-level RIPscrip primitives. Simple graphical drawing primitives, low-level RIPscrip protocol mode settings, etc. |
| 1 | Simple user interface objects (buttons, mouse fields, clipboard slots, formatted text regions). This level consolidates one or more simple building blocks from level 0 and also introduces more abstract user interface objects (eg, mouse fields). |
| 2 | Basic context switching information (switching styles, and other window or context senstive commands. |
| 3 | Basic time-related commands (baud rate emulation and delay commands). |
| 4 | Open for future development |
| 5 | Open for future development |
| 6 | Open for future development |
| 7 | Open for future development |
| 8 | Open for future development |
| 9 | Binary related data transfer functions (ie, block protocol modes, UU-Encoding, etc). |

Each level/character pair is a unique command: `!|L`, `!|1L`, and `!|15L` are three different commands. The consolidated 3.x inventory across all levels is [9.0 Command Reference](9.0-command-reference.md).

## ANSI Sequences (Auto-Sensing)

_Evidence: DLL; [exact producers, original ANSI/enable probes and client output path](../research/issue-7-framing-identification.md); inherited vendor allocation: 1.54/2.00a4._

The normal ANSI text path recognizes these RIP control sequences. RIPtel’s engine identification phrase is **`RIPSCRIP030001`**, shared by autosense and zero-argument [`$RIPVER$`](5.1-text-variables.md#ripver).

| Sequence | Engine effect / response |
| --- | --- |
| `ESC[!` or `ESC[0!` | When RIP is enabled, send exactly `RIPSCRIP030001` (14 ASCII bytes); no NUL, CR or LF |
| `ESC[1!` | Disable RIP framing; no reply; ANSI control remains available |
| `ESC[2!` | Enable RIP framing; no reply; parser state is preserved |
| `ESC[3!` | When RIP is enabled, send `RIPSCRIP030001` followed by one CR |

Queries 0/3 while disabled produce no reply. The callback uses only the first ANSI parameter (later parameters are ignored); other selectors produce no reply. The ordinary ANSI decimal accumulator wraps to 16 bits, so `65536` reaches selector 0. Private-prefixed `ESC[?0!` does not invoke this callback. As described [above](#esc-priority-and-resumption), these sequences require the ANSI path; their printed bytes inside an unfinished RIP text argument do not become controls.

The phrase format is **`RIPSCRIPxxyyvs`**: two decimal major digits, two minor digits, one vendor code and one vendor subversion. The vendor allocation is 0 generic/unspecified, 1 RIPterm/TeleGrafix, 2 Qmodem Pro. Thus RIPtel’s `030001` means language 03.00, vendor 0, subversion 1; the last two digits are not a two-digit language revision. Product version RIPtel 3.1 and driver build 3.0.7 are separate identities.

A new compatible implementation may use the explicitly documented **generic profile `RIPSCRIP030000`** (language 03.00, vendor 0, subversion 0), with the same selector/terminator policy. This is an interoperability choice permitted by this reconstruction, not a claim to be TeleGrafix. The [complete byte/reply reference](9.2-versions.md#generic-implementation-profile) gives exact bytes and separates this profile from historical replies.

RIPTEL.HLP’s FAQ prints only `RIPSCRIP03000`; retain that as a documentary quote, not a complete executable reply. SyncTERM independently sends `RIPSCRIP030001` in its RIP 3 mode, but its documented one-way-disable bug does not establish RIPtel behavior. The original RIPtel pipeline demonstrably re-enables. Client-configured CR-to-CRLF translation may affect selector 3’s CR; default/0 have no line ending to translate.

> **Product-era note:** the recovered 2.x-generation RIPterm binaries report `RIPSCRIP020000` despite product-version changes; see the [2.0 identity record](../../2.0/ripscrip/9.2-versions.md). That string likewise uses the vendor/subversion allocation, not a separate product build field.

## Scene Header Segments

_Evidence: DLL; [derivation and original-parser probes](../research/issue-5-scene-headers.md)._

The shipped [`RIP_HEADER`](#rip_header) is one `h` command with a base block of eight digits in its full-width spelling, followed by concatenated typed segments. The base fields are revision, global flags and segment count; each segment has a type digit and its own fixed fields. A pipe or line ending terminates the complete header. All header numbers use base 64. See the [complete field/flag tables and checked examples](#rip_header); the Alpha 4 flag list is not the shipped 3.0.7 layout. Audio is a stop-playback segment with no table slot.

## Wire-Format Observations from the Corpus

_Evidence: corpus._

The 116 TeleGrafix-authored RIPtel demo scripts are the best available picture of real 3.x on the wire:

- **SOH marks scene start.** 111 of 116 files begin their _first_ command line with SOH + `|`, then use `!|` for every subsequent line - SOH apparently flags start-of-scene to the 3.0 stream parser, while `!|` remains the 1.54-compatible introducer. (Three files invert the pattern, nearly all-SOH.)
- **The standard prologue** opens 90+ files: `J10|n2000|M08|fZKQO` - base math 36, 2-digit coordinates, 8-bit palette color mode, 1280×960 world frame (see [1.2 Math & Coordinates](1.2-math-and-coordinates.md)).
- **Trailing text after fixed-length arguments is tolerated** and used as inline commentary - the driver stops reading once the fixed fields are consumed: `!|fZKQO                 Set world coordinats to 1280x960`. Chained `!|command|! comment` forms (the `!` comment opcode) are ubiquitous.
- **Harmless corpus typos.** A missing `!` introducer (`|1<ESC>0000$COMPAT$`, CURVES.RIP) and bare `!|` lines pass through the shipping driver without visible failure. For a separator such as `!|----`, the first dash selects [RIP_FILLED_SKEWED_OVAL](2.2-curves.md#rip_filled_skewed_oval). The next dash is invalid in its first numeric field, so the collector discards the command without drawing.
- **Line endings are CRLF**, with `\` continuation across physical lines for long vertex lists (POLYPOLY.RIP). See [6.0 Writing 3.x .RIP Files](6.0-writing-rip-files.md) for authoring conventions.

## How commands are documented

_Evidence: editorial; format follows 2.00a4._

The chapters of this reference detail the reconstructed RIPscrip 3.x command set (the consolidated index is [9.0 Command Reference](9.0-command-reference.md)). Each command has these aspects:

- **SYMBOL** - the symbolic constant that is referenced in RIPscrip documents. This is the universal name for the command. _(v2.A3)_

- **FUNCTION** - A short description of the command.

- **LEVEL** - The Command Level. Sub-levels (if any) are represented with decimal points (eg, 1.3.5 for Level-1, Sub-level 3, Sub-Sub-level 5). This is for discussion purposes only. The decimal points are never part of the actual command.

- **COMMAND** - The character identifying the command

- **ARGUMENTS** - The arguments or parameters for the command. Commands that do not require any parameters after the command type character are shown here as "\<none\>". Each parameter is shown in the order it appears in the command, and is represented by a name. If a parameter is numeric, it is followed by a width specifier indicating how many meganum or ultranum digits the parameter consists of (e.g., ":2" means a 2-digit number, or a value between 0 and 1295 for meganums, or 0 and 4095 for ultranums). If a parameter does not have a width specifier, it is by default a text parameter, and should be the last parameter of the command.

  If a command is variable length (see [POLYGON](2.3-shapes-and-fills.md#rip_polygon)), then it will appear with an ellipe (...), meaning that the command repeats the specific parameters a variable number of times. _(v2.A2)_

  If the parameter is a variable-width coordinate that can be set by the [RIP_SET_COORDINATE_SIZE](1.2-math-and-coordinates.md#rip_set_coordinate_size), or via the [RIP_HEADER](#rip_header) commands, then the parameter will be followed by a coordinate specifier (e.g., ":XY" means that the parameter is a variable-width coordinate). _(v2.A2, revised v2.A3)_

  A `:CM` color field uses the [active color mode's width and radix](2.0-color-modes-and-palettes.md#color-mode-wire-format). Other color fields use the rules in their command entries.

- **FORMAT** - This represents the format of the command, with the starting `!|`, the level digits, the command type character, and the parameter list, with the parameter names in angle brackets. (These parameters are spaced apart, but these spaces never appear in the physical commands.)

- **EXAMPLE** - An actual example of the RIPscrip command. In this reconstructed edition, examples are drawn from the RIPtel corpus wherever one exists.

- **DRAW COLOR** - If YES, then this command uses or affects the current Drawing Color.

- **BACK COLOR** - If YES, then this command uses (or affects) the current background pen drawing color. _(v2.A1)_

- **LINE STYLE** - If YES, then this command uses or affects the current Line Style Pattern.

- **FILL COLOR** - If YES, then this command uses or affects the current Fill Color.

- **FILL PATRN** - If YES, then this command uses or affects the current Fill Pattern.

- **WRITE MODE** - If YES, then this command will take advantage of the current Write Mode (eg, COPY, or XOR).

- **FONT STYLE** - If YES, then this command uses or affects the current Font Style/size/orientation. _(v2.A3)_

- **VIEWPORT** - If YES, then this command adheres to the graphical viewport (draws inside it). Any RIPscrip command that adheres to the graphical viewport will be drawn (when received) only if the viewport is activated. If the viewport is deactivated, then the command is parsed, but completely ignored. _(v1.54, revised v2.A4)_

- **USES PORT** - If YES, then this command adheres to, is affected by, or modifies the definition of a [port](7.0-drawing-ports.md). _(v2.A3)_

- **BASE MATH** - Indicates which base math this command responds to. The possible settings are N/A (does not apply), Meganums (uses meganums ONLY), Ultranums (uses Ultranums ONLY), and Current (uses current base math setting as set by either RIP_HEADER or [RIP_SET_BASE_MATH](1.2-math-and-coordinates.md#rip_set_base_math)). _(v2.A2)_

In addition - because this is a reconstructed edition - every command entry carries an **_Evidence:_** line naming the sources for that command: `2.00a4`, `HLP` (the RIP_* name in the 3.0.7 inventory), `corpus` (with file names), and/or `SyncTERM` (with ripper.c line cites). Commands attested only by a single source, and argument layouts inferred rather than documented, are flagged in the entry.

## RIP_HEADER

_Configure a scene using a base header and typed state segments_

_Evidence: DLL (RIPtel 3.1’s RIPscrip 3.0.7 driver); [primary derivation and original-routine probes](../research/issue-5-scene-headers.md). This shipped contract replaces the Alpha 4 header flag list previously reproduced here. It does not change the preserved 2.0 source edition._

|  |  |
| --- | --- |
| **Level** | 0 |
| **Command** | `h` |
| **Arguments** | `revision:2 flags:4 segments:2`, followed by typed segments below |

**Format:** `!|h <revision> <flags> <segments> <segment>…` **Example:** `!|h01000201502O2220`

All fields, including every segment, use **base 64 regardless of current base math**. Spaces shown in the grammar are explanatory and are not sent. `revision` accepts 0 or 1, `flags` accepts 0..31, and the declared segment count accepts 0..10. The accepted revision tags are the inherited 00/01 tags, not a client version number or a new `03` tag; the driver remembers the tag for the scene.

The full-width byte grammar is shown below. The [numeric shorthand rules](#numeric-shorthand-and-segment-selectors) also apply.

```text
!|h RR FFFF NN S1 S2 … SNN terminator
RR:2, FFFF:4, NN:2                 all base 64
terminator = command pipe, CR, LF, or form-feed
```

Segments are concatenated **without pipes, commas, spaces or nested introducers**. A pipe ends the entire header and starts the next command. The segment count is not a byte-level terminator: the parser consumes typed segments until a command/line terminator, then validates the declared count and decoded argument length. Ordinary backslash line continuation works inside fields and between segments. Do not append unmarked prose after the final segment.

The driver validates the entire decoded header before performing global resets or segment actions. A bad revision, flag value, slot or segment count suppresses its application. Runtime failures in an individual operation do not roll back earlier operations. Segments run in wire order; repeats are permitted. A shipped validation exception is that a declared count of zero ignores parsed extra segments; those extras are not applied. Well-formed headers still send exactly the declared segments.

### Numeric shorthand and segment selectors

The three base fields and all ordinary segment fields use the common numeric collector. A period as the first numeric byte completes the whole field with value zero. A period after a digit discards the header. A pipe, CR, LF or form feed can finish the last field of the active base or segment record if that field has at least one digit, even when fewer digits were sent than its stated width. The delimiter then ends the entire header. An empty final field or an incomplete earlier field prevents header dispatch. In the full-width spelling, digits continue filling the current field to its stated width before the next field or selector begins.

The original 3.0.7 collector also accepts `<` within an ordinary numeric field. It completes that field immediately with the buffered value, or with zero if the field is empty. It can therefore finish an earlier field while collection continues. Use full-width fields, a leading period, or final-field shortening for the documented wire forms. At a segment selector boundary `<` discards the header. [Original driver evidence](../research/issue-281-header-numeric-shorthand.md#numeric-collection-and-selector-boundaries).

Each segment starts with a literal ASCII digit `0` through `9`. The same byte selects the segment layout and supplies its first argument. A period or a bare DEL (0x7F) where the type digit is expected discards the header. Within an ordinary numeric field DEL is ignored. Backslash continuation is consumed both within ordinary numeric fields and at selector boundaries. In either position, a pipe ends or discards the current header as appropriate and starts the next command, including after a backslash. [Original driver evidence](../research/issue-281-header-numeric-shorthand.md).

Feed `!|` and the body, then send CR or a pipe separately.

| Body           | Arguments and result at the delimiter                     |
| -------------- | --------------------------------------------------------- |
| `h..01601`     | `(0, 0, 1, 6, 1)` validates.                              |
| `h...`         | `(0, 0, 0)` validates.                                    |
| `h010000016.`  | `(1, 0, 1, 6, 0)` validates.                              |
| `h0100000161`  | `(1, 0, 1, 6, 1)` validates with a shortened flags field. |
| `h010000016`   | The flags field is empty. No header dispatch.             |
| `h01000001.01` | The selector is invalid. No header dispatch.              |

After the invalid selector in `!|h01000001.01\|c02`, the pipe starts the color command. A following delimiter dispatches only [RIP_COLOR](2.0-color-modes-and-palettes.md#rip_color) with value 2.

### Global header flags

These values may be ORed. The sequence is reset, remember revision, release a previous input lock, optionally lock input again, select table zeros, clear refresh state, then execute the segments.

| Value | Shipped effect |
| --- | --- |
| 1 | Perform the [complete shared HARD field/lifetime reset](1.3-world-view-virtual-canvas.md#hard-reset-state-and-lifetime), overriding live/saved protection; then apply HEADER revision/input-lock/segment stages |
| 2 | Drawing/soft reset, as `RIP_RESET_WINDOWS`; ignored when bit 1 is also set |
| 4 | Lock mouse/keyboard input during scene receipt and select the wait cursor; `#` releases this lock |
| 8 | Select slot 0 of text-window, button-style, graphics-style, drawing-port, palette and environment tables |
| 16 | Clear refresh state |

Zero requests no optional global operation, but still remembers the revision and releases an existing input lock. It does not imply the Alpha 4 default reset/coordinate flags. A later segment can change a state just selected/reset globally, including the cursor. This mechanism is separate from local-file start and from the `#` scene-end marker.

### Scene Input Gates

In the portable profile, a successfully validated HEADER releases both previous scene gates at its unlock stage. With global flag 4 it then sets both gates, selects pointer 6 (wait), and requests a return to arrow when the mouse gate is released. Apply subsequent header options and segments in their normal order. The mouse gate suppresses pointer-event delivery. The keyboard gate suppresses keyboard activation and ordinary forwarding. The [RESET input actions](5.1-text-variables.md#reset) release just their respective gate.

NO_MORE, including a configured scene-end timeout, releases both remaining gates. A new validated HEADER performs the same gate release before any relock. If the mouse gate is still set and the return to arrow is pending, select pointer 0 on release. A cleared mouse gate leaves the pointer selected at scene end. The full release also clears the pending return. A pointer appearance change alone leaves both input gates in place. A successful [MCURSOR variable](5.1-text-variables.md#mcursor), a shared SOFT or HARD pointer reset, or an ENV selection that changes the pointer cancels the pending scene return. Wire `RIP_SET_MOUSE_CURSOR` leaves it pending. [Original lock and pointer-release helper](../research/issue-286-reset-input-lock.md).

### Segment fields

The first field is a literal type digit `0`..`9`; it is also the first decoded numeric argument. Table slots are always checked 0..35, even if the operation flags do not use the supplied slot. Coordinate width/RGB fields are present in an environment segment even when their setting bits are absent.

| Type | Object | Fields after type | Accepted flags |
| --- | --- | --- | --- |
| 0 | Button style | `flags:2 slot:1` | 0..255 |
| 1 | Graphics style | `flags:2 slot:1` | 0..255 |
| 2 | Drawing port | `flags:4 slot:1` | 0..65535 |
| 3 | Text window | `flags:4 slot:1` | 0..524287 |
| 4 | Color palette | `flags:2 slot:1` | 0..255 |
| 5 | Environment | `flags:4 slot:1 coordinate_width:1 rgb_bits:1` | 0..65535; see validation defect below |
| 6 | Mouse fields/buttons | `flags:2` | 0..31 |
| 7 | Waveform audio | `flags:2` | 0..1 |
| 8 | Graphics screen | `flags:2` | 0..15 |
| 9 | Character set | `charset:2` | Charset 0 or 1; descriptor/validator mismatch below |

Types 6, 7 and 8 have **no table slot field**. In particular, audio is a single stop-playback action, not a 36-entry audio table.

### Button, graphics-style, palette and environment flags

For types 0, 1, 4 and 5:

| Value | Effect, in this order |
| --- | --- |
| 1 | Delete unprotected nonzero table entries and select slot 0 |
| 2 | Select the supplied slot |
| 4 | Delete other unprotected entries, temporarily protecting the current nonzero entry when necessary so it survives |
| 8 | Delete this object family’s base backup area |
| 16 | Delete the first existing unprotected numbered save area, scanning 0..9; **one area per header segment**, not all areas |
| 32 | Clear this object family’s backup stack |

The numbered-save behavior is a shipped defect in the shared deletion helper: it returns after its first successful deletion. Repeat the operation if clearing several such areas is required.

The remaining two low-byte bits differ by object:

| Type | 64 | 128 |
| --- | --- | --- |
| 0 button style | Reset current unprotected style to defaults | Reset all unprotected styles to defaults |
| 1 graphics style | Reset current unprotected style to defaults | Reset all unprotected styles to defaults |
| 4 palette | Upload the existing current palette if defined and unprotected; no RGB/default/definition change | Upload existing current palette only if an invalid definition guard passes and current is unprotected; see defect below |
| 5 environment | Reset every defined, unprotected environment to base 36, 640×350 world frame, coordinate width 2 and RGB bits 0; restore the previous selection | Set those defaults on the current environment directly, including a protected current environment |

**Palette correction:** 64 scans entries but only uploads the current palette; it does not reset defaults or other slots. For 128, the original INUSE helper does not recognize the supplied -1/current sentinel and reads the flag word **two bytes before the palette array**. Bit 1 of that unrelated word gates the upload; the following current-protection check is valid. This is an out-of-bounds shipped defect with no reliable defined-slot semantics. Neither bit changes stored RGB values or definition flags. The earlier reconstruction's “reset defaults” description is withdrawn; use the explicit [PAL reset lifecycle](7.1-data-tables.md#palette-reset-lifecycle) when defaults are required. _Evidence: original upload/guard instructions and [controlled-canary native checks](../research/issue-16-table-lifecycle.md#header-correction-and-failed-hypotheses)._

Environment adds:

| Value | Effect |
| --- | --- |
| 256 | Set base math to 64 |
| 512 | Set base math to 36; skipped if 256 is also set |
| 1024 | Set coordinate width from the segment’s field; downstream setter accepts only 2..5 |
| 2048 | Set RGB bits to 0 (palette mode) |
| 4096 | Set RGB bits from the segment’s field; downstream setter accepts 0..8 |
| 8192 | Set world frame to 4096×3072 for base 64, otherwise 1280×960, using the base math in effect at this point |
| 16384 | Set world frame to 640×350; runs after and overrides 8192 |
| 32768 | Select the arrow cursor |

**Environment validation defect:** when 1024 is set, the validator checks the **slot number**, rather than coordinate width, against 2..5. When 4096 is set it checks the **slot number**, rather than RGB bits, against 1..8. A header using these settings with slot 0 is rejected even if the fields are valid. The actual setters then silently ignore an invalid width/RGB field, while the other segment effects continue. Direct environment setters, including bit 128, do not consult environment protection; the all-environment reset under bit 64 does. These are distinct paths, not a uniform permission rule.

The [completed ANSI ESC snapshot lifecycle](1.4-terminal-ansi-view.md#snapshot-initialization-and-lifetime) clears that interpreter-owned value on an accepted hard-reset flag, before fallible setup. A soft-only or selection/viewport-only header retains it; a later subsystem failure does not resurrect a hard-cleared snapshot. This is an explicit portable snapshot boundary, separate from the existing header operations.

Global drawing/hard resets have a separate [image-style reset scope](4.1-jpeg-images.md#defaults-and-reset-scope): drawing reset changes port zero and the old current port even if protected, while other protected survivors retain image state. A header without a global reset performs no global image-style sweep; type-2 bits 1/8 can still initialize PORT 0 as [specified below](#port-zero-initialization). These global effects are distinct from those local drawing-port operations. _Evidence: [original outer reset/header tests](../research/issue-21-image-style.md#original-outer-resetheader-checkpoint)._

### Drawing-port flags

| Value | Effect |
| --- | --- |
| 1 | Delete unprotected nonzero ports, select port 0 and initialize its viewport/cursor/image/pair fields as below |
| 2 | Select the supplied port slot |
| 4 | Attempt to delete the current physical target port if defined and unprotected, and clear the physical selection; a protected target is retained |
| 8 | Delete other unprotected ports while preserving the current port through temporary protection; initialize PORT 0 fields as below if a nonzero logical port remains current |
| 16 | Delete the port base backup |
| 32 | Delete one unprotected numbered port save area |
| 64 | Clear the port backup stack |
| 128 / 256 | Deactivate all / current viewports |
| 512 / 1024 | Activate all / current viewports |
| 2048 / 4096 | Maximize all / current defined, active, unprotected viewport rectangles to the full RIP screen canvas |
| 8192 / 16384 | Clear all / current defined, active ports to RGB black over their full bounds; protection does not block the fill |
| 32768 | Clear the global and unprotected per-port viewport queries |

Viewport maximization requires an unprotected port. Black fill also accepts protected ports. Their all/current forms resolve **existing definitions and the logical current port at that stage**, not the supplied slot field unless a separate selection bit is requested. The physical render target and selected logical port can differ; bit 4 remains the distinct physical-target deletion path. The deletion helper refuses deliberate deletion of port 0, including that path, but bit 4 still clears physical selection after the failed deletion. #### Port Zero Initialization

_Evidence: [fingerprinted initializer/caller reads and field derivation](../research/issue-156-header-port-zero-reset.md), completing the earlier #5 stage order and #105 initializer identification. Pair absence is an explicit completion of the adopted portable pair lifetime._

Type-2 **bit 1** deletes unprotected nonzero definitions, selects logical PORT 0, and then initializes the existing PORT 0. **Bit 8** deletes other unprotected nonzero definitions while preserving the current definition and its original protection, then initializes **PORT 0 only if the logical current index is nonzero at that stage**. Bit 8 does not select 0 or initialize the current nonzero port. Its condition is logical selection, not the cached physical rendering target. The segment's supplied slot is not a selector without bit 2.

Whenever either stage actually invokes this initializer, it has **the same PORT-0 field effects**, even if PORT 0's viewport was inactive:

| PORT-0 state | Result of either invoked initializer |
| --- | --- |
| Definition/type/full DEVICE bounds/backing screen | Retain the existing always-defined, unprotected full-screen port; no replacement allocation or surface resize |
| Stored viewport rectangle V | Set to PORT 0's full stored bounds B, with no WORLD conversion or extra far-edge unit |
| Viewport active/inactive flag | **Retain** the prior flag; restoring full geometry does not activate an inactive viewport |
| Per-port graphics text cursor | Home to `(0,0)`; this is the graphics cursor, not any TW live/saved ANSI cursor |
| Stored image rectangle and flags | Set the all-minus-one **viewport fallback** marker and flags **0**; it follows V when subsequently used, not a copied viewport rectangle |
| Fixed PORT-0 query and floating viewport query | **Retain** their expressions/ownership; ordinary activation/selection gates still govern later queries |
| Remembered copy pair P0 | **Clear to absent**, even when geometry was already full; the initializer publishes no transfer pair |
| Screen pixels, including content drawn through other screen ports/TWs | **Retain**; no clear, fill, blit or repaint is requested by initialization |

This is an intermediate field initializer, not a full SOFT/drawing reset and not HEADER's later active-gated bounds-only or black-fill leaf. It does not apply SOFT's old-current image-style exception, default unrelated tables, reset TW/ANSI state, clear the outline metric snapshot or the [ESC 7/ESC 8 snapshot](1.4-terminal-ansi-view.md#snapshot-initialization-and-lifetime), or delete a backup. In a surviving nonzero current/protected port, cursor/image/query/pair/viewport state is retained. Definitions actually deleted by bit 1/8 lose their owned state normally; their previously drawn screen pixels remain. Backups, other table selections/configuration, global WORLD and floating queries retain their state unless another requested header operation changes them.

The stage order still matters: bit 1 runs before bit 2 selection, which runs before bit 8. With bits 1 and 8 and no intervening nonzero selection, bit 1 initializes 0 and bit 8 subsequently skips initialization because logical current is now 0. A bit-2 selection of a nonzero port before bit 8 can make its condition true. Later activation/bounds/fill/query bits act on the resulting state under their own contracts; they are not implicit initializer effects. Skipping bit 8's initializer leaves every PORT-0 field intact, including its narrow V, image state, cursor and remembered pair.

**Independent literal vectors:** start each row separately on a populated 64×48 screen with PORT 0 full B=`[0,64) × [0,48)`, narrow V=`[10,20) × [20,30)`, viewport **inactive**, graphics cursor `(7,9)`, explicit image rectangle `(2,3;12,13)`/flags 15, fixed query `Q0` and remembered pair `P0=A`. Floating viewport query is `QF`. Port 5 is a defined unprotected current screen port with its own distinct state; another port 6 is protected. No global resets/other segments are present, input is initially unlocked, and append CRLF. `0001` and `0008` are the four-character UltraNum flag fields; the final slot field 0 does not perform selection.

Bit-1 literal: `!|h01000001200010`

Bit-8 literal: `!|h01000001200080`

| Independent start / literal | PORT 0 after processing | Selection/other definitions and pixels |
| --- | --- | --- |
| Current 5; bit-1 literal | V=B; **still inactive**; graphics cursor `(0,0)`; image fallback/flags 0; `Q0` and `QF` retained; P0 absent | Current becomes 0. Unprotected 5 is deleted with its owned state; protected 6 retains its fields. Every screen pixel remains unchanged |
| Current 5; bit-8 literal | Exactly the same PORT-0 result as the preceding row | Current stays 5; it survives temporary protection with its original unprotected state and other fields intact. Protected 6 survives; other unprotected nonzero definitions are deleted. Screen pixels remain unchanged |
| Start instead with current 0; bit-8 literal | Initializer skipped: narrow inactive V, `(7,9)`, explicit image/flags 15, `Q0`, `QF` and P0=A all retained | Current stays 0; unprotected 5 is deleted, protected 6 survives. Screen pixels remain unchanged |

Starting with active PORT 0 instead produces the same field results while retaining **active**. On an invoked stage, a later ordinary permitted transfer may publish a new pair; the old A cannot be recovered by PCB alone. A separately requested black fill can paint after initialization, and a separate saved PORT restore can reinstate saved pair state. None is an implicit action of bits 1/8.

#### Port Bounds Reset and Black Fill

The original helpers establish the viewport rectangle for flags 2048/4096 and the visible fill under 8192/16384. [Viewport rectangle derivation](../research/issue-301-viewport-maximize-rectangle.md) · [Black-fill derivation](../research/issue-153-header-port-clipping.md).

Let **B** be the target port's full stored rectangle, in its backing surface's DEVICE coordinates, **V** its stored viewport, and **S** its physical storage extent. For a screen port, B addresses the shared screen canvas at its stored position; for a bitmap port, B addresses its own bitmap (normally `[0,width) × [0,height)`). Let **C** be the full RIP screen canvas, `[0,0,screen_width,screen_height)`. All rectangles use half-open DEVICE coordinates.

| Operation | Eligibility | Definition/pixel result |
| --- | --- | --- |
| 2048 all / 4096 current: maximize viewport | Defined, viewport active, **unprotected** | Set V to C for either port kind. Retain all other fields and pixels |
| 8192 all / 16384 current: black fill | Defined, viewport active; **protected targets allowed** | Clear **B intersect S** to RGB `(0,0,0)`, with the temporary fill scope below. V and every port-definition field remain unchanged |
| Undefined target, or inactive viewport for either operation | Ineligible | No target creation, geometry change, activation, selection or pixel fill |

Test the active gate when the operation runs. A prior current-activate bit 1024 can make a later current geometry flag 4096 eligible. The maximize operation uses the same rectangle as MVP, and ordinary drawing and query rules apply to the new V. Live RESET(VIEW) has its own rectangle and activation rules. [MVP](5.1-text-variables.md#mvp) · [Live RESET(VIEW)](5.1-text-variables.md#reset).

**Fill rectangle and color:** use the full B, even when V is much narrower or differently positioned. The viewport's active flag is the **eligibility gate**; V is not the geometric clip for this particular clear. Limit writes to B and the target's actual backing extent; never write outside available storage. The full fill is opaque RGB black, independent of current PAL index 0, STYLE drawing/background colors, W/fill pattern, ANSI background, image-style flags and graphics color-mode precision. It is not an XOR/pattern fill, a stored `PAL[0]` token or permission to rewrite a protected palette to manufacture black. Use the same [fixed black color model as the outer clear](1.3-world-view-virtual-canvas.md#physical-screen-clear-and-palette-ordering); index-0 palette changes do not reinterpret these clear pixels as index 0. Bitmap storage must supply the same logical black result when subsequently copied under normal COPY/color rules.

This is distinct from the [type-3 TW erase](#text-window-geometry-erase-and-caret-profile), which uses the adopted contract for index 0 of the current graphics palette and homes TW cursors. A type-2 port black fill homes **no graphics/text cursor** and changes no stored cursor request.

- **Screen target:** clear only its full B intersect the physical screen. Screen ports share pixels, so overlapping graphics/TWs can be overwritten even when their definitions are protected; their records are unchanged.
- **Bitmap target:** clear only its own B intersect its bitmap storage. It does not clear/select screen port 0 or copy the bitmap to the screen. Later explicit copies/drawing use the updated bitmap normally.
- **All form:** visit existing active ports 0..35; inactive/undefined entries are skipped and protection does not shield content. The screen result is the union of eligible screen rectangles, plus each eligible bitmap's own clear. Active full-screen port 0 can therefore clear the entire screen; inactive 0 is not silently activated.

**Temporary clipping scope — explicit portable completion:** the original screen branch selects a full-port DC region and fills with BLACK_BRUSH; the bitmap branch requests the full rectangle on its own DC without selecting that region in this leaf. Inherited native DC clipping/palette realization is not a portable extra state contract. Apply the black clear over B intersect S uniformly to both kinds; neither a previously narrow bitmap-DC clip nor an OS presentation region defines another protocol mask.

After this operation, there is **no separately observable clipping state** beyond the existing port/viewport records. V was not enlarged: subsequent protocol operations still use their own target's V and physical bounds under their usual rules. An implementation may cache host regions, but must scope/refresh them so that an old shared-DC region cannot change later commands' required clipping. Do not serialize a second clip selector, create a damage/scene buffer, or treat the last screen region in the all-port loop as a persistent protocol setting. This is a deliberate portable completion, not a claim to reproduce all historical inherited-DC coverage.

**Other state:** the fill retains logical current port, definition/bounds/V, activation/protection, resident/floating queries, graphic/text cursor coordinates, stored image-style rectangle/flags, STYLE/ENV/PAL state and independent backups. It is ordinary erasure, so the [remembered copy pair](7.0-drawing-ports.md#remembered-copy-pairs) is retained and no transfer pair is published. Geometry reset changes only V; its existing DEVICE-relative pair offsets survive as for another viewport edit. Stored image style is not reset as by SOFT; ordinary viewport-fallback interpretation follows an applied new V. Other header bits/global prelude/segments still have their separately specified effects, including any explicit selection, activation, deletion or query reset.

**Literal current-fill example:** `!|h01000001204000`

This is revision 1, globals 0, one type-2 segment, flags `0400` = 16384, slot field 0. The fill uses the **logical current** port; that slot field does not select 0. Assume an initially unlocked input state, no other segments/global resets and CRLF after the literal. PAL entry 0 is nonblack `(200,10,180)`; STYLE background/color/W/fill and ANSI background are deliberately different.

| Current target / entry state | Result of the same literal |
| --- | --- |
| Defined active protected screen port 5, B=`[10,18) × [20,24)`, narrow V=`[12,15) × [21,23)` on a 64×48 canvas, populated pixels | All 8×4 cells of B become RGB black, including cells outside V. Pixels outside B remain unchanged. Keep current 5, narrow V, protection, all cursor/image/query/pair state and nonblack PAL entry 0 |
| Defined active bitmap port 9, B=`[0,8) × [0,4)`, narrow V=`[2,5) × [1,3)`, populated bitmap; protected or unprotected | All 8×4 cells of its own bitmap B become black, including cells outside V. Screen pixels remain unchanged; current stays 9 and V/protection/metadata remain. Later permitted viewport expansion and COPY can reveal the cleared outer cells |
| Same defined target but viewport inactive | No fill; keep pixels, V and inactivity. Protection is irrelevant to this active gate |
| Undefined target | No creation or fallback to screen; retain current index and every existing definition |

After the screen example, ordinary nonblack COPY drawing at backing point `(11,22)` is still clipped out by unchanged V, while `(13,22)` is eligible under the drawing command's normal rules. The clear did not leave B as a new drawing viewport. For a partially physical rectangle B=`[-2,4) × [1,3)` on a `[0,8) × [0,4)` surface, the fill extent is `[0,4) × [1,3)`; it is not fitted, translated or expanded.

**Literal current-maximize example:** `!|h01000001201000`

Flags `0100` = 4096. On a defined unprotected port with narrow V but **inactive** viewport, it leaves V and inactivity unchanged. On an active unprotected target it sets V=C without painting; on an active protected target it skips the geometry change. The current-fill example still clears that protected active target. `!|h01000001201G00` adds activation bit 1024 to 4096 (total 5120), so an otherwise eligible inactive current port is activated first and then receives C. Flag 2048 (`!|h01000001200W00`) applies the same canvas rectangle to each eligible port, including both targets of the MVP example. Both geometry flags preserve the image style and remembered copy pair. [MVP example](5.1-text-variables.md#mvp).

The color/extent vectors define expected protocol state and pixels for a software surface; they do not measure native Windows palette/DC history or cursor rasterization.

#### Text-window Geometry, Erase and Caret Profile

_Evidence: accepted header dispatch, primary MTW target semantics and [#152's supplied read-only static observations and reconciliation](../research/issue-152-header-tw-geometry.md). This completes the protocol; it does not require a new client/probe or reproduction of the native cross-window cursor write._

The geometry helper used by **1024/2048**, and by the existing slot-zero geometry actions of **1/4**, is a maximization that retains its font and window kind, not live `RESET(TW,0)`'s fresh-record initializer. Geometry applies only to an already **defined, active, unprotected** target. It does not create or activate a missing/inactive window; a protected target is skipped entirely, including the geometry operation's cursor home. Eligibility is tested at the operation's stage, after any earlier selection/activation action; it is not frozen at header entry.

For the target's existing font mode, take its [nominal columns C and rows R](1.4-terminal-ansi-view.md#font-sizes) and its **current device cell metrics cw/ch** under the existing MicroANSI metric rules. Loaded MAF metrics remain controlling when available. Keep the old font mode even when the user default is different; do not run automatic fitting or substitute the selected window's font.

| Target field | Geometry-reset result |
| --- | --- |
| Font and ordinary/extended kind | Retain both |
| Column/row counts | That retained font mode's nominal C/R |
| Origins and stored bounding/display rectangles | Both rectangles become `[0,C*cw) × [0,R*ch)` at device origin (0,0). No WORLD/PORT/viewport origin, clipping or extra far unit |
| Ordinary cell corners | `(0,0)..(C-1,R-1)` for an ordinary window. Extended kind remains extended; legacy ordinary cell-corner queries do not become applicable |
| Vertical scrolling margins | Full target height, first through last nominal row |
| Live cursor | Home **this target** to window-relative (0,0) |
| CSI-saved cursor | Retain its old coordinates |
| Definition/protection/activation | Retain; no implicit activation/unprotection |
| Requested cursor visibility/shape | Retain, including a hidden cursor; geometry reset is not CON |
| ANSI colors/direct colors, rendition/modes, explicit tabs, G0/G1/invocation and other non-geometric TW-local state/bindings | Retain |
| Fixed resident query and floating TW query | Retain; the separate 16384 query action is still available |
| Current TW index, other windows and independent backups/parser/ESC snapshot/other families | No change from this geometry operation |
| Screen raster | No clear, scroll, move or repaint; changed geometry does not paint blank cells or replay history |

**Cursor home applies to the target:** the report identifies native live-coordinate calls using the current sentinel even when modifying noncurrent TW 0. That cross-window write is not adopted. The primary MTW description homes the window being maximized; apply that target-relative rule here. If flag 4 preserves selected TW 5 while maximizing TW 0, home TW 0 and leave TW 5's cursor/state/selection alone. A selected window can still be homed by another explicitly requested operation that actually targets it. No bug investigation or native pixel identity is required to apply this protocol rule.

Unlike this geometry operation, [live RESET(TW,0)](5.1-text-variables.md#live-text-window-reset-contract) always installs fresh ordinary user-default-font state, activates it and replaces CSI/ANSI/query defaults. [MTW](5.1-text-variables.md#mtw) supplies the retained-font/kind and no-paint intent used here. Do not implement all three operations by an unconditional fresh-window reset.

| Erase, 4096/8192 | Defined and active | Protected active targets allowed | Fill the full stored **bounding rectangle**, limited by physical screen bounds, then home that target's live cursor. **HEADER erase color completion:** adopt the existing [wire e / ETW palette-index-0 reconciliation](1.4-terminal-ansi-view.md#text-window-erase-sources) for 4096/8192. Fill with **index 0 of the graphics palette current at this operation**, independently of the current/target ANSI background brush, STYLE background, W/fill pattern and graphics PORT selection/activation/viewport clip. The target is a screen text window even when an offscreen graphics port is selected. This is indexed erase, not a fixed RGB-black clear. The native iterator shares the ANSI-brush paint path recorded for e/ETW; that implementation source is not substituted for the documented portable color rule.

The bounding rectangle includes margins outside a centered extended display region. Use the rectangle present when erase runs, not a stale pre-reset box; physical screen limits still bound the fill. Other stored fields and independent snapshots are not erased with its pixels. The cursor overlay may be updated according to existing requests; exact cursor/font raster is outside this field/color contract.

### Character-set descriptor defect

Type 9 advertises only `type:1 charset:2`. Its consumer stores 0 (USASCII) or 1 (KANJI) in the [shared SDCS metadata](5.1-text-variables.md#sdcs). However, validation and application advance **three decoded arguments**, while the byte parser supplies only two. A standalone type-9 segment therefore fails validation. A following segment can instead be read at the wrong offset: constructed `!|h01000002900200060` parses as type 9 followed by a port segment, but validates/applies as charset 0 followed by a mouse segment with flags 0; it performs no port switch. Other malformed combinations can read outside the intended argument structure. There is no independently usable, consistently framed character-set segment in this driver; do not invent a third reserved wire field. This discrepancy is preserved as a shipped defect, not an alternative grammar for well-formed scenes.

### Checked examples

Constructed example, checked through the original parser and header/environment consumers:

```text
!|h01000201502O2220
```

It is revision 1, global flags 2 (drawing reset), one environment segment: type 5, flags `02O2` = 9730 = 2+512+1024+8192, slot 2, coordinate width 2, unused RGB field 0. It selects environment 2, sets base 36/two-character coordinates and world frame 1280×960. Slot 2 satisfies the shipped coordinate-validation defect. Terminate the physical line with CRLF or chain the next command with a pipe.

Another checked example demonstrates mixed segment widths:

```text
!|h01000003001070150002028
```

Revision 1, global flags 0, three segments: button flags 1/slot 0; audio flag 1; environment flags 2/slot 0, with coordinate 2 and RGB 8 consumed but not applied. It deletes unprotected nonzero button styles and selects style 0, stops waveform playback, and selects environment 0. Both examples are constructed primary-parser oracles; no shipping demo header is claimed.

## RIP_NO_MORE

_Evidence: 2.00a4; corpus (287 uses in 95 files); SyncTERM (ripper.c:13315)._

_End of RIPscrip Scene_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `#`      |
| **Arguments** | \<none\> |

**Format:** `!|#` **Example:** `!|#`

**Attributes used:** none

This command indicates that RIPscrip commands are complete. This allows the terminal program to activate Mouse Regions, or respond to queued up Mouse Clicks without disturbing the natural flow of the script transmission.

For noise-immunity, the Host should transmit three or more RIP_NO_MORE command consecutively to make sure the message gets to the terminal. The terminal should also time-out if no data is received for a while, and assume RIP_NO_MORE.

The actual duration of the "time-out" is entirely up to the implementor of their terminal program. A good recommended setting would be at least an entire second or more after the receipt of the last RIPscrip command. Raw ASCII/ANSI text does not contribute to the time-out in any way. Only an actual RIPscrip command could cause the time-out counter to be reset (thus starting the time-out countdown all over again). Timing-out is not a pre-requisite to supporting RIPscrip. It is a highly desirable feature to do this, but it is not required. _(v1.54)_

This command also releases both [scene input gates](#scene-input-gates) previously set with RIP_HEADER. This is useful to prevent the user from clicking on buttons before the scene is completely drawn. See the RIP_HEADER command for more details on this mode of operation. _(v2.A1)_

Nearly every RIPtel demo scene ends with one (287 uses in 95 of 116 files). _Evidence: corpus._

## RIP_COMMENT

_Added in RIPscrip v2.A2._

_Evidence: 2.00a4; corpus (1,683 comment commands across the RIPtel demos, 305 with prose)._

_Put in a comment as part of a RIPscrip sequence_

|               |             |
| ------------- | ----------- |
| **Level**     | 0           |
| **Command**   | `!`         |
| **Arguments** | `string...` |

**Format:** `!|!This is a comment` **Example:** `!|!Show RIP_SKEWED_OVAL`

**Attributes used:** Base Math (N/A)

A comment may be embedded inside a RIPscrip file. A comment is one line or longer in length. A comment is a special case of a RIPscrip command letter. In this case, it is the command letter "!". If a "!" is encountered right after a "!|", a "SOH |" or an "STX |" sequence, then the remainder of the command line is a comment. Comments may be line-continued with backslashes just like regular RIPscrip commands can. Some examples of comments might be:

```text
!|!This is a comment

!|c0F|!Set the color to white|c00|!Set the color to black

!|c0F|!this is a very long, continued\
comment line.  Line-continued comments\
adhere to standard RIPscrip line continuation rules
```

Note that the second example shows a comment starting after a legitimate RIPscrip command (set color). This is valid.

The RIP_COMMENT is treated exactly like any other RIPscrip command for the purposes of parsing RIPscrip commands, EXCEPT that the string is explicitly ignored for [text variables](5.1-text-variables.md). Any use of `|` will be interpreted as the beginning of the next command, and `\` will interpreted as a line continuation. No other characters need be escaped out.

In the RIPtel corpus, comments are the single most valuable evidence stream: `!|command|! comment` chains are ubiquitous, and TeleGrafix's authors used comments to name six otherwise-undocumented drawing primitives outright (NEWCMDS.RIP) and to leave positional field-layout cribs above complex commands. _Evidence: corpus._

## RIP_GROUP_BEGIN

_Added in RIPscrip v2.A2._

_Evidence: 2.00a4 - not in the RIPSCRIP.HLP inventory, not observed in the RIPtel demo corpus, not in SyncTERM._

_Start a grouping of RIPscrip commands_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `(`      |
| **Arguments** | \<none\> |

**Format:** `!|(` **Example:** `!|(`

**Attributes used:** none

This command has one special usage, that is to group blocks of commands together into logical groupings. This has no functional use to a terminal program, but to a paint program, it can be used to perform block moves of commands from one area in a scene to another. In order to accomodate this, a standardized method of doing group definitions is being created.

To specify a command grouping, specify the commands like this:

```text
!|(

  ...
  ... RIPscrip commands
  ...

!|)
```

When putting RIPscrip data files online on a host, you would typically want to remove groupings for efficiency, although this is not required. A terminal program should just ignore RIP_GROUP_BEGIN and [RIP_GROUP_END](#rip_group_end) commands, at it has no conceivable use for the information at this time.

Also note that a group may consist of several groups and commands. In other words, groups may be nested inside of each other for the purpose of bundling them together.

**NOTE:** Any currently active group definitions are "closed" when a [RIP_NO_MORE](#rip_no_more) command is encountered in a paint program or some kind of conversion utility that uses groups. _(v2.A3)_

The 2.00a4 spec's suggestion to strip groupings from files placed online is consistent with their total absence from the shipping demo corpus. _Evidence: corpus._

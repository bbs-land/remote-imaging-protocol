[Drawing ports](../../glossary.md) - the fundamental drawing abstraction the 3.0 engine inherits from 2.0 and, by corpus evidence, the workhorse of shipped 3.x content: screen regions and offscreen (clipboard) surfaces, each with its own coordinate origin and [viewport](../../glossary.md).

## Drawing Ports - What Are They?

_Added in RIPscrip v2.A4._

_Evidence: 2.00a4; HLP._

A drawing port is an area where graphics can be drawn. This is much like having a tablet of paper, where each page can be drawn to individually. However, just like a tablet of paper, only the piece of paper that is on the top of the tablet can be drawn to (the current piece of paper). The same concept applies to drawing ports. At any one moment in time, there is a "current drawing port". This current port is the one that will display graphical drawing operations when they are received.

There are two types of drawing ports:

1. A screen (visual) drawing port, and
2. An offscreen bitmap drawing port (also known as a "Clipboard Port").

The 3.0 driver additionally distinguishes **snapshot ports** - offscreen ports created by capturing screen contents - in its error strings ("No mouse/button fields on offscreen drawing ports"). _Evidence: HLP._

### Screen Drawing Ports

_Evidence: 2.00a4._

A screen drawing port is the most commonly used form of drawing ports. A screen drawing port is a port that is somewhere on top of the screen. What this means is when a graphical drawing operation occurs, it is displayed in that port and subsequently to the screen immediately. Screen drawing ports are methods of dividing up the user's screen into separate regions, of which each can be thought of as completely separate drawing areas. You can switch between them pretty much at will to draw your graphics.

Here is a typical example of one screen and how it can be divided up with multiple drawing ports:

```text
                                 ┌─── Screen boundary
                                 │
                                 ▼
     ╔══════════════════════════════════════════════════╗
     ║ Port 0                                           ║
     ║                                                  ║
     ║  ┌────────────────────┐  ┌────────────────────┐  ║
     ║  │ Port 1             │  │ Port 2             │  ║
     ║  │                    │  │                    │  ║
     ║  └────────────────────┘  └────────────────────┘  ║
     ║  ┌────────────────────────────────────────────┐  ║
     ║  │ Port 3                                     │  ║
     ║  │                                            │  ║
     ║  └────────────────────────────────────────────┘  ║
     ║  ┌────────────────────────────────────────────┐  ║
     ║  │ Port 4                                     │  ║
     ║  │                                            │  ║
     ║  └────────────────────────────────────────────┘  ║
     ╚══════════════════════════════════════════════════╝
```

As you can see, you have quite a bit of flexibility in placing your ports around on the screen. In this example, we have five ports defined on the screen. You might notice that port number 0 doesn't seem to have a rectangle associated with it. Actually, it does - it is the screen's boundary. Port number 0 is defined as the actual screen and cannot be redefined (you can alter its viewport though - see below for more details about viewports). Port 0 is always the full size of the screen. You can create your own screen ports, but port 0 is one that you cannot redefine the boundary of. This gives you the ability to always switch to port 0 to address the entire screen, but have the luxury of other ports when you only want to work with a portion of the screen.

### Offscreen Drawing Ports (Clipboard Ports)

_Evidence: 2.00a4; HLP._

An offscreen bitmap port, otherwise known as a "clipboard port", is very much like a screen port, but it isn't actually a part of the screen. It is more like another screen that you cannot see, but one that you can still draw to. You might be asking yourself why something like this is part of RIPscrip? The answer is quite simple - they are extremely powerful! An offscreen port can be used for placing a piece of graphics data temporarily while you are showing a dialog box on the screen, only to restore the original graphics when the user clicks the "OK" button on the dialog box. The graphical data that was overwritten by the dialog box isn't deleted - it's been saved temporarily on a screen that you cannot see, but is restored to the screen when necessary. Another use of this might be if you had a very complicated scene to display, but you didn't want the user to see each little graphics operation until the entire scene was complete; switch to an offscreen bitmap port, draw your scene, then switch back to the screen and copy the offscreen port's graphics to your screen. Voila, the user sees the scene appear on his screen complete - not piecemeal!

There are numerous reasons why you would use offscreen ports; things like storing a bitmap that you just loaded from the hard disk onto an offscreen port so that when you paste it to the screen a large number of times, there isn't a large amount of disk activity on the user's machine. Another good example is in the situation of an online game where the screen is some kind of map, and one or more offscreen ports are used to hold small "icons", or bitmaps of game pieces. Simply copy the images from the offscreen port(s) to appropriate locations on the map and you've accomplished a rather complicated situation without adversely affecting the user's system with intense hard drive activity due to constantly loading bitmaps off the disk - the side effect, the game moves much more swiftly and with a lot less "jerkiness" due to the hard disk accesses.

Just like with screen drawing ports, you can select an offscreen bitmap port as the one which will receive graphical drawing operations. Selecting an offscreen port as the current port lets you draw simple graphics objects, photos and other such things to it. But remember, the graphics you draw to an offscreen port are of little value unless at some point you actually copy it to the screen so that the user can see it.

Some things cannot be done to offscreen ports. For example, you cannot place a mouse field or a clickable button on an offscreen port. The reason for this is that the mouse only has any meaning to the screen - the environment that the user interacts with. How can the user click on a button that he can't see? He can't. You also cannot place [text windows](1.4-terminal-ansi-view.md) or assign resident query expressions to offscreen ports. The 3.0.7 driver enforces the rule with its own error string ("No mouse/button fields on offscreen drawing ports"). _Evidence: 2.00a4; HLP._

An offscreen port is most easily thought of as a graphics screen that you can't see. You can work with it to your heart's content, but the user can't see the contents of it until you copy the data to the screen. As long as you keep this one fundamental concept in mind, there should be no confusion about ports.

### The Port Table

_Evidence: 2.00a4; HLP._

Ports live in a 36-slot [data table](7.1-data-tables.md#drawing-port-table), entries numbered **0-35**:

- **Port 0 is always the screen.** It is the full size of the display, exists at all times, and cannot be created, deleted, or redefined - confirmed verbatim by the 3.0.7 driver's error strings "Can't delete graphics port #0" and "Can't create drawing port #0". You can always switch to port 0 to address the entire screen (its viewport may still be altered).
- **Ports 1-35** are user-definable - the driver rejects out-of-range numbers with "The given port number is invalid (1-35 only)". Each may be a screen sub-region or an offscreen bitmap.

Each port remembers its own drawing state, including:

- the current X/Y location (used by the [RIP_TEXT](3.0-text-output-and-fonts.md)-family commands),
- the current image style settings ([RIP_IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style)),
- its viewport location and dimensions,
- any fixed viewport "resident query" expression ([5.5](5.5-file-transfer-and-queries.md)),
- an optional [remembered source/destination copy pair](#remembered-copy-pairs), separate from the text cursor and image-style rectangle, for the specified port-transfer producers and `$PCB$`.

Image style includes a per-port rectangle and flags. Default rectangle means viewport fallback, flags 0. A drawing reset changes **port zero and the port current before reset**, even if that old current port is protected; other protected surviving ports retain their image style. A hard reset removes nonzero ports. See the [image reset table](4.1-jpeg-images.md#defaults-and-reset-scope) and [original lifecycle tests](../research/issue-21-image-style.md#original-outer-resetheader-checkpoint).

The entire drawing port data table additionally keeps track of the "current viewport" query expression (otherwise known as a floating viewport query). _(v2.A4)_

The whole port table can be saved and restored through [data backup areas](7.2-data-backup-areas.md).

HEADER's [full-port black fill and gated viewport reset](1.1-protocol-and-command-hierarchy.md#port-bounds-reset-and-black-fill) distinguish content from definition protection: the fill allows active protected ports, clears the full physical port bounds and leaves the stored viewport/pair/image/query state intact. Its temporary clipping is not another port-state field. The geometry reset requires defined, active, unprotected targets and retains existing pair offsets as a viewport edit.

### Ports and Coordinates

_Evidence: 2.00a4._

A port is a specific drawing area. No matter whether the port is a screen port or an offscreen bitmap port, it is still a drawing area, and as such, it has a legal number of horizontal and vertical pixels that can be drawn to. Every graphical drawing operation uses graphical coordinates with which they draw their image to the current port. For example, a circle needs to know the center point, and the radius of the circle in order to draw itself.

Each port has what can be thought of as its own set of coordinates. Just like the screen where (0,0) is the upper-left corner of the screen, when a port is active (ie, current), (0,0) is the coordinate of the upper-left corner of the drawing port. If a port had a width of W and a height of H, then the lower-right coordinate would be (W-1,H-1). This holds true for all drawing ports, even offscreen bitmap ports. These are **pixel positions**. The shipped [RIP_DEFINE_PORT](#rip_define_port) and [RIP_PORT_COPY](#rip_port_copy) handlers instead use lower-right **extent boundaries** for their rectangles: width is right minus left, without adding one. A 640-pixel surface has last pixel X=639 and right boundary X=640. Do not turn a last-pixel illustration into a wire rectangle by treating both conventions as identical. _Evidence: [original driver extent/copy derivation](../research/issue-10-port-geometry.md)._

For example, if you draw a circle at (50,50) with a radius of (25,25) to the current port (a screen port), then you might have something like the following diagram:

```text
                               ┌──── Screen Boundary
 (0,0)                         ▼
   ╔══════════════════════════════════════════════════╗
   ║                                                  ║
   ║    ┌───────────────────────────────────────┐     ║
   ║    │(10,10)            │◄─25─►│            │◄───────Port
   ║    │                 ▄▄▄▄▄                 │     ║
   ║    │              ▄▀▀     ▀▀▄              │     ║
   ║    │             █           █             │     ║
   ║    │            █      ■ ◄─── █ ──────────────────── (60,60) on
   ║    │             █  (50,50)  █             │     ║   the screen
   ║    │              ▀▄▄     ▄▄▀              │     ║
   ║    │                 ▀▀▀▀▀                 │     ║
   ║    │                              (124,124)│     ║
   ║    └───────────────────────────────────────┘     ║
   ║                                                  ║
   ╚══════════════════════════════════════════════════╝
```

In this example, the port starts at (10,10) on the screen and goes down to (124,124) on the screen (a width of 115 and a height of 115). Since you said to draw the circle centered at (50,50) in the current port, what actually happens on the screen is that the circle is physically drawn at (50+10,50+10) to the screen, or centered at the "absolute" coordinate of (60,60) in relation to the actual screen.

As you can see, each port can be thought of as its own little drawing universe, with its own set of coordinates. This makes drawing things like graphs, or showing game map windows easy - without having to make extensive calculations in the host software to figure out where things need to be placed. This is considered "port relative" coordinates.

Screen ports are defined as some location on the actual screen from the upper-left corner to the lower-right corner (in the current [world coordinate](../../glossary.md) system). From this information, the width and height of the port can be easily calculated, and the physical pixel dimensions are derived and remembered.

Offscreen ports are a bit different though. Since they're not part of the user's actual screen, they don't have this upper-left location on the screen. In this manner, an offscreen port is always thought of as having an upper-left corner of (0,0) and its lower-right corner as (W-1,H-1).

### Ports and Viewports

_Evidence: 2.00a4._

The coordinate illustrations below describe the intended port-relative model. For exact RIPtel 3.1 behavior after an explicit viewport command, the [original producer](1.3-world-view-virtual-canvas.md#rip_viewport) stores directly converted context coordinates without adding the screen-port origin or intersecting with port bounds. [POINT uses that stored origin; PIXEL omits it](2.1-lines.md#rip_point). Newly created ports still begin with their default port-sized viewport. _Evidence: [original driver and native checks](../research/issue-11-pixel-pen-units.md)._

Each drawing port has an associated viewport, or clipping rectangle. A viewport is a rectangle inside the port that defines the drawing limits inside that port. It's similar in concept to a coloring book with invisible lines. You can draw all you want, but you can't go outside the lines. If any operation would extend beyond the edge of this clipping rectangle, it will be truncated. For example, if you have a drawing port that is 100x100 pixels in size, and you define the viewport to be from (25,25) to (74,74), you would have a 50x50 drawing area right in the center of the drawing port. If you then draw a circle in the exact center of the drawing port with a radius of 60 pixels, you would have pieces of the circle that extend beyond the top, left, bottom and right borders of the viewport. What you would see would be four arcs in each corner of the viewport as in the following example:

```text
                           Viewport from (25,25) to (74,74)
                           ───────┬────────────────────────
         (0,0)                    │
            ╔═════════════════════│════╗
            ║          ░░░░░      │    ║
            ║       ░░░     ░░░   ▼    ║
            ║   ┌─██───────────██─┐    ║
            ║   │█               █│    ║
            ║   █                 █    ║
            ║  ░│                 │░   ║
            ║ ░ │                 │ ░  ║
            ║ ░ │                 │ ░  ║
            ║ ░ │                 │ ░  ║
            ║  ░│                 │░   ║
            ║   █                 █    ║
            ║   │█               █│    ║
            ║   └─██──────────-██─┘    ║
            ║       ░░░     ░░░        ║
            ║          ░░░░░           ║
            ╚══════════════════════════╝ (99,99)
```

If you notice in the above diagram, the rectangle inside the port defines the viewport. The solid squares (█) denote pixels inside the viewport that would actually be drawn, and the shaded squares (░) show pixels that will not be drawn because they are outside the viewport.

You can alter the location and size of the viewport inside any given drawing port. By default, the viewport is set to the full size of the drawing port when the port is created. If you attempt to make the viewport go outside the actual port, it will be adjusted to fit so that it is completely within the port. If an attempt is made to define a viewport that is completely outside the boundary of its port, then the definition is ignored as an error condition. If the lower-right corner is outside the boundary of the port, then the lower-right corner of the newly defined viewport is set to the lower-right corner of the port itself.

Just like drawing ports, a viewport also "adjusts" drawing coordinates. When you alter the location of a viewport inside of a drawing port, the origin (0,0) for drawing operations relates to the upper-left corner of the viewport itself, not the actual underlying drawing port. All drawing operations pertain to a port's viewport, not the port itself. The port is considered the maximum limits for the viewport inside - just like the screen, you can only draw to areas inside the screen; the same applies to viewports and ports.

As an example, let's say you have a screen port defined and you alter the viewport (remember, by default it is the full size of the port when the port is defined until you re-define it). The following diagram will give you an idea of our example:

```text
                          ╔════ Screen boundary
                          ▼
╔═════════════════════════════════════════════╗
║(0,0) screen                                 ║
║    ┌───────── (0,0) port                    ║
║    ▼          (25,25) screen                ║
║    ■───────────────────────────────────┐ ◄══════ Port boundary
║    │           │ (0,0) viewport        │    ║
║    │        ┌──┤ (40,40) port          │    ║
║    │        ▼  │ (65,65) screen        │    ║
║    │        ■─────────────────────┐    │    ║
║    │        │                     │    │    ║
║    │        │                     │ ◄═══════════ Viewport boundary
║    │        │          ■          │    │    ║
║    │        │          ▲          │    │    ║  │ (130,130) viewport
║    │        └──────────│──────────■ ◄──────────┤ (170,170) port
║    │                   │               │    ║  │ (195,195) screen
║    │                   │               │    ║
║    └───────────────────│───────────────■ ◄────── (200,200) port
║                        │                    ║    (225,225) screen
╚════════════════════════│════════════════════╝
                         │    │ (50,50) viewport
                         └────┤ (90,90) port
                              │ (115,115) screen
```

This inherited diagram labels inclusive pixel positions: screen pixels (25,25) through (225,225) span 201 pixels in each axis, and port pixels (40,40) through (170,170) span 131. These illustrative last-pixel labels are not the extent boundaries consumed by RIP_DEFINE_PORT; a boundary rectangle from 25 to 225 has extent 200, whereas one from 25 to 226 includes pixel 225. The diagram's point at viewport (50,50) / port (90,90) is at screen **(115,115)**. The upper-left coordinate of the viewport would map to the screen coordinates (25+40,25+40) or (65,65), and the lower-right corner would map to (25+40+130,25+40+130) or (195,195).

As you can see, mapping a screen port's coordinates to those actually used on the screen can get quite involved. But when you get down to the benefits of coordinate systems, this approach provides quite a bit of flexibility in moving things around without having to change coordinate systems all the time.

### Ports, Viewports and Graphical Operations

_Evidence: 2.00a4._

We've already discussed how a viewport "truncates" a graphical operation if it extends beyond the border of the port's viewport.

What if you're copying graphical data from one port to another? Graphics data can only be copied from one port to another in rectangular portions, and just like all other graphical operations, this kind of situation adheres to the viewports of both the source and the destination ports! Let's take an example where you are copying a rectangle of graphics from port 1 to port 2. For sake of clarity, we'll copy the entire viewport over (not a sub-area of the viewport). The following diagram shows what would happen if the two viewports aren't the exact same size (specifically, the source viewport is larger than the destination viewport):

```text
      ┌─── Port 1's viewport             ┌─── Port 2's viewport
      │                                  │
╔═════│═══════════════════════╗     ╔════│══════════════════╗
║     ▼                       ║     ║    ▼                  ║
║   ┌───────────────────┐     ║     ║ ┌─────────────┐       ║
║   │███████████████████│     ║     ║ │█████████████│░░░░░  ║
║   │███████████████████│     ║     ║ │█████████████│░░░░░  ║
║   │███████████████████│     ║     ║ │█████████████│░░░░░  ║
║   │███████████████████│     ║     ║ └─────────────┘░░░░░  ║
║   │███████████████████│     ║     ║  ░░░░░░░░░░░░░░░░░░░  ║
║   └───────────────────┘     ║     ║                       ║
╚═════════════════════════════╝     ╚═══════════════════════╝
            Port 1                            Port 2
```

The squares that are shown as solid (█) are the graphics data that is to be copied (port 1), and the graphics data that is actually copied (port 2). The shaded squares (░) are graphics data from the source viewport that aren't copied to the destination. This shows how a viewport "truncates" graphical drawing operations, even when copying data from one port to another.

### Copying Data From One Port to Another

_Evidence: 2.00a4._

When you copy graphical data from one port to another (or to another location on the same port for that matter), you are duplicating the graphical contents of the source port onto the destination port. Whether the result is an exact replica of the original image or not is another matter. Whenever you copy a rectangle of data from one port to another, you need to specify a rectangle in the source port, and another one in the destination port. These two rectangles do not need to be the same pixel size. If they are different either in the width or height dimensions, then scaling of the source image will occur! For example, if the source image's rectangle doesn't have the same dimensions as the rectangle in the destination port, you could have a situation similar to the following:

```text
╔══════════════════════════════╗   ╔══════════════════════════════╗
║   ┌────────────────────┐     ║   ║  ┌────────────────────────┐  ║
║   │██▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀██│     ║   ║  │██▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀██│  ║
║   │█ ▀▄            ▄▀ █│     ║   ║  │█ ▀▄                ▄▀ █│  ║
║   │█   ▀▄        ▄▀   █│     ║   ║  │█   █▀▀▀▀▀▀▀▀▀▀▀▀▀▀█   █│  ║
║   │█     █▀▀▀▀▀▀█     █│     ║   ║  │█   █▄▄▄▄▄▄▄▄▄▄▄▄▄▄█   █│  ║
║   │█     █      █     █│     ║   ║  │█ ▄▀                ▀▄ █│  ║
║   │█     █      █     █│     ║   ║  │██▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄██│  ║
║   │█     █▄▄▄▄▄▄█     █│     ║   ║  └────────────────────────┘  ║
║   │█   ▄▀        ▀▄   █│     ║   ║                              ║
║   │█ ▄▀            ▀▄ █│     ║   ║                              ║
║   │██▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄██│     ║   ║                              ║
║   └────────────────────┘     ║   ║                              ║
╚══════════════════════════════╝   ╚══════════════════════════════╝
        Source (Port 1)                  Destination (Port 2)
```

Notice that the image in the destination is shorter, but much wider than the original. This is because in this example we specified our destination rectangle to be shorter, but wider in size than the original image in the source port. If the two rectangles had the same width and height values, then our destination image would be pixel-for-pixel identical to the original (providing that the viewport of the destination port didn't truncate the image of course).

When copying rectangular pieces of data from one port to another, you have to be careful about viewports. If either the source or the destination rectangle are completely outside that port's viewport, then the copy operation isn't performed - nothing would be visible if it did happen, because either the source or the destination image wouldn't be visible inside the viewport.

Here is another example showing a straight copy operation without any scaling being performed. We are assuming that the source and destination rectangles are the same size. The port's boundary and its viewport are shown in the following diagram:

```text
     ╔════════════════════╗       ╔═══════════════════════════╗
     ║  ┌────────────┐    ║       ║  ┌───────────────────┐    ║
     ║  │██  ██  ██  │░░░ ║       ║  │██  ██  ██  ░░░░   │    ║
     ║  │  ██  ██  ██│░░░ ║       ║  │  ██  ██  ██░░░░   │    ║
     ║  │██  ██  ██  │░░░ ║       ║  │██  ██  ██  ░░░░   │    ║
     ║  │  ██  ██  ██│░░░ ║       ║  │  ██  ██  ██░░░░   │    ║
     ║  │██  ██  ██  │░░░ ║       ║  │██  ██  ██  ░░░░   │    ║
     ║  │  ██  ██  ██│░░░ ║       ║  │  ██  ██  ██░░░░   │    ║
     ║  └────────────┘░░░ ║       ║  └───────────────────┘    ║
     ║   ░░░░░░░░░░░░░░░░ ║       ║   ░░░░░░░░░░░░░░░░        ║
     ║   ░░░░░░░░░░░░░░░░ ║       ║   ░░░░░░░░░░░░░░░░        ║
     ╚════════════════════╝       ╚═══════════════════════════╝
```

The shaded squares (░) are graphics that extend beyond the source's viewport. Those pixels aren't copied to the destination port, but they are shown in the upper-right diagram to show where the graphics would have been in the destination port if they were copied.

Let's take another example but this time we will show scaling because this situation may not be intuitive. Let's assume that our source rectangle is twice as large as our destination rectangle both in the width and height dimensions. This means that our image will be reduced by 1/2. But what happens if the source image needs to be "truncated" to fit in the viewport? For this initially unequal-size copy, only the data that remains after truncation is scaled into the destination rectangle. If the destination rectangle also had to be truncated, then the scaling is still performed. In this fit branch no vertical or horizontal "blank" zone is created during scaling. When you say "scale to fit", it does exactly what you told it to - it makes the graphics fit in the given area. Here is the diagram that shows this situation:


## Observed Usage in the 3.x Era

_Evidence: corpus (WIPE00.FN-WIPE24.FN); HLP._

The port system is the workhorse of TeleGrafix's own 3.x demo material. The RIPtel demo corpus contains **9,104 uses of `2C` (RIP_PORT_COPY)** - by far the most frequent command after RIP_LINE - almost all of them in the WIPE00-WIPE24 "wipe" transition library: each wipe composes the next scene in an offscreen port, then reveals it with a sequence of narrow port-to-screen copies to animate slides, splits, and dissolves. The supporting pattern (define port 1 full-screen, copy the screen into it, switch, draw, copy back) appears throughout the `.FN` function scenes, with TeleGrafix's own comments narrating it: "Create a port for the status line backup area, and copy the area where the status line will go into that drawing port."

The corpus uses only four level-2 port commands - `2P` (define), `2p` (delete), `2s` (switch), `2C` (copy) - confirming these as the practical core of the port system on the wire. (SyncTERM's `RIPSCRIP030001` mode implements **no level-2 commands at all** - the single largest gap between the open-source reconstruction and shipped 3.x content.)

## RIP_DEFINE_PORT

_Define a drawing port_

_Added in RIPscrip v2.A3._

_Evidence: 2.00a4; HLP (`RIP_PortDefine`; "Can't create drawing port #0", ports 1-35 only); corpus (14 uses in 12 files) - not in SyncTERM._

|               |                                                    |
| ------------- | -------------------------------------------------- |
| **Level**     | 2                                                  |
| **Command**   | `P`                                                |
| **Arguments** | `port-num:1 x0:XY y0:XY x1:XY y1:XY flags:4 res:4` |

**Format:** `!|2P <port-num> <x0> <y0> <x1> <y1> <flags> <res>`

**Example:** `!|2P10000ZKQO00030000`

**Attributes used:** viewport, port, [Base Math](../../glossary.md) (current setting)

This command physically defines a new graphical drawing port. The port can be either onscreen (a video port) or an offscreen bitmap port (a Clipboard Port). When defined, the newly created port becomes the current graphical drawing port (if the `<flags>` say to - see below).

An existing unprotected target may be redefined with the new parameters. A protected target rejects redefinition: its definition and contents remain intact, and the current drawing port becomes **port 0**, regardless of flag 2. Thus, with current port 2 and protected target 1, this protocol operation leaves target 1 protected and selects port 0. This is the documented protocol rule. _Evidence: ALPHA 4 §3.4.3.1 and the [protocol derivation](../research/issue-72-define-port-contract.md#protected-redefinition-and-resource-failures)._

The `<port-num>` parameter determines which entry in the master Port Table you wish to define. When working with ports, you need to be concerned about the port number you're working with - that's the location of the port, and that's how you access it when you need to switch ports - by port number. You are allowed up to 36 separate graphical ports (0-35 in decimal). Port #0 cannot be re-defined because it is always defined as the Screen Port. You can however, alter the viewport for Port #0 to make a sub-area on the screen to draw in (and clip). The viewport for Port #0 may also be deactivated as can the viewport on any other graphical Port. _(v2.A4)_

Port geometry uses **extent boundaries** in the current world coordinate system, without an extra inclusive pixel. For a screen port, convert both corners to device coordinates, then use `width = device_x1 - device_x0` and `height = device_y1 - device_y0`. For an offscreen port, the effective near corner is **(0,0)**: send x0=y0=0, and interpret x1/y1 as the far extent boundaries from that origin. The protocol's flag-1 rule treats supplied nonzero x0/y0 as zero; they do not reduce the requested offscreen dimensions. With equal world/device dimensions, an offscreen request (2,1)–(6,4) therefore means a **6×4** port at (0,0); its canonical form is (0,0)–(6,4). A sender needing a 4×3 port sends (0,0)–(4,3). _Evidence: ALPHA 4 §3.4.3.1, coordinate paragraph and flag-1 definition; [origin/extent derivation](../research/issue-72-define-port-contract.md#offscreen-origin-and-extents)._

A W×H port has last pixel (W-1,H-1) and far boundaries W,H. Supply ordered coordinates that convert to positive dimensions within the implementation's supported range. Zero-sized or reversed extents do not specify a special allocation mode, and no integer-width wrapping rule is defined by the protocol. The general extent-boundary distinction is documented in the [geometry derivation](../research/issue-10-port-geometry.md#native-allocation-and-copy-checkpoint); it does not override this command's explicit offscreen-origin rule.

On successful definition, initialize the viewport to cover the whole port, then apply the requested initial state. Flag 4 makes that viewport inactive; flag 8 protects the new definition; flag 2 selects the new port. These are independent postconditions, so setting protection does not prevent the same command from establishing its requested viewport state. For example, decimal flags 15 create an offscreen port that is current, has an inactive viewport and is protected. You may later change an unprotected port's viewport with [RIP_VIEWPORT](1.3-world-view-virtual-canvas.md#rip_viewport).

The `<flags>` parameter for this command allows you to make some important distinctions to the port. The possible port flags are OR'd together to create one final number where each bit represents some flag value. The possible flag values and what they mean are described as follows:

| Value | Description |
| --- | --- |
| 1 | Use an offscreen bitmap at origin (0,0), with x0/y0 treated as zero as described above. Without this bit, define a screen port. Offscreen drawing becomes visible through an explicit port-copy operation. |
| 2 | Port is made the active drawing port immediately upon completion of this command. This has the net effect of creating the port and immediately switching to it. Without this flag, you would have to use a [RIP_SWITCH_PORT](#rip_switch_port) command to draw directly into this port. |
| 4 | Deactivate this port's viewport immediately upon creation. This has the net effect of creating the port and setting the viewport to a deactivated status. _(v2.A4)_ |
| 8 | The newly defined port is immediately protected. This means that the port cannot be deleted without explicitly unprotecting the port. |

Only bits **1, 2, 4 and 8** are defined here; any combination of these four bits is permitted. Higher bits are reserved and senders must leave them zero. The protocol documentation does not specify whether a receiver rejects or ignores nonzero reserved bits. The four-character wire field does not by itself define additional flags. _Evidence: ALPHA 4 §3.4.3.1 flag table; [scope of the documented flags](../research/issue-72-define-port-contract.md#documented-flags)._

> **NOTE:** The `<res>` parameter is reserved for future use and should be set to "0000" for future compatibility with later RIPscrip revisions.

The example above is the corpus's standard form (TELPORT.FN, FONTS.RIP, DRAGON.RIP): it requests the full **world extent** 1280×960 (`ZKQO`) with flags `0003` (offscreen + switch). At world 1280×960 and device 640×480, its translated corners are (0,0) and (640,480), and the original allocator creates a **640×480 physical bitmap**. Its last pixel is (639,479). There is no 641×481 extra edge and it is not a physical 1280×960 bitmap. Offscreen allocations are not clamped to the display: endpoints 2560,1920 under the same conversion create a 1280×960 bitmap, subject to the ordinary pixel budget. _Evidence: corpus for the wire example; [original allocation instructions and native observations](../research/issue-10-port-geometry.md#native-allocation-and-copy-checkpoint) for physical dimensions._

### Resource-failure guarantees

The documented protected-target rejection above is distinct from a failure to allocate a new port. The source describes unprotected replacement as deletion followed by creation, but supplies **no atomic-replacement or rollback guarantee**. An allocation failure therefore does not guarantee that the old target definition or its pixels survive. The resulting target definition, current selection and clipboard assignment after a resource failure are implementation-defined; applications cannot assume a particular recovery state.

Flag 1 chooses offscreen storage; it does not itself capture an image or assign the [clipboard pointer](4.0-icons-and-bitmaps.md#rip_get_image). An application recovering from a failed replacement should explicitly select port 0, establish the required port definitions, and re-establish a clipboard capture if needed. It must not rely on an undocumented allocation-failure state. _Evidence: scope of ALPHA 4 §3.4.3.1 and the [failure-contract derivation](../research/issue-72-define-port-contract.md#protected-redefinition-and-resource-failures)._

### PORTW/PORTH for the full-world example

The allocated port stores width 640 and height 480 in device pixels; inverse world conversion gives extents 1280 and 960. However, the shipped driver has an **inverted argument-parser success test** in both size-variable callbacks. For valid queries, including the default forms, each callback returns NULL and sets the variable-error flag instead of returning a numeric string. The ordinary macro expander retains the original expression. Thus the exact shipped outputs are:

| Expression | Stored dimension/domain value | Ordinary macro-expansion result |
| --- | --- | --- |
| `$PORTW$` or `$PORTW(CUR,PORT,WORLD)$` | 1280 world units | Expression unchanged; variable error set |
| `$PORTH$` or `$PORTH(CUR,PORT,WORLD)$` | 960 world units | Expression unchanged; variable error set |
| `$PORTW(CUR,PORT,DEVICE)$` | 640 pixels | Expression unchanged; variable error set |
| `$PORTH(CUR,PORT,DEVICE)$` | 480 pixels | Expression unchanged; variable error set |

The dimension column describes the allocated geometry and the intended conversion, **not** decimal output from the defective callbacks. An implementation repairing that query defect may return those dimension values, but should identify that as a correction to the shipped client. Command-specific handling of a failed macro is separate from ordinary expansion. _Evidence: original registration, argument decoder 0x2f743, callbacks 0x2f863/0x2f642 and [complete macro-expansion checks](../research/issue-10-port-geometry.md#unexpected-original-portwporth-query-defect)._

## RIP_SWITCH_PORT

_Switches to a new port_

_Added in RIPscrip v2.A3._

_Evidence: original RIPtel 3.1 slot 118/handler 0x468eb, protection/selection/creation/binding consumers and [12,187,782 native table checks](../research/issue-54-switch-port-precedence.md#original-wire-order-and-native-checkpoint); 2.00a4; HLP (`RIP_SwitchPort`); corpus (35 uses in 31 files)._

|               |                      |
| ------------- | -------------------- |
| **Level**     | 2                    |
| **Command**   | `s`                  |
| **Arguments** | `port-num:1 flags:2` |

**Format:** `!|2s <port-num> <flags>`

**Example:** `!|2s002`

**Attributes used:** port, base math (current setting)

This command selects drawing port 0..35. A defined screen or offscreen port may be selected even when protected. **An ordinary undefined destination is created as a screen port with default full-screen geometry, then selected.** The original handler uses the same selector as `CUR(PORT,n)`; it does not reject every absent port or automatically select port 0 merely because the target was absent. Only failed creation falls back to physical screen port 0. Subsequent drawing uses the actual selected port.

The protection flags execute in this fixed order:

| Order | Value | Action |
| --- | --- | --- |
| 1 | 4 | Protect the source, meaning the current port before selection |
| 2 | 8 | Unprotect that source |
| 3 | — | Select/create the requested destination; on creation failure select 0 |
| 4 | 1 | Protect the actual current port after selection/fallback |
| 5 | 2 | Unprotect that actual current port |

**Unprotect wins within each operand:** values 1+2 (3) leave the destination unprotected; values 4+8 (12, MegaNum `0C`) leave the source unprotected. These combinations are accepted. If source and destination are the same port, destination actions happen last, so they can override source actions. A same-port command still applies all its flags. Port 0’s protection cannot be changed by any of these actions.

**Failure is not transactional.** Source flags run before selection and remain applied if creation fails. Destination flags refer to the actual fallback port 0 in that case; they do not target the still-undefined requested entry or return to the old source. Port 0 ignores them. In particular, destination-unprotect cannot rescue a protected-but-undefined target: the constructor has already failed before that action runs. An out-of-range target (36 or above), or disabled graphics processing, returns before any protection writes.

For the following examples, source 1 initially exists and is unprotected. These are base 36 flag fields; `0C` is numerical 12:

| Command | Target condition | Final current | Final source 1 protection | Final target protection |
| --- | --- | --- | --- | --- |
| `! | 2s106` | Same existing port 1 | 1 | Unprotected: destination-unprotect follows source-protect | Same as source |
| `! | 2s109` | Same existing port 1 | 1 | Protected: destination-protect follows source-unprotect | Same as source |
| `! | 2s103` | Same existing port 1 | 1 | Unprotected: unprotect wins within destination pair | Same as source |
| `! | 2s10C` | Same existing port 1 | 1 | Unprotected: unprotect wins within source pair | Same as source |
| `! | 2s704` | Ordinary undefined 7 | 7, newly created screen port | Protected | Unprotected |
| `! | 2s701` | Ordinary undefined 7 | 7, newly created screen port | Unprotected | Protected |
| `! | 2s704` | Creation of 7 fails | 0 | Protected, retained through failure | Failed target unchanged; port 0 unchanged |
| `! | 2s701` | Creation of 7 fails | 0 | Unprotected | Failed target unchanged; destination-protect is ignored on 0 |

The native failure fixture uses an undefined record with its protection bit already set: original creation rejects it before writing, selects 0 and preserves that record. It is a controlled proof of the original failure branch, not a claim that ordinary query/protection commands can create that state. The exhaustive defined/absent/same-target matrices and exact controlled-service boundaries are in the [derivation](../research/issue-54-switch-port-precedence.md).

The shipping descriptor has **two fields**, one MegaNum character for port and two for flags: three characters after `2s`, with no reserved field. This corrects the inherited `res:3` signature for this opcode; it is not evidence that arbitrary reserved characters should be appended or that every switch-family layout has been reconciled. Only low flag bits 1/2/4/8 act; the full base 36 two-character domain 0..1295 is accepted without rejecting higher bits.

Every wipe function in the corpus ends with a switch back to the screen (WIPE00.FN's comment “Switch to port 0”; `!|2s002` attempts destination-unprotect, which port 0 ignores), and port-composition scenes switch to port 1 with `!|2s100` before drawing offscreen. These three-character inputs agree with the actual descriptor rather than relying on truncation of a six-character field. _Evidence: original descriptor; corpus._

## RIP_DELETE_PORT

_Deletes a specific port definition_

_Added in RIPscrip v2.A3._

_Evidence: 2.00a4; HLP (`RIP_PortDelete`; "Can't delete graphics port #0"); corpus (12 uses in 12 files) - not in SyncTERM._

|               |                                |
| ------------- | ------------------------------ |
| **Level**     | 2                              |
| **Command**   | `p`                            |
| **Arguments** | `port_num:1 dest_port:1 res:2` |

**Format:** `!|2p <port_num> <dest_port> <res>`

**Example:** `!|2p1000`

**Attributes used:** port, base math (current setting)

This command physically deletes one or more graphical ports. The exact port depends on the `<port_num>` parameter. If the port number specified is between 1-35, then the given port is deleted (providing of course that it is unprotected). If you attempt to delete a protected port, then this command will fail. If you attempt to delete port #0 (the screen port), then you will be activating a special case of this command - all unprotected ports from 1-35 are automatically deleted. This is a good garbage collection command mode when you want to start with a new slate of ports without the overhead of sending many delete port commands.

The `<dest_port>` parameter defines the port number that will be switched to after the delete operation is finished. Typically, this will be set to port #0 (switch to screen port), but it need not be. If the destination port is undefined, then it will automatically switch to port #0. If you instruct this command to delete all ports, then the destination port may or may not be set to the screen port - it all depends on whether or not the destination port both exists, and is protected - remember, a protected port cannot be deleted with this command without first being unprotected. So, if you delete all ports and switch to another port that isn't port #0, and that port is protected, then that protected port is selected as the new active port. If however, that port doesn't exist (ie, it did exist at the beginning of this command, but wasn't protected), then the screen port #0 will be selected.

> **NOTE:** The `<res>` parameter is reserved for future use and should be set to "00" for future compatibility with later RIPscrip revisions.

The example, from NEWPORT.FN ("Make sure port #1 is deleted before continuing"), removes port 1 and returns to the screen; MAKEPORT.FN's `!|2p00` ("Delete all ports (screen is unaffected)") is the garbage-collection special case in the wild, with trailing reserved digits omitted - tolerated by the shipping parser. _Evidence: corpus._

> _Editor's note:_ the 2.x ALPHA 4 draft's entry for this command misprints its own Format/Example as `!|2s` (the switch-port opcode); the corpus confirms the wire opcode is `2p` as the argument table says, and this edition prints the corrected form.

## RIP_PORT_COPY

_Copies graphics data from one port to another_

_Added in RIPscrip v2.A3._

_Evidence: 2.00a4; HLP (`RIP_PortCopy`); corpus (**9,104 uses in 46 files** - the most-used command in the entire corpus) - not in SyncTERM._

|  |  |
| --- | --- |
| **Level** | 2 |
| **Command** | `C` |
| **Arguments** | `source_port:1 sx0:XY sy0:XY sx1:XY sy1:XY dest_port:1 dx0:XY dy0:XY dx1:XY dy1:XY write_mode:1 res:5` |

**Format:** `!|2C <source_port> <sx0> <sy0> <sx1> <sy1> <dest_port> <dx0> <dy0> <dx1> <dy1> <write_mode> <res>`

**Example:** `!|2C1XC00ZKQO0000028QO0`

**Attributes used:** viewport, port, base math (current setting)

This command copies graphics data from one port to another (or possibly even the same port). The area copied is a rectangular area based on the (sx0,sy0)..(sx1,sy1) parameters in the `<source_port>` and the (dx0,dy0)..(dx1,dy1) parameters in the `<dest_port>`. The `<source_port>` and `<dest_port>` parameters specify which port numbers are to be used for the source and destination respectively. They may be set to the same port number which signifies that a bit-blit operation is to occur from one location of the current port to another. Both the source and destination ports are specified as port numbers from 0-35. If either port doesn't exist (or is deactivated) then this command will do nothing.

The source port parameters (sx0,sy0)..(sx1,sy1) define the upper-left and lower-right corners of the rectangle in the source port that is to be the source image data. If all four parameters are set to zero, then the entire source port's viewport is used as the image. These parameters determine the portion of the source port that is to be used to copy to the destination port. The image data is taken from within the port's currently defined viewport. If the (sx1,sy1) parameters takes the image out of the bounds of the source port's viewport, then the values are adjusted to make it fit inside the viewport.

The destination port parameters (dx0,dy0)..(dx1,dy1) define the destination rectangle. After world-to-device conversion, RIPtel 3.1 chooses among these cases **in order**:

1. If **all four destination coordinates are zero**, use the complete destination viewport. This takes precedence over the zero-endpoint verbatim case; a differently sized source is fitted to that viewport.
2. Otherwise, if **both destination end coordinates are zero**, place the source at (dx0,dy0) and synthesize the destination end by adding the source rectangle's physical width/height. This starts as an equal-size, unscaled copy.
3. Otherwise, use the explicit destination rectangle. Compare its physical width/height with the source rectangle **before clipping** to choose unscaled versus scaled copying.

All-zero source coordinates select the complete source viewport independently. Other rectangles are translated relative to their port's viewport. Right/bottom values are extent boundaries for this command: width is right minus left, height is bottom minus top.

For an initially **equal-size** copy, clip the source and destination against their respective viewports, shortening the other rectangle's right/bottom by the same amounts. The original no-scale branch remains selected, preserving one source pixel per destination pixel. For an initially **unequal-size** copy, clip the two rectangles independently, then scale the surviving source into the surviving destination. A rectangle wholly outside its viewport produces no copy. The driver does not reclassify an initially unscaled copy as scaled merely because clipping shortened its destination. This also applies to explicitly sized equal rectangles, not only the zero-endpoint shorthand. _Evidence: original handler 0x46372, compositor 0x134d0, coupled trim 0x13456 and [native geometry matrix](../research/issue-10-port-geometry.md#native-allocation-and-copy-checkpoint)._

For the concrete case of a 4×1 source and 2×1 destination viewport with destination `(1,0,0,0)`, the final copy is destination **(1,0), size 1×1**, from source **(0,0), size 1×1**. It copies only the first source pixel to destination X=1. It does not fit the four source pixels into that one pixel. With destination `(0,0,0,0)`, the final scaled copy fits the entire 4×1 source into the 2×1 destination viewport. Exact sampling/filter output is outside this geometry contract. _Evidence: original BitBlt/StretchBlt arguments captured for all five put modes in the [probe](../research/issue-10-port-geometry.md#native-allocation-and-copy-checkpoint)._

The `<write_mode>` parameter determines the Raster Transfer mode that is used to write the image data to the destination rectangle. The possible values and their various effects on the destination image are as follows:

| Mode | Description                                          | Logical |
| ---- | ---------------------------------------------------- | ------- |
| 0    | Copy the image to the port verbatim                  | COPY    |
| 1    | Exclusive-OR image with the one already on the port  | XOR     |
| 2    | Logically OR image with the one already on the port  | OR      |
| 3    | Logically AND image with the one already on the port | AND     |
| 4    | Copy the inverse of the image onto the port          | NOT     |

Working with a port copy operation, the source rectangle for the image is contained in the source port number. The destination rectangle is based in the destination port. If either rectangle extends beyond its port viewport, apply the equal-size versus unequal-size clipping rule above. Preserve an initially unscaled copy; only the fit branch independently trims and scales the remaining rectangles.

> **NOTE:** The `<res>` parameter is reserved for future use and should be set to "00000" for future compatibility with later RIPscrip revisions.

By use count this is _the_ RIPscrip 3.x command: the WIPE00-24.FN transition library is almost nothing but port-copy animation, sliding successive slices of a pre-rendered offscreen scene onto the screen. The example line, from a wipe, copies the slice of offscreen port 1 from x = `XC` (1200) to `ZK` (1280), full height `QO` (960), onto screen port 0 at (0,0)-(80,960) in COPY mode - one frame of a right-to-left push (reserved digits omitted, as the shipping driver tolerates). Between the wipes and the `.MSE` status-line backups ("Copy the screen image to the port"), 46 of the 116 corpus files depend on it. _Evidence: corpus._

### Remembered Copy Pairs

**Explicit portable completion:** the primary PCB description establishes destination ownership, reversal into the current port and viewport-relative placement. It does not completely specify initialization, units, producers, commit/failure or reset scope. The following rules complete that contract, preserving the accepted copy/capture geometry; [derivation, documentary limits and rejected alternatives](../research/issue-144-remembered-port-copy-pairs.md). This is abstract per-port state, not a new wire field, query, private file layout or second clipboard buffer.

Each live port p owns either **no pair** or `P[p]=(Rs,Rd)`. Both rectangles have positive area and use half-open DEVICE extent boundaries `(left,top;right,bottom)`. They are the **final logical source and destination rectangles submitted by the protocol compositor**, after the producer's WORLD conversion, sentinel expansion and existing pre-trim classification/viewport clipping rules, but **before physical storage/sample clipping**, expressed as offsets from their respective viewport origins **at that transfer**. They are not raw WORLD coordinates, sentinel values, original unclipped requests, a raster-mode setting or cached pixels.

Let `Os` and `Od` be the source/destination viewport origins in the backing-surface DEVICE coordinates used by the compositor. For screen ports these include the port's screen origin; for offscreen ports use the bitmap's viewport origin. Add a port origin only once if a backend already stores absolute viewport bounds. Given final logical rectangles `S*` and `D*`, publish on the **destination**:

```text
Rs = S* - Os             Rd = D* - Od
P[destination] = (Rs,Rd)
```

Subtraction/addition translates all four rectangle boundaries. No second rounding or unit conversion occurs. Store the existing logical kernel's final rectangles, rather than recomputing a physical intersection that would change its coupled-versus-independent trimming or mapping. In particular, initially equal-size transfers remain unscaled under coupled clipping; initially unequal transfers retain their independently trimmed fit path. A later operation classifies its own initial extents; the pair does not preserve/inherit the old branch.

For [`PCB`](5.1-text-variables.md#pcb) from port p into the current port c, snapshot its valid pair, then reverse it:

```text
requested source      = current viewport origin of p + Rd
requested destination = current viewport origin of c + Rs
```

These are **explicit DEVICE rectangles**, not another WORLD/sentinel command. Run the same copy geometry using current viewports and plain mode **0 COPY**. WORLD changes leave stored offsets unchanged; moving either viewport reanchors that side and changing its extent can trim or eliminate the new transfer. Reverse fitting is geometry reuse, not a promise to reconstruct pixels discarded by an earlier stretch. Global W and the producer's earlier transfer mode are neither changed nor used as PCB's mode.

#### Physical Storage and Sample Coverage

**Explicit boundary completion:** a [stored viewport can exceed physical backing](1.3-world-view-virtual-canvas.md#rip_viewport). The final pair above is after **logical viewport** clipping, not a rectangle or mask of physical pixels written. [Derivation and independent physical-boundary vectors](../research/issue-146-physical-clip-pairs.md). This qualifies “actual/final transfer” throughout the remembered-pair contract, including every named producer, PCB and saved pairs; it does not change their ownership, selectors, units, lifecycle or existing geometry branch.

After obtaining S*/D*, preserve their correspondence while clipping raster access to the physical destination and rejecting source samples outside physical source storage. Do not independently trim to physical bounds and refit the remaining rectangles. In the fit path the nominal X boundary correspondence is `xd = dl + (xs - sl) * (dr - dl) / (sr - sl)`, with the analogous Y rule; unscaled copying retains its translation. This boundary formula describes geometry, not a chosen sample position or filter. It is the mapping established **after logical viewport trimming**, not a request to undo that stage. Keep backing accesses within available storage; physical clipping neither enlarges storage nor changes the stored viewport. Existing sampling/filter/edge freedom remains unchanged.

A physical source boundary can map to a fractional destination boundary. **Do not round it into Rs/Rd, derive the pair from raster coverage/counts, or substitute a backend's smaller physical blit pair.** A sampler may touch a different edge subset, and skipped samples or zero coverage need not form a useful integer pair. Even when a backend can return a coupled integer physical blit rectangle, the protocol publishes the full final logical pair. P is geometry; it does not assert that all represented pixels were initialized/written or preserve a damage/coverage layer. A later PCB reverses the logical pair and applies its own current logical and physical limits; pixel restoration is not guaranteed for regions never physically captured.

Determine logical eligibility and positive-area S*/D* **before** relying on a legacy service's outward success value. Publication follows this table:

| Logical request / completed stage | Pair on an existing destination |
| --- | --- |
| Undefined/inactive operand, empty logical viewport, wholly logically clipped/empty transfer, or another command-defined no-op | Retain old pair, even if a service returns success for that no-op |
| Eligible nonempty logical transfer completes successfully, with some physical writes | Publish its full logical S*/D* |
| Same eligible nonempty logical transfer completes successfully, but physical bounds/sample rejection yield zero writes | Publish the same full logical S*/D*; physical zero coverage is not a logical no-op. A successful bounds-check/skip may complete this stage without issuing a raster call |
| Underlying transfer/snapshot/allocation failure, even if an outer helper ignores that failure and returns success | Do not publish; retain old pair on a surviving existing definition. Deleted/replaced/new-definition effects keep their existing rules |

No success Boolean is exposed by PCB. This rule requires neither a write count nor a new coverage buffer; the logical kernel's geometry and the actual stage completion status suffice. An unchanged pixel value or zero physical coverage alone does not mean failure. Conversely, an outer helper's unconditional success does not turn an observed failed transfer into a publication.

For the following independent DEVICE examples, all logical viewports contain the requested rectangles, origins are zero, height is one, and the named transfer completes successfully. Physical intervals are backing limits; all pair coordinates are logical half-open boundaries.

| Case | Pair published on destination / physical boundary |
| --- | --- |
| Physical source [0,2), logical source S*=[0,4), destination D*=[0,3) with physical [0,3) | Rs=(0,0;4,1), Rd=(0,0;3,1). Source boundary 2 maps to destination 3/2; neither an edge rounded to 1 nor to 2 enters the pair. Different samplers may write different edge cells |
| Same physical source, equal logical S*=[0,4), D*=[0,4), destination physical [0,4) | Rs=(0,0;4,1), Rd=(0,0;4,1). Physical source access is limited to [0,2), but even a backend's coupled [0,2)→[0,2) result does not replace the logical pair |
| Physical source [0,4), logical S*=[0,4), D*=[0,3), destination physical [0,1) | Rs=(0,0;4,1), Rd=(0,0;3,1). Destination edge 1 corresponds to source 4/3 under the unchanged 4→3 map; do not refit 4→1 or round 4/3 into metadata |
| Physical source [0,2), logical S*=[2,4), D*=[0,3), destination physical [0,3), all source samples rejected | Successful logical stage publishes Rs=(2,0;4,1), Rd=(0,0;3,1), although no destination pixel changes |
| Physical destination [0,1), logical S*=[0,2), D*=[2,4), destination viewport includes [2,4) | Successful physical bounds skip publishes Rs=(0,0;2,1), Rd=(2,0;4,1), although no raster call/write is necessary |
| Request wholly outside a logical viewport, or actual underlying transfer failure, with an old pair A | Retain A; an outer success return does not change logical emptiness or hide an observed failure |

Both axes follow the same rule. Subsequent viewport/WORLD changes and backup/restore continue the existing DEVICE-offset contract; physical clipping never rewrites those offsets after publication.

#### Producers and Publication

A pair starts absent; no implicit whole-viewport/default pair exists. Publish exactly once on the receiving port after a **logically nonempty successful transfer stage**, before later outer-command stages; [physical zero coverage still publishes](#physical-storage-and-sample-coverage). Source pair state normally stays unchanged. A successful same-port transfer snapshots the old pair first, then replaces that same owner's pair with the new final transfer; it must not read its own partially updated metadata.

| Operation | Pair producer and receiver |
| --- | --- |
| Wire `2C` PORT_COPY, any accepted put mode | Publish its final S*/D* on its explicit destination; no selection or clipboard assignment |
| Wire `1C` GET_IMAGE | Newly allocated/replaced capture target starts absent; after actual copy success publish the actual source/target geometry. Preserve existing selection/replacement/current-port/failure rules, including which live source is actually used |
| LOAD_ICON with clipboard capture / LOAD_BITMAP duplicate 0 | Same shared capture rule, using the renderer-returned DEVICE rectangle; do not add wire 1C's extra caller increment |
| LOAD_BITMAP explicit duplicate 1..35 | New target starts absent; successful COPY of the rendered region publishes its final pair. Existing same-current skip, invalid target and protected replacement rules remain controlling |
| Initial button auto-stamp capture | Publish on the capture target using the adopted logical effect footprint C and logical clipboard viewport; capacity outside that viewport is not part of the pair. The same-target ignore guard publishes nothing |
| PUT_IMAGE | On a successful nonempty transfer, publish on the current destination from the assigned source's full logical viewport to its DEVICE-projected anchor, after normal clipping. Its existing same-port no-op publishes nothing; its own mode still controls the pixels. The source needs no remembered pair |
| PCB | On success publish its actual reversed transfer on the current destination, under COPY, just like the named port-transfer operations above |
| Ordinary drawing/erasure, direct image-file rendering/placeholder/wallpaper, later button face/feedback redraw | Preserve pair state. An internal renderer copy is not another protocol-level pair producer |

Wire GET_IMAGE retains its adopted extent increments: at WORLD=DEVICE, `(1,1)..(3,3)` requests source `[1,4)×[1,4)` (3×3) and allocates/targets `[0,4)×[0,4)` (4×4). With no clipping it records **Rs=(1,1;4,4), Rd=(0,0;4,4)**; PCB later fits 4×4 back into 3×3. Shared LOAD capture of an already returned w×h rectangle instead has its existing helper allocation w+1 by h+1; explicit duplication uses w×h. Record each route's final logical transfer, with physical storage/sample clipping outside pair geometry. The [auto-stamp completion](4.3-buttons.md#auto-stamp-geometry-and-redraw) is distinct: logical C is used one-for-one, even if a backend allocates extra capacity. For C=[97,123)×[47,63), full capture gives Rs=(97,47;123,63), Rd=(0,0;26,16) at viewport origins zero.

#### Success, Failure, Protection and Overlap

For an existing destination definition, a command-defined no-op, wholly **logically** clipped rectangle, invalid/inactive/undefined operand, rejected request or failed transfer leaves its previous pair unchanged. A logically nonempty successful copy publishes even when pixels remain identical or physical clipping/sample rejection writes nothing, as defined above. Snapshot source pixels before overlapping writes, including distinct screen ports sharing one backing surface; this reads the source before writing the destination without choosing a scaling filter. If preparing that snapshot fails, there is no transfer/pair publication. A later rendering failure does not imply pixel rollback.

**Copying to/from protected defined active ports is allowed by the primary protocol.** Pair publication is operational copy bookkeeping and is allowed on such a content target; it does not authorize changing a protected viewport or redefining/deleting a protected port. Capture/duplicate replacement retains its separate protection checks.

Replacement/capture has its existing stage effects: if an old target was deleted, its old pair is gone; a surviving newly allocated clear target has **no pair** until a logically eligible nonempty copy stage succeeds, even if an outer helper reports success after ignoring an underlying failure or logical no-op. A successful physical-only skip publishes under the boundary rule above. A protected replacement rejection retains the old definition/pair. Allocation failure and current/clipboard changes keep the existing operation's documented or implementation-defined recovery scope; this metadata rule adds no rollback. Inactive/trim failure discovered only after capture allocation likewise need not undo that allocation. Later label, wallpaper or other outer-stage failure does not undo a previously completed transfer or its published pair.

PORT_COPY, PUT_IMAGE and PCB preserve current-port selection, clipboard assignment, unrelated tables, text cursors and image-style settings; only pixels and the receiving pair change on success. This does not suppress the explicit selection/pointer/replacement side effects of capture/duplicate producers. All malformed/runtime handling stays under the existing macro/command error and **void parser/session boundary**; pair absence/failure supplies no Boolean protocol result or connection termination.

#### Pair Lifetime and PORT Backups

| Event | Pair state |
| --- | --- |
| Successful new definition, first-use creation or redefinition, even with the same numeric slot/geometry | Absent until a named transfer publishes it |
| Viewport move/resize/activation or viewport-only reset; WORLD/STYLE/image-style/text-cursor/protection/selection edit | Retain DEVICE offsets; later PCB uses current origins/eligibility and clips normally |
| Ordinary content drawing/erase | Retain geometry; PCB reads the source's then-current pixels, not a hidden saved image |
| Backing-bitmap replacement outside whole-PORT restore | Clear, then publish only if that operation has a successful listed transfer stage; direct image drawing into existing storage is not backing replacement |
| Delete a port | Discard its pair; pointer/current deletion effects keep their existing rules |
| Full SOFT/drawing reset, including HEADER global bit 2 | Deleted nonzero definitions lose pairs; protected surviving nonzero ports retain theirs; reset port zero starts with no pair. Separate image-style reset exceptions do not clear protected survivors' pairs |
| HARD / HEADER global bit 1 | All new/default port definitions start without pairs |
| HEADER type-2 bit 1, or bit 8 when its nonzero-current condition invokes the [PORT-0 initializer](1.1-protocol-and-command-hierarchy.md#port-zero-initialization) | Clear P0 to absent without painting. Surviving nonzero definitions retain pairs; skipped bit-8 initialization retains P0. Actual deletions still discard owned pairs |
| HEADER without full reset | Only its actual definition-deletion/replacement/reset operations clear affected pairs; viewport-only/lock/selection operations retain them |
| Whole-PORT save or backup-to-backup copy | Own the optional-pair flag and both rectangles with the port definition; no drawing, transfer or publication |
| Whole-PORT restore, including RCB / PORT in RESTOREALL | Restore saved pair or saved absence with each applied definition, after resource setup. A protected live port absent from the snapshot retains its own pair under existing restore exceptions |
| SCREEN/ENV/STYLE or another unrelated backup alone | Does not save/restore/transform this PORT metadata |

The documented screen-port **text-cursor** restore exception is separate; this portable pair is restored as port-definition metadata. Do not synthesize it from restored pixels, default viewports, image-style rectangles or the assigned clipboard pointer. Failed replacement/restore cannot invent a valid pair for an incomplete new definition; unchanged surviving definitions retain their state under the existing failure rules. No source-port ID or source-object lifetime is retained in the pair: its Rs describes an offset usable in whichever port is current when PCB runs.

#### Independent Rectangle and State Vectors

Assume DEVICE unit geometry, positive active viewports, all referenced definitions valid, and COPY unless stated. `(l,t;r,b)` denotes half-open rectangles; these are geometry/state vectors, not original-client executions or raster-filter oracles.

| Case | Stored pair / PCB result |
| --- | --- |
| 0→5→0: source viewport origin O0=(100,50), copy source offsets (2,3;6,5) into port 5 offsets (0,0;4,2), O5=(0,0) | P5 has Rs=(2,3;6,5), Rd=(0,0;4,2). PCB(5) into current 0 reads (0,0;4,2) and writes (102,53;106,55) |
| Move current port 0 viewport origin to (120,70) | Same P5 now writes (122,73;126,75); changing WORLD alone does not change either DEVICE rectangle |
| Also move source port 5 viewport origin to (1,1), with sufficient extent | PCB now reads (1,1;5,3) and writes the same (122,73;126,75) |
| Source 4×1, destination 2×1, destination wire shorthand (1,0,0,0) | Existing coupled trim transfers only S*=(0,0;1,1), D*=(1,0;2,1). Store that pair on the destination; reverse copies only that one cell back |
| Source 4×1, destination all-zero/full 2×1 viewport | Store Rs=(0,0;4,1), Rd=(0,0;2,1). Reverse fits two cells into four; it does not recover discarded source detail |
| Initially unequal request S=(0,0;4,1), D=(0,0;2,1), source viewport only 2×1 | Independent trimming leaves S*=(0,0;2,1), D*=(0,0;2,1). Store those equal final extents. PCB classifies its new 2×1→2×1 request as unscaled; it does not inherit the original fit branch |
| GET_IMAGE (1,1)..(3,3), no clipping | Capture pair is 3×3→4×4 as above; PCB reverses 4×4→3×3, not the original allocation extent into a fourth logical source row/column |
| PUT_IMAGE from a 2×1 source viewport at origin (3,4), destination anchor DEVICE (7,8), no clipping | Current destination gets Rs=(0,0;2,1), Rd=(7,8;9,9) with destination viewport origin zero; PCB from it reverses that location into current destination offsets (0,0;2,1) |
| Valid source but no pair; omitted pointer absent/dangling; explicit undefined or inactive source/destination | PCB performs no copy, selects/creates nothing and changes no pair/pointer |
| Protected defined destination and nonempty successful transfer | Copy and pair publication allowed; definition/protection/viewports unchanged |
| Wholly logically clipped copy or backend failure into an existing port with old P | Keep old P; no uncopied requested rectangle becomes eligible for PCB |
| Capture replacement allocates a new clear bitmap, then logical copy is wholly clipped/fails | New definition/pointer follow existing capture rules, but its pair is absent; no old pair survives deletion |

For same-port overlap, take four unit cells `ABCD`, a valid P with Rs=(0,0;3,1), Rd=(1,0;4,1), and a 4×1 viewport. `PCB(CUR)` snapshots cells 1..3, copies them to 0..2, producing `BCDD`, then stores **Rs=(1,0;4,1), Rd=(0,0;3,1)**. A second unclipped PCB(CUR) copies the current cells 0..2 to 1..3, producing `BBCD`, and reverses the pair again. Ordinary drawing could have supplied the initial cell values without changing P. This independent unit-cell COPY model defines overlap/order, not platform sampling. With further clipping, publish the actual new final pair rather than promising an exact swap.

For selector cases, start each invocation independently with current 0, assigned clipboard 5, P0 absent and P5 valid. Bare PCB / PCB() / PCB(5) use P5; PCB(CUR) and PCB(0) do nothing because P0 is absent. With no assigned clipboard, bare PCB remains a no-op even if P0 is valid; explicit CUR/0 may still paste. A dangling pointer is not repaired, while a malformed explicit selector fails validation before reading or changing any pair.

For lifecycle cases, save PORT with P5=A and P6 absent; later change P5 to B and establish P6=C. A successful full restore reinstates A and absence respectively, and reuse of that BASE repeats the same result. A protected live port absent from the snapshot retains its own pair. A viewport-only reset preserves A, a full SOFT clears P0 and any deleted unprotected slot but keeps a protected surviving P5, and HARD leaves every default/new pair absent. Redefining slot 5 never resurrects A; successful new creation is absent until a listed transfer succeeds. Failed replacement that retains the old definition retains A; deletion followed by allocation failure loses A, and a newly allocated target whose transfer fails is defined but has no pair. Capture's already documented pointer/current effects still apply; pair handling introduces no additional table or selection changes.

Repeated PCB(5) into a different current port leaves **P5** unchanged, so it reuses the same nominal offsets while reading current pixels and applying current viewport clipping. It can change the current destination's pair, and shared backing or later drawing can change the pixels read on a following invocation. Same-port identity rectangles are nonempty successful transfers if otherwise eligible; they do not erase a pair or invoke full-viewport sentinels.

## RIP_PORT_WRITE

_Writes port image to a disk-based bitmap file_

_Added in RIPscrip v2.A3._

_Evidence: 2.00a4; HLP (`RIP_PortWrite`) - not observed in the RIPtel demo corpus, not in SyncTERM._

|               |                                                     |
| ------------- | --------------------------------------------------- |
| **Level**     | 2                                                   |
| **Command**   | `W`                                                 |
| **Arguments** | `port_num:1 x0:XY y0:XY x1:XY y1:XY res:4 filename` |

**Format:** `!|2W <port_num> <x0> <y0> <x1> <y1> <res> <filename>`

**Example:** `!|2W5000020200000FILENAME.BMP`

**Attributes used:** viewport, port, base math (current setting)

RIPtel 3.1 exports a defined screen source differently from an offscreen bitmap source. These are the original client's rules, including the offscreen crop omission; do not substitute generic capture/intersection behavior. _Evidence: original wire handler 0x4699a, writer 0x27a90, BMP serializer 0x4dc4c and [335,450 native geometry/serialized-pixel checks](../research/issue-10-port-geometry.md#post-pr-port_write-results)._

**Screen source:** use a half-open device rectangle. The original handler uses the decoded coordinates directly as device offsets relative to the stored viewport origin, without the ordinary world-to-device conversion. When all four coordinates are zero, copy the full stored viewport. When both ending coordinates are zero, retain the given start and use the viewport's right/bottom boundaries. Otherwise require x1>x0 and y1>y0 before clipping, then clamp the ending axes **independently** to the viewport's right and bottom. A valid ending axis is retained; neither axis expands merely because the other is outside. The old “lower-left corner” wording was incorrect: it is the **lower-right boundary** being trimmed. No extra inclusive pixel is added.

For a screen viewport `[0,8)×[0,4)` and equal world/device dimensions:

| Requested rectangle | Exported size | Source pixels  |
| ------------------- | ------------- | -------------- |
| `(0,0)-(0,0)`       | 8×4           | x0..7, y0..3   |
| `(1,1)-(0,0)`       | 7×3           | x1..7, y1..3   |
| `(1,1)-(9,2)`       | **7×1**       | x1..7, y1 only |
| `(1,1)-(2,9)`       | **1×3**       | x1 only, y1..3 |

The quoted 7×2 alternative in the follow-up assumes an inclusive ending Y. The original writer instead allocates width=right−left and height=bottom−top, so ending y2 excludes row 2.

**Offscreen source:** with the command's reserved fields zero, the writer serializes the **entire backing bitmap**, ignoring the crop rectangle computed by the handler. Both requested partial rectangles above therefore export the whole 8×4 bitmap when that is its actual allocation. A 10×6 backing bitmap with an 8×4 viewport exports 10×6. This is a shipped omission, not a rule that all ports crop identically. An explicitly nonzero rectangle failing the handler's x1>x0/y1>y0 check still rejects before reaching the writer.

**Inactive/protected/undefined source:** the command tests definition, but never tests the stored viewport-deactivated bit or rejects a protected defined source. A defined deactivated source still exports its stored screen rectangle or whole offscreen bitmap and replaces the output file. An undefined source reports `Drawing port is not in use` and returns before opening/replacing the file. An explicit empty rectangle likewise diagnoses and leaves the old file unchanged. Export does not change current-port selection, stored geometry, protection or cursor state. The native probe checks labeled output pixels, dimensions and a pre-existing file sentinel with RAM-only file services; no real file is replaced during verification.

> **NOTE:** The `<res>` parameter is reserved for future use and should be set to "0000" for future compatibility with later RIPscrip revisions.

Documented in 2.00a4 and named in the 3.0 driver's string table, but the demos never write to disk - they keep their snapshots in offscreen ports instead of round-tripping through files. _Evidence: HLP; corpus._

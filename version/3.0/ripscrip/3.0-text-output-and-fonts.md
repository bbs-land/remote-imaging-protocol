## RIP_MOVE

_Move the current drawing position to (X,Y)_

|               |             |
| ------------- | ----------- |
| **Level**     | 0           |
| **Command**   | `m`         |
| **Arguments** | `x:XY y:XY` |

**Format:** `!|m <x> <y>` **Example:** `!|m0509`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/3.0-text-output-and-fonts.md#rip_move)) · HLP (`RIP_Move`) · SyncTERM (ripper.c:14568) - not observed in the RIPtel demo corpus

This command moves the current graphics drawing cursor to (x,y). You could use this to draw text at a certain point, but you'd probably use [RIP_TEXT_XY](#rip_text_xy) instead. This command is primarily provided for future development which will make use of its ability to relocate the current drawing position without physically drawing anything.

The demos always position text with [RIP_TEXT_XY](#rip_text_xy) instead, so `m` never appears in the corpus - consistent with the 2.00a4 note that it was "primarily provided for future development".

## RIP_TEXT

_Draw text in current font at current XY location_

|               |               |
| ------------- | ------------- |
| **Level**     | 0             |
| **Command**   | `T`           |
| **Arguments** | `text-string` |

**Format:** `!|T <text-string>` **Example:** `!|Thello world`

**Attributes used:** Draw Color, Write Mode, Font Style, Viewport, Port **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/3.0-text-output-and-fonts.md#rip_text)) · HLP (`RIP_Text`, plus `$TEXTXY$` variable) · SyncTERM (ripper.c:14026) - not observed in the RIPtel demo corpus

This command displays text at the current location in the graphics window, as set with the [RIP_MOVE](#rip_move) command, or immediately after horizontal text drawn with [RIP_TEXT_XY](#rip_text_xy) or a previous RIP_TEXT command. Only horizontal text updates the current graphical cursor position used with the RIP_TEXT related commands. Any form of screen reset ([RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) or [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) with reset options) will reset this current position to (0,0). A RIP_ERASE_VIEWPORT command does not reset this position.

The text is also affected by the most recent settings of these commands:

| Command | Description of Command |
| --- | --- |
| [RIP_FONT_STYLE](#rip_font_style) | font style (vector font, direction, size) |
| [RIP_WRITE_MODE](2.0-color-modes-and-palettes.md#rip_write_mode) | drawing mode (normal or XOR) |
| [RIP_COLOR](2.0-color-modes-and-palettes.md#rip_color) | drawing color (from the 16-color palette) |
| [RIP_EXTENDED_FONT_STYLE](#rip_extended_font_style) | extended font styles (True Type style) |

The current drawing position is set immediately to the right of the drawn text. Subsequent Line, Circle or other such commands will not affect this position. This provides a means so that you can quickly do another RIP_TEXT command (presumably in another color) at a later time and have the text show up immediately after the previous text (even after subsequent graphical operations like circles, rectangles, lines, etc).

**IMPORTANT NOTE:** Note that this "current graphics cursor location" is only updated for horizontal text moving from left-to-right in "left justified" mode. Any other orientation does not reset the location! _(v2.A4)_

The corpus always uses the combined [RIP_TEXT_XY](#rip_text_xy) form instead (638 uses versus zero bare `T` commands), but the mechanism survives - the `$TEXTXY$` variable in RIPtel's help reads back the "last graphical text X/Y" this command family maintains.

## RIP_TEXT_XY

_Draw text in current font/color at specific spot_

|               |                             |
| ------------- | --------------------------- |
| **Level**     | 0                           |
| **Command**   | `@`                         |
| **Arguments** | `x:XY y:XY` and text-string |

**Format:** `!|@ <x> <y> <text-string>` **Example:** `!|@HS2ARIPscrip Buttons`

**Attributes used:** Draw Color, Write Mode, Font Style, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/3.0-text-output-and-fonts.md#rip_text_xy)) · HLP (`RIP_TextXY`) · corpus (638 uses in 40 files) · SyncTERM (ripper.c:13445, descriptor `2#2#++`)

This command is an efficient combination of [RIP_MOVE](#rip_move) and [RIP_TEXT](#rip_text). The text is drawn at the specified location according to the same settings that apply to RIP_TEXT (see above).

The current drawing position is set immediately to the right of the drawn text. Subsequent Line, Circle or other such commands will not affect this position. This provides a means so that you can quickly do another RIP_TEXT command (presumably in another color) at a later time and have the text show up immediately after the previous text. See the RIP_TEXT command for a more thorough discussion of this subject.

This is the workhorse text command of the corpus (638 uses, versus zero bare `T` commands). In 3.x scenes it renders in whichever font was last selected - very often an [RIP_EXTENDED_FONT_STYLE](#rip_extended_font_style) outline font - and the text argument may contain `<<NAME>>` macros (`!|@809U<<LAB1>>` labels buttons from `.DEF`-file [text variables](../../glossary.md)) or `$&VAR$` dereferences. NEWS.RIP draws a drop-cap this way (`@A91G` + one large character) with the flowed article text starting mid-word after it (see the [drop-cap idiom](3.1-column-text-system.md#drop-caps)).

| 01   | Triplex Font              | Scalable   |
| 02   | Small Font                | Scalable   |
| 03   | Sans Serif Font           | Scalable   |
| 04   | Gothic [Old English] Font | Scalable   |

| 06   | Simplex Font              | Scalable   |

| 08   | Complex Font              | Scalable   |
| 09   | European Font             | Scalable   |
| 0A   | Bold Font                 | Scalable   |

(\*) Font 00 is an 8x8 font at 640x350. Its actual cell-size varies depending on the current resolution. This is equivalent to the 80x43 font of the text window. See the [RIP_TEXT_WINDOW](1.4-terminal-ansi-view.md#rip_text_window) for a more detailed discussion of font sizes and resolutions. _(v2.A3)_

### Direction and Size

For the Direction parameter, use 00 to indicate horizontal and 01 for vertical. Horizontal text appears from left to right. Vertical text is drawn with the base-line to the right, and is read from bottom to the top.

For the Size parameter, use 01 for the normal default size, 02 for level 2 magnification, 03 for level 3 magnification, and 0A for level 10 magnification. For the bitmapped font (00), these magnification factors are actual scaling factors - size 2 is twice as large as size 1, size 3 is three times as large, etc. The vector fonts (01-0A) are not direct magnification factors - they are based on the following table:

| Mag Factor | Actual Scaling Factor |
| ---------- | --------------------- |
| 01         | 3/5 of actual size    |
| 02         | 2/3 of actual size    |
| 03         | 3/4 of actual size    |
| 04         | 1/1 of actual size    |
| 05         | 4/3 of actual size    |
| 06         | 5/3 of actual size    |
| 07         | 2/1 of actual size    |
| 08         | 5/2 of actual size    |
| 09         | 3/1 of actual size    |
| 0A (10)    | 4/1 of actual size    |

The physical pixel dimensions of any particular font cell at a given magnification level vary depending on resolution in such a way that they appear to be the same size on the screen. For example, if a font at magnification level 4 is 35 pixels tall at 640x350 resolution, at 640x480 resolution, the font would be the same width, but would be 48 pixels tall. This makes sure that the fonts are resolution independent. _(v2.A3)_

Per-font metric tables (top/bow/base/drop) are with the button-label material in [4.3 Buttons](4.3-buttons.md#font-metrics-and-descenders).

### Justification and Special Effect Flags

The `<flags>` parameter allows you to alter the orientation and other special attributes of the subsequent text operations. The possible flag values which may be combined are as follows (they must be OR'd together): _(v2.A4)_

| Value | Description of Flag |
| --- | --- |
| 1 | Right justify text in relation to the base point |
| 2 | Center justify text horizontally around base point |
| 4 | Bottom justify the font (at the bottom of any descenders. |
| 8 | Baseline justify the font (base point is at the base line of the font). |
| 16 | Vertically center the text (base point is vertically in the center of the font cell). |
| 32 | Dropshadow the text using the current background drawing color (set with [RIP_BACK_COLOR](2.0-color-modes-and-palettes.md#rip_back_color)). The foreground text is drawn using the current foreground drawing color (set with [RIP_COLOR](2.0-color-modes-and-palettes.md#rip_color)). The shadow is drawn one pixel down and one pixel to the right of the font for both vertical and horizontal text. |

Flag values 1 and 2 are mutually exclusive. This means that either one of them may be specified, but not both! If both are omitted, then the text is "left justified". Flags 4, 8 and 16 are also mutually exclusive. If either of them are omitted, then the text is drawn with "top" justification. If both flags 1 and 2 are specified, or more than one of the flags 4, 8 and 16 are specified then the command is considered an error and is completely ignored. _(v2.A4)_

Each form of justification uses the base point as a starting point. Where the text is drawn in relation to this base point is a matter of the justification. Here is an example of horizontal text with all of the base point justifcation references pointed out: _(v2.A4)_

## RIP_EXTENDED_FONT_STYLE

_Added in RIPscrip v2.A1; the shipped argument block supersedes the ALPHA 4 draft._

_Select the current outline font, its facings, rotations, shadow and spacing_

|  |  |
| --- | --- |
| **Level** | 0 |
| **Command** | `y` |
| **Arguments** | `s:1 f:1 flags:4 size:2 shadow:2 str_rot:2 char_rot:2 baseline:2 spacing:2 unused:2 reserved:6 font_name` |

**Format:** `!|y <s> <f> <flags> <size> <shadow> <str_rot> <char_rot> <baseline> <spacing> <unused> <reserved> <font_name>`

**Example:** `!|y0000BW1Q080000001a1a000000Marin`

**Attributes used:** Graphics Style, World Frame (font sizing and optional baseline conversion), Viewport (optional baseline conversion). **Numeric base:** every numeric field is **always UltraNum (base 64)**, independent of Base Math and coordinate size. **Evidence:** DLL 3.0.7 (dispatch slot 75; handler RVA `0x1adc0`; text consumer `0x42870`; renderer `0x40ed0`) · corpus (FONTS.RIP, SHADOW.FN, TELLISTS.MNU). The [derivation and original-instruction probe](../research/issue-3-extended-font-style.md) identify the binary, give exact locations and reproduce the results.

The command selects outline-font mode in the current graphics-style record. Subsequent [RIP_TEXT](#rip_text) and [RIP_TEXT_XY](#rip_text_xy) use it; [RIP_FONT_STYLE](#rip_font_style) selects the alternative legacy font mode. Buttons and flowed text also use outline fonts but their placement routines can supply their own alignment or suppress rotation; the ordinary graphics-text rules below do not override those commands' placement policies.

### The Shipped 3.x Wire Layout

**26 fixed characters precede the font-name string.** TeleGrafix's comment in FONTS.RIP is a width crib, not a definition of every field's meaning:

```text
sfFFFFZZOOSSCCBBCCWWRRRRRR
```

Offsets below are zero-based from the first character after `y`. All ranges and defaults are decimal. The default column records the dormant outline fields initialized by the driver's `RIP_SetDefaultSettings`; these are not optional command arguments and do not imply that reset selects outline-font mode.

| Offset | Width | Crib | Field | Accepted value and effect | Reset value |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 | `s` | Stored compatibility byte | 0–63; stored and forwarded, but not read by the outline renderer. Use `0`. | 0 |
| 1 | 1 | `f` | Stored compatibility byte | 0–63; stored and forwarded, but not read by the outline renderer. Font facings come from `flags`, not this byte. Use `0`. | 0 |
| 2 | 4 | `FFFF` | Flags | 0–16777215; bit definitions below. Unused bits are stored without a rendering effect. | 0 |
| 6 | 2 | `ZZ` | Nominal point size | 0–4095 is accepted by the command. Rendering requires 1–4095; zero is a deferred render error, not a default-size request. | 25 |
| 8 | 2 | `OO` | Shadow distance | 0–4095 world units; zero disables the shadow. This is not orientation. Positive values scale with canvas width/world width and have a minimum device displacement of one. | 1 |
| 10 | 2 | `SS` | String rotation | Exactly 0, 900, 1800 or 2700, in tenths of a degree; controls the direction in which the string advances. | 0 |
| 12 | 2 | first `CC` | Character rotation | Exactly 0, 900, 1800 or 2700, in tenths of a degree; controls each glyph's orientation independently of string advance. | 0 |
| 14 | 2 | `BB` | Baseline displacement magnitude | 0–4095; device units unless flag `0x0200` requests conversion from world Y units when this command executes. Flag `0x0100` reverses its sign. | 0 |
| 16 | 2 | second `CC` | Character-spacing percentage | 1–4095; 100 is ordinary spacing. Zero rejects the command. Flag `0x0400` changes the reference width used for the extra spacing. | 100 |
| 18 | 2 | `WW` | Unused | All two-digit values are consumed and ignored. It is not a second scale or spacing factor. Use `00`; the shipping demos often use `1a`. | No stored field |
| 20 | 6 | `RRRRRR` | Reserved | Six numeric characters are consumed and ignored. Use `000000`. | No stored field |
| 26 onward | string | — | Typeface name | Must be present and nonempty before macro expansion. Expansion runs before the result is stored; the stored name is limited to 39 bytes. | `Marin` |

The six-character reserved value has no semantic numeric range: the shipped parser uses a 32-bit accumulator, so values exceeding 32 bits wrap, with no effect on this command. The common `1a1a` idiom is therefore **100% spacing followed by an ignored field**, not an X/Y scale pair. UltraNum `a` is 36, so `1a` = 1×64+36 = 100; a base-36 reader produces the wrong value.

The initial `s` and `f` bytes have no active selector semantics in this driver. Their historical intended names need not be guessed to implement them. Their values remain part of the stored graphics style.

### Flags, Justification and Shadow

Flags below are **decimal or hexadecimal bit values**, not literal four-character wire spellings. Encode their combined value as four UltraNum characters.

| Mask/value | Shipped effect |
| --- | --- |
| `0x0001` (1) | Bold |
| `0x0002` (2) | Italic; combines with bold |
| `0x0004` (4) | Underline |
| `0x0008` (8) | Strike-through |
| `0x0030` (48), selector `(flags >> 4) & 3` | 0 = left/start, 1 = right/end, 2 = centered along string advance. Selector 3 is accepted but skips the selector-specific justification adjustments; it is not an additional supported authoring mode. |
| `0x00c0` (192), selector `(flags >> 6) & 3` | Shadow direction: 0 = upper left, 1 = upper right, 2 = lower left, 3 = lower right, in device axes. Applies only when shadow distance is nonzero. |
| `0x0100` (256) | Negate the baseline displacement |
| `0x0200` (512) | Convert baseline displacement from world Y units to device units when the style is defined, truncating the scaled magnitude to an integer |
| `0x0400` (1024) | Base the extra-spacing adjustment on the font bounding-box width rather than the individual glyph's advance |
| `0xfff800` | Stored but unused by the ordinary outline renderer; emit zero |

These are the shipped flag assignments. In particular, underline and strike-through differ from the draft table, and the draft's separate vertical-justification field has no counterpart in `y`. The two apparent alignment validation branches in the DLL are ineffective: they mask to `0x30`/`0xc0` and compare against larger, unreachable bounds. Do not invent command rejection or flag normalization for these combinations.

Shadowing draws one displaced copy of the glyph bitmap in the current background color, then the foreground glyph; it does not extrude the outline through intermediate offsets. For distance `d > 0`, the device displacement is `max(1, trunc(d * canvas_width / world_width))` on each shadow axis. The direction bits select the signs independently of the string and character rotations.

### Size, Rotation, Baseline and Spacing

Font size is a whole nominal point count. The renderer gives the font engine `10 * size` tenths of a point and derives separate effective X/Y DPI as `trunc(72 * client_dimension / world_dimension)`. Consequently it follows the world frame rather than physical monitor DPI: at matching world and client dimensions, one nominal point corresponds to one device unit before the font's own metrics are applied. It does not use the current Base Math to reinterpret size, and arbitrary glyph rasterization need not match the original engine pixel for pixel.

The two rotation fields are independent and absolute; they are not added together. All sixteen pairs are valid:

| Wire field | Decimal | Angle | String advance | Character orientation |
| --- | --- | --- | --- | --- |
| `00` | 0 | 0° | Right | Upright |
| `E4` | 900 | 90° | Up | Quarter turn counterclockwise |
| `S8` | 1800 | 180° | Left | Half turn |
| `gC` | 2700 | 270° | Down | Quarter turn clockwise |

For example, `!|y0000B00W04E400001a1a000000Dixon` selects an upward string with upright glyphs; `!|y0000B00W0400E4001a1a000000Dixon` selects a rightward string with quarter-turned glyphs. Decode the actual bytes rather than relying on the corpus's comments: FONTS.RIP includes a `00`/`E4` pair labelled “180 x 90”.

The shipped baseline-displacement branches are irregular. Let `B` be the stored displacement, negated when `0x0100` is set. The table gives the additional device offset relative to the same command with a zero displacement; positive X is right and positive Y is down. Do not replace this with a general perpendicular-to-baseline rule.

| String rotation | Character 0° | Character 90° | Character 180° | Character 270° |
| --- | --- | --- | --- | --- |
| 0° | `(0, B)` | `(B, 0)` | `(0, 0)` | `(0, 0)` |
| 90° | `(B, 0)` | `(B, 0)` | `(0, 0)` | `(0, 0)` |
| 180° | `(0, 0)` | `(B, 0)` | `(0, -B)` | `(0, 0)` |
| 270° | `(0, B)` | `(0, 0)` | `(0, 0)` | `(0, 0)` |

With `0x0200`, conversion happens once at definition time, so later world-frame changes do not retroactively rescale the stored displacement.

For spacing percentage `P` and normal glyph advance `w`, the adjustment helper returns `trunc((P - 100) * reference_width / 100)`, using truncation toward zero. Normally the reference is `w`; with `0x0400` it is the realized font’s device-space bounding-box width. The ordinary glyph advance is first converted from the font engine’s 1/1440-inch units to device units; the bounding-box width is already in device units. The adjustment is added to the ordinary advance. The flag does not make glyphs monospaced: at `P=100` it changes nothing. For a glyph advance of 8 and a font bounding-box width of 12, `P=125` adds 2 normally, or 3 with `0x0400`. `P=50` and a reference width of 7 produce an adjustment of −3.

### Exact Decode of the Example

```text
s f flags size shadow str char baseline spacing unused reserved font
0 0 00BW  1Q   08     00  00   00       1a      1a     000000   Marin
```

`00BW` = 736 = `0x02e0`: centered text, lower-right shadow, and world-unit baseline conversion. `1Q` = 90 nominal points; `08` = shadow distance 8; both rotations and the baseline displacement are zero; spacing is 100%. The second `1a` and the six reserved characters have no effect. No bold, italic, underline or strike-through bits are set.

### State, Errors and Font Names

A successful command selects extended mode and replaces the current style's outline fields and expanded typeface name. A protected graphics style, invalid rotation, zero spacing or missing input name rejects the command before those fields change. Size zero is stored successfully and fails only when text is rendered. No command argument means “retain the old field”; provide the complete block.

Names resolve case-insensitively against the `.RFF` catalogue. The [shipping fonts](../assets/fonts/README.md) include BRUSH, COBB, DEFAULT, DIXON, EUREKA, MARIN, OAKLAND and SYMBOL, with thin, condensed, wide, expanded and hollow variants. The name may be a variable, as in SHOWFONT.FN's `…000000$&FONT_NAME$`. Name expansion can produce an empty or unavailable name after the initial presence check; a failed lookup produces no outline text and leaves the selected extended style intact. **RIPtel 3.1 does not switch to RIP_FONT_STYLE's default at size one on a failed outline-name lookup.** Font-load failure likewise does not install that fallback.

The [2.00a4 draft entry](../../2.0/text/RIPScrip-2.0-alpha-4.txt) describes a superseded 13-character layout, facings and alignment fields. It is not a second accepted `y` form in the shipped 3.0 driver. Earlier shipping clients already used a 26-character block, but this derivation establishes **RIPtel 3.1 / driver 3.0.7**; it does not silently assert every semantic detail for RIPterm 2.x.

## RIP_TEXT_METRIC

_Return measurements of text in the current graphics font_

|               |                                   |
| ------------- | --------------------------------- |
| **Level**     | 0                                 |
| **Command**   | `r`                               |
| **Arguments** | `mode:1 domain:1 reserved:4 text` |

**Format:** `!|r <mode> <domain> <reserved> <text>` **Example:** `!|r010000Hello`

**Numeric base:** current Base Math; the four reserved digits are consumed and ignored. **Evidence:** DLL 3.0.7, dispatch slot 57, handler RVA `0x20371–0x209ce`, output helper `0x6947`; [derivation, controlled metric oracles and client-output trace](../research/issue-5-scene-headers.md).

This is a host query using the current graphics style’s font, not a text-window mode setter. It supports both legacy/system and extended/outline font modes. It prepares the font and measures text without drawing the supplied string. Mode and domain are checked before text processing or a reply:

| Mode | Result                                  |
| ---- | --------------------------------------- |
| 0    | Width of the complete string            |
| 1    | Height of the complete string           |
| 2    | Width of each byte measured separately  |
| 3    | Height of each byte measured separately |

| Domain | Units |
| --- | --- |
| 0 | World units: convert device width by world-width/device-width and height by world-height/device-height, with integer truncation |
| 1 | Device units |

Other mode/domain values reject the command. Per-byte results are independent character measurements, not cumulative positions or Unicode code-point measurements. Full-string measurements use the driver’s current font metric routines, so they need not equal a sum of independently measured bytes.

Except for a case-insensitive exact `$TEXTDATA$` argument, the handler copies at most 1023 input bytes, NUL-terminates the copy, expands text variables with a 1022-byte expansion limit and stores the result as the retained `$TEXTDATA$`. The exact sentinel instead measures the previously retained text without replacing it.

The engine replies with signed decimal numbers, independently of Base Math. Each result is narrowed to signed 16 bits; world conversion also uses signed 16-bit values. Modes 0/1 return `number\r`. Modes 2/3 return `number:number:…\r`, with no trailing colon. Here `\r` denotes one CR byte. RIPtel’s client output layer can add LF after CR according to its line-ending configuration; this translation is separate from the engine’s reply format.

A literal empty text argument in extended-font mode produces **no reply**. In system-font mode it follows the metric routines normally: width mode returns zero, height mode returns that font’s empty-string height, and per-byte modes return a bare CR. A nonempty expression expanded to empty text still reaches the metric/reply path in extended-font mode; the early empty check tests the original argument. The outline-font initialization call’s return value is not checked before metric queries, so a reply alone is not proof of successful font loading.

For a controlled font with width 3 per byte and height 7, querying `ab` in device domain returns `6\r`, `7\r`, `3:3\r` or `7:7\r` for modes 0..3. With world/device ratios of 2, world-domain replies are `12\r`, `14\r`, `6:6\r`, `14:14\r`. These are original-handler test oracles with synthetic font metrics, not pixel measurements of a shipped typeface.

**Format:** `!|1T <x1> <y1> <x2> <y2> <res>` **Example:** `!|1T0F3M434G00`

This command defines a rectangular portion of the graphics viewport that is to display text, usually a long stream of text. Following this command should be a number of [RIP_REGION_TEXT](#rip_region_text) commands with the text to be displayed. The [RIP_END_TEXT](#rip_end_text) terminates this stream of text, something like this:

```text
RIP_BEGIN_TEXT

     RIP_REGION_TEXT
     RIP_REGION_TEXT

     RIP_REGION_TEXT

```

There must be at least one RIP_REGION_TEXT command in between the header and the footer. There may be as many as needed.

These commands ignore the current font "direction"; all text is always displayed horizontally in the current font type, style and size. _(v2.A3)_

**3.x extension (DLL-confirmed):** The trailing digits are separate one-digit global column and article identifiers, each 0..35. NEWS.RIP uses `01`, `11`, `21`, `31` for columns 0..3 of article 1. ## RIP_REGION_TEXT

_Display a line of text in rectangular text region_

|               |                             |
| ------------- | --------------------------- |
| **Level**     | 1                           |
| **Command**   | `t`                         |
| **Arguments** | `justify:1` and text-string |

**Format:** `!|1t <justify> <text-string>` **Example:** `!|1t1Southern California was pounded`

**Attributes used:** Draw Color, Write Mode, Font Style, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/3.0-text-output-and-fonts.md#rip_region_text)) · HLP (`RIP_RegionText`) · corpus (42 uses in N2_TITLE.RIP) · SyncTERM (ripper.c:16623)

A number of these commands may come sandwiched between the [RIP_BEGIN_TEXT](#rip_begin_text) and [RIP_END_TEXT](#rip_end_text) commands. The `<text-string>` should already word-wrapped in such a way that it will fit inside the rectangular region based on the current font, font size, and drawing color.

There are four possible settings for the `<justify>` parameter: _(v2.A3)_

| Justify | Description                         |
| ------- | ----------------------------------- |
| 0       | Left justify this line              |
| 1       | Right/left "full" justify this line |

If a text line falls off the bottom of the region, it is discarded -- the rectangular Text Region does not scroll.

This command is intended to import some sort of text file document directly into a RIPscrip scene and format it nicely to fit inside a simple rectangular area. If the `<justify>` parameter is set to a value of "1" for a given RIP*REGION_TEXT line, then that line will be justified to both the left and right margins (the RIP_BEGIN_TEXT boundaries). This is so that the displayed text aligns on both sides with the invisible boundaries. This "justification" is done by splitting each RIP_REGION_TEXT line up into chunks of word-groups, broken up at their "white-space" locations. Each spacer is then padded by however many pixels are necessary to keep each spacer of approximately equal size. Only enough spare pixels are added to make sure that the right-edge of the text region aligns with the right border of the boundary. The result is a nicely formatted text block. *(v1.54)\_

The corpus uses justify `1` for body lines and `0` for each paragraph's final line - N2_TITLE.RIP's article, quoted in full in the [census](../../3.0/research/riptel-script-census.md), is a TeleGrafix pitch for RIPscrip's JPEG/sound/24-bit future.

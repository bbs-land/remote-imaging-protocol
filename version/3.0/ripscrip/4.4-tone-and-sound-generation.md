# 4.4 Tone & Sound Generation

[◀ Prev: 4.3 Buttons](4.3-buttons.md) · [Contents](README.md) · [Next: 4.5 Audio Files (WAV) ▶](4.5-audio-files.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

The Active [Text Variables](5.1-text-variables.md) below request synchronous tones. This chapter specifies the requests made by **RIPtel 3.1's original RIPscrip 3.0.7 driver**, including its differences from the inherited [1.54](../../1.54/ripscrip/4.3-tone-and-sound-generation.md) and [2.0](../../2.0/ripscrip/4.4-tone-and-sound-generation.md) recipes. Earlier-version reference and verbatim text remain separate historical records. Exact device waveform reproduction is outside this contract. [WAV playback](4.5-audio-files.md) is a separate capability.

A terminal that omits a sound should still recognize its variable and consume it as an action, as explained in [5.1](5.1-text-variables.md). The summary is in [9.1](9.1-text-variable-reference.md#sounds-active).

**Primary evidence:** original registered callbacks, numeric validation and synchronous `Beep(frequency,duration)` requests, captured without playing audio. Exact addresses, source hashes, native matrices and controlled-service limits are in the [tone derivation](../research/issue-28-tone-variable-contract.md). The inherited draft, help strings and SyncTERM are not executable oracles for these shipped sequences.

## Sound Related Text Variables

Frequencies are in **Hz** and durations in **milliseconds**. Successful actions return no characters. Invalid arguments set the variable error and issue no tone: they do **not** play a default effect. In ordinary text expansion the invalid expression remains literal. The callback ignores the audio service's success/failure return; an unsuccessful audio request does not itself make the text variable invalid.

| Variable | Argument count | Defaults for omitted trailing arguments | Shipped request |
| --- | --- | --- | --- |
| ALARM | 0 or 1 | count=3 | Two tones per repeat |
| BEEP | 0..2 | frequency=1000, length=75 | One tone; no added gap |
| BLIP | 0..2 | frequency=1000, length=25 | One tone; no added gap |
| MUSIC | 0 or 1 | count=4 | Six tones per repeat |
| PHASER | 0..4 | start=2500, stop=50, increment=20, time=2 | Descending sweep |
| REVPHASER | 0..4 | start=50, stop=2500, increment=20, time=2 | Ascending sweep |
| T | Exactly 2 | None | One tone; no added gap |

Supplied numeric fields must fit **0..65535**; negative, nonnumeric, oversized or extra fields reject the action. BEEP/BLIP/T forward zero frequency or duration to the audio service without a macro error. ALARM/MUSIC accept count zero as no requests. Sweep increment and time must instead be **1..65535**, and their strict endpoint ordering is checked before any tone. Defaults apply only to omitted trailing arguments, not to invalid values. _Evidence: original callbacks and exhaustive simple-tone WORD/boundary/arity matrices; [derivation](../research/issue-28-tone-variable-contract.md)._

The pseudocode uses `tone(hz, ms)` for one synchronous request. It has no implicit trailing silence. The callbacks do not insert the inherited BEEP 75 ms or BLIP 10 ms gaps, nor a separate gap between repeated notes. Actual audio-service timing is not specified.

### $ALARM$

_Warning/failure sound_

**Format:** `$ALARM(count)$`

**Syntax:** `$ALARM$` or `$ALARM(count)$`, count **0..65535**, default **3**.

Each repeat requests **320 Hz for 200 ms**, then **160 Hz for 225 ms**. The inherited second duration 425 ms is not the shipped value.

```c
for (unsigned i = 0; i < count; ++i) {
    tone(320, 200);
    tone(160, 225);
}
```

**Example:** `$ALARM(3)$` is equivalent to `$ALARM$`. **Returns:** nothing.

_Evidence: original callback 0x8600 and captured count/default sequences; [derivation](../research/issue-28-tone-variable-contract.md)._

### $BEEP$

_Beep sound_

**Format:** `$BEEP(frequency,length)$`

**Syntax:** `$BEEP$`, `$BEEP(frequency)$` or `$BEEP(frequency,length)$`; each supplied field **0..65535**. Defaults: **1000 Hz**, **75 ms**.

```c
tone(frequency, length);
```

RIPtel 3.1 adds **no explicit 75 ms silence** after this request. The inherited draft specifies such a gap, but the original callback has only the single tone call. With both arguments supplied, BEEP and T make identical requests; their difference is that BEEP permits omissions and T does not.

**Example:** `$BEEP(1000,75)$` is equivalent to `$BEEP$`. **Returns:** nothing.

_Evidence: original callback 0x868e and native request captures; [derivation](../research/issue-28-tone-variable-contract.md)._

### $BLIP$

_Blipping/barrier sound_

**Format:** `$BLIP(frequency,length)$`

**Syntax:** `$BLIP$`, `$BLIP(frequency)$` or `$BLIP(frequency,length)$`; each supplied field **0..65535**. Defaults: **1000 Hz**, **25 ms**.

```c
tone(frequency, length);
```

The original driver uses 1000 Hz, rather than the inherited 50 Hz default, and adds **no explicit 10 ms silence**. The inherited example `$BLIP(50,10)$` is a valid custom request but is not equivalent to the parameterless effect. Its default duration is 25 ms.

**Example:** `$BLIP(1000,25)$` is equivalent to `$BLIP$`. **Returns:** nothing.

_Evidence: original callback 0x873a and native default/argument captures; [derivation](../research/issue-28-tone-variable-contract.md)._

### $MUSIC$

_Musical success sound_

**Format:** `$MUSIC(count)$`

**Syntax:** `$MUSIC$` or `$MUSIC(count)$`, count **0..65535**, default **4**.

Each repeat requests these **six** notes, in this order:

| Note | Frequency (Hz) | Duration (ms) |
| ---- | -------------- | ------------- |
| 1    | 1125           | 17            |
| 2    | 775            | 14            |
| 3    | 625            | 10            |
| 4    | 725            | 14            |
| 5    | 825            | 10            |
| 6    | 600            | 25            |

```c
for (unsigned i = 0; i < count; ++i) {
    tone(1125, 17);
    tone(775, 14);
    tone(625, 10);
    tone(725, 14);
    tone(825, 10);
    tone(600, 25);
}
```

The requested durations total **90 ms per repeat**. This shipped sequence supersedes the inherited nine-note recipe for this reconstructed v3 reference. SyncTERM's three swept segments are not an equivalent sequence and do not establish RIPtel 3.1 behavior.

**Example:** `$MUSIC(4)$` is equivalent to `$MUSIC$`. **Returns:** nothing.

_Evidence: original callback 0x87e6 and exact native sequence/count captures through count 65535; [derivation](../research/issue-28-tone-variable-contract.md)._

### $PHASER$

_Descending frequency sweep_

**Format:** `$PHASER(start,stop,increment,time)$`

**Syntax:** **0..4 positional arguments**, with omitted trailing defaults **(2500,50,20,2)**. START/STOP must fit **0..65535**, **START > STOP**, INCREMENT and TIME must be **1..65535**. Thus START is at least 1; STOP may be zero, subject to the shipped wrap defect below.

For ordinary inputs that terminate without WORD wrap, the requests are `start, start-increment, ...` while frequency is **≥stop**, each for `time` ms. The stop frequency is included only if a step lands exactly on it. The default makes **123 requests**, **2500,2480,...,60 Hz**, each **2 ms**.

Invalid ordering, zero increment, zero time, out-of-range/nonnumeric fields or more than four fields produce a variable error **before any request**. They do **not** fall back to (2500,50,20,2). For example, `$PHASER(1,2)$` and `$PHASER(2500,50,20,0)$` produce no sound. `$PHASER(3000)$` retains the other three defaults.

**Example:** `$PHASER(2500,50,20,2)$` is equivalent to `$PHASER$`. **Returns:** nothing on success.

_Evidence: original callback 0x8892, complete optional-suffix tests and boundary matrices; [derivation](../research/issue-28-tone-variable-contract.md)._

### $REVPHASER$

_Ascending frequency sweep_

**Format:** `$REVPHASER(start,stop,increment,time)$`

**Syntax:** **0..4 positional arguments**, with omitted trailing defaults **(50,2500,20,2)**. START/STOP must fit **0..65535**, **START < STOP**, INCREMENT and TIME must be **1..65535**. START may be zero; STOP is at least 1.

For ordinary inputs that terminate without WORD wrap, the requests are `start, start+increment, ...` while frequency is **≤stop**, each for `time` ms. The stop frequency is included only if a step lands exactly on it. The default makes **123 requests**, **50,70,...,2490 Hz**, each **2 ms**.

Invalid inputs set the variable error before any tone, with **no fallback to defaults**, just as for PHASER. The inherited descending description and START>STOP requirement are incorrect for REVPHASER.

**Example:** `$REVPHASER(50,2500,20,2)$` is equivalent to `$REVPHASER$`. **Returns:** nothing on success.

_Evidence: original callback 0x89d2 and native ordering/default/boundary captures; [derivation](../research/issue-28-tone-variable-contract.md)._

#### Shipped Sweep Arithmetic Defect

Both callbacks use an **unsigned 16-bit frequency accumulator**, including their update and loop comparison:

```c
uint16_t f = start;
while (descending ? f >= stop : f <= stop) {
    tone(f, time);
    f = (uint16_t)(descending ? f - increment : f + increment);
}
```

A step can wrap rather than finish a sweep. With descending STOP=0, or ascending STOP=65535, the loop cannot pass its exit test. Other steps can also cycle if their modulo-65536 progression never reaches a value beyond the stop. This is a shipped implementation defect, not fallback-to-default behavior. Native verification bounds execution after 65536 requests; implementors should bound this defect rather than reproduce an endless audio loop. The usual default sweeps terminate without wrapping. _Evidence: original WORD instructions and bounded modular sequence captures; [derivation](../research/issue-28-tone-variable-contract.md)._

### $T$

_Play one audio tone_

_Added in RIPscrip v2.A4._

**Format:** `$T(frequency,length)$`

**Syntax:** **Exactly two required parameters**, each **0..65535**. The inherited optional/default syntax is not implemented: `$T$` and `$T(1000)$` set the variable error and issue no tone.

```c
tone(frequency, length);
```

T adds no explicit trailing silence. In RIPtel 3.1, `$T(1000,75)$` and `$BEEP(1000,75)$` request the same one tone, and the latter is also the default BEEP request. Their documented older-client gap distinction is not present in this driver's callbacks.

**Example:** `$T(1000,75)$`. **Returns:** nothing on success.

_Evidence: original callback 0x8b0d, original registration and full expansion/arity/WORD-boundary tests; [derivation](../research/issue-28-tone-variable-contract.md)._

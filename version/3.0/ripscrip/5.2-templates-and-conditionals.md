Templates - the Host Command Language's mechanism for _building_ [host commands](5.0-host-commands.md) out of pieces, which the White Paper calls "a cookie-cutter approach to host commands," constructed from whichever buttons are selected and which are not. RIPtel 3.1 retains slot templates and adds a macro/conditional preprocessor (`<<NAME>>`, `<<IF>>…<<ELSE>>…<<ENDIF>>`). The original driver now establishes their processing order and shipped exceptions; inherited template examples below describe the intended design where the documented chaining defect prevents reliable shipped output.

## Shipped Processing Order

_Evidence: RIPtel 3.1’s RIPscrip 3.0.7 DLL; [source locations, controlled fixtures and native oracles](../research/issue-6-macro-evaluation.md). These rules establish the executable contract independently of SyncTERM._

The driver has two stages with different rescan rules. Preprocessing handles angle macros/conditionals; ordinary expansion handles dollar variables, slot embedding and enabled host directives. The number of ordinary passes depends on the consumer.

| Consumer | Sequence |
| --- | --- |
| Ordinary graphical text | Preprocess its argument, then make one ordinary expansion pass before drawing |
| `RIP_TEXT_METRIC` | Preprocess, then one ordinary pass permitting data callbacks but no direct user-variable fallback; `<<NAME>>` can still supply a user value during preprocessing |
| Host-command execution | Preprocess the host-command string, split/handle command blocks and templates, then make exactly two ordinary passes on each resulting response before transmission |

A button's third payload slot is [stored host source](4.3-buttons.md#creation-and-deferred-host-validation), not an ordinary graphical-text argument evaluated at definition. Its pure preflight does not run this host pipeline or reject a suffix that the established execution stages never reach. The separate filename/label slots keep their normal rendering consumers.

Graphical filename, label, T/@ and metric arguments have the [consumer-specific permission, byte and continuation contract](#graphical-consumer-expansion). Host execution additionally enables active-only callbacks, ordinary slot embedding, playback and control decoding. Descriptive Value/Active labels are not permission masks: some mixed setters are callable in graphical contexts and others are not. A newly inserted dollar result does not restart the angle stage.

Pick lists are enabled in **both ordinary HCL passes**: the first-pass mask defers controls/backslashes, not modal selection. Their [complete parser/pass profile](5.4-popup-lists.md#ordinary-passes-and-transmission) splices a selected original response and skips it in that pass; there is no fresh recursion or early response-prefix transmission. Pass-two selections receive no third pass.

Within **one ordinary pass**, scan from left to right. A successful variable or `$?N$` expansion replaces the reference and continues **after the inserted text**, so new codes in that insertion are not evaluated during the same pass. Active variables can perform an action and insert no text. A known built-in rejected for invalid arguments does not become a user-variable lookup. The [overflow boundary abort](3.1-column-text-system.md#pagination---overflow-and-resetoverflow) stops ordinary expansion before following codes in that pass.

For host responses, the first ordinary pass defers control-character decoding and backslash processing; the second uses the full caller feature set. This defers the outer scanner only: [dollar-argument local quoting](5.1-text-variables.md#enclosing-ordinary-passes) still runs in the first pass, and an outer backslash there does not shield the following dollar from lookup. [Exact control/bracket rules](5.0-host-commands.md#control-characters) distinguish complete bracket directives recognized before these passes from literal brackets and later-emitted control bytes; an ESC never suppresses template recognition. This permits one additional layer of dollar/template expansion, not unrestricted recursion:

| Given definitions | Input | Observed host text |
| --- | --- | --- |
| A=`$B$`, B=`$SHIFT$` | `$A$` | Literal `$SHIFT$` after two passes; no third pass |
| Template 3=`$SHIFT$`, Shift down | `$?3$` | `1` |
| Template 4=`$?3$`, template 3=`$SHIFT$` | `$?4$` | Literal `$SHIFT$` |
| A=`<<N>>`, N=`X` | `$A$` | Literal `<<N>>`; preprocessing has already finished |

These are controlled original-instruction oracles, not demo-corpus strings. Applying only one ordinary pass to A=`$SHIFT$`, input `$A$`, leaves literal `$SHIFT$`.

### Graphical Consumer Expansion

_Evidence: bounded read-only original caller flags, registration/evaluator gates and renderer order; [derivation](../research/issue-124-graphical-expansion.md). The byte-bound and continuation rules explicitly complete cases not fully determined by the sources. This section applies to RIPscrip 3.0; it leaves host responses and 1.54 unchanged._

| Consumer | Angle preprocessing | Ordinary pass | Working/final limit L |
| --- | --- | --- | --- |
| Nonempty `1U` filename, including the common first slot on non-ICON types | Enabled | One; eligible built-ins and user forms | 255 bytes |
| Nonempty `1U` label | Enabled | One; eligible built-ins and user forms | 255 bytes |
| Ordinary graphical `T` / `@` text | Enabled | One; eligible built-ins and user forms | 1022 bytes |
| `TEXT_METRIC` argument | Enabled | One; eligible built-ins, **no ordinary user fallback** | 1022 bytes |

The exact case-insensitive metric sentinel `$TEXTDATA$` instead measures its already retained text: do not preprocess/expand it again. Empty filename/label slots skip their own expansion. An empty resulting filename cannot supply an ICON image; a non-ICON button still uses its chosen face type. Only the first two literal payload delimiters split the raw slots; later inserted `<>` bytes do not split them again. The [stored host slot](4.3-buttons.md#creation-and-deferred-host-validation) remains opaque throughout creation and redraw.

#### Eligible Providers and Rejected Codes

**Source-derived gate:** each graphical ordinary pass, angle named lookup and evaluated conditional operand permits callbacks in either of these complete original registration sets, case-insensitively. These sets describe permission, not a promise that every callback returns text or is implemented by a partial client:

| Registration class | Eligible names |
| --- | --- |
| Data-capable (64 names) | ADOW, AMPM, BACKSTAT, CDCS, COLORS, CTRL, CURSOR, DATE, DATETIME, DAY, DOW, DOY, FIELDID, FILEEXISTS, FYEAR, HOUR, IFS, INUSE, ISPALETTE, ISPROT, LANG, M, MHOUR, MIN, MONTH, MONTHNUM, MSTAT, PALENTRY, RAND, RESX, RESY, RIPVER, SEC, SHIFT, STATBAR, TERMINFO, TEXTXY, TIME, TIMEZONE, TWFONT, TWGOTO, TWH, TWIN, TWW, TWX0, TWX1, TWY0, TWY1, PORTH, PORTW, PORTX0, PORTX1, PORTY0, PORTY1, WDAY, WORLDH, WORLDW, WOY, WOYM, X, XY, XYM, Y, YEAR |
| Mixed data/active (20 names) | BASEMATH, BAUDEMUL, BSMODE, BSXMIT, CHARSET, COLORMODE, COORDSIZE, CUR, CURX, CURY, DCS, HOSTDIR, IMGSTYLE, ISEXTWIN, MCURSOR, NULL, OFFSCREEN, OPTION, OVERFLOW, SDCS |

Apply each eligible callback's own argument/protection/failure rules. A setter is **not** prohibited merely because its result is empty: valid `CUR`, `COORDSIZE`, `OVERFLOW`, `HOSTDIR`, WORLDH/WORLDW and other setters in these sets retain their actions. **WORLD itself is active-only**, so both `$WORLD(CUR)$` and `$WORLD(CUR,1600,1200)$` are blocked here despite its descriptive Value/Active entry. MKILL and every other recognized original built-in outside the sets are likewise blocked. This distinction controls over the historical flow chart or the index's descriptive Type column.

| Syntax or outcome | Graphical behavior |
| --- | --- |
| `<<NAME>>` | Enabled; synthesized `&` lookup uses the same eligible built-in gate, otherwise the adopted user-variable rules |
| `<<?N>>` | Enabled angle-template lookup; existing worker rescanning/conditional rules apply |
| Conditional operands | Same eligible built-ins and user providers; existing branch eligibility/validation rules govern which providers run |
| Ordinary `$NAME$`, `&`, define/default/storage/prompt/format directives | Allowed for filename/label/T/@; retain the [complete user prompt/effect matrix](5.1-text-variables.md#prompt-and-effect-matrix), including missing `&` prompts |
| Ordinary unknown user name in TEXT_METRIC | Keep literal reference; no ordinary prompt, assignment or storage operation. Its angle stage may still obtain a user value |
| Ordinary `$?N$` | Disabled; keep the complete token literal, without reading/expanding that slot |
| Playback prefixes `$>…$`, `$)…$`, `$<…$`, `$(…$` | Disabled; keep literal, with no playback or user fallback |
| Ordinary recognized but disallowed, invalid/rejected, or unavailable built-in | Keep the reference bytes literal and continue after it; no same-name user fallback, no invented action or mandatory dialog |
| Successful callback with zero replacement bytes | Remove the token and continue; earlier callback effects remain |
| Hard provider abort, structural/preprocessing failure | Stop this rendering operation; do not scan its remaining suffix or run a host slot |

**Explicit disabled-feature completion:** reserve recognized built-in/special tokens before considering user fallback. An unavailable implementation of a known callback cannot turn `$MUSIC$`, a playback token or another reserved name into a user question. A genuinely unknown ordinary name remains a user variable where that consumer allows it. A failed angle provider rejects preprocessing under its existing rules rather than copying the unresolved angle bytes into final output. Nonfatal diagnostics may be recorded internally; none of these failures terminates the connection. The host consumer's own feature/error behavior remains separate.

#### Graphical Byte and Escaping Policy

**Explicit portable prefix policy:** the raw `1U` filename/label maxima remain **127/255 bytes**, checked before providers; excess rejects pure preflight rather than truncating those raw slots. For T/@ and metric, the original initial copy retains at most 1023 bytes. For each graphical consumer above, then enforce its own L at expansion entry, **after every replacement/removal and before further scanning**, throughout angle preprocessing as well as the ordinary pass. Keep only the first L bytes of the complete current working text. The resulting post-angle text, ordinary intermediate text and final consumer argument all fit L; filename extension/path preparation happens afterward under the existing file rules. The host response's 4096-byte cap is not substituted here. In particular, the native preprocessor's hard-coded 4096 call does not enlarge this profile's graphical limit.

Count bytes, excluding storage NUL, not Unicode characters or eventual glyphs. For each raw argument, template or provider value, use its prefix before the first NUL; discard bytes after that NUL **in that input/value**. A NUL in one replacement value does not discard the retained source following the reference. Encoded backslashes/control spellings count until consumed. A clipped suffix never executes or reappears after later shrinking; effects already completed by the callback causing growth are retained. A callback still present in the retained suffix can execute normally. Clipping can leave incomplete angle/dollar syntax, to which that stage's ordinary syntax rules apply; do not pre-scan a discarded suffix for errors or actions.

All four ordinary consumers enable **outer backslash quoting**, but disable the host control-pair decoder: one backslash removes itself and skips recognition of the following byte for that pass; a trailing backslash is removed. Thus `\$NAME$` emits literal `$NAME$`, doubled backslashes emit one, and `^M`, backtick-M, `^^` and doubled backticks stay spelled as supplied. Filename paths are subject to the same outer quoting; a backslash already present in an inserted value is skipped with that value. Dollar-argument local quoting remains its separate parser rule. Angle introducer quoting/rescanning follows the existing angle worker contract, not a universal backslash removal before every stage.

One ordinary pass resumes **after** inserted values/templates; it does not interpret their new dollars, outer backslashes, control pairs or angle directives. Angle insertion uses its own existing named-versus-template rescan rules first. There is no second ordinary pass for any consumer in the table.

#### Creation, Redraw and Prompt Continuations

**Explicit portable lifetime/failure completion, preserving the observed stage order:**

1. Run the adopted pure `1U` preflight before providers or painting. Freeze the field's style/font attributes, creation WORLD, geometric inputs and effective destination identity/generation before filename expansion. Completed setters can change live tables/environment for later providers/commands, but cannot retroactively reflow this pending field. This does not freeze user values, image contents or future lookup results.
2. Expand the common filename slot once, then prepare/resolve it and choose/load an image under the existing normal/hot/fallback rules. Finish natural image geometry from that initially chosen image. Non-ICON types still prepare a nonempty first slot without turning it into an icon face. A filename-stage hard failure precedes new face/effect painting.
3. Render face/effects, and perform requested auto-stamp capture and its existing clipboard/current-style mutation. Expand and render the label afterward; a requested capture must succeed first. Thus a label prompt can occur with the face already painted, the clipboard changed and auto-stamp flags already written. It is not part of pure preflight.
4. Store the original filename/label **sources**, not just a globally cached expansion. Repeat a nonempty filename's common preparation and a nonempty label's expansion whenever their renderer stages actually run on creation or redraw, using then-current variables, while retaining the instance's captured geometry/font/style/destination. An auto-stamped field follows its now-CLIPBOARD type; re-expanding an old filename does not force an icon load or a fresh auto-capture. A redraw taking an earlier restore/skip path need not evaluate later stages it never reaches.

A permitted user prompt suspends that specific continuation without holding renderer/table locks. Keep owned source/working bytes, scan offset, captured drawing state and stable instance/destination generations. Resume once at the suspended lookup after success or the [documented cancellation](5.1-text-variables.md#empty-input-cancellation-and-no-output): ordinary cancellation supplies `NONE`, transparent cancellation supplies no text, neither writes storage; successful empty and `*` rules remain adopted. These are normal lookup outcomes, **not** an automatic cancellation of creation or a held gesture. A separate hard abort stops rendering. Never restart prior stages/providers or repeat auto-stamp merely because a prompt completed.

Serialize subsequent interpreter/input dispatch behind the suspended continuation; retain physical release/cancel information against the original capture token and process it in order before a later activation. Reset/deletion/destination replacement invalidates suspended drawing immediately. The [auto-stamp same-destination guard](4.3-buttons.md#auto-stamp-geometry-and-redraw) prevents replacing the destination during capture; a legacy helper's PORT0 fallback does not authorize rebinding a label continuation. On resume, abandon a stale instance/destination without painting, restoring old feedback onto a replacement or admitting a pending field into a new scene. A held redraw that survives resumes the same gesture; its later inside/outside release decides commitment under the existing pointer rules. An already committed keyboard/release action retains its snapshot and once-only host continuation even if optional feedback fails or its field disappears. Prompt completion never synthesizes a click/repeat, transfers capture or forwards a consumed key.

A pending new field becomes input-eligible only after successful creation rendering. Later provider/font/file/capture failures admit no new field, but do **not** undo completed user-variable effects, painted pixels, palette/file effects, clipboard capture or style writes. For existing fields, redraw failure does not delete their definition or roll back already committed selection/action state; remove temporary feedback safely only from the surviving original instance. Preserve live setter effects when restoring private drawing context. T/@ hard expansion failure draws none of that argument; metric hard expansion failure sends no metric reply. Already completed providers/retained TEXTDATA assignments are not rolled back by a later font/metric failure; the metric entry's cached-font/result rules still apply. None of this executes the third host slot as a rendering test. Rendering itself creates no FIELDID activation scope; existing outer callback scopes remain in force. Recheck field capacity and destination/scene generation before admitting a suspended creation; failure cannot evict an earlier field to make room.

#### Independent Graphical Vectors

Assume RESX=`800`, user variable V=`$RESX$`, slot 3=`$RESX$`, slot 4=`$?3$`, and use an ordinary filename/label/T/@ consumer unless stated otherwise. Each backslash below is one actual input byte.

| Source / condition | Result |
| --- | --- |
| `$&V$` | Literal `$RESX$`; insertion skipped in the only ordinary pass |
| `\$V$` | Literal `$V$`; no V lookup in that pass |
| `$?3$` | Literal `$?3$`; ordinary embedding disabled |
| `<<?3>>` | `800`: angle insertion supplies `$RESX$` for the one ordinary pass |
| `<<?4>>` | Literal `$?3$`; no second ordinary pass/ordinary embedding |
| `$WORLD(CUR,1600,1200)$after` | Literal complete source; no WORLD change, no user fallback; `after` continues |
| `$MKILL$after` | Literal `$MKILL$after`; no field deletion |
| `$HOSTDIR(OFF)$after` | Clear host directory, emit `after`; a successful empty setter result is consumed |
| `$>SCENE.RIP$after` | Literal complete source; no playback or filename-as-user lookup |
| Ordinary unknown `$&V$` in metric | Literal `$&V$`, without ordinary lookup; `<<V>>` in metric can instead obtain V and then expand its `$RESX$` to `800` |
| `^M` followed by doubled backticks | Literal spellings, not CR/backtick decoding |

For a **255-byte raw label**, use `$&BIG$` (6 bytes) followed by 249 `x` bytes. If BIG is 255 `A` bytes, the result is exactly 255 `A` bytes; the original suffix is permanently gone. For `$&BIG$$-=SIDE=Y$`, the same growth discards the assignment before it can execute. Conversely if BIG is 245 `A` bytes and the suffix is `$CUR(BUT)$` (10 bytes), that complete retained getter can execute normally. For a provider value `A`, NUL, `$MKILL$`, only `A` is inserted; a following retained source `Z` still yields `AZ`.

With AUTO-STAMP enabled and label `$&MISSING$`, an absent MISSING without a default prompts **after** successful capture. Accepting `Ready` draws Ready and completes the pending field; canceling this transparent lookup draws no label and still completes it, leaving storage unchanged. A hard provider abort instead admits no new field, while the captured clipboard/style changes and painted face remain. On a held existing button, ordinary prompt cancellation is likewise not an outside release; a subsequently recorded inside release still commits once if that same field survives.

After successful auto-stamp, a missing permitted label variable with no transparent flags can prompt. Accepting `Hi` resumes only label rendering and then admits the new field; ordinary cancel renders `NONE` and also continues. A transparent cancel yields an empty label. A hard provider abort leaves completed capture/style/pixels intact, admits no new field and never runs the host slot. The same lookup can prompt again on a later actual label redraw; release/cancel/deletion during suspension obeys the stable-token continuation rules above. These are documentary/policy vectors, not original client executions.

### Response and Embedding Byte Limit

**Explicit portable policy, resolving [issue #93](https://github.com/bbs-land/remote-imaging-protocol/issues/93):** the inherited specification supplies the 4096-byte final embedding/chaining limit but does not completely define its timing or discarded-suffix effects. The following enforcement/storage rules complete that contract; they are not a claim of reproduced native overflow behavior. The [derivation and independent boundary vectors](../research/issue-93-template-embedding-limits.md) distinguish source constraints from these choices.

For each individual host **response block**, set `L=4096`. After the existing preprocessing/bracket/template-composition stages, truncate that response to its first L bytes **before the first ordinary pass**. This also applies to a direct response containing no embedding. Run exactly the two ordinary passes already specified. During either pass, every successful replacement (slot embedding or another dollar result) is immediately clipped as follows, **before scanning the remaining source**:

```text
old = prefix + reference + suffix
new = first_L_bytes(prefix + replacement + suffix)
resume_at = byte_length(prefix) + min(byte_length(replacement), L - byte_length(prefix))
```

The retained inserted bytes are skipped for the rest of that pass, as before. Resume scanning only the retained suffix; if the replacement fills the remaining capacity, there is no suffix to scan. Implementations can copy only the needed prefixes rather than allocating an excessive temporary string. Keep the working string bounded after every change and at each pass boundary; no separate final-output-only budget replaces these earlier checks.

The limited quantity is **the current working text's bytes**, excluding storage NUL. Before pass two this includes still encoded control/backslash spellings. During pass two it includes any already decoded prefix and unprocessed encoded suffix. It is not a count of Unicode characters, decoded final payload alone, the original input length alone, or the aggregate bytes of a session/multiple response blocks. The final second-pass result therefore contains at most L bytes before any separate client-configured transport/newline translation.

Truncation discards the tail permanently. A dollar callback/playback/assignment wholly in that discarded tail **does not execute in either pass**. A complete callback still present in the retained suffix executes when the normal scanner reaches it; exceeding the limit does not unconditionally stop all retained work. The callback whose result caused growth has already been evaluated normally; clipping its output does not undo its own side effects. Earlier preprocessing, bracket definitions, prior blocks or already completed callbacks are likewise not rolled back. If later decoding/replacement shortens the string, previously discarded bytes never reappear.

Clip bytes exactly, without moving the boundary to preserve an escape or reference. An incomplete retained dollar reference follows the ordinary syntax-failure rules and cannot fetch its missing terminator from discarded bytes or invoke a partial callback. A trailing caret/backquote remains literal under the existing control rules. **Explicit edge choice:** a trailing outer backslash, including one left by clipping, remains one literal backslash; when a following byte exists, the existing pass-two rule removes the backslash and skips that following byte as literal. This does not alter argument-local dangling-escape rejection. No prefix is repaired, padded or decoded early to make more room. Truncation itself is nonfatal.

#### Stored Templates and Composition

**Explicit storage policy:** retain at most the first 4096 bytes of each individual stored template definition whenever it is assigned or replaced. Count the unexpanded ordinary body bytes, including dollar/template/control/backslash notation, after whatever earlier preprocessing the existing stage order already performed. Template delimiters/slot number and storage NUL do not count. Store that capped definition for future use. When selected checkbox contributions form an effective slot body, cap the assembled result at the same bound before insertion; this does not delete the underlying button definitions or change selection/activation. Required radio-group rules remain unchanged.

The existing chain composition limit and intended chain correction remain in force **before ordinary response expansion**. This section does not turn chain composition into a new ordinary pass or repeat angle preprocessing/segmentation on inserted text. The inherited eight angle-pass limit is unchanged. The response cap here does not impose a new limit on an entire RIP scene or on graphical text consumers.

#### Boundary and Side-Effect Vectors

All vectors start at the stated storage/response stage, assume the ordinary operation is otherwise valid/permitted, and use ASCII `X` bytes; lengths exclude storage NUL. They are policy calculations, not native probes.

| Input / definition | Stored or transmitted result |
| --- | --- |
| Direct response of 4095 X bytes | 4095 X bytes |
| Direct response of 4096 X bytes | 4096 X bytes |
| Direct response of 4097 X bytes | First 4096 X bytes, even without embedding |
| Define slot 3 with 4095 / 4096 / 4097 X bytes | Store respectively 4095 / 4096 / 4096 X bytes |
| Slot 3 = 4095 X bytes; response `$?3$Y` | 4095 X bytes plus Y: 4096 bytes |
| Slot 3 = 4096 X bytes; response `$?3$Y` | 4096 X bytes; Y is discarded during pass-one insertion |
| Slot 3 = 4096 X bytes; response `$?3$$D(1)$$-=FLAG=changed$` | 4096 X bytes; no D delay request, no assignment and FLAG unchanged |
| Slot 3 = `ABCDE`; response `$?3$$D(1)$` followed by 4086 X bytes (4096 source bytes) | Insertion clips the final X, retains D; D runs in pass one, then output is `ABCDE` plus 4085 X bytes (4090 bytes) |
| Slot 3 = `$?4$`, slot 4 = 4096 X bytes; response `$?3$Y` | Pass one leaves `$?4$Y`; pass two inserts/clips to 4096 X bytes, with no third pass |
| Slot 3 = 4092 X bytes followed by `$?4$` (4096 bytes), slot 4 = `Z`; response `$?3$Y` | Pass one discards Y; pass two produces 4092 X bytes plus Z (4093 bytes). Freed space does not restore Y |

For a control-boundary distinction, slot 3 contains 4094 X bytes followed by **two raw bytes** `^m` (total 4096), and the response is `A$?3$`. Pass one insertion produces 4097 bytes before clipping, retaining A, 4094 X bytes and a final caret. Pass two leaves that caret literal: the 4096-byte result ends in **`0x5e`**, not a carriage return. Decoding before clipping would instead retain `0x0d`, so it is a different policy.

For a backslash boundary, replace that raw `^m` pair with backslash followed by Z (`\Z`, again two bytes). The same insertion retains only the final backslash, and the explicit dangling-outer-backslash rule leaves it literal: result ends in **`0x5c`**. Early decoding would instead end in Z (`0x5a`). Parenthesized argument escaping remains a distinct stage, and pass-two inserted results are still skipped during that pass; clipping does not create an additional decoding/rescan pass.

### Angle Rescanning and Limits

`<<NAME>>` synthesizes a silent `$&NAME$` lookup. Its inserted result is scanned again **at the same position within the current preprocessor pass**. Nested named macros can therefore expand immediately: A=`<<B>>`, B=`C`, input `<<A>>` becomes `C`. A checked chain of sixteen names finishes in one pass. Cyclic named substitution is not stopped by the wrapper’s pass count and can loop within a pass; it is not a valid way to request bounded recursion.

The additional angle-template form **`<<?N>>`**, with one MegaNum slot digit, inserts template N but skips its contents for the rest of that pass. Nested angle syntax inside it can run on a later pass. An unavailable required radio-group template follows the usual missing-selection failure path.

The preprocessor makes at most **eight whole passes**, stopping earlier on a stable pass or failure. Reaching eight changed passes still reports success and can leave angle syntax unexpanded. For templates 0=`<<?1>>` through 8=`<<?9>>`, template 9=`END`, input `<<?0>>` becomes `<<?8>>` after one wrapper invocation, and a second invocation reaches `END`. This cap applies to whole passes, not immediate named-macro nesting. Escaped angle introducers are skipped during their current pass; removing an escape does not promise literal preservation through all subsequent passes.

### Outer Angle Scanner and Branch State

_Reconstructed from the unchanged RIPtel 3.1 worker, completed with the explicit portable validation/branch rules marked below; [source bytes, addresses and derivation](../research/issue-96-angle-worker-boundaries.md). This section resolves issue #96 and precedes both conditional operand decoding and ordinary dollar passes._

Work on bytes, with NUL/end of supplied input as the bound. At each cursor position, recognize only `<<` as an angle introducer. A single `<` or an unattached `>>` is ordinary text: retain it in an active branch, discard it in an inactive branch. A recognized introducer without a complete eligible `>>` is a preprocessing error, even in inactive text. Do not infer a missing delimiter from later stages or reinterpret a malformed recognized control as a new independent command block.

#### Special Introducer Escape and Lookahead

Backslash has a special outer-worker role **only when immediately followed by `<<` at the current cursor**. In active text, remove that one backslash, keep both `<` bytes, and resume after those two bytes, so this introducer is not recognized again in the current worker pass. In inactive text, discard all three bytes and continue at their old position; subsequent ordinary bytes remain subject to the inactive branch's deletion. Neither path makes the rest of the text an opaque quoted region. All other outer backslashes are ordinary bytes here; this is not the later generic ordinary-pass unquoting rule.

There is no odd/even backslash-run rule. With two backslashes before `<<`, the first is ordinary and the second escapes the introducer. Removing an escape marks the pass changed: a later wrapper pass can recognize the now-unescaped introducer. This preserves the existing eight-pass rule and does not promise permanent literal quoting.

For an unescaped `<<`, first perform **outer lookahead**, without interpreting quotes or provider arguments:

1. Search from just after `<<` for `>>`. If the byte immediately before a found pair is a backslash, skip that pair and restart searching after both `>` bytes. Otherwise select it as the outer end E. The test is the immediately preceding byte, irrespective of preceding backslash parity; skipped pairs are not unquoted or removed.
2. If there is no eligible pair, reject the construct. Independently search its body for `<<`, skipping a found pair by the same immediately-preceding-backslash test and restarting after the pair. An eligible nested `<<` before E rejects the header.
3. Quotes do not suppress either search. A backslash that protects a delimiter in this lookahead remains in the header delivered to its next parser. Text after E belongs to the subsequent worker scan, not this header.

Thus a conditional literal containing `<<` needs an immediately preceding backslash **at the outer angle stage**, even though the conditional literal scanner alone would treat those `<` bytes as data. A literal `>>` needs protection both for outer lookahead and for the conditional scanner's own terminator rule. A doubled backslash before `>>` satisfies the outer preceding-byte test but the operand parser first decodes a literal backslash and then encounters an unescaped terminator; the two stages cannot share one quote/parity state.

**Portable consistency rule:** syntax-parse an IF/ELSEIF expression within its selected header and require it to consume exactly E. If its own terminator differs from E, reject the header before retrieving operand values. This closes the two-parser boundary without changing the previously published [operand-stage examples](#parser-stage-examples) when their bytes actually reach that parser. The outer lookahead is an additional gate, not a replacement for operand-local escapes, quote closure, grouping or decoded limits.

#### Exact Control, Name and Template Boundaries

There is **no whitespace skipping after the opening `<<` before classification**. Fold ASCII letters for the following case-insensitive tests, in this order:

| Bytes immediately after `<<` | Classification |
| --- | --- |
| `IF ` | IF header; the final byte in this prefix is literal ASCII space `0x20` |
| `ELSEIF ` | ELSEIF header; same required ASCII space |
| `ELSE>>` | Complete ELSE control, with no intervening whitespace |
| `ENDIF>>` | Complete ENDIF control, with no intervening whitespace |
| `?N>>`, one case-insensitive MegaNum slot digit N | Angle-template insertion; no extra bytes between N and the closing pair |
| Any other body ending at E | Named/reference-body expansion, subject to the ordinary provider grammar |

After the required space in IF/ELSEIF, the [conditional scanner's WS rules](#conditional-operand-byte-grammar) apply, so additional spaces or HT are allowed there. A tab **instead of** that required space does not introduce an IF/ELSEIF control. No trimming or name-boundary inference is added to the fixed tests. An exact ELSE/ENDIF is reserved and errors when misplaced; it does not fall back to looking up a same-named variable.

For the fallback form, take the complete body bytes unchanged (without `<<`/`>>`) and synthesize `$&` + body + `$`. It has no extra conditional-left unquoting stage. The existing [dollar parser/provider](5.1-text-variables.md#variable-resolution-in-3x) governs prefixes, names, arguments, question/default syntax, caller permissions and case-insensitive lookup. The synthetic `&` is idempotent under the adopted directive policy. Do not restrict a body to an identifier by analogy, or treat leading/trailing whitespace as harmless. Do not include another pair of dollar delimiters around the body name.

**Portable bounded validation:** a fallback body must fit 255 bytes and form exactly one complete valid synthesized reference; reject empty bodies, malformed template forms, embedded reference terminators/trailing material or excess body bytes before any provider call. These are preprocessing failures, as is a rejected/failed named-angle provider; they are not the conditional comparison's false-on-value-failure path. Use safe storage for returned values under the existing enclosing preprocessor limit rather than requiring native fixed-buffer copying. The ordinary reference/argument limits remain separate.

Named results are rescanned immediately at the insertion point, including any angle controls they introduce. Ordinary bytes from such a result are kept/discarded according to the current branch state. Angle-template results retain their existing deferred scan: skip the inserted body for the current pass. Standalone named and template lookups are not suppressed merely because their containing branch is inactive; their lookup/required-selection effects still occur. **Explicit inactive-template output policy:** discard that insertion's result when the branch is inactive, so deferred scanning cannot retain unselected output. This rule concerns inserted output, not rollback of its lookup. It does not evaluate an inactive nested IF's operand providers.

| Source at the outer worker | Classification / next stage |
| --- | --- |
| `<<if N=1>>` | IF; case-insensitive control |
| `<<IF ` + HT + `N=1>>` | IF, then ordinary conditional whitespace skipping |
| `<<IF` + HT + `N=1>>` | Fallback body contains HT; ordinary reference parser rejects it, not an IF condition |
| `<< IF N=1>>` | Fallback with leading space; rejected provider syntax |
| `<<ELSE >>` or `<<ENDIF >>` | Fallback with trailing space; rejected provider syntax; no branch transition |
| `<<IF>>`, `<<IFX>>`, `<<ELSEIF>>`, `<<ELSEIFX>>`, `<<ELSEX>>`, `<<ENDIF_X>>` | Ordinary named lookups, if permitted/defined; not controls |
| `<<?a>>` | Template slot 10; inserted text skipped this pass |
| `<<?AB>>` or `<<?A >>` | Reject malformed template; do not invent a longer slot name |
| `<<$N$>>` or `<<>>` | Reject synthesized reference syntax; no optional dollar wrapper here |
| `<<F(A\)B)>>` | Body reaches dollar parser unchanged; its argument-local escape can decode `A)B` |
| `\<<N>>` in active text | One worker leaves `<<N>>` and performs no N lookup for this introducer; a later wrapper pass can expand it |
| `\\<<N>>` in active text | One worker leaves `\<<N>>`; no odd/even cancellation rule |

Every backslash displayed is one actual byte at the stated stage. These are source-derived/policy vectors, not new original-client observations.

#### Branch Frames, Validation and Provider Order

Maintain a frame for each open IF: its parent activity, whether any branch has already been selected, whether ELSE has occurred, and current branch activity. Every new frame starts with no earlier selection and no ELSE; sibling frames do not inherit those flags. Initial root activity is true. Syntax-validate **every recognized IF/ELSEIF expression**, including skipped branches, without retrieving operand values. Only after successful header validation decide whether to evaluate it. Pure validation/provider separation (including template operands) is the portable contract; it need not copy a native parser that fetches a template string while tokenizing it. Validation here checks conditional tokenization, operators and Boolean/group structure, not the later provider's reference/argument semantics. A provider-format rejection still makes an evaluated comparison false under the adopted operand contract.

| Header/state | Validate expression? | Evaluate operand providers? | New current branch / selection |
| --- | --- | --- | --- |
| IF, parent active | Yes | Yes, in existing comparison/reduction order | Active iff true; mark selected iff true |
| IF, parent inactive | Yes | No | Inactive; parent inactivity excludes every branch of this frame |
| ELSEIF, parent inactive | Yes | No | Inactive |
| ELSEIF, parent active, earlier branch selected | Yes | No | Inactive; keep the earlier selection locked |
| ELSEIF, parent active, no earlier selection, condition true | Yes | Yes | Active; lock selection for all later ELSEIF/ELSE branches |
| ELSEIF, parent active, no earlier selection, condition false/value failure | Yes | Yes | Inactive; a later ELSEIF/ELSE can still select |
| First ELSE | Not applicable | No | Active only if parent active and no earlier branch selected; mark ELSE seen |
| ENDIF | Not applicable | No | Pop frame, restore the parent's current activity |

No Boolean short-circuiting is added **inside an evaluated expression**. Skipping an ineligible ELSEIF expression's value providers is a different gate. Standalone named/template angle lookups in inactive text follow their separate rule above; later ordinary dollar callbacks in discarded text do not run.

**Explicit structural policy:** reject a second ELSE, ELSEIF after ELSE, stray ELSEIF/ELSE/ENDIF, or end of a worker pass with an unclosed IF. Reject malformed skipped headers even after an earlier branch succeeded. The ELSEIF-after-ELSE rule is explicit protocol validation rather than a promise that every native state path enforces it. No previously selected branch can be reopened by a later ELSEIF.

**Portable depth limit:** allow at most **16 simultaneously open IF frames**, counting inactive frames too. Check before pushing; the seventeenth IF fails nonfatally before its providers run or storage is accessed. ELSEIF/ELSE reuse their frame and are allowed at depth 16; they do not consume another level. This intentionally defines the limit by IF depth rather than copying every native depth guard. Parentheses/comparison counts and the eight wrapper passes are distinct quantities. Earlier completed provider effects are not rolled back by a later syntax/depth failure; no unsafe fixed native array behavior is required.

For the chain `<<IF A=1>>x<<ELSEIF B=1>>y<<ELSEIF C=1>>z<<ELSE>>w<<ENDIF>>`, assuming successful data lookups:

| Values        | Conditional provider order               | Output |
| ------------- | ---------------------------------------- | ------ |
| A=1           | A only; B/C headers still syntax-checked | `x`    |
| A=0, B=1      | A, B; C header still syntax-checked      | `y`    |
| A=0, B=0, C=1 | A, B, C                                  | `z`    |
| A=0, B=0, C=0 | A, B, C                                  | `w`    |

With A=1 and D=`q`, `<<IF A=0>><<D>><<IF B=1>>x<<ELSEIF C=1>>y<<ENDIF>><<ELSE>>r<<ENDIF>>` looks up A then D and produces `r`; it does not retrieve B or C. Replacing `<<D>>` with `<<?3>>` still obtains slot 3, but an inactive result is discarded under the explicit rule above. A malformed nested/ELSEIF expression instead fails preprocessing, even though B/C would not have been evaluated. Sixteen nested true IFs may evaluate sixteen conditions; a seventeenth fails before evaluating that header. No original callback execution is asserted by these vectors.

For an inactive-parent example, take A=1 and D=`q`: `<<IF A=0>><<D>><<IF B=1>>x<<ELSEIF C=1>>y<<ENDIF>><<ELSE>>r<<ENDIF>>` produces `r` with lookup order A,D; B/C are syntax-checked without retrieval. Replacing `<<D>>` with `<<?3>>` still obtains slot 3 but discards its returned text under the explicit inactive-template policy.

#### Outer Versus Operand Quoting Examples

For the following complete headers, let N have the literal value named in the result column when evaluation is eligible:

| Outer header bytes | Gate / operand result |
| --- | --- |
| `<<IF N="a<<b">>` | Reject nested unprotected `<<` during outer lookahead, before N is retrieved |
| `<<IF N="a\<<b">>` | Outer lookahead skips protected `<<`; operand stage decodes RHS `a<<b` |
| `<<IF N="a>>b">>` | Outer chooses the early pair; operand stage rejects the open quote |
| `<<IF N="a\>>b">>` | Outer skips protected pair; operand stage decodes RHS `a>>b` |
| `<<IF N="a\>\>b">>` | No contiguous inner terminator at the outer stage; operand stage decodes the two protected bytes to `a>>b` |
| `<<IF N="a\\>>b">>` | Outer skips that pair irrespective of parity; operand stage decodes a backslash, then rejects unescaped `>>` before quote closure |

These are headers; a valid complete conditional also needs its body and matching ENDIF. Outer protection is not removed by lookahead, so operand-local quoting runs on the displayed bytes, independently of earlier wire escaping and later ordinary passes. The later response/storage clipping policy remains a separate stage.

### Definitions, Composition and Side Effects

Angle preprocessing occurs **when the host-command string containing a definition is processed**, before the definition block is stored. Dollar variables in that stored block await its use. For N=`2`, processing `[3:]<<N>>-$SHIFT$` stores `2-$SHIFT$` and transmits nothing. With button-associated definitions this processing is tied to activation of that host command; it is not a universal assertion that every directive runs when a button arrives over the wire.

Slot chaining parses up to 36 listed slot digits, visits them in list order, composes a response and only then performs its ordinary passes. A template without `$?$` discards the previous feed: template 3=`$SHIFT$`, template 4=`FOUR`, source `[34]X` transmits `FOUR` without evaluating SHIFT. **Marker-bearing chaining has the offset defect below**, so its inherited ideal substitution outputs are not verified shipped outputs.

Inactive conditional branch text does not imply zero preprocessing activity. With N=`0`, A=`X`, `<<IF $N$=1>><<A>>$SHIFT$<<ELSE>>N<<ENDIF>>` reads both N and A, removes the first branch, and does not query SHIFT in the later ordinary stage. A nested IF inside an inactive parent is syntax-checked without evaluating its comparison. Operands within an evaluated AND/OR expression are all evaluated; there is no Boolean short-circuiting.

### Shipped Template-Chain Defect

The `$?$` substitution call in the slot-chain routine computes the insertion offset relative to the **feed buffer**, although the marker lies in the **template-copy buffer**. The insertion helper then narrows that wrong offset to a signed 16-bit value. Results depend on buffer placement and can truncate or write outside the intended destination. There is no portable, deterministic RIPtel output for this defective marker path.

The native probe executes the original chain up to this call, verifies its wrong operands and intercepts the unsafe insertion. It does not claim successful original rendering of the intended substitution. The `[ABC]` and combined examples below retain the inherited design explanation, explicitly subject to this defect. An implementation can implement the intended composition without reproducing an invalid memory write; that choice is a correction to the shipped defect and should be identified as such.

## Templates

_Evidence: 2.00a4._

A template is a special variety of a host command that is used to construct other host commands. Their group/selection model is designed around [RIP_BUTTON](4.3-buttons.md#rip_button), especially radio and check-box groups. The common shipped host-command processor also accepts template-enabled blocks without a button association; the inherited buttons-only restriction is not enforced by that processor. See the [processing contract](#shipped-processing-order) and the inherited context chart in [5.0](5.0-host-commands.md#what-can-go-where).

A template, like a normal "raw" host command, is stored in the Host Command field of the RIP_BUTTON command. Unlike raw host commands that get sent to the host immediately, templates do not transmit immediately. In fact, it's possible for a template to never get transmitted to the BBS at all. Templates are not normally sent directly to the BBS - they are almost always used in conjunction with some other button's host command.

There are three types of host commands:

1. **DIRECT HOST COMMANDS** - Send a string of text to the host immediately after the associated button is clicked.
2. **TEMPLATE DEFINITIONS** - Defines a template to be used by other buttons (if ever). See below for further details about how to define templates.
3. **TEMPLATE EXECUTION** - This allows you to plug a piece of string data into one or more templates (defined previously). The resulting string is then acted upon like a Direct Host Command and transmitted to the BBS immediately.

The RIP_BUTTON command "segments" its Text Parameter Block into three portions - the Icon File, Text Label followed by the Host Command block. Each of these segments is separated by the two-character delimiter `<>` like this:

```text
ICONFILE.ICN<>Button Label<>HOST COMMAND.
```

With the Button command, the Host Command segment can be sub-divided into numerous smaller sub-segments, or Command Blocks. This is done with another two-character delimiter `[]`. So, technically, you could do this:

```text
ICONFILE.ICN<>Button Label<>HELLO^m[]WORLD^m
```

This command would show an Icon Button using the file ICONFILE.ICN as its Icon Image, labeling it with the phrase "Button Label", and defining an extended Host Command block with two segments. If the user clicks on this button, the following will be sent to the BBS:

```text
HELLO<cr>
WORLD<cr>
```

Notice how the `[]` is not transmitted. This is because it is simply a delimiter separating two Command Blocks from each other. Now each of these two command blocks are Direct Host Commands, but they don't have to be. One of them could have been a Direct Host Command, and another could just as easily have been a template definition.

## Basic Template Mechanics

_Evidence: 2.00a4; SyncTERM (ripper.c:11949-11982, 11637-11882)._

There can be up to 36 different templates defined simultaneously. Each template number corresponds directly to a Button Group Number. Templates are identified by a single [MegaNum](../../glossary.md) digit 0-9 and A-Z, leaving 36 distinctly separate groups. SyncTERM implements the full store/apply machinery (`ripper.c:11637-11882`). To define a template, you use a variation of the Command Block delimiter `[]` with the template identifier followed by a colon like this:

```text
[5:]This is template #5's definition
[G:]This is template #16's definition
```

Defining a template is simple. Activating a template however, is another story. What if three buttons in the same group all define their own templates for the same group/template like this:

```text
Button #1:   [5:]This is button #1's template
Button #2:   [5:]This is button #2's template
Button #3:   [5:]This is button #3's template
```

Now, when these three buttons are received by the terminal, it [the terminal] knows the Host Commands for each button (it memorized each of them). Now, which of these three templates is the currently active one? None of them! A template definition doesn't become the active template until that button containing its definition is clicked (selected). What this means is, you can have a bunch of buttons all belonging to the same Button Group with their own respective template definitions, but only the template relating to the most recently clicked button will be the currently active template for that group.

In the adopted 3.0 contract, a committed pointer or keyboard activation processes its source and can activate template definitions. **Initial preselection does not process host text or activate templates.** The inherited eager-preselection exception is superseded by the opaque-creation rule. A definition reached during a later activation replaces that owner's definition for that slot under the complete ownership rules below.

In either case when templates are defined, nothing is actually transmitted to the BBS unless the Command Block contains some Direct Host Command sub-block(s) like this:

```text
[5:]Template definition[]hello world^m
```

If this button were clicked, then Group number 5 would have the template activated with the template text "Template definition". Then the Direct Host Command `hello world^m` would be transmitted to the BBS. In this example, we see how a single host command can do multiple things - in this case, it defined a template in group #5 AND transmitted something to the BBS!

## Radio Buttons and Check-Box Templates

_Evidence: 2.00a4; SyncTERM (ripper.c:11736-11800)._

Radio groups have at most one persistently selected member; checkboxes toggle independently. Their [selection/feedback timing](4.3-buttons.md#grouped-selection-and-feedback) commits only on valid pointer release or eligible keyboard delivery, before optional redraw and clicked-source processing. Selected checkbox contributions concatenate in creation order, not activation order. The following complete 3.0 ownership rules supersede any inherited implication of eager creation processing or a universal single retained body.

Let's take a couple simple examples step-by-step to see how templates are maintained internally.

**EXAMPLE 1 - RADIO BUTTON TEMPLATES**

Let's say you have four buttons in Button Group #3, and that button group is defined as a Radio Button group. Here are the host command definitions for each of those buttons in this example:

```text
Button #1:   [3:]ABCD
Button #2:   [3:]EFGH
Button #3:   [3:]IJKL
Button #4:   [3:]MNOP
```

Now, if none of the buttons are clicked, then template group #3 is blank. If button #1 is clicked, the template for group #3 would be defined as "ABCD". Now, if button #4 is clicked, what would the template definition for group #3 be? That's right, "MNOP". Notice how only one of the given templates is active at any given moment.

**EXAMPLE 2 - CHECK BOX TEMPLATES**

Now let's explore the slightly more complex world of check box templates. As stated previously, check box templates can be strung along together to make a larger template - template construction of sorts. Let's say you have a Button Group #2 defined as a check box group with 7 buttons defined in it. Each of the buttons are initially drawn as "unselected", or unclicked (inactive). Here are the button host command definitions for each of the 7 buttons:

```text
Button #1:   [2:]Apples^m
Button #2:   [2:]Oranges^m
Button #3:   [2:]Cherries^m
Button #4:   [2:]Grapes^m
Button #5:   [2:]Pears^m
Button #6:   [2:]Banannas^m
Button #7:   [2:]Lemons^m
```

Now, if all 7 buttons are not clicked, then template group #2 would be blank. Let's click on some buttons and see what the template will become as we change which buttons are clicked and which aren't:

```text
Button #3 clicked (ON) .... Template:  Cherries^m
Button #5 clicked (ON) .... Template:  Cherries^mPears^m
Button #3 clicked (OFF) ... Template:  Pears^m
Button #5 clicked (OFF) ... Template:  <blank>
Button #2 clicked (ON) .... Template:  Oranges^m
Button #1 clicked (ON) .... Template:  Apples^mOranges^m
Button #4 clicked (ON) .... Template:  Apples^mOranges^m
                                       Grapes^m
```

As you can see, the active template for a check box group is actually a combination of all selected buttons' templates, in ORDER OF DEFINITION, not in the order that they were clicked. Pay close attention to the end of the example where buttons were clicked in the order of 2, 1 then 4. If you notice the active template though, they are in 1, 2 then 4 order! They are in the order that the buttons were originally defined.

### Associated Template Ownership and Lifetime

**Explicit portable completion:** the primary examples establish group selection and creation-order composition; the original checkbox helper retains only one body per record and does not fully specify multi-slot/cross-group/mutation behavior. Use the following abstract state; it is not a required in-memory layout. [Derivation and exact source limits](../research/issue-131-grouped-button-lifetime.md).

- Each stable grouped button owns a map `A[N]` for slots 0..35. Initially the map is empty, even for a selected button: creation retains the complete **opaque host source** without parsing `[N:]`. Only a definition block actually reached by that button's committed host continuation creates/replaces its A[N]. Store the post-angle, still ordinary-unexpanded body, capped to 4096 bytes. Last reached definition wins **separately for each N**; untouched entries remain. Empty definitions are defined empty bodies, not removal of another slot.
- N may differ from the style's group G. Within G, pure composition for each published N concatenates A[N] from surviving selected members in **creation order**, skipping absent entries. Radio exclusivity normally leaves at most one member. Cap the assembled bytes to 4096 before insertion. Store no concatenated expansion result back into underlying owners; ordinary providers run only when the body is used by the normal host pipeline.
- Each slot has an ordinary baseline B[N] and one current publisher: ordinary or a particular group. A nonassociated `[N:]` replaces B[N] and makes the slot ordinary-published. A reached grouped `[N:]` updates that owner's A[N] and claims publication of N for G. A different group can claim the same N later; this is last-publication-wins per slot, not merged cross-group ownership.
- Rebuild after selection, associated-definition changes, deletion/MKILL or applying replacement field definitions. A pure rebuild changes **only slots still published by that group**, so it cannot overwrite a later ordinary assignment or another group's claim. While G lives, an empty aggregate publishes empty. When its last member disappears, release its publications to B[N] (or undefined/empty if no baseline); do not resurrect an older superseded group publisher. Reaching a new grouped definition can claim a slot again. Rebuilding never evaluates opaque sources/providers.

For `[N:]` outside a grouped association, ordinary storage remains the existing plain slot operation. These baselines/publication tags clarify lifetime; they add no new wire syntax. A later explicit assignment is not lost merely because an old selected field is deleted. Mouse-field deletion removes its associations and reassembles affected publications but preserves ordinary baselines. For SOFT/drawing reset, preserve the already effective slot values as ordinary definitions before discarding deleted owners and their publication tags. This adopts the existing [SOFT template-preservation rule](1.3-world-view-virtual-canvas.md#state-that-survives), rather than importing the original field-clear helper's numbered-slot deletion. Do not evaluate any source while preserving those bytes. [HARD reset](1.3-world-view-virtual-canvas.md#hard-reset-state-and-lifetime) clears all 36 slots, baselines, associations and publication tags, while its current owned HCL continuation and session/persistent user variables survive. A later lookup sees the cleared store; already copied program bytes are retained. A reset explicitly clearing host-template storage clears the affected baselines/publications; table/style selection alone does not assemble or evaluate host text. Applying restored/replaced fields gives fresh instance tokens: any restored associated definition data belongs to those fresh owners, never to a suspended former instance. The [mouse-backup capture and publication rules](7.2-data-backup-areas.md#grouped-mouse-snapshots-and-template-publication) save persistent state/maps but exclude global baselines/publication tags, preserve current ordinary assignments, and rebuild only the surviving logical groups' current publications without host execution.

**Clicked-source processing:** checkbox OFF still runs its own complete angle preprocessing, block segmentation, reached definitions and direct/assignment/response blocks once. Its updated A[N] is retained but excluded while OFF. Turning it ON later can contribute it again. Radio switching processes only the clicked source; the deselected radio's source and all other selected sources are **not** re-evaluated. An old selected source may need optional graphical redraw, whose filename/label stages are distinct from its host source. Definitions remain post-angle ordinary bodies; the existing two ordinary response passes and 4096-byte working-prefix/storage/assembly limits stay unchanged.

**Suspension and mutation:** keep committed raw source/FIELDID in owned storage. Before each association write, verify that its original stable owner survives; if it was deleted/replaced/reset, skip that associated write rather than applying it to a duplicate-ID replacement or treating it as an unassociated ordinary definition. Already committed direct blocks/providers continue under existing host-stage/error rules; prior effects and selection are not rolled back. Never replay the selection commit or a completed block after a prompt. Each pure publication uses a fresh atomic snapshot of current live selected owners, not a stale aggregate saved before a prompt. Adding a field alone creates no A entries or activation; a separately committed later/nested operation may change current composition without acquiring the earlier action's identity.

### Required Radio Selection

**Explicit selection-based criterion:** when template slot N is referenced by the ordinary/angle/template provider, a live radio group numbered N requires **a selected live radio member**. This check is independent of whether the effective slot bytes are empty or defined. No selected member fails even if an ordinary B[N] contains text. A selected member with empty/undefined associated text satisfies selection: use the effective slot, treating absent text as empty. A checkbox group may have no selected members and embed empty normally. Cross-slot publication by group G to N does not create a required radio group N; actual live radio membership does.

After the last radio member is deleted, its requirement disappears; a later ordinary/empty slot is looked up normally. HKEYOFF and pointer disable affect activation eligibility, not selected state, publication or whether an existing radio group requires a choice. Neither silently selects a default. Invalid mixed-group definitions reject as specified above.

Missing required selection rejects the affected lookup/response nonfatally with optional notification/highlight of surviving relevant fields. It does not click a field, run any label/host provider, retry the failed source automatically or terminate the connection. Earlier blocks/transmissions and the committed selection/action stay completed. A later user choice needs a fresh explicit activation/query to use the template. This logical criterion completes the old missing-slot/count/notification paths; exact native highlight pixels/timing are not required.

Assume Base Math 36, coordinate size 2, active full PORT0 and WORLD=DEVICE. The first style defines checkbox group 2, PLAIN+MOUSE, dynamic size, no effects. C2 starts selected, but both associations and all host provider counts start empty/zero:

For radio group 4, define R1 selected and R2 unselected with duplicate numeric ID 7 (their stable instances are distinct):

A proposed checkbox in live radio group 4 rejects before painting/admission, leaving the old style/fields/slots intact.

If R2's committed host continuation suspends, then R2 is deleted and a new ID-7 field is created, its saved source/FIELDID still belong to old R2. It may finish its already committed direct block once, but cannot install associated definitions into the replacement, redraw it or restore old selection. New fields receive no action from this continuation. Pure deletion/rebuild and missing-selection highlighting execute zero host providers.

## Embedded Templates - `$?N$`

_Evidence: 2.00a4; SyncTERM (ripper.c:11918-11923)._

There are two ways of using templates: Template Embedding and Template Chaining. Template embedding is a way of "inserting" a template inside another host command - you can insert the contents of an active template inside of a button's Direct Host Command. The direct host command is "expanded" around the inserted template and the contents of the specified template are made part of the direct host command.

Let's illustrate this with an example. Taking the check box example above which had a list of fruits as check box buttons, we will build a menu to take someone's order for fruit. Here is what the simple menu screen will look like:

```text
╔════════════════════════════════════════╗
║     What would you like to order?      ║
║                                        ║
║ ┌────────────┐                         ║
║ │ ■  Apples  │                         ║
║ │ ·  Oranges │        ┌────────────┐   ║
║ │ ■  Cherries│        │Submit order│   ║
║ │ ·  Grapes  │        └────────────┘   ║
║ │ ■  Pears   │                         ║
║ │ ·  Banannas│                         ║
║ │ ■  Lemons  │                         ║
║ └────────────┘                         ║
╚════════════════════════════════════════╝
```

We will use two separate button groups. Group #0 will contain one button, the "Submit Order" button. Button Group #2 will be a check box button group containing our seven choices of fruits as in the preceding example. Here are the Host Command definitions for each of the eight buttons:

```text
Group #0 (normal button - not a radio or check-box button)
──────────────────────────────────────────────────────────
     SUBMIT ORDER:   I wish to order $?2$ right now^m

Group #2 (check box button group)
─────────────────────────────────
     APPLES:    [2:]APPLES^m
     ORANGES:   [2:]ORANGES^m
     CHERRIES:  [2:]CHERRIES^m
     GRAPES:    [2:]GRAPES^m
     PEARS:     [2:]PEARS^m
     BANANNAS:  [2:]BANANNAS^m
     LEMONS:    [2:]LEMONS^m
```

Notice in the "Submit Order" button that there is a special code in the Direct Host Command, `$?2$`. This is a special variation of a [text variable](5.1-text-variables.md), used only in Template Embedding. It instructs the terminal to "insert template #2 here". The format of the template embedding code is:

```text
$?x$
```

...where "x" is the template identifier (0-Z) that is to be inserted. Now back to the example: if the user clicked on "APPLES", "CHERRIES", "PEARS" and "LEMONS" as in the menu shown above, then clicks on "Submit Order", the Submit Order button's host command reads:

```text
I wish to order $?2$ right now^m
```

After template #2 is inserted where the embedding code is, the host command would look like this:

```text
I wish to order APPLES^mCHERRIES^mPEARS^mLEMONS^m right now^m
```

And after the `^m`'s are converted to carriage returns the final host command would be like this:

```text
I wish to order APPLES
CHERRIES
PEARS
LEMONS
right now
```

What if the user didn't click on any of the fruits, but did click on the Submit Order button? Well, since template #2 belongs to a group that is a Check Box group, which can have zero or more items selected simultaneously, the `$?2$` code would be expanded to a null string, or nothing, so the final host command would be:

```text
I wish to order  right now
```

If a live radio group 2 has no selected member, the lookup instead fails under the [required-selection rule](#required-radio-selection), with optional notification/highlight and no synthesized activation. A selected radio with empty or undefined associated text satisfies selection and can embed empty. Checkbox groups can have no selected members.

The inherited final embedding limit is 4096 bytes. The [completed byte-limit policy](#response-and-embedding-byte-limit) specifies entry and per-replacement clipping, encoded-byte timing, stored-template limits and suffix side effects. Discarded source does not execute later merely because decoding frees space. (The numerical bound is inherited; the enforcement details are explicit interoperability choices.)

## Template Chaining - `[ABC]`

> **Shipped-driver qualification:** the marker-substitution examples in this section and Advanced Template Concepts describe the inherited intended algorithm. RIPtel’s original `$?$` insertion has the [wrong-buffer offset defect](#shipped-template-chain-defect); do not use those expected strings as unqualified RIPtel compatibility oracles.

_Evidence: 2.00a4; SyncTERM (ripper.c:11949-11982)._

Template Chaining is the second form of using templates. Rather than inserting the contents of a template into a host command, like in embedding, template chaining feeds data into a template and then takes the result and transmits that to the BBS. In other words, Template Embedding inserts a template into a Host Command. In Template Chaining, a Host Command is inserted into a template (the exact opposite).

Template Chaining uses a similar insertion code to embedding but with a subtle difference - there is no template identifier. The code is:

```text
$?$
```

This is a "generic insertion code". It is used in the template definition itself, not in the Direct Host Command like the template embedding code was used. The actual data that replaces the `$?$` depends on the Direct Host Command that is "feeding" the template.

A template chaining operation is performed almost exactly like defining a template with a subtle difference: the colon (`:`) is omitted from the template definition like this:

```text
[5]This is template chaining
[5:]This is template definition
```

What's the difference? In the case of the `[5:]`, a template for group #5 is defined. In the `[5]` example, the template chaining instruction is invoked on Template #5. The phrase "This is template chaining" will be fed into template number 5. If template number 5 has a generic insertion code `$?$` in it, then it will be replaced with the phrase "This is template chaining". The final result after the replacement will be a direct host command that will be transmitted to the BBS. Since template #5 doesn't have an insertion code, the phrase "This is template chaining" will be lost in the chaining process and the final host command would be "This is template definition".

Here are a couple examples of template chaining illustrating several ways that it may be used (we'll only show "active" template definitions):

```text
[3:]This is a plain old template
[4:]This template inserts $?$ here!
[5:]This has two insertion codes $?$ and $?$

[3]This text is lost in the chaining process
[4]SOMETHING
[5]HERE
```

This would be the result of the three chaining operations:

```text
3 ... This is a plain old template
4 ... This template inserts SOMETHING here!
5 ... This has two insertion codes HERE and HERE
```

There are three distinctly different situations in this example. The first shows a regular template without an insertion code being used in a chaining operation - the data that was fed into template #3 was lost because template #3 didn't have an insertion code. In the second example, a single insertion code is used and the word "SOMETHING" is inserted in place of the insertion code. The third example shows that an insertion code can be used more than once in a given template.

Chaining applies the same [required-selection rule](#required-radio-selection) as embedding. A live radio group with no selected member rejects that lookup, even when its ordinary slot contains bytes. A selected member with empty/undefined associated text passes selection; an empty effective slot sends nothing. An empty checkbox or ordinary slot likewise sends nothing.

In the preceding examples, only one template was used (chained-to). In reality, you can chain to multiple templates with ease. Just add the template identifiers for the templates you want to chain to in the order you wish to chain to, like this:

```text
[1E3]This is a three-level chaining operation
```

The Host Command would be fed into template #1 first. After any replacements, the result of the template #1 chaining would be fed into template #E. After any replacements/insertions are performed on template #E, the final result is fed into template #3, and the final result of that chaining operation is sent to the BBS.

Here is an example of multiple template chaining calls:

```text
[1:]red green $?$ blue
[E:]LOUD QUIET $?$ YELL
[3:]soft $?$ hard smooth gritty

[1E3](host command)
```

We can break this down conceptually into three separate chaining operations to illustrate what happens step-by-step:

```text
[1E3](host command)
```

Results in:

```text
[E3]red green (host command) blue
```

Resulting in:

```text
[3]LOUD QUIET red green (host command) blue YELL
```

And then finally:

```text
soft LOUD QUIET red green (host command) blue YELL hard smooth gritty
```

This last phrase is then sent to the BBS verbatim. Template chaining is useful for controlling HOW particular data is transmitted to the BBS, while template embedding is useful for controlling WHAT data is transmitted to the BBS. You can think of template chaining as a method of defining "commands" that will be sent to the BBS where the commands can be different depending on which buttons are clicked in that group. Template embedding on the other hand is often used for controlling the data parameters that are used with particular commands.

You are allowed up to 36 separate template chaining levels in one template chaining operation. After all chaining is completed, the final host command cannot exceed 4096 bytes. If a chaining operation would exceed that amount, it is truncated to exactly 4096 bytes. Subsequent ordinary response passes use the [entry/per-replacement byte limit](#response-and-embedding-byte-limit); this preserves the composition-before-expansion boundary and does not add a pass.

## Advanced Template Concepts

_Evidence: 2.00a4._

Template Embedding and Template Chaining do not need to be separate methods. You can combine them if you wish - you can have embedded templates inside of template chains. This provides for utter flexibility in doing whatever you want.

Here are a couple of examples of combinations:

**EXAMPLE 1**

```text
[5:]EMBEDDED VALUE

[3:]Here is a $?$ and an $?5$

[3]CHAINED HOST COMMAND
```

This would result in:

```text
Here is a CHAINED HOST COMMAND and an EMBEDDED VALUE
```

**EXAMPLE 2**

```text
[5:]EMBEDDED VALUE

[3:]Here is a $?$ and an $?5$
[4:]print("$?$")

[34]CHAINED HOST COMMAND
```

This would result in:

```text
print("Here is a CHAINED HOST COMMAND and an EMBEDDED VALUE")
```

**EXAMPLE 3**

```text
[4:](hello)
[5:]ANOTHER $?5$ EMBEDDED $?4$ VALUE

[3:]Here is a $?$ and $?5$

[3]CHAINED COMMAND
```

This would result in:

```text
Here is a CHAINED COMMAND and ANOTHER ANOTHER $?5$ EMBEDDED $?4$
VALUE EMBEDDED (hello) VALUE
```

Taking this one step-by-step:

```text
Step #1:   Here is a CHAINED COMMAND and $?5$

Step #2:   Here is a CHAINED COMMAND and ANOTHER $?5$
           EMBEDDED $?4$ VALUE

Step #3:   Here is a CHAINED COMMAND and ANOTHER ANOTHER
           $?5$ EMBEDDED $?4$ VALUE EMBEDDED (hello) VALUE

     <end of processing>
```

**EXAMPLE 4**

```text
[5:]HELLO

[3:]$?5$ $?$ WORLD

[4:]print("$?$")^m

[344](silly)
```

This would result in:

```text
print("print("HELLO (silly) WORLD")^m")^m
```

Example #1 shows a situation with a single chaining operation and a single embedding operation done at the same time. Example #2 shows a more complex situation where multiple levels of template chaining are going on while embedding is also being used.

Example #3 is somewhat different though. Why weren't the embedded template codes expanded at the lowest level of template #5? If you look closely at template #5, it has an insertion code instructing the system to insert template #5 (itself) in the middle of the template. This is legal, but only because an embedded template inside an embedded template cannot have any more embedding performed on it. In other words, you are allowed up to two levels of embedded templates, but the lowest level (2nd) cannot have any insertion codes, text variables, control characters or pick-list definitions in it - if it does, they will be treated as "raw" text instead of host command directives.

Example #4 shows a more involved Template Chaining operation in which the same template is chained to more than once in a given operation. This is allowable for extra flexibility, although in the real world will probably not be used much.

## Host Command Language and Templates

_Evidence: 2.00a4._

In any template definition or host command, you can have [text variables](5.1-text-variables.md), [pick lists](5.4-popup-lists.md) or control characters anywhere. You can freely use them in a Direct Host Command, in a template chain and in embedded templates. They do get a bit odd though in how they interact with Embedded Templates - but only if you have an embedded template within an embedded template. Which host-command features may appear where is summarized in [5.0 Host Commands](5.0-host-commands.md#what-can-go-where).

Recall from the previous discussion: at the lowest level of the embedding, there is no processing done on the string of text. This is to prevent endless loops and combinatorial explosion of data and CPU time. Text variables, pick lists and control characters WILL be processed at the first level of an embedded template, but not at the second level.

Here are some examples that better illustrate text variables:

**EXAMPLE 1**

```text
[3:]The date is $DATE$ ... $?$

[3]HELLO
```

Results in:

```text
The date is 07/18/93 ... HELLO
```

**EXAMPLE 2**

```text
[3:]The date is $DATE$

HELLO THERE, $?3$
```

Results in:

```text
HELLO THERE, The date is 07/18/93
```

**EXAMPLE 3**

```text
[2:]The time is $TIME$^m
[3:]The date is $DATE$^m

HELLO THERE^m$?3$$?2$
```

Results in:

```text
HELLO THERE
The date is 07/18/93
The time is 03:43:32
```

**EXAMPLE 4**

```text
[1:]The day is $DOW$^m

[2:]The time is $TIME$^m
[3:]The date is $DATE$^m$?1$^m

HELLO THERE^m($?3$)($?4$)($?1$)
```

Results in:

```text
HELLO THERE
(The date is 07/18/93)
The day is $DOW$^m
(The time is 03:43:32)
(The day is Sunday)
```

Notice how the `$?1$` embedded template used in template #3 does not get processed - it is just inserted raw.

## Processing of Templates

_Evidence: 2.00a4._

Template definitions may contain text variables, pick lists, control characters, and template insertion codes. When do these special "directives" get processed? For ordinary dollar variables, pick lists and control characters, the inherited answer is when the template gets USED rather than when it becomes ACTIVE. The shipped angle preprocessor is earlier: angle macros/conditionals in the definition’s host-command string run before that definition is stored, as specified [above](#definitions-composition-and-side-effects). To better illustrate this, let's look at a simple example.

Let's say you have three radio buttons (group #2) on the screen and another button (group #0) which uses the template for the radio button group. Here's the host command definitions for each of these four buttons:

```text
Group #2 - Radio Button Group
─────────────────────────────
     Button #1:  [2:]It's a pretty day at $TIME$
     Button #2:  [2:]It's a rainy day at $TIME$
     Button #3:  [2:]It's a hazy day at $TIME$

Group #0 - Ordinary button group
────────────────────────────────
     Button #4:  Today's forecast:^m$?2$
```

Now, let's say that none of the radio buttons are drawn as "selected" for starters. At 11:45:03 in the morning, the user clicks on button #2 indicating it's a rainy day. The active template for group #2 would be defined as:

```text
It's a rainy day at $TIME$
```

At 11:46:37 he clicks on the Forecast button. The host command sent to the BBS would be:

```text
Today's forecast:
It's a rainy day at 11:46:37
```

Notice that the time that is inserted in place of `$TIME$` is the time that the user clicked on the Forecast button, NOT the time he clicked on the "rainy day" button which activated the proper template. This illustrates that text variables, pick lists, and control characters are not "processed" until they are referenced (used) by some other button or template in an active Host Command situation.

## Command Block Segmentation and Templates

_Evidence: 2.00a4._

Remember that a single Host Command can be segmented into multiple "Command Blocks" by separating them with the delimiter `[]`. Here's a real-world example of a host command broken down into several command blocks:

```text
[3:]Template Definition[4]Template chaining[]BBS TEXT
```

If you look carefully at the above host command, three distinct things are happening. First, template #3 is defined with the text "Template Definition". Secondly, the phrase "Template chaining" is chained (fed) into template #4 (whatever that one is) and the final result of the chaining operation is sent to the BBS. Finally, the last command block is processed which happens to be a Direct Host Command, so the text "BBS TEXT" will be transmitted to the Host as well.

If a host command doesn't have one of the command block delimiters like a template definition (eg, `[3:]`), or a template chain directive (eg, `[3]`), or a Direct Host Command Directive (eg, `[]`), then the Host Command is, by default, considered to be a Direct Host Command. The following are all considered Direct Host Commands and they all do the exact same thing:

```text
HELLO^mWORLD^m
HELLO^m[]WORLD^m
[]HELLO^mWORLD^m
[]HELLO^m[]WORLD^m
```

Here are some more examples of Command Blocks using the previous example as a foundation, but this time we throw in another command block. Again, all four of these examples do the exact same thing:

```text
HELLO^mWORLD^m[3:]Template Definition
HELLO^m[]WORLD^m[3:]Template Definition
[]HELLO^mWORLD^m[3:]Template Definition
[]HELLO^m[]WORLD^m[3:]Template Definition
```

## Command Blocks, Radio and Check Box Templates

_Evidence: 2.00a4._

If you think about Command Blocks, you might be inclined to think that figuring out which template definition block of a command block to activate might get insane. It could! Look at the following set of three Radio Button definitions:

```text
Button #1:  [3:]Hello world[3:]This is Pluto
Button #2:  [3:]Hello world[3:]This is Saturn
Button #3:  [3:]Hello world[3:]This is Jupiter
```

What happens if button #2 is clicked, thus activating that template? What template command block is used to create the final, active template? The answer is the last one! The text that becomes the actual active template for template #3 would be this:

```text
This is Saturn
```

If a Host Command references this template as in the following example, you will see that the secondary template definition is the one that is actually in use:

```text
I'm a martian singing in the rain^m$?3$
```

Resulting in:

```text
I'm a martian singing in the rain
This is Saturn
```

In short, Command Blocks are processed in all situations, and if a discrepancy exists where two or more template definitions in the same Host String correspond to the same template group, the last definition is the one that becomes active. This applies even if you are dealing with Check Box buttons. In the above example of the martian, if Buttons #1, 2 and 3 were Check Box Buttons instead, the "Hello World" template definitions would still be lost and would NOT get concatenated together to create the final Host Command. If buttons #1 and #3 are clicked, then template #3 would be:

```text
This is PlutoThis is Jupiter
```

It would NOT be:

```text
Hello worldThis is PlutoHello worldThis is Jupiter
```

## The 3.x Macro Layer - `<<NAME>>`

_Evidence: DLL (preprocessor RVA `0x4c213`/`0x4c244`); corpus (MENU.DEF, MENU.MNU, MENU.MSE, MENU.ENT); [derivation](../research/issue-6-macro-evaluation.md)._

**New in this generation.** Beyond the slot templates, the driver and corpus establish a second expansion mechanism: `<<NAME>>` expands to the value of the text variable `NAME` - anywhere in a command's argument text, including _inside_ a `$…$` reference. No surveyed non-TeleGrafix implementation supports it.

The demo's menu system is built on it. A `.DEF` configuration file sets plain variables with the [set-syntax](5.0-host-commands.md#setting--reading-user-variables-from-host-commands):

```text
!|1^[0000$-=LAB2=Demos$
!|1^[0000$-=CMD2=>TELDEMOS.FN$
!|1^[0000$=-MSG2=Demonstrations of RIPscrip graphics$
```

and the _generic_ menu scenes consume them by macro:

```text
!|1b3Y7YCCAY0000000000TELBUT.BMP|@809U<<LAB1>>       (button label text)
!|1M003W7YCEAW1000000ID=1:$<<CMD1>>$                 (host command, composed inside $...$)
!|@HSKA$&MSG<<FIELDID>>$                             (macro composing a variable NAME)
```

The second line is the striking one: `$<<CMD1>>$` expands `<<CMD1>>` to `>TELDEMOS.FN` _first_, yielding `$>TELDEMOS.FN$` - a [local playback directive](5.3-local-playback.md) assembled at run time. The third composes a variable _name_ from the built-in `$FIELDID$`, then dereferences it with `$&…$` (see [Mouse-Field Identities](5.0-host-commands.md#mouse-field-identities---idn)). One `.MSE` overlay and one `.MNU` screen thus serve every menu in the product; only the tiny `.DEF` files differ. Original-driver execution confirms preprocessing before ordinary `$…$` parsing. The [stage/rescan tables](#shipped-processing-order) give the exact limits; this is no longer an evaluation-order hypothesis.

## Inline Conditionals - `<<IF>> … <<ELSEIF>> … <<ELSE>> … <<ENDIF>>`

_Evidence: corpus (BUTTONS.RIP, TELDEMOS.RET, MENU.RET, SPECLEFX.RIP, FXSHWIMG.FN); SyncTERM absent._

**New in this generation.** The same `<<…>>` bracket introduces conditionals, evaluated before the containing command executes. Keywords are case-insensitive (`<<IF>>` and `<<if>>` both appear). The branch grammar is:

```text
<<IF expr>> text <<ELSEIF expr>> text <<ELSE>> text <<ENDIF>>
```

A comparison has a variable/template left operand and an optionally quoted literal right operand. The shipped operators and reduction rules are [below](#comparison-semantics); the following examples come from shipping TeleGrafix scripts:

**Choosing a background by color depth** - the most common idiom, appearing as the _filename argument_ of a `1R` ([RIP_READ_SCENE](5.5-file-transfer-and-queries.md#rip_read_scene)):

```text
!|1R00000000<<IF $COLORS$<"256">>BLUEBACK.FN<<ELSE>>BLUEFADE.FN<<ENDIF>>
```

**A computed "Back" button** - as a mouse-field host command:

```text
!|1M000M0B37121000000ID=1:<<if $RETURN$!="">>$<<RETURN>>$<<else>>$NULL$<<endif>>
```

If a return scene was recorded (`$-=RETURN=>NEWSPAPR.RIP$`), play it; otherwise do nothing (`$NULL$`).

**Compound conditions** - connectives and parentheses (TELDEMOS.RET, MENU.RET):

```text
<<IF $NO_WIPES$="" OR $NO_WIPES$="NONE">>$>TELPORT.FN$<<ELSE>>$RESET$<<ENDIF>>
<<IF $TGMENU_WIPES$="1" and ($NO_WIPES$="" or $NO_WIPES$="NONE")>>$>WIPE01.FN$<<else>>$NULL$<<ENDIF>>
```

**The slideshow idiom** - the Special Effects demo's image cycler, rotating the same JPEGs that N2_PHOTO.RIP's newspaper gallery displays. The display subroutine FXSHWIMG.FN seeds the rotation on first use, testing whether a variable exists at all via `$INUSE(TV,name)$` (`TV` = the text-variable object class; returns `0`/`1`):

```text
!|1p0000<<IF $INUSE(TV,NEXT_IMG)$="0">>$-=NEXT_IMG=ASTRO.JPG$<<ENDIF>>$&NEXT_IMG$
```

and the "Next Image" button (SPECLEFX.RIP) advances it - a multi-branch `<<ELSEIF>>` spread over continued lines (`\` at line end continues the command):

```text
!|1U4GCUA2E60000<>Next Image<>\
<<IF $NEXT_IMG$="ASTRO.JPG">>$-=NEXT_IMG=JUPITER.JPG$\
<<ELSEIF $NEXT_IMG$="JUPITER.JPG">>$-=NEXT_IMG=BEACH2.JPG$\
<<ELSE>>$-=NEXT_IMG=ASTRO.JPG$\
<<ENDIF>>\
$>FXSHWIMG.FN$
```

State machine, existence test, silent assignment, computed playback: a complete client-side program in five lines of button command. The matching cleanup is `$RESET(TV,NO_WIPES)$`, deleting a variable by name.

### Comparison Semantics

_Evidence: DLL, operand parser RVA `0x4b6e3`, comparison `0x4bd00`, numeric predicate `0x4bc9c`, reduction `0x4bf60`; [primary derivation and distinguishing native examples](../research/issue-6-macro-evaluation.md)._

The left operand is a variable reference (with or without surrounding dollar delimiters) or a `?N` template reference. The right operand is literal text, optionally double-quoted. Quoted text preserves its spaces; unquoted text ends at its first unescaped whitespace or closing group parenthesis, and decoded trailing whitespace is trimmed. The [operand byte grammar](#conditional-operand-byte-grammar) defines the separate lexical stages, escapes and bounded limits. Dollar codes inside the literal or returned operand values are not recursively evaluated by the comparison. A quoted literal on the left, such as `<<IF "2"<"10">>`, is rejected; use a variable with value `2` to ask that comparison.

Operators are `=`, `!=`, `>`, `>=`, `<`, `<=`. If **both** values consist of decimal digits, with an optional leading minus and at least one digit, compare signed integers after the driver’s wrapping 32-bit decimal conversion. Otherwise use case-insensitive byte-string comparison. A leading plus, empty string or embedded/trailing whitespace does not satisfy that numeric predicate. Equality also uses numeric comparison when both values qualify; quotes on the right do not force lexical comparison.

With N=`2`, this checked expression returns `YES`:

```text
<<IF $N$<"10">>YES<<ELSE>>NO<<ENDIF>>
```

With N=`$SHIFT$`, comparing `$N$="$SHIFT$"` is true without querying SHIFT: both compared values are literal dollar text. Comparing to `""` tests emptiness of the returned value, not every possible unavailable-variable sentinel (for example HOSTDIR returns `<NONE>`).

AND and OR are case-insensitive and have **equal precedence, reduced left to right**. There is no operand short-circuiting. Parentheses control grouping. For N=`1`:

| Expression             | Result                                |
| ---------------------- | ------------------------------------- |
| `N=1 OR N=0 AND N=0`   | false                                 |
| `N=1 OR (N=0 AND N=0)` | true                                  |
| `NOT N=1 AND N=0`      | true; see the shipped reduction order |

The reducer repeatedly scans adjacent Boolean/operator/Boolean triples from left to right, then NOT/Boolean pairs, then parenthesized single Boolean values, until one result remains. NOT therefore does not have conventional precedence over an eligible binary reduction. The parser recognizes case-insensitive `NOT `, `AND ` and `OR ` with an actual ASCII space after the word, as detailed [below](#connectors-and-failure-boundaries); preserve this reduction rule rather than substituting a conventional Boolean-expression parser.

IF/ELSEIF/ELSE/ENDIF structure is validated, including nested inactive IF syntax; missing ENDIF rejects preprocessing. Operand parsing is distinct from evaluation: a comparison whose value evaluation fails yields false rather than necessarily aborting the entire preprocessing operation. An inactive parent prevents evaluation of its nested comparison, while named angle substitutions in inactive branch text still have the [earlier-described effects](#definitions-composition-and-side-effects). A malformed structure does not make a new independent command block.

_Reconstruction from original RIPtel 3.1 parser/caller instructions, completed with the explicit portable bounds and classification choices below; [source addresses, limits and distinguishing derivation](../research/issue-90-conditional-operand-grammar.md). This fills issue #90 without changing the comparison or reduction rules above._

These rules apply to **the bytes actually presented to the conditional parser**, after any earlier wire/angle processing. Examples show actual bytes at this stage: every backslash displayed is one byte. They are not host-language string literals. A source spelling at an earlier stage must preserve those bytes through that stage's own quoting rules.

Use byte strings, with NUL as end of input. **Portable classification choice:** `WS` is exactly ASCII HT, LF, VT, FF, CR and space (`0x09..0x0d`, `0x20`); `ALPHA` is ASCII `A..Z`, `a..z`. Case-insensitive keyword matching folds ASCII letters. High bytes are not whitespace or initial name letters under this profile; later payload bytes are preserved. This fixes locale-dependent classification without promising a Unicode identifier or rejecting all control/high bytes as the separate dollar-argument lexer does.

#### Left Reference Scanning and Provider Input

After grouping/NOT handling and leading `WS`, choose one of these forms:

| Form | Conditional scanner behavior | Provider input |
| --- | --- | --- |
| `?N` | Read exactly one case-insensitive MegaNum digit `0..9/A..Z` after `?`; no surrounding dollars | Template slot N, passed as an index |
| Bare reference | First byte must be `ALPHA`; scan as described below | Decoded reference body L |
| `$` followed by a reference | Consume the opening dollar; next byte must be `ALPHA`; scan until its closing dollar | Decoded reference body L, without those two dollars |

A quoted left literal, `_NAME`, a raw prefix directive (`&`, `-`, `+`, `=`, `#`, `*`) or a leading backslash fails this conditional syntax. A leading dollar does not enable a second prefix parser: `$&NAME$` and `$?N$` are not left-reference spellings here. Use `NAME`/`$NAME$` and bare `?N`. A digit cannot start an ordinary left reference; later digits are copied normally, and a template slot can be a digit. The ordinary provider still applies its own name/reference syntax.

After the first reference byte, the conditional scanner is deliberately broader than the provider's name/argument grammar:

| Next source byte | Bare reference | Dollar-enclosed reference |
| --- | --- | --- |
| Backslash followed by a non-NUL byte | Consume both; append the following byte literally | Same |
| Unescaped `$` | Syntax error: no opening dollar | Finish the reference and consume the closing dollar |
| Unescaped `WS` | Finish the reference without consuming the separator | Append the byte |
| Unescaped `=`, `!`, `<`, `>` | Finish the reference before the operator | Append the byte |
| Any other non-NUL byte, including parentheses, comma, quote, underscore, DEL or high byte | Append the byte | Append the byte |
| NUL | No complete comparison can follow | Missing closing delimiter/operator; reject |

An escape bypasses delimiter tests on its following byte; it does not change the required first-byte test. No C/JSON escapes exist: `\\` decodes to one backslash, `\n` to the letter `n`, and `\=` to `=`. A dangling backslash rejects. There is no nesting/balancing of parentheses by this left scanner. It can copy an entire function-style reference, but does not validate its argument bytes or make quotes protect spaces in a bare left reference. Use dollar enclosure or a local escaped space to preserve such spaces.

Skip separator `WS` after the left reference, then require one of the six comparison operators above, preferring the two-byte `!=`, `>=`, `<=` forms. `>>` at that position is a premature conditional terminator, not a `>` operator with an invented RHS.

For an ordinary left reference, submit **exactly** `$&` + L + `$` to the existing [dollar-reference parser](5.1-text-variables.md#variable-resolution-in-3x), then evaluate that parsed reference under the existing conditional provider rules. Preserve L's case and bytes; the provider performs its normal case-insensitive lookup and any name/keyword normalization. Parenthesized argument bytes undergo the **later, separate** [argument decoding](5.1-text-variables.md#argument-bytes-and-local-backslashes). Raw directives are not added to L; the synthetic `&` supplies retrieval semantics, subject to the adopted missing-value/prompt rules.

**Portable validation choice:** the synthesized reference must be one complete reference, without an embedded terminator or trailing material. Otherwise the provider rejects it; do not evaluate an unintended prefix. A left token that this scanner copied is not automatically a legal provider reference. Provider-format rejection or a failed value lookup makes the comparison false under the adopted evaluation-failure rule; it does not turn L into a literal or recursively expand its returned value. A conditional scanner failure (bad initial byte, missing operator/delimiter or excessive token length) is instead a preprocessing syntax failure. A successful empty value is a value, not a failure. Template N goes directly to its existing slot provider and selection rules; it is not rewritten as `$&?N$`.

Examples of the two left decoding stages:

| Left source token | Decoded L / provider input |
| --- | --- |
| `N` or `$N$` | L=`N`; provider receives `$&N$` |
| `$RAND(9,2)$` | L=`RAND(9,2)`; provider receives `$&RAND(9,2)$` with two ordinary arguments |
| `F(MY\ BBS)` | L=`F(MY BBS)`; one ordinary argument `MY BBS` if the provider accepts F |
| `$F(A\\)B)$` | L=`F(A\)B)`; provider's argument stage then decodes `A)B` |
| `$F(A\"B)$` | L=`F(A"B)`; provider rejects the resulting double quote in its argument |
| `$F(A\\\\B)$` | L=`F(A\\B)`; provider rejects consecutive backslashes in the argument |
| `?a` | Template slot 10; `?aX` does not consume X as part of the slot |

The double-quote row describes L's bytes explicitly: the source backslash is consumed and the following double quote is copied as one byte. The provider rejection occurs after successful conditional token scanning. These are normalization cases, not newly executed callback observations.

#### Right Literal Scanning

After the operator, skip leading unescaped `WS`. If the next byte is a double quote, consume it and enter quoted mode; otherwise use unquoted mode. A single quote has no quoting role. The right side is always literal data, not another variable lookup.

Process in this order:

1. NUL ends scanning; an open quote is an error. The enclosing expression still requires a real terminator or connector.
2. In unquoted mode, unescaped `WS` or `)` ends the literal without consuming that separator.
3. Backslash quotes the following non-NUL byte: consume the backslash and append the next byte. **Special pair:** when the next two bytes are `>>`, consume and append both together. Neither closes the condition. Reject a dangling backslash before reading/appending beyond the input.
4. Otherwise unescaped `>>` ends scanning **even inside double quotes**. With a quote still open, this is a missing-quote error; it does not silently end a valid quoted literal.
5. Otherwise a double quote closes a quoted literal and is consumed. In unquoted mode, a quote after the first byte is ordinary payload; it does not enter quoted mode.
6. Append any other non-NUL byte unchanged and continue.

Quoted literals retain all their decoded whitespace. Unquoted literals remove **decoded trailing `WS` only**, even when an escape produced it. The initial pre-literal skip removes unescaped leading whitespace, but an escaped leading space is retained; do not replace that combination with an unconditional trim on both ends. A completed quoted literal must be followed by `WS`, `>>`, a legal connector or a closing group parenthesis; adjacent text is not concatenated.

Besides the delimiters above, all non-NUL bytes are literal payload here, including `$`, single quotes, `/`, `*`, `+`, commas, `[`, `]`, opening parentheses, operators, DEL, high bytes and control bytes that earlier framing permits. In particular, `\"`, `\\`, backslash-space, `\)`, `\$` and `\>>` are valid local spellings; the first two are **not** governed by the dollar-argument restrictions. Escaping an ordinary byte merely copies that byte: no named, octal, hex or Unicode escape decoding is performed. Neither the literal nor the returned left value is recursively evaluated for dollar codes.

An empty unquoted RHS immediately before `>>` or a valid closing `)` is an empty string. So are `""` and an unquoted literal whose trailing-whitespace removal empties it. NUL immediately after the operator/leading whitespace is a missing RHS/termination error. A `)` that ends an empty RHS still needs a matching outer group; `N=)>>` alone is not a valid grouped expression.

#### Connectors and Failure Boundaries

After a complete RHS, skip `WS`, then require `>>`, a closing group parenthesis or the next exact connector. Keywords are case-insensitive **`AND `, `OR ` and `NOT `, including the final ASCII space `0x20`**. Generic whitespace before/after a recognized keyword is a separate step. Thus `AND` followed by a tab or `(` is not a connector; `AND ` followed by a tab or `(` is. NOT is recognized in its existing unary/group context, not inside a reference name or literal. Preserve the earlier reduction order, nesting checks and lack of Boolean short-circuiting.

**Portable bounded policy:** each decoded ordinary left body L and decoded RHS may contain at most **255 bytes**, excluding optional dollar/quote delimiters and storage NUL. Check before every append; an escaped `>>` needs two available slots. Check RHS capacity before trimming, so trimming cannot rescue an over-limit field. These are byte counts, not Unicode character counts. The right bound matches the original explicit checks; the complete left-source/caller safety contract was not established and is fixed here rather than inheriting an unchecked write. A provider result longer than 255 bytes is a nonfatal evaluation failure (false comparison), not an instruction to truncate or copy beyond storage.

There is no separate smaller source-byte limit for an operand; earlier enclosing command/expansion limits still apply. Escapes consume source bytes without counting the removed backslash in the decoded limit: 255 quoted `\A` pairs have 510 payload source bytes and decode to 255 `A` bytes; one more decoded byte rejects. A maximally escaped ordinary left body uses one unescaped initial `ALPHA` plus up to 254 quoted bytes (509 source bytes, or 511 including wrapping dollars). Template syntax is two source bytes; the existing slot service governs its returned value, subject to the bounded provider-result policy above.

Malformed or excessive operands reject the affected preprocessing operation nonfatally: no unsafe read/write, implicit truncation or evaluation of the rejected comparison is required. This does not promise rollback of other provider actions already performed while processing an earlier valid comparison or stage. Value-provider failure remains false, distinct from syntax failure. Inactive parent branches retain their established syntax-check-without-evaluation behavior.

#### Parser-Stage Examples

Each row includes its actual terminator. Values shown are decoded bytes, not a claim about a particular N/F provider. `HT` in explanatory prose means byte `0x09`.

| Parser-stage input | Result |
| --- | --- |
| `N=A\ B>>` | RHS `A B` |
| `N=A\\ B>>` | RHS first decodes to A followed by one backslash, then B is unexpected trailing text: reject |
| `N="a\\\"b">>` | RHS bytes `61 5c 22 62`: one backslash and one quote between a and b |
| `N="a\"b">>` | RHS bytes `61 22 62`: a quote and no backslash |
| `N="a>>b">>` | Reject: unescaped `>>` precedes closing quote |
| `N="a\>>b">>` | RHS `a>>b`; escaped pair is data |
| `N="a\\>>b">>` | Reject: doubled backslash quotes a backslash, leaving unescaped `>>` |
| `N=A\)>>` | RHS `A)`; no group close |
| `(N=)>>` | Empty RHS, then valid group close |
| `1N=A>>` or `$1N$=A>>` | Reject: initial ordinary reference byte must be alphabetic |
| `N=>>` or `N="">>` | Empty RHS |
| `N=` followed by NUL | Reject: missing RHS/termination |
| `N=\ A\ >>` | RHS bytes `20 41`: escaped leading space retained; escaped trailing space trimmed |
| `N="$SHIFT$">>` | Literal RHS `$SHIFT$`; no SHIFT lookup |
| `N=\$N\$>>` | Literal RHS `$N$`; both local backslashes are consumed |
| `N="a"b>>` | Reject: no concatenation after closing quote |
| `N=A AND N=B>>` | Two comparisons with AND |
| `N=A` + HT + `AND N=B>>` | Valid separator before exact `AND ` |
| `N=A AND` + HT + `N=B>>` | Reject: keyword lacks its ASCII-space suffix |
| `NOT (N=A)>>` | Recognized NOT and grouped comparison |
| `NOT` + HT + `N=A>>` | Reject as NOT syntax |

These examples describe source-derived scanning plus the explicitly identified bounded policy. They do not reopen the already adopted numeric/lexical comparisons, user-variable prompt/storage rules or ordinary dollar argument grammar.

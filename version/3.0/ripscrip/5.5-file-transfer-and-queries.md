The wire commands that exchange data and files with the host: text-variable query and definition, local scene playback from the command stream, file queries, timing control for local playback, block-mode file transfer, UU-encoded data blocks, capability negotiation and the multi-lingual groundwork.

## RIP_QUERY

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_query)); HLP (`RIP_Query`; query OBJECT/OPTION keywords, resident queries); original driver/client and [native query derivation](../research/issue-51-deferred-query-order.md); corpus (489 uses in 62 files); SyncTERM (ripper.c:14881, descriptor `1#3#++`)._

_Query the contents of a text variable_

|               |                                        |
| ------------- | -------------------------------------- |
| **Level**     | 1                                      |
| **Command**   | `Σ` (the Escape character, ASCII 27)   |
| **Arguments** | `mode:1 window_num:1 res:2 query_text` |

**Format:** `!|1<escape> <mode> <window_num> <res> <query_text>` **Example:** `!|1<escape>2Q00this is a query $COMMAND$^m`

**Attributes used:** [Base Math](../../glossary.md) (current setting)

> **NOTE:** Σ is used to indicate the Escape character (ASCII 27 or ESC).

The Query Text Variable command instructs the terminal to immediately respond with some piece of information, whether statically stored, stored internally in RAM (dynamic information), or pre-defined text variables.

This command is unique in RIPscrip in the fact that the command character that is used is NOT a printable character. The escape character (ASCII 27) introduces this command as a measure of security: since the query command can query the terminal for critical (potentially private) information, you would not want a user to be able to query another user's terminal for something like his address information. Since most hosts do not allow the user to enter an escape character, this character is ideal for this purpose - using escape allows only the host (under most circumstances) to be in control of any queries.

The query text can contain control characters, pick-list definitions and text variables - see [5.0 Host Commands](5.0-host-commands.md) for these features.

The `<mode>` parameter selects immediate execution or a stored query. **RIPtel 3.1 accepts and stores modes 1–4 but does not execute them on mouse clicks.** Its original left-down/up event paths only dispatch mouse fields; the client forwards those events directly to the driver. An overlapping numbered viewport query, numbered text-window query and both floating queries therefore execute **none** of those four expressions. This shipping omission replaces the inherited click-order claim for RIPtel 3.1; it is not evidence about earlier clients. _Evidence: original handler/event/client paths and [72,972 native query checks](../research/issue-51-deferred-query-order.md#event-path-and-native-checkpoint)._

| Mode | Stored target or execution | RIPtel 3.1 behavior |
| --- | --- | --- |
| 0 | Immediate query | Execute now upon receipt |
| 1 | Floating current-viewport query | Store one global viewport expression; no click execution |
| 2 | Floating current-text-window query | Store one global text-window expression; no click execution |
| 3 | Numbered viewport query | Store on `<window_num>` (0..35) if defined and unprotected; no click execution |
| 4 | Numbered text-window query | Store on `<window_num>` (0..35) if defined and unprotected; no click execution |
| 5 | Mouse-field entry query | Store one expression, execute when the pointer enters a mouse field |
| 6 | Mouse-field exit query | Store one expression, execute when the pointer exits a mouse field |

Modes 1/2 are **floating**: their strings are independent of any numbered entry. Modes 3/4 attach to the specified table entry. No definition executes those stored strings. Sending the same mode/target with case-insensitive `$OFF$` removes the stored expression; defining another nonempty expression replaces it. “Resident” describes stored queries: the shipping `queryDefineResident()` helper is shared by modes 1–6, including floating and numbered forms. It does not name a separate dispatch-order class. Stored query copy/backup ownership is described under [COPY](5.1-text-variables.md#copy).

### Resident Hover Definitions

Modes **5=entry / 6=exit** each own one global handler, shared by identified simple fields and mouse buttons. `<window_num>` is consumed as an ordinary numeric field but its value is ignored for these two modes: it does not select a field, public ID, viewport or text window. The two reserved digits are likewise consumed and ignored; send `00`. Invalid/incomplete numeric framing still follows the existing [parser boundary](1.1-protocol-and-command-hierarchy.md#command-syntax---parser-exact-behavior). No definition executes its stored expression, changes membership or starts an entry/exit. [Recovered definition/consumer evidence and completion limits](../research/issue-132-hover-handler-lifetime.md).

| Supplied text, after outer command framing | Definition result for that mode |
| --- | --- |
| Empty C-string prefix / missing text | Nonfatal definition error; retain previous handler; do not install an empty replacement |
| Exactly `$OFF$`, ASCII case-insensitive, before the first NUL | Remove the handler; retain field memberships |
| Any other nonempty accepted source | Replace with an owned copy of its raw bytes; do not expand variables, angle text, escapes or controls as a storage test |

The sentinel compares the **entire C-string prefix**: `$oFf$` removes; ` $OFF$`, `$OFF$ `, `$OFF$suffix`, quoted/escaped spellings and a variable whose later value is `$OFF$` are ordinary stored sources. `$OFF$` followed by a NUL and otherwise ignored suffix bytes matches at the consumer's C-string boundary; this does not add a new raw-NUL wire escape. Only an explicit definition command can remove/replace a handler; obtaining `$OFF$` during later host expansion does not redefine it.

**Explicit portable stored-source bound:** accept at most **1023 bytes** before the storage NUL, excluding command/numeric fields. Reject a longer definition nonfatally **before replacing/removing the old handler**; do not truncate it into another expression/sentinel. This bound completes the original 1024-byte query scratch route; the original owned-string allocator alone supplies no complete safe oversized-input contract. It is separate from enclosing command framing and the [4096-byte host working-prefix/embedding policy](5.2-templates-and-conditionals.md#response-and-embedding-byte-limit). A committed callback subsequently uses that normal host pipeline, including angle preprocessing, block handling, two ordinary response passes, limits, prompt and failure rules. Parser success does not become a Boolean host-action result: definition/host failures remain void/nonfatal and do not close the connection or roll back earlier effects.

Membership is maintained **even while both handlers are absent**. Enabling/replacing one while the pointer already lies inside does not manufacture a new entry on a same-position movement. Handler availability/source is read separately immediately before each surviving callback, not frozen once for the whole movement. See [hover commitment, lifecycle and vectors](4.2-mouse-fields-and-pointer.md#hover-and-callback-context) for exact traversal, suspension and reset rules. Stored modes 1–4 remain unexecuted on physical clicks.

### Stored Click Modes and Historical Intent

**No same-click mutation policy exists for modes 1–4 in RIPtel 3.1.** The event path does not scan those queries, execute an earlier one, snapshot their eligibility, or re-evaluate later regions. Disabling, deleting or moving a later region, or changing the current selection through an earlier mode 1–4 expression, cannot occur during that click because the earlier expression is never invoked. Implementors reproducing this client must preserve that omission; a client that implements the older documented click feature needs a separately specified mutation policy. Immediate-mode and mouse-field actions retain their actual [host-expression behavior](5.2-templates-and-conditionals.md); this finding does not suppress those execution paths.

**Historical click contract (2.00a4 documentation, not observed RIPtel 3.1 behavior).** The inherited record says modes 1/2 act on the current viewport/text window and modes 3/4 on the numbered target; text-window queries use text-cell mouse coordinates. It limits activation to clicks outside buttons/mouse fields. Its later A4 explicit sequence is:

1. Numbered screen-port/viewport queries, slots 0..35, when enabled and containing the original mouse-down point.
2. Numbered text-window queries, slots 0..35, when enabled and containing that point.
3. The floating current-viewport query, when that viewport contains the point.
4. The floating current-text-window query, when that window contains the point.

The A4 prose then ignores further click handling until release. An older A1 sentence instead says resident text-window queries precede viewport queries; it conflicts with the later explicit A4 list and supplies no numbered/floating distinction that resolves the discrepancy. Neither statement establishes a shipping RIPtel 3.1 order, and neither specifies whether earlier query effects change later eligibility. They are retained here as documentary intent, without inventing an operational order or snapshot rule for this client. See the [derivation](../research/issue-51-deferred-query-order.md) for original addresses, positive execution controls and scope.

Some examples of query statements:

```text
                      ^m     Send a carriage return to the BBS now!
My name is $FULL_NAME$^m     Send text "My name is <insert-name-
                             here>" followed by a  carriage return
                             to the BBS.  The <insert-name-here>
                             will be replaced with whatever the
                             variable $FULL_NAME$ contains.
```

> **NOTE:** The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc. It should be set to 00 for compatibility with future releases.

**The 3.x record.** The corpus is saturated with the immediate form (mode 0) used as a _command executor_ rather than a data query: `$COMPAT$` (set 1.54-compatible environment), `$COFF$$DTW$` (cursor off + deactivate text window), `$D(1)$` (delay - 197 uses driving the wipe animations), `$MCURSOR(n)$`, `$SBAROFF$`, and conditional dispatch such as `!|1<ESC>0000<<IF $TGMENU_WIPES$="1">>$>WIPE01.FN$<<else>>$NULL$<<ENDIF>>` (see [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md)). Deferred modes 5/6 appear in the corpus wired to mouse-field _entry/exit_ status-line updates (`.MSE` overlays), a 3.x extension of the documented click modes - see [Query Deferral Modes](5.0-host-commands.md#query-deferral-modes). One authoring typo (CURVES.RIP's `|1<ESC>…` with no `!`) shows the shipping driver's tolerant introducer handling. _Evidence: corpus; HLP._

## RIP_DEFINE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_define) - flagged obsolete there already); HLP (`RIP_Define`; the DLL also exports `RIP_DefineTextVariable`); SyncTERM (ripper.c:15899) - not observed in the RIPtel demo corpus._

_Define a text variable_

|               |                      |
| ------------- | -------------------- |
| **Level**     | 1                    |
| **Command**   | `D`                  |
| **Arguments** | `flags:3 res:2 text` |

**Format:** `!|1D <flags> <res> <text>` **Example:** `!|1D00700text_var,60:?question?default data`

**Attributes used:** Base Math (current setting)

This command is used to create a text variable on the Client (terminal) system. Simply put, a text variable is a piece of information assigned to an identifier that can either be saved to the terminal's [persistent variable store](../../glossary.md) (static variables) or kept in memory only (dynamic variables). Per the 2.00a4 draft, identifiers are 1-12 characters - any alphanumeric character and underscores (`_`), where neither an underscore nor a number can be the first character; RIPtel 3.1's help raises the name limit to 20 characters for the in-line variable syntax (see [5.0](5.0-host-commands.md#setting--reading-user-variables-from-host-commands)), while SyncTERM's reconstruction keeps 12. Values run to 255 characters; where and how persistent variables are stored is implementation-defined.

The `<flags>` parameter combines three separate values into one MegaNum flag that determines how the variable definition will operate:

| Value | Description of Flag                   |
| ----- | ------------------------------------- |
| 001   | Save variable to the persistent store |
| 002   | Cannot specify a blank response       |
| 004   | Non-interactive query                 |

When a variable is flagged as persistent, it becomes a part of the Client system's actual configuration: the value is saved indefinitely until either changed or manually erased. You may choose not to allow the user to enter a blank response, requiring them to enter some piece of information for the variable.

The last flag determines whether the definition is interactive or not. An interactive definition will attempt to define the variable: if it already exists, the value pops up on the screen asking the user to confirm it is correct; if it does not exist, a similar pop-up box appears asking the user to enter data for the given variable. In a non-interactive situation, the Client system checks whether the variable exists. If it does, nothing happens (unless a default response is specified in this command, whereby the Client's variable is updated with the new information). If the value is not defined, the definition becomes interactive by default, since the user actually has to enter something anyway.

The `<text>` parameter is segmented in nature, much like the [RIP_BUTTON](4.3-buttons.md#rip_button) command's. Its syntax:

```text
variable-identifier[,field-width]:[?question-text?][default-value]
```

An example:

```text
FULL_NAME,30:?What is your full name?John Doe
```

The first section is the variable-identifier, immediately followed by an optional field-width (default 60; limit the values to 1-60). The colon (`:`) indicates that the identifier field is completed and that the remainder contains the question and/or the default response (if any) - with neither, the parameter reads `TEXT_VAR,width:` with no additional data. The question-text is specified between question marks (`?this is a question?`). The remainder is a default-value for the variable's contents; it may be omitted so that the user must enter his/her own value instead of some "canned response".

> **NOTE:** The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc. It should be set to 00 for compatibility with future releases.

THIS COMMAND IS NOW OBSOLETE. USE THE SPECIALLY ENHANCED TEXT VARIABLE SYSTEM WITHIN QUERIES OR HOST COMMANDS TO PRODUCE THE SAME RESULTS AS THIS COMMAND AND MUCH MORE! _(v2.A1)_

The corpus confirms the succession: the demos define hundreds of variables exclusively through the `$-=NAME=value$` [set form](5.0-host-commands.md#setting--reading-user-variables-from-host-commands) and the `$[directives]NAME[@question][=default]$` prompt syntax, never `1D`. The host may also delete variables; RIPtel confirms with the prompt _"The host wants to delete the variable %s. Proceed?"_, and protected variables trigger a "Data Security Activated" message. _Evidence: corpus; HLP._

## RIP_READ_SCENE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_read_scene)); HLP (`RIP_ReadScene`; "Can't locate local RIPscrip scene file %s"; DLL export `RIP_PlaybackLocalRIPFile`); corpus (92 uses in 34 files); SyncTERM (ripper.c:16534)._

_Playback local .RIP file_

|               |                     |
| ------------- | ------------------- |
| **Level**     | 1                   |
| **Command**   | `R`                 |
| **Arguments** | `res:8 filename...` |

**Format:** `!|1R <res> <filename>` **Example:** `!|1R00000000testfile.rip`

**Attributes used:** Draw Color, Back Color, Line Style, Fill Style, Write Mode, Font Style, Port (dependent on the contents of the source file), Base Math (current setting)

`1R` plays the selected local file synchronously. The caller waits while that file is the input source and resumes when playback returns. Use eight zero digits in the reserved field. The shared file engine is also used by [HCL scene playback](5.3-local-playback.md#local-scene-playback---filerip). [RIPtel 3.1 derivation](../research/issue-170-local-scene-boundaries.md)

### Scene Name and Lookup

Supply a nonempty RIP text parameter for the wire filename. After framing, apply angle preprocessing and one ordinary expansion pass with the same feature mask as graphical text. This permits data variables, user-variable fallback and ordinary backslash quoting. The filename pass skips inserted text for the rest of that pass. The ordinary host-response pass pair, control notation, pick lists and playback filename substitutions do not apply. For example, if `SCENE` holds `child.fn`, `!|1R00000000$&SCENE$` looks up `child.fn`. A literal `child.fn` takes the same lookup path.

1. Apply the [ASCII filename-tail predicate](#name-preparation-and-lookup) to the expanded name. An unacceptable final byte or an empty result leaves nothing to open. Otherwise retain the longest acceptable suffix. Append `.RIP` if that suffix contains no period. For example, `prefix*child` selects `child.RIP`, while `child*` is unusable. The star here has its literal byte value and does not substitute the field ID.
2. Resolve the resulting scene resource name using the configured host directory, shared `ICONS` and ordered icon search path. The supported resource names are case-insensitive. Retain an explicit extension such as `.FN` or `.TXT`. Scene lookup has no FILE_QUERY alias step or reply record. The 20 decoded byte bound and the `*?[]` replacements belong to the HCL prefix's [shared filename contract](5.3-local-playback.md#shared-filename-contract).
3. On a hit, open and play that file. A lookup miss or a failure to open the file returns to the caller without entering a child scene or generating a status reply. The client can report a local diagnostic. The resolver disables retrieval, including when invoked by wire `1R`. Globally disabled RIP graphics processing suppresses the wire command before filename evaluation.

### File Boundaries and Nested Scenes

Start each file at a fresh RIP line boundary and with no partial ANSI escape from its caller. The local text reader folds CRLF to LF. A bare CR, LF or form feed still terminates an ordinary RIP command, subject to the normal [backslash continuation rules](1.1-protocol-and-command-hierarchy.md#chaining-continuation-and-line-endings). The byte loop skips NUL. The RIPtel 3.1 text reader also treats DOS Ctrl+Z as end of file. Any bytes routed as ordinary text use the terminal/column path, which supplies CR before LF. RIP consumes its own terminator before that text path.

EOF does not add a CR or dispatch an unfinished command. Discard any incomplete RIP command or ANSI escape from the file. Execute the remainder of the caller in its own input context. Keep completed child effects on drawing state, pixels and text. For example, a color or font left changed by the child still affects the parent's next draw.

An authored nested `1R` **must be the final command on its line, followed by CR**. A following CRLF is also suitable. The shipped ordinary parser dispatches a valid `1R` on pipe as well as on a line ending. After normal return it uses the same delimiter to select the command-opcode state for pipe or line-end state for CR. This describes the compatibility parser's ordinary case. A pipe followed by another opcode remains outside the inherited authoring rule.

The shipped nesting counter records active playback depth for cancellation and supplies no numeric recursion limit. A portable implementation may bound active scenes. If it cannot admit another scene, treat the refused invocation as a local no-action return before consuming child data. Keep the active callers and their completed effects. A refused HCL playback token still completes with an empty replacement. Authors must use finite scene chains.

### Local Input and Replies

Scene bytes are processed locally as input. They are never forwarded verbatim as output. Commands reached during playback can still generate normal host replies. This holds for both `1R` and `$>FILE.RIP$`. For example, an immediate [RIP_QUERY](#rip_query), a valid [FILE_QUERY](#rip_file_query), or an enabled ANSI device status report uses its usual output path. An active connection is required for transmission. Client [output conversion](9.2-versions.md#engine-replies-and-terminators) is separate from file input normalization.

On normal return, HCL playback completes with an empty replacement. The parent response finishes its remaining expansion and sends any nonempty result as usual. A child reply produced during playback therefore precedes the parent's response. It is an independent reply and does not replace or become part of the parent's working text.

### Independent Playback Examples

Assume MegaNums, an identity world-to-device map, an active viewport covering all points, COPY mode, draw color 1, and an active connection. In the byte strings below, `\r` and `\n` each denote one byte and `\x1b` denotes ESC.

```text
CHILD.RIP = !|c02\r\n!|1\x1b0000CHILD\n!|X0200
caller    = !|1R00000000CHILD\r!|X0300\r
```

The file changes draw color to 2 and sends the five bytes `CHILD`. It does not draw (2,0), since the last command has no delimiter. The caller draws (3,0) in color 2. Replacing the two child terminators with CR, LF, CRLF or form feed gives the same RIP results. Appending CR to the file instead also draws (2,0) in color 2. The shipped parser's normal pipe case `!|1R00000000CHILD|X0300\r` also dispatches the parent point after playback. The line-final CR form is the authored nested form.

For a separate HCL response `$>CHILD$OK`, the outbound byte sequence is `CHILDOK`, issued as `CHILD` from the file and then `OK` from the parent. If the scene is missing, only `OK` is sent. For independent reply cases, use a child containing `!|1F000000PRESENT.RIP\r`, with a locally readable resource at that name, or the ANSI status request `ESC [ 5 n` (bytes `1b 5b 35 6e`). The former sends ASCII `1`. The latter sends `1b 5b 30 6e`. Neither result depends on which playback form opened the file.

**The 3.x record.** In the corpus this is the _subroutine call_ of an entire scene architecture - `.FN` function scenes, `.DEF` variable definitions, `.MSE` overlays - and it gains three undocumented argument forms: _Evidence: corpus._

- **Plain `.TXT` files**: `!|1R00000000DRAGON.TXT` inside an open `1e` column region feeds the file's ordinary text into the columns with word wrapping. See [Flowing Whole Files](3.1-column-text-system.md#flowing-whole-files---1r-on-plain-text).
- **Overflow pages**: `!|1R00000000$OVERFLOW(1,CUR)$` re-reads the current page of a column stream's overflow buffer ([pagination](3.1-column-text-system.md#pagination---overflow-and-resetoverflow)).
- **Computed filenames**: `!|1R00000000<<IF $COLORS$<"256">>BLUEBACK.FN<<ELSE>>BLUEFADE.FN<<ENDIF>>` - the corpus's ubiquitous color-depth dispatch - and `$&MAIN_STORY$` variable dereferences (NEWSPAPR.RIP). See [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md#inline-conditionals---if--elseif--else--endif).

The host-command twin of this command is the `$>FILE.RIP$` playback prefix - same engine, click-triggered - compared in [5.3 Local File Playback](5.3-local-playback.md#playback-prefixes-vs-dedicated-commands).

## RIP_FILE_QUERY

_Query resource existence and metadata, with exact 3.0 replies_

|               |                            |
| ------------- | -------------------------- |
| **Level**     | 1                          |
| **Command**   | `F`                        |
| **Arguments** | `mode:2 res:4 filename...` |

**Format:** `!|1F <mode> <res> <filename>` **Example:** `!|1F040000MiXeD.RiP`

**Attributes used:** Base Math (current setting). The reserved field is consumed but ignored by this handler; send it as zero. Modes 0..4 are the numeric values printed below as 00..04. **Evidence:** original RIPtel 3.1 driver slot 94/handler 0xbde4, original format strings/name/lookup/metadata/send consumers and the [derivation](../research/issue-168-file-query-replies.md). This replaces the inherited 2.00a4 dot-only mode 04 description in the current 3.0 reference; [earlier editions](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_file_query) remain historical records.

The host uses this command for the [resource staleness check](6.2-asset-delivery-and-storage.md#the-delivery-workflow). Lookup is local, through the ordinary connection/host directory → shared ICONS → configured search-path order, with retrieval disabled. It is not a request to download, display or delete the resource. Current graphics port, viewport activation/protection and drawing colors do not determine the file result.

### Name Preparation and Lookup

Keep two distinct names: **N**, the prepared name placed in a mode 04 reply, and **Q**, the resource name used for lookup. Neither is the resolved filesystem path or a spelling read back from the directory.

1. Copy the supplied filename. This handler performs **no HCL evaluation or playback filename substitutions**: `*`, `?`, `[` and `]` do not stand for field identity, mouse buttons or modifiers here. Dollar text is not evaluated as a variable or local-playback directive.
2. The original ASCII filename-tail preparation rejects an empty string or an unacceptable final byte. Its acceptable byte set is **0x20..0x7f**, excluding `" * + , / ; < = > ? [ ] |`. If the final byte is acceptable, keep the longest trailing run of acceptable bytes. If every byte is acceptable, keep the whole string. This is a byte predicate, not whitespace trimming; spaces, periods, dollar signs, colon and backslash pass it. Uppercase ASCII a..z in that retained run to form N. A name with no usable tail produces no reply.
3. Split N into DOS drive/directory/name/extension components and reconstruct **only name+extension** as Q. Discard drive and directory for this lookup; do not add those prefixes to the resource search path. N retains its prepared spelling for the reply.
4. Apply the original ordered legacy-marker rewrites to Q: try `.ICN→.BMP`, then `.HIC→.BMH`, then `.MSK→.BMM`, stopping at the first matching rule. A rule finds its first occurrence of the old marker, replaces that marker **and the remainder of Q** with the new marker, and marks this query as an alias. Ordinary names ending in an alias extension therefore have the expected extension translation. N is not rewritten. No default extension is appended when none is supplied.

For example, `MiXeD.RiP` prepares N=Q=`MIXED.RIP`. `PiXeL.iCn` prepares N=`PIXEL.ICN` and Q=`PIXEL.BMP`. The string-rewrite helper is not a last-extension parser: `A.ICN.EXTRA` looks up `A.BMP` but reports N=`A.ICN.EXTRA`. Tail preparation also is not placeholder expansion: `Ab*tail.icn` keeps N=`TAIL.ICN` and looks up `TAIL.BMP`, whereas a final `*` produces no usable tail. Backslashes are not HCL escapes in this handler. These preparation rules describe the bounded string operation; available resources remain governed by the existing [lookup namespace](6.2-asset-delivery-and-storage.md#lookup-order-file-override), not arbitrary path access.

### Exact Engine Reply Bytes

In the table, `N` is the name above, `S` is signed 32-bit decimal reported size, and `D.T` is the file's **local last-modification time** formatted exactly `MM/DD/YY.HH:MM:SS`. All six date/time fields are two digits; the hour is 24-hour. There are no spaces around separators. `\r` denotes one byte **0x0d**, not two printable characters. No reply includes a storage NUL.

| Mode | Lookup succeeds, file opens and requested metadata succeeds | Lookup misses | File opens, but metadata query fails |
| --- | --- | --- | --- |
| 00 | `1` | `0` | Metadata is not requested; send `1` |
| 01 | `1\r` | `0\r` | Metadata is not requested; send `1\r` |
| 02 | `1.S\r` | `0\r` | `1.0\r` |
| 03 | `1.S.D.T\r` | `0\r` | `1.0.00/00/00.00:00:00\r` |
| 04 | `1.N:S.D.T\r` | `0.N:0.00/00/00.00:00:00\r` | `1.N:0.00/00/00.00:00:00\r` |

The **colon after N** in mode 04 is required. Periods inside N are ordinary filename bytes, and N is emitted literally without escaping; match the prepared request name rather than blindly treating every period as a field separator. Mode 04's miss is the full zero-metadata record, not the simple `0\r` used by modes 01..03.

A lookup hit followed by **open failure sends no reply in any mode**, including existence-only modes. That is different from a miss. Modes 02..04 require the subsequent file-metadata call even though file length was obtained earlier; if that call fails, the leading `1` remains but size/date/time use the zero placeholders above. On metadata success, the handler formats the selected length as signed decimal; a failed underlying length request can therefore yield `-1` unless successful alias conversion replaced it. Do not reinterpret an open failure or signed length error as an ordinary lookup miss.

**Suppression/rejection:** globally disabled RIP graphics processing suppresses this handler's lookup/reply independently of current-port state. Invalid mode, missing/empty raw filename or unavailable scratch storage reports the normal local command error and emits no query reply. An unusable prepared name silently emits none. No connected client transport means no wire transmission even if the engine generated a reply. There is no new timeout/error reply or automatic transfer.

The engine hands the reply string directly to the client send boundary; it does not run it through HCL substitutions. The recovered RIPtel client can append **LF (0x0a) after CR** according to its output setting, so an engine `...\r` may appear on that client's connection as `...\r\n`. Mode 00 has neither ending. The command's canonical reply above is the engine byte sequence; this client-level conversion does not add a second CR or make CRLF an intrinsic FILE_QUERY format. See the existing [engine/client terminator distinction](9.2-versions.md#engine-replies-and-terminators).

### Legacy Bitmap Alias Sizes

Start with the opened resource's ordinary file length L. **Only a query rewritten by one of the three legacy-marker rules** attempts a translated size; a direct `.BMP`, `.BMH` or `.BMM` query uses ordinary length.

For an alias, read the initial **14-byte BMP file header** and **40-byte information-header prefix**. If either read is short/fails, or the initial bytes are not `BM`, keep L. No raster decoding, palette adoption, display or mask loading is involved. For an ordinary Windows BMP with positive width W and height H in the recovered helper's positive 16-bit domain, use:

`S = 6 + 4 × ceil(W/8) × H`

This is the legacy planar icon-equivalent length: six header bytes and four plane rows of ceil(W/8) bytes each. The same formula is used for **ICN, HIC and MSK aliases**, regardless of the BMP's actual bit depth or file length. It does not use DWORD-padded BMP row bytes or add an extra hot-icon/mask record. Direct BMP lookup never performs this conversion merely because the content begins BM. The date/time still comes from the opened translated resource; only the reported size is converted.

**Explicit portable completion:** use ordinary L for unsupported header layouts, zero/negative dimensions or dimensions outside **1..32767**, rather than adopting signed-low-word wrap or negative translated lengths from an invalid/out-of-domain header. For modes 03/04, a timestamp that cannot be represented/converted is treated as metadata unavailable and uses that mode's metadata-failure record. Mode 02 with a successful metadata query does not need to convert the timestamp and retains S. These are safe metadata completions, not new decoder requirements or claims of native parity outside the ordinary header domain. Existing length-query errors retain their separate signed representation. Metadata failure overrides the size with zero even when an alias length was computed successfully.

### Independent Reply Vectors

Assume a successful local metadata value **1993-01-02 03:04:30** and literal engine endings as shown. With `MIXED.RIP` length 20345, the full command `!|1F040000MiXeD.RiP` yields exactly:

`1.MIXED.RIP:20345.01/02/93.03:04:30\r`

Changing mode to 00/01/02/03 yields respectively `1`, `1\r`, `1.20345\r` and `1.20345.01/02/93.03:04:30\r`. No reply uses the mixed-case wire spelling or the resolved path.

A valid **9×2, 1-bit BI_RGB BMP** has 14+40 header bytes, two four-byte palette entries and two four-byte padded raster rows: **70 actual bytes**. Let it exist as `PIXEL.BMP` with that same timestamp:

| Query | Lookup | Reported size and mode 04 engine reply |
| --- | --- | --- |
| `PiXeL.iCn` | `PIXEL.BMP` | S=6+4×2×2=**22**; `1.PIXEL.ICN:22.01/02/93.03:04:30\r` |
| `PiXeL.bMp` | `PIXEL.BMP` | S=**70**; `1.PIXEL.BMP:70.01/02/93.03:04:30\r` |
| `MISSING.ICN`, mapped resource absent | `MISSING.BMP` | `0.MISSING.ICN:0.00/00/00.00:00:00\r` |
| `PIXEL.ICN`, lookup hit/open fails | `PIXEL.BMP` | **No reply**, including modes 00/01 |
| `PIXEL.ICN`, open succeeds/metadata fails | `PIXEL.BMP` | `1.PIXEL.ICN:0.00/00/00.00:00:00\r` |

A failed/short alias header read retains ordinary length; a usable 70-byte file whose initial bytes are not BM reports 70 rather than 22. An opened zero-length ordinary file has mode 02 success `1.0\r`; that byte form alone does not distinguish it from the metadata-failure placeholder. With client LF insertion enabled, append a single LF to each CR above; a mode 00 `1` stays one byte.

## RIP_DELAY

_Added in RIPscrip v2.A0._

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_delay)) - not in the RIPSCRIP.HLP name inventory, not observed in the RIPtel demo corpus, not in SyncTERM._

_Causes the Client Terminal to Pause_

|               |                  |
| ------------- | ---------------- |
| **Level**     | 3                |
| **Command**   | `D`              |
| **Arguments** | `delay_period:4` |

**Format:** `!|3D <delay_period>` **Example:** `!|3D002D`

**Attributes used:** Base Math (current setting)

This command will cause the remote terminal to pause for `<delay_period>` number of "timer ticks". A Timer Tick is defined as being 1/60th of a second, so a delay period of 60 would be equal to one full second of delay.

During the time period of the delay, the remote terminal should be queueing up any incoming RIPscrip code or raw text (if any) into some form of internal buffer to prevent character loss. After the delay period is complete, the data in that buffer (if any) should be processed immediately and the terminal should resume processing the incoming stream of data.

**The 3.x record** points to this command having been superseded by the text-variable form: the corpus performs all of its pacing - 197 occurrences - with `$D(1)$` inside [RIP_QUERY](#rip_query) commands (`!|1<ESC>0000$D(1)$`, the heartbeat of every wipe animation), and RIPSCRIP.HLP carries a `D` _variable_ processor (`tvarProc` list) but no `RIP_Delay` command name. See [5.1 Text Variables](5.1-text-variables.md). _Evidence: corpus; HLP._

## RIP_BAUD_EMULATION

_Added in RIPscrip v2.A0._

_Set the live rate for local RIP playback_

|               |                                                    |
| ------------- | -------------------------------------------------- |
| **Level**     | 3                                                  |
| **Command**   | `e`                                                |
| **Arguments** | `rate_val:2` in RIPtel 3.1, `rate_val:4` in 2.00a4 |

**Format:** `!|3e <rate_val>` **RIPtel 3.1 example:** `!|3e8C` sets 300 in base 36.

**Attributes used:** Base Math (current setting)

The inherited [2.00a4 form](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_baud_emulation) specifies four digits. RIPtel 3.1 decodes the first two numeric digits and its handler uses only that value. For instance, the inherited four-digit `01UN` example delivers 1 to this client. Use two digits for RIPtel 3.1 or use the decimal [BAUDEMUL setter](5.1-text-variables.md#baudemul) for larger rates. Zero selects full speed.

### Live Playback Rate and ENV State

There is one live rate per interpreter. `3e` and `$BAUDEMUL(rate)$` replace it. `$BAUDEMUL$` reads it. The value governs local file playback through the shared file engine. It does not change connection receive speed or set a delay on received network bytes.

The live value starts at 0 and survives ordinary [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows), including a reset reached during a scene. ENV records have no rate fields. Selecting a different slot with `2E` does not assign a rate, and defaulting ENV records during SOFT leaves the live value in effect. [ENV backup](7.2-data-backup-areas.md#environment-table-save-area) saves the live rate alongside the table and current index. Restoring such a backup explicitly restores that rate.

Playback uses the live value while reading the file. In RIPtel 3.1, a nonzero value supplies a byte group size and a nominal delay between groups, approximating ten bit times per byte. A live change to another nonzero rate is picked up during the byte loop. At 2,400, a group has seven bytes with a scheduled delay of 29 ms. At 9,600, a group has fifteen bytes with a scheduled delay of 15 ms. File decoding, rendering and clock resolution affect elapsed time. Zero disables the pacing waits. [Original timing and state derivation](../research/issue-172-local-playback-baud.md)

### Independent Rate Examples

Set the live rate with `$BAUDEMUL(2400)$` and start local playback with a defined nonzero ENV selected. Replay these three lines. The markers `\x1b` and `\r` represent ESC and CR bytes.

```text
!|1\x1b0000BEFORE=$BAUDEMUL$\r
!|*\r
!|1\x1b0000AFTER=$BAUDEMUL$\r
```

The connected host receives `BEFORE=2400` and `AFTER=2400` as two replies. ENV 0 is selected by the reset. Reader bytes on both sides of the reset remain paced at the same rate. The reset does not start a new pacing group. Timing measurements can isolate the scheduled waits from time spent executing the reset.

For a separate fixture, start with defined ENV 0 and ENV 5 and select 0. Set 2,400 and save `$SENV$`. Select 5 with `!|2E05`. The getter still returns `2400`. Set 9,600 with `$BAUDEMUL(9600)$`, then select 0 with `!|2E00`. The getter returns `9600`, and the next file uses that rate regardless of the selected slot. The draft form `$BAUDEMUL(5,2400)$` is rejected and leaves 9,600 in effect. Now apply `$RENV$`. The backup explicitly restores `2400` alongside ENV 0 and the saved table.

## RIP_ENTER_BLOCK_MODE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_enter_block_mode)); HLP (`RIP_EnterBlockMode`; "Invalid file transfer protocol number", upload confirmation "Upload file(s) '%s'?", DLL exports `RIP_GetBlockModeFilename`/`RIP_GetBlockModeTransferType`; RIPtel itself uses Zmodem for actual transfers); SyncTERM (ripper.c:17069; manual parse from 17150) - not observed in the RIPtel demo corpus._

_Enter block transfer mode with host_

|               |                                                  |
| ------------- | ------------------------------------------------ |
| **Level**     | 9                                                |
| **Command**   | `Σ` (the Escape character, ASCII 27)             |
| **Arguments** | `mode:1 proto:1 file_type:2 res:4 [filename] <>` |

**Format:** `!|9<escape> <mode> <proto> <file_type> <res> [filename] <>` **Example:** `!|9<escape>00010000ICONFILE.BMP<>`

**Attributes used:** Port (in image or local-playback file types), Base Math (current setting)

This command is used to auto-initiate any desired File Transfer Protocol. The `<filename>` parameter is optional on downloads, required for uploads, and if omitted must be replaced with a `<>` parameter (end of string).

The `<mode>` parameter specifies upload or download: "1" for upload mode, "0" (zero) for download mode. A filename is required for uploads. If the user has Data Security enabled on the terminal, they are prompted to OK the upload before it proceeds (RIPtel asks "Upload file(s) '%s'?"). If the user does not authorize the upload, ten Ctrl-X's (ASCII 24 or CAN) are sent at one-tenth second intervals. The `<file_type>` parameter is ignored for uploads.

### Transfer Protocols

The `<proto>` parameter is the file transfer protocol specifier, merged here with SyncTERM's 3.0-era dispatch (ripper.c:17187-17300):

| Value | Protocol | Filename Required? | SyncTERM |
| --- | --- | --- | --- |
| 0 | Xmodem (checksum) | Yes | supported |
| 1 | Xmodem (CRC) | Yes | supported |
| 2 | Xmodem-1K | Yes | supported |
| 3 | Xmodem-1K (G) | Yes | supported |
| 4 | Kermit | Yes | **rejected** |
| 5 | Ymodem (batch) | No | supported |
| 6 | Ymodem-G | No | supported |
| 7 | Zmodem (crash recovery) | No | supported |
| 8 | Zmodem (no crash recovery) _(v2.A0)_ | No | - |
| 9 | Super Kermit _(v2.A4)_ | No | - |

### File Types

The `<file_type>` parameter determines what type of files are to be received during the block transfer:

| Value | Description of Block Transfer Contents                         |
| ----- | -------------------------------------------------------------- |
| 0     | RIP file sequence (display it)                                 |
| 1     | Generic file sequence (store files for future use) _(v2.A0)_   |
| 2     | BMP file sequence (store them in proper directories) _(v2.A1)_ |
| 3     | Image file sequence (display it) _(v2.A0)_                     |
| 4     | COMPOSITE DYNAMIC file sequence (batch protocols only)         |
| 5     | ACTIVE DYNAMIC file sequence (batch protocols only)            |

Whether the `<filename>` is specified or not, this command must have a `<>` sequence after the filename (even if there is none). With a filename, using Xmodem/CRC:

```text
!|9<escape>01020000filename.icn<>
```

Without a filename, using Zmodem:

```text
!|9<escape>07040000<>
```

In brief: type 0 plays the received RIP file back like any other local RIP file; type 1 stores generic files for future use with no processing; type 2 is identical to type 1 but designated for icon files (`.BMP`, `.BMH`, `.BMM`) - use type 1 instead, as type 2 might change in future revisions; type 3 displays received JPEG images through the current [RIP_IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style) settings (full current-viewport size if none recorded); types 4 and 5 (batch protocols only) route each received file by its extension, storing it - and for ACTIVE DYNAMIC, also playing/displaying `.RIP` and `.JPG`/`.GIF` files on arrival. _(v2.A0)_ The full per-extension routing table, and where "the proper directory" is for every file type - the connection-directory model - are in [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md#block-mode-routing---the-extension-table); files with unrecognized extensions are simply placed there with no further processing.

> **NOTE:** This command must be terminated with a carriage return. A vertical bar (`|`) command delimiter cannot be used to separate this command from a subsequent one on the same line. In other words, this command must be the last command on a line of text. The protocol must begin on the very next line.

SyncTERM also sandboxes the command: filenames containing `\` are rejected, and received files land in a per-BBS `RIP` cache subdirectory rather than RIPterm's global icon directory. _Evidence: SyncTERM._

## RIP_BEGIN_UUENCODE_BLOCK

_Encoded-stream command stub in RIPtel 3.1_

|               |                     |
| ------------- | ------------------- |
| **Level**     | 9                   |
| **Command**   | `U`                 |
| **Arguments** | `file_type:2 res:4` |

**Format:** `!|9U <file_type> <res>` **Example:** `!|9U000000`

The original 3.0.7 dispatch record names **RIP_BeginEncodedStream**, with two decoded fields: mega2 type and mega4 reserved. The complete shipped handler only flushes pending host work, accepts types **0 or 1** without further action, and reports an invalid-type error for larger values. It does **not** start a UU decoder, consume a following encoded file, write a file, display a JPEG or delete one. Its presence in the HLP name inventory is not evidence that the draft feature works.

The [ALPHA 4 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_begin_uuencode_block) described eight reserved characters and a subsequent UU-encoded file with the block-mode file-type meanings. That is the historical intended mechanism, not the recovered RIPtel 3.1 behavior. In particular it supplies no alternative implementation of image-style DELETE. _Evidence: original dispatch slot 128 at RVA 0x81c20 and complete handler 0x252c0–0x252f1; [native type matrix and cleanup derivation](../research/issue-21-image-style.md#received-file-cleanup-and-encoded-stream-checkpoint)._

## International Support in RIPscrip

_Evidence: 2.00a4._

The RIPscrip language itself is not tied to any particular language. However, there is a need to establish a means of determining and specifying what RIPscrip / text window fonts with special characters should be used, and what language should be used in the terminal software. It is up to the individual application to use whatever files it needs to support a particular language. RIPscrip provides a standardized way of specifying the language support to use: a character code for each of the languages supported. _(v2.A2)_

Currently, English is the only supported language in RIPscrip. For the purposes of multi-lingual extensibility, the convention was established in the 2.x draft: _(v2.A4)_

| Code | Description of Language |
| ---- | ----------------------- |
| ENG  | English                 |

The means of setting the language is for the user to specify in the terminal, preferably in the dialing directory. This allows the user to select a different language for different systems. There is no ability for the host to specify to the terminal what language to use. _(v2.A2)_

The means of finding out what languages the terminal supports is handled via the [`$IFS()$`](5.1-text-variables.md#ifs) text variable. For example, if the host were to query the terminal with a `$IFS(ENG)$`, the terminal would respond affirmatively. _(v2.A2)_

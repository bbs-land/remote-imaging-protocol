# 2.1 Lines

Straight-line primitives - single pixels, points, lines and multi-segment poly-lines - the line-style state (pattern and thickness) they draw with, and the 3.x-era census discovery [RIP_PolyMarker](#rip_marker).

_The 1.54 record of these commands is [2.1 in the v1.54 reference](../../1.54/ripscrip/2.1-lines.md)._

## RIP_PIXEL

_Draws one pixel using current drawing color_

|               |             |
| ------------- | ----------- |
| **Level**     | 0           |
| **Command**   | `X`         |
| **Arguments** | `x:XY y:XY` |

**Format:** `!|X <x> <y>` **Example:** `!|X0032`

**Attributes used:** Draw Color, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.1-lines.md#rip_pixel)) · HLP (`RIP_Pixel`) · corpus (7 uses in LANDSCPE.RIP, EAGLE.RIP) · SyncTERM (ripper.c:14084)

**Write operation:** apply current W (COPY/XOR/OR/AND/destination-NOT) to each covered pixel, on screen and offscreen ports. POINT's thickness square receives one contribution per covered pixel, not one per unit of thickness. N and the line-pattern gap policy do not change these solid point operations. The [independent nonblack-destination matrix](../../2.0/techspecs/2.3-drawing-composition.md#independent-pixel-vectors) defines their required results; an old client's SetPixel/FillRect boundary is not a protocol exception.

This command will draw a single pixel in the current drawing color at the given (x,y) graphics position. This command is included for completeness, but in practice it would be extremely inefficient to make heavy use of it.

RIPtel 3.1 first converts both coordinates from world units: `dx = floor(x*device_width/world_width)`, `dy = floor(y*device_height/world_height)`. It then attempts **one device pixel**, independent of line thickness. At world 1280×960/device 640×480, `!|X0202` attempts device (1,1), so X is **not** a device-coordinate wire command. _Evidence: original handler 0x1e1d1, conversion 0x31084 and [native placement checks](../research/issue-11-pixel-pen-units.md#reproducible-native-checkpoint)._

**Shipped origin defect:** X computes a viewport-offset rectangle for invalidation but passes the **unoffset** converted dx/dy to the actual SetPixel call. The selected drawing context is the master screen for an onscreen port, or that port's own bitmap for an offscreen port. Clipping still uses the current viewport rectangle in that context. Consequently a viewport whose stored device origin is (65,65) clips away X(2,2)'s attempt at (1,1). It does not move that attempt to (66,66). A newly initialized screen subport likewise does not make X add its origin. _Evidence: [original drawing/DC/clip path](../research/issue-11-pixel-pen-units.md#original-drawing-path-derivation)._

The sibling [RIP_POINT](#rip_point) (`j`) shares the world conversion but applies the stored viewport origin and uses the current thickness to size its square. These commands are not complete aliases. An implementation that repairs X's omitted origin should identify that as a correction to the original RIPtel behavior.

## RIP_POINT

_Plots a solid point using the current drawing color and stored line thickness_

|               |             |
| ------------- | ----------- |
| **Level**     | 0           |
| **Command**   | `j`         |
| **Arguments** | `x:XY y:XY` |

**Format:** `!|j <x> <y>` **Example:** `!|jNK62`

**Attributes used:** Draw Color, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** HLP (`RIP_Point`) · corpus (8 uses in SEABYME1.RIP, SEANITE.RIP) · SyncTERM (ripper.c:14518 - provenance comment "Not in Alpha docs") - not documented in the 2.00a4 spec

**Write operation:** apply current W (COPY/XOR/OR/AND/destination-NOT) to each covered pixel, on screen and offscreen ports. POINT's thickness square receives one contribution per covered pixel, not one per unit of thickness. N and the line-pattern gap policy do not change these solid point operations. The [independent nonblack-destination matrix](../../2.0/techspecs/2.3-drawing-composition.md#independent-pixel-vectors) defines their required results; an old client's SetPixel/FillRect boundary is not a protocol exception.

POINT converts its XY arguments through the **same world-to-device calculation as X**, then adds the current viewport's **stored device origin** in the selected screen or offscreen drawing context. Let that origin be `(ox,oy)`, the converted point `(dx,dy)`, and the current stored thickness byte `t`. It fills the rectangle:

```text
radius = floor(t / 2)
left   = ox + dx - radius
top    = oy + dy - radius
right  = ox + dx + 1 + radius   (excluded)
bottom = oy + dy + 1 + radius   (excluded)
```

The square therefore has side `2*floor(t/2)+1`: stored thickness 0/1 gives one pixel, 2/3 gives 3×3, 4/5 gives 5×5. Clip that square against the current viewport. This is a solid brush fill; the line pattern does not make a patterned point. _Evidence: original j handler 0x1e2f8, thickness-expansion helper 0x2551b and [native rectangle/DC/clip observations](../research/issue-11-pixel-pen-units.md#original-drawing-path-derivation)._

At world 1280×960/device 640×480 with stored viewport origin (0,0) and thickness 1, `!|j0202` and `!|X0202` both plot device (1,1). With stored origin (65,65), j plots (66,66), while X's unoffset (1,1) attempt is clipped away. With thickness 3, j fills a 3×3 square around its mapped center; X still attempts one pixel. These are observable differences, replacing the earlier hypothesis that only j performs world conversion.

The origin is already expressed in the drawing context's coordinates: do **not** add the screen port's origin again. A new screen subport's default viewport begins at its screen origin; a new offscreen port begins at bitmap (0,0). The shipped [RIP_VIEWPORT](1.3-world-view-virtual-canvas.md#rip_viewport) producer has its own origin defect: it stores the directly converted viewport coordinates without adding the screen port's origin. For example, on a port beginning at screen (25,25), viewport input world (80,80)..(118,118) under 2:1 reduction stores device `[40,40,60,60)`, and j(2,2) plots (41,41), **not** (66,66). _Evidence: [original viewport producer and probe](../research/issue-11-pixel-pen-units.md#viewport-producer-and-screen-port-origin)._

RIP_POINT is absent from the 2.00a4 command listing, but the shipped HLP inventory and seascape demos use it (stars/detail dots in SEANITE.RIP). Its exact behavior above is derived from RIPtel 3.1 / driver 3.0.7; do not infer the same defects in earlier clients from this evidence.

## RIP_LINE

_Draw a line in the current color/line style_

|               |                           |
| ------------- | ------------------------- |
| **Level**     | 0                         |
| **Command**   | `L`                       |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY` |

**Format:** `!|L <x0> <y0> <x1> <y1>` **Example:** `!|L1C2J1H2K`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.1-lines.md#rip_line)) · HLP (`RIP_Line`) · corpus (7,574 uses in 23 files - the most-used drawing command) · SyncTERM (ripper.c:13800)

This command will draw a line in the current drawing color, using the current line style, pattern and thickness. The line is drawn from (x0,y0) to (x1,y1) in the graphics viewport.

By raw count this is the corpus's dominant primitive: the hand-digitized artwork scenes (SHUTTLE.RIP, SAILBOAT.RIP, HAWK.RIP, SPACSHUT.RIP, FOUND.RIP) are essentially thousands of short line strokes.

## RIP_POLYLINE

_Added in RIPscrip v1.54._

_Draw a Poly-Line (multi-faceted line)_

|               |                                         |
| ------------- | --------------------------------------- |
| **Level**     | 0                                       |
| **Command**   | `l`                                     |
| **Arguments** | `npoints:2 x1:XY y1:XY ... xn:XY yn:XY` |

**Format:** `!|l <npoints> <x1> <y1> ... <xn> <yn>` **Example:** `!|l0E0A20462046244B244B9G469G469K0A9K0A9G059G05240A240A200A20`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.1-lines.md#rip_polyline)) · HLP (`RIP_Polyline`) · corpus (6 uses in 3 files) · SyncTERM (ripper.c:14529)

This command will draw a multi-faceted line. It is identical in nature to the [RIP_POLYGON](2.3-shapes-and-fills.md#rip_polygon) command, except that the last point is NOT connected to the first point. Generally speaking, a Poly-Line is not an "enclosed area". The segments of the Poly-Line are drawn using the current drawing color, line pattern, thickness and Drawing Write Mode.

The `<npoints>` parameter indicates how many (x,y) coordinate pairs (vertices) follow. An open Poly-Line with N vertices has **N-1 segments**, joining consecutive pairs without a closing segment. _Editorial correction: the inherited sentence incorrectly equated the vertex and segment counts; its own five-segment/six-vertex example below establishes the distinction ([derivation](../research/issue-11-pixel-pen-units.md))._ The original two-digit count reaches **1295 vertices in MegaNum or 4095 in UltraNum**, independently of coordinate width. See [polygon counts and wire limits](2.3-shapes-and-fills.md#polygon-counts-and-wire-limits) for the exact maximum prefixes and the historical 4096 advertisement: its stale extra scratch conversion does not add an input vertex or a closing segment. The N2_TITLE.RIP example above is a 14-vertex (`0E`) newspaper rule.

**Small counts:** `00` is diagnosed by the handler without drawing; a one-vertex command reaches GDI and draws no point; two vertices are the ordinary single-segment case. No case moves the stored pen/cursor or changes RIP drawing style. See the [exact lower-bound and state rules](2.3-shapes-and-fills.md#small-counts-and-drawing-state), separate from the maximum-count encoding.

An example of a five sided (6 vertices) Poly-Line might be:

```text
P1 o                                             o P6
    ▀▄                          o P4           ▄▀
      ▀▄                      ▄▀█            ▄▀
        ▀▄                  ▄▀  █          ▄▀
          ▀▄              ▄▀    █        ▄▀
            ▀▄          ▄▀      █      ▄▀
              ▀o▄▄▄▄▄▄o▀        █    ▄▀
             P2       P3        █  ▄▀
                              P5█▄▀
                                o
```

## RIP_LINE_STYLE

_Defines a line's pattern and thickness_

|               |                                         |
| ------------- | --------------------------------------- |
| **Level**     | 0                                       |
| **Command**   | `=`                                     |
| **Arguments** | `off_draw:1 style:1 user_pat:4 thick:2` |

**Format:** `!|= <off_draw> <style> <user_pat> <thick>` **Example:** `!|=001EKF03`

**Attributes used:** Line Style, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.1-lines.md#rip_line_style)) · HLP (`RIP_LineStyle`) · corpus (120 uses in 31 files) · SyncTERM (ripper.c:13369, descriptor `2#4#2#`)

This command establishes the current line pattern and thickness for many subsequent graphics primitive commands. There are four built-in line styles plus provisions for custom line patterns.

| Style | Description | Binary | Hex |
| --- | --- | --- | --- |
| 0 | Normal, Solid Line | 1111111111111111 | FFFF |
| 1 | Dotted Line | 0011001100110011 | 3333 |
| 2 | Centered Line | 0001111000111111 | 1E3F |
| 3 | Dashed Line | 0001111100011111 | 1F1F |
| 4 | Custom Defined line (see about `<user_pat>` below) |  |  |

If the `<style>` is set to a value of 4 (custom pattern), then the `<user_pat>` parameter is used as a 16-bit representation of the pixels in the line pattern. For example:

| Repeating Pattern | Binary Coding    | Hex  | Decimal | MegaNum |
| ----------------- | ---------------- | ---- | ------- | ------- |
| `- - - - - - - -` | 1010101010101010 | AAAA | 43690   | 0XPM    |
| `----    ----`    | 1111000011110000 | F0F0 | 61680   | 1BLC    |

So, the most-significant-bit of `<user_pat>` is toward the starting point of the line or border that uses this fill pattern. If the `<style>` parameter is not 4, then the `<user_pat>` parameter is ignored.

**Protocol gap policy:** documented `<off_draw>` 0 leaves pattern gaps transparent; 1 draws them using Back Color. For standalone strokes those color contributions use W; polygon-related filled borders use COPY. Custom style 4 means the supplied mask, including at wider supported stroke sizes. See the [drawing contract](../../2.0/techspecs/2.3-drawing-composition.md#source-selection-and-gaps).

**Historical width/unit extension:** the first field retains the inherited name `<off_draw>`, but the shipped driver accepts **0..3** and also uses it to select thickness units:

| `<off_draw>` | Thickness input | Off pixels in the shipped style state |
| --- | --- | --- |
| 0 | Device pixels | Transparent |
| 1 | Device pixels | Background color |
| 2 | World units, converted using X scale only | Transparent |
| 3 | World units, converted using X scale only | Transparent; the original tests the whole field for equality to 1 |

Values above 3 are rejected. The value-3 background behavior in the table is historical client compatibility information, not a replacement for the documented 0/1 gap policy; it is not equivalent to independently combining background bit 1 and scale bit 2. _Evidence: original validation 0x1cd8e, conversion 0x1cdfd–0x1ce24, background-state assignment 0x1cec0–0x1cedb and [full native flag/width domain](../research/issue-11-pixel-pen-units.md#exact-widthflag-handling)._

### Thickness units and stored width

`<thick>:2` always consumes **two numeric characters**, independent of the current XY-coordinate width. It uses the current base math. Decoding those characters supplies a number; it does not itself choose a coordinate space.

With first field 0 or 1, the number is a **device-pixel pen-width request**. Thus `!|=00000003` requests width **3 device pixels** at world 1280×960/device 640×480. It still requests 3 at world 640×350/device 640×480: changing only Y scale does not change it. Endpoint coordinates continue to undergo their ordinary XY world conversion independently.

With first field 2 or 3, clamp the decoded number to at least 1, compute `floor(thick*device_width/world_width)`, then clamp that result to at least 1. **Only X scale is used**, even when X/Y scales differ. For example, `!|=20000003` requests width 1 at 1280×960→640×480, but width 3 at 640×350→640×480. There is no anisotropic X/Y pen pair. _Evidence: original 0x1ce08 passes only an X pointer to 0x31084; [native conversion profiles](../research/issue-11-pixel-pen-units.md#reproducible-native-checkpoint)._

After the applicable conversion and minimum clamp, the original stores **only the low eight bits** of the width and passes that byte to CreatePen. This is truncation, not saturation: unscaled 256 stores/passes 0, 257 gives 1, and 4095 gives 255. Width 0 at the GDI boundary is a cosmetic one-device-pixel pen; POINT instead uses the stored byte in its square rule above, so zero also gives a 1×1 point. A modern implementation that supports larger widths without this truncation is repairing a historical limitation. _Evidence: original store 0x1ce35 and CreatePen call 0x1ce83; [native checks](../research/issue-11-pixel-pen-units.md#exact-widthflag-handling); Microsoft's [CreatePen contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createpen) defines its zero-width behavior._

These units specify the requested line width; exact raster edges, caps and the choice of side for an even-width stroke remain properties of the drawing implementation. POINT's explicit odd-square rule is separate from those pen-edge choices.

When a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) or a [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) command is executed that resets the environment, the current line style is set to a single pixel wide solid line. Off pixels are set to transparent mode. _(v2.A3)_

The 3.x corpus exercises the full syntax as documented: the example above, from ONLINE.RIP, sets a custom pattern `1EKF` at thickness 3, and NEWCMDS.RIP prologues use it exactly per spec ("Solid line 3 pixel wide": `!|=00000003`). HLP error strings add that a custom line pattern "can't have blank pattern".

## RIP_MARKER

_Draw a predefined marker using its own fill and stroke selector_

|               |                                                            |
| ------------- | ---------------------------------------------------------- |
| **Level**     | 0                                                          |
| **Command**   | `;`                                                        |
| **Arguments** | `x:XY y:XY marker:2 width:XY height:XY rotation:2 flags:2` |

**Format:** `!|; <x> <y> <marker> <width> <height> <rotation> <flags>`

**Example:** `!|;1L40001S1S0000`

The DLL names this command `RIP_PolyMarker()`. Four fields use the current XY width, and the three scalar fields have width two in the current Base Math. At XY width 2 the payload has 14 digits. Marker indices are **0–35**, rotation is **0–359** whole degrees, and valid flags are **0–3**. Reject an out-of-range scalar before drawing. Width and height are the full world-space extents. The [marker demos](../research/riptel-script-census.md#0---rip_marker-hypothesized-name) exercise the command 361 times. [Original source and verification](../research/issue-212-polymarker.md)

### Marker Contour Projection

1. Convert the center and the full dimensions separately from WORLD to device coordinates. Apply X scaling to X and width, and Y scaling to Y and height. Truncate each nonnegative ratio to an integer. Add the current viewport's device origin to the center once. Replace either projected dimension of zero with one.
2. For marker **0**, use the [shared Q14 ellipse sampler](../techspecs/2.1-arc-consumer-contract.md#reproducible-q14-numeric-profile), with each device radius the integer half of its projected full dimension. Sample parameters 0 through 360 inclusive with the requested rotation. A projected dimension of one gives a radius of zero along that axis.
3. For markers **1–35**, obtain the normalized vertices for the marker index from the [complete contour data](../techspecs/data/polymarker-contours.json). Iterate in the supplied order and close the path from its last vertex to its first. Use the same separate [Q14 sine and cosine tables](../techspecs/data/skewed-ellipse-q14.json) as the ellipse sampler.

For a normalized vertex `(px,py)`, let `Q = 16384`, `r = (360 - rotation) mod 360` and `floorQ(z) = floor(z/Q)`, including negative values. Let `(cx,cy)` be the translated device center and `(dw,dh)` the projected full dimensions. For the 35 table contours use:

```text
sx = floor(dw * Q / 100)
sy = floor(dh * Q / 100)
u  = floorQ(px * sx)
v  = floorQ(py * sy)
x  = cx + floorQ(u * C[r] - v * S[r])
y  = cy + floorQ(u * S[r] + v * C[r])
```

Keep the two scale truncations, both signed shifts and the rotation dot products in that order. Positive authored rotation turns counterclockwise in screen space. With unit WORLD scale, viewport origin (0,0), center (100,100) and size 100×60, marker 14 starts at **(100,70)** for rotation 0 and **(70,100)** for rotation 90. The two base-36 commands with flags 1 are `!|;2S2S0E2S1O0001` and `!|;2S2S0E2S1O2I01`. At rotation 0 its fourth vertex is **(109,129)**, showing the staged truncation on the positive Y extent. With scale X=1/2, Y=1 and viewport origin (5,7), the same center and extents yield device center (55,107), size 50×60 and rotated tip **(25,107)**.

### Marker Fill and Stroke

| Flags | Fill               | Stroke                                       |
| ----- | ------------------ | -------------------------------------------- |
| 0     | None               | Current line style, thickness and Draw Color |
| 1     | Current fill style | Current line style, thickness and Draw Color |
| 2     | None               | Same as flag 0                               |
| 3     | Current fill style | None                                         |

The flags determine both contributions independently of [N](2.3-shapes-and-fills.md#rip_set_border). The fill uses the even-odd interior and current Fill/Back Color pattern. The stroke follows the closed contour using current Draw Color with the current line pattern and thickness. Transparent line gaps contribute no stroke. Opaque line gaps use Back Color. The selected [W](2.0-color-modes-and-palettes.md#rip_write_mode) operation applies to the fill and the flag-selected stroke on the current clipped port.

RIPtel 3.1 submits separate fill-only and stroke-only polygons for flag 1 with transparent line gaps. With opaque gaps it submits a single polygon with both objects. The [portable composition rules and independent color examples](../techspecs/2.3-drawing-composition.md#marker-composition) define the overlaps without requiring exact GDI edge pixels.

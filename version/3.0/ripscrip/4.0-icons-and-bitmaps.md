# 4.0 Icons & Bitmaps

[◀ Prev: 3.1 Column Text System](3.1-column-text-system.md) · [Contents](README.md) · [Next: 4.1 JPEG Images ▶](4.1-jpeg-images.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

Raster imagery on the terminal: capturing screen regions to a [clipboard](../../glossary.md) port, pasting them back with logical put modes, loading and writing disk-based [icons](../../glossary.md), and the block-move commands. Under the 2.0 engine that 3.x inherits, icons are Windows **BMP** bitmaps - `.BMP` for icons, `.BMH` for [hot icons](../../glossary.md), `.BMM` for [icon masks](../../glossary.md) - replacing the 1.54 `.ICN`/`.HIC`/`.MSK` formats.

_The 1.54 record is [4.0 in the v1.54 reference](../../1.54/ripscrip/4.0-images-and-icons.md); the 2.0 record is [4.0 in the v2.0 reference](../../2.0/ripscrip/4.0-icons-and-bitmaps.md). Byte-level format is in the [v2.0 icon formats techspec](../../2.0/techspecs/3.0-icon-formats.md), with the [RIPtel 3.1 bitmap-mask/depth delta](../techspecs/3.0-bitmap-mask-delta.md) and the RIPtel file census in the [binary-formats research](../../3.0/research/riptel-binary-formats.md)._

## RIP_GET_IMAGE

_Copy rectangular image to the clipboard port_

|               |                                 |
| ------------- | ------------------------------- |
| **Level**     | 1                               |
| **Command**   | `C`                             |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY res:1` |

**Format:** `!|1C <x0> <y0> <x1> <y1> <res>` **Example:** `!|1CEM6XFZ7U0`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_get_image)) · HLP (`RIP_GetImage`; clipboard port concept, `$SCB$`/`$RCB$` variables) · corpus (4 uses in LANDSCPE.RIP) · SyncTERM (ripper.c:15847)

GET_IMAGE captures a rectangle from the current drawing port into a clipboard bitmap port. RIPtel 3.1 uses this selection order:

1. If a clipboard pointer is already assigned, attempt to delete/recreate **that exact port**, without scanning for another candidate.
2. Otherwise, scan **#1 through #35 for the first unused slot** and assign it. An existing offscreen port is not preferred over an unused slot.
3. If no unused slot exists and no pointer was assigned, report failure without deleting any existing port or changing current selection. The clipboard remains undefined.

A protected assigned target **rejects** the operation before deletion/allocation: its definition/pixels, clipboard pointer and current selection survive. The driver does not skip it or fall back to a lower unused slot. If the pointer was absent, an existing protected offscreen port does not participate in selection; the first unused slot still wins. _Evidence: original wire/shared helpers and native whole-record/resource state captures; [derivation](../research/issue-42-clipboard-capture-state.md)._

| Initial state | Result and current selection |
| --- | --- |
| Source #0, no clipboard, #1 unused, offscreen #7 exists | Allocate #1; leave #7 intact; current stays #0 |
| Source #7, no clipboard, #1 unused | Copy into #1; source #7 remains current/intact; no same-source no-op |
| Source #0, clipboard #7, #1 unused | Replace #7; #1 remains unused; current stays #0 |
| Clipboard #7 protected, source #0 or #7 | Reject; retain pointer #7, all target data and initial current selection |
| Source #7, clipboard #7 unprotected | **Shipped defect:** delete source #7, select #0, recreate #7 and copy from **#0**; current remains #0 |
| Every nonzero slot defined, no clipboard | Fail without allocation/deletion; retain all definitions/pixels and current selection |
| Every nonzero slot defined, clipboard #7 unprotected | Reuse #7; no free-slot search is required |

The inherited source-equals-target no-op description is not implemented by this driver. The destructive same-source case is reachable by selecting a previously captured clipboard port as the current source. It must not be mistaken for a successful copy of that port's old pixels. _Evidence: original post-allocation source lookup and distinct screen/offscreen surface tags; [derivation](../research/issue-42-clipboard-capture-state.md)._

### Capture Failure and Geometry

Replacement is **not transactional**. An unprotected assigned target is deleted before bitmap-port allocation. If budget, DC creation, bitmap creation or bitmap selection fails, the clipboard pointer becomes undefined and the target remains undefined; its former pixels/definition are **not restored**. Unrelated port definitions/pixels survive. Current selection changes only if deletion removed the current port, in which case it remains **#0** even after failure. With a previously unused target, allocation failure leaves it undefined and retains the original current source. Failure to delete a protected target is the earlier rejection case and retains the previous clipboard pointer instead of clearing it.

After allocation, a source-trim or GDI copy failure also has no rollback: the new clipboard remains defined and can remain clear. The shared helper reports success after its compositor call without propagating that call's result. PUT_IMAGE and WRITE_ICON use the resulting clipboard pointer, not a hidden copy of the old target. _Evidence: original deletion/creation/compositor branches and injected failure captures; [derivation](../research/issue-42-clipboard-capture-state.md)._

The wire handler normalizes opposing corners and converts world coordinates to device coordinates, then adds one to both converted far coordinates. The shared clipboard helper adds another unit when deriving allocation extents, using low-WORD arithmetic. For ordinary nonwrapping bounds, bitmap width/height are therefore converted far-minus-near **plus two**. The actual source rectangle has only the first far increment and is offset by the source viewport. This can select a **stretch** copy rather than a verbatim transfer: at unit scale, `(1,1)`..`(3,3)` allocates **4×4** and requests a **3×3** source copied into that 4×4 destination. This is shipped caller/helper behavior, not a request to infer exact Windows interpolation. Clipping still uses the port viewports. _Evidence: original handlers and captured StretchBlt dimensions; [derivation](../research/issue-42-clipboard-capture-state.md)._

The clipboard pointer connects the earlier GET_IMAGE/PUT_IMAGE/WRITE_ICON family to the multi-port table. A normal [RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) selects port 0 and deletes unprotected nonzero ports. If it deletes the clipboard port, that pointer clears; a **protected clipboard port and its pointer can survive**. The inherited unconditional statement that every reset leaves no clipboard is too broad. Use the [table lifecycle rules](7.1-data-tables.md) for protection/reset and [data backup areas](7.2-data-backup-areas.md) for whole-port backup semantics. _Evidence: original SOFT call order and native port-deletion component; [derivation](../research/issue-42-clipboard-capture-state.md)._

See the [RIP_DEFINE_PORT](7.0-drawing-ports.md#rip_define_port) command for more details about offscreen ports and the size limitations of them. _(v2.A3)_

In the corpus, LANDSCPE.RIP grabs small texture tiles this way for re-stamping with [RIP_PUT_IMAGE](#rip_put_image); for port-addressed copies the 3.x demos overwhelmingly prefer the level-2 [RIP_PORT_COPY](7.0-drawing-ports.md#rip_port_copy). _Evidence: corpus (LANDSCPE.RIP)._

## RIP_PUT_IMAGE

_Pastes the clipboard port's contents to another port_

|               |                          |
| ------------- | ------------------------ |
| **Level**     | 1                        |
| **Command**   | `P`                      |
| **Arguments** | `x:XY y:XY mode:2 res:1` |

**Format:** `!|1P <x> <y> <mode> <res>` **Example:** `!|1PV4OM000`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_put_image)) · HLP (`RIP_PutImage`) · DLL ([`$PCB$` is the executable paste name; `$P$` is not an alias](5.1-text-variables.md#p)) · corpus (1 use in NEWSPAPR.RIP) · SyncTERM (ripper.c:16481)

This command takes the contents of the port identified by the clipboard pointer (see the [RIP_GET_IMAGE](#rip_get_image) command above) and copies it to a position (x,y) in the currently active drawing port. If the two ports refer to the same port number, then this command is ignored. If the clipboard pointer is clear (ie, no clipboard port is in use), then this command is also ignored. _(v2.A3)_

The area in the active drawing port that is overwritten with the graphics data is determined by the dimensions of the clipboard port previously established with a RIP*GET_IMAGE function. *(v2.A3)\_

The position on the active drawing port that is to receive the image is specified by the (x,y) parameters. These define the upper left corner that will be the rectangle to receive the image data. If any part of the image would go off the edge of the viewport (or the screen) then it is truncated appropriately. _(v2.A3)_

The image that is retrieved from the clipboard port does so based on the port's viewport (the entire contents of the viewport are copied to the active drawing port). If the clipboard port is only used with the RIP*GET_IMAGE command, then the viewport will be the full size of the port. If however, some port related commands are used on this clipboard port, then it is possible to alter the viewport inside this port. This gives you the ability to paste sub-areas of the port's actual image onto the destination drawing port. *(v2.A3)\_

The `<mode>` parameter defines "how" the image will be pasted on the active drawing port:

| Mode | Description                                          | Logical |
| ---- | ---------------------------------------------------- | ------- |
| 00   | Paste the image on-screen normally                   | (COPY)  |
| 01   | Exclusive-OR image with the one already in the port  | (XOR)   |
| 02   | Logically OR image with the one already in the port  | (OR)    |
| 03   | Logically AND image with the one already in the port | (AND)   |
| 04   | Paste the inverse of the image in the port           | (NOT)   |

NOTE: The 1-byte `<res>` parameter is RESERVED FOR FUTURE USE and should be set to zero.

Its single corpus appearance re-stamps a captured screen region in the newspaper demo; everywhere else the demos use the more general [RIP_PORT_COPY](7.0-drawing-ports.md#rip_port_copy). _Evidence: corpus (NEWSPAPR.RIP)._

## RIP_WRITE_ICON

_Write contents of the clipboard port to disk_

|               |                  |
| ------------- | ---------------- |
| **Level**     | 1                |
| **Command**   | `W`              |
| **Arguments** | `res:1 filename` |

**Format:** `!|1W <res> <filename>` **Example:** `!|1W0filename.icn`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_write_icon)) · HLP (`RIP_WriteIcon`) · SyncTERM (ripper.c:16969) - not observed in the RIPtel demo corpus

This command takes the contents of the clipboard port and writes it to disk as a BMP type bitmap file. The image written to disk is the image contained inside the viewport of the clipboard port (see the [RIP_PUT_IMAGE](#rip_put_image) command for more details about viewports and the clipboard port). If the clipboard pointer indicates that there is no clipboard in use, then this command does nothing. _(v2.A3)_

Once the file is written to disk, you may subsequently use the [RIP_LOAD_ICON](#rip_load_icon) or [RIP_LOAD_BITMAP](#rip_load_bitmap) commands to load the icon back onto a drawing port. _(v2.A3)_

Path or sub-directory information is not allowed in the filename portion of the command. If an Icon by the same name already exists on disk, it is overwritten. _(v2.A3)_

NOTE: The `<res>` parameter is reserved for future use by TeleGrafix. For future compatibility, it should be set to "0". _(v2.A3)_

The demos keep their snapshots in offscreen ports instead of round-tripping through disk, so the command never appears in the corpus. _Evidence: corpus (absence)._

## RIP_LOAD_ICON

_Loads and displays a disk-based icon to current port_

|               |                                                       |
| ------------- | ----------------------------------------------------- |
| **Level**     | 1                                                     |
| **Command**   | `I`                                                   |
| **Arguments** | `x:XY y:XY mode:2 clipboard:1 scale:1 res:1 filename` |

**Format:** `!|1I <x> <y> <mode> <clipboard> <scale> <res> <filename>` **Example:** `!|1I001101010button`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_load_icon)) · HLP (`RIP_LoadIcon`; plus 1.54-compat strings "Can't convert RIP 1.54 Icon %s to 2.0 BMP format!") · SyncTERM (ripper.c:16302) - not observed in the RIPtel demo corpus

This command instructs the terminal to read an icon from disk and display it at the given upper-left (x,y) location in the current drawing port. If the width or height of the Icon would make it go off the right or left edge of the port's viewport, it will be truncated to fit inside the viewport. _(v2.A3)_

The `<mode>` parameter defines the modes in which the Icon will be displayed on the current drawing port. The modes are identical to the [RIP_PUT_IMAGE](#rip_put_image) command, and are as follows:

The .BMP file extension does not need to be included as part of the filename. If omitted, it will automatically be appended to the filename. If an extension is provided, it will be used verbatim. _(v2.A1)_

| Mode | Description                                        | Logical |
| ---- | -------------------------------------------------- | ------- |
| 00   | Paste the image on-screen normally                 | (COPY)  |
| 01   | Exclusive-OR image with the one already on screen  | (XOR)   |
| 02   | Logically OR image with the one already on screen  | (OR)    |
| 03   | Logically AND image with the one already on screen | (AND)   |
| 04   | Paste the inverse of the image on the screen       | (NOT)   |

The `<clipboard>` parameter can be one of two values: _(v2.A2)_

| Value | Description                                                 |
| ----- | ----------------------------------------------------------- |
| 0     | Load the image onto the port verbatim                       |
| 1     | Load the image onto the port and put it onto clipboard port |

If the `<clipboard>` parameter specifies to put the icon's image onto a clipboard port, the order of operation is the following: _(v2.A3)_

1. The image is loaded onto the current drawing port, truncated to the viewport if necessary.
2. Original RIPtel 3.1 calls the [GET_IMAGE shared helper](#rip_get_image) with the renderer-returned **unclipped device rectangle**. Its normal target selection, protection, extra far-coordinate increment and failure behavior apply. In particular, an assigned clipboard equal to current is **not skipped**: the documented destructive same-source defect applies. Viewport clipping of the initial paint does not shrink the rectangle passed to this helper. _Evidence: [loader and clipboard derivation](../research/issue-42-clipboard-capture-state.md#integration-review-loader-failures-and-completely-clipped-images)._

The `<scale>` parameter indicates whether the icon should be scaled to the device coordinates when it is loaded. A `1` indicates that it should be scaled, and a `0` indicates that it not should be scaled. This is important when dealing with older RIPscrip 1.54 icons. Icons that are loaded with RIPscrip 1.54 need to be resolution independent. This is performed when this command has a 1 in the scale parameter's position. All scaling is performed in this command as if the icon were created in a 640x350 environment. So, if an icon is loaded that is 35 pixels tall, and it is displayed in a 640x480 environment, it will be stretched vertically to make it 48 pixels tall. This makes sure that icons loaded in this mode are displayed at the correct size so that they are resolution independent. _(v2.A3)_

NOTE: By default this value must be set to `1` (scaled)! _(v2.A2)_

The `<filename>` parameter must not contain any sub-directory or path information and must specify a valid Icon file name. On ordinary lookup or renderer failure, RIPtel 3.1 attempts a missing-resource placeholder on the **current drawing port** and retains the current selection, clipboard pointer and port definitions/resources. This applies to both `<clipboard>=0` and1, whether the assigned target is protected, screen/offscreen, current or already undefined. The inherited claim that failure clears the clipboard/pointer is false for this driver: neither deletion, pixel erasure nor pointer-only clearing occurs. If the clipboard port is itself current, ordinary placeholder drawing can change its pixels; different screen ports can also share drawing pixels. A different offscreen clipboard keeps its pixels. The placeholder may itself fail to render; clipboard state still survives. This failure path never reaches GET_IMAGE, unlike the separate GET_IMAGE allocation-failure path that really clears its pointer. _Evidence: [original failure/placeholder branches and native state matrix](../research/issue-42-clipboard-capture-state.md#load_icon-failure-retains-clipboard-state)._

NOTE: The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc.. It should be set to 0 for compatibility with future releases. _(v2.A2)_

The 3.0 driver retains this 1.54-lineage icon stamper chiefly for backward compatibility - HLP shows built-in `.ICN`→BMP conversion (below) - but the corpus ships no `.ICN` files at all and always uses [RIP_LOAD_BITMAP](#rip_load_bitmap). _Evidence: HLP; corpus (absence)._

## Legacy `.ICN` icons and on-the-fly conversion

The 1.54 icon format - Borland `getimage()` memory dumps, documented in the [v1.54 reference](../../1.54/ripscrip/6.1-content-file-roles.md) - is not a native 3.x format, but the 3.0 driver retains read support by _converting_ legacy icons to BMP on the fly: the DLL exports `RIP_ConvertIconToBmp` and carries the error strings "Can't convert RIP 1.54 Icon %s to 2.0 BMP format!" and "1.54 icon file %s has an invalid width". No `.ICN` files ship with RIPtel; hosts are expected to serve BMPs. See [6.1 Content File Roles](6.1-content-file-roles.md#legacy-icn-icons-ripscrip-154) for the file-role view of the same behavior.

_Evidence: HLP (RIPSCRIP.HLP error strings; RIPTEL.EXE export table)._

## RIP_LOAD_BITMAP

_Loads and displays a disk-based bitmap to screen_

|  |  |
| --- | --- |
| **Level** | 1 |
| **Command** | `b` |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY duplicate_port:1 mode:1 flags:2 trans_color:2 res:4 filename` |

**Format:** `!|1b <x0> <y0> <x1> <y1> <duplicate_port> <mode> <flags> <trans_color> <res> <filename>` **Example:** `!|1b0000HS0Y000G000000STRIP6.BMP`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_load_bitmap)) · HLP (`RIP_LoadBitmap`; also the `$<FILE.BMP$` macro shorthand) · corpus (69 uses in 28 files) · original slot88/handler0xc569 and [native flag/wallpaper derivation](../research/issue-58-load-bitmap-flags.md)

This command is nearly identical in nature to the [RIP_LOAD_ICON](#rip_load_icon) command but it is more flexible in that it supports arbitrary scaling of the bitmap to the destination screen and it supports dithering methods. It can be made to exactly match the RIP*LOAD_ICON command. *(v2.A1)\_

This command instructs the terminal to read a bitmap from disk and display it at the given upper-left (x0,y0) location. If the (x1,y1) values are non-zero, then it specifies the lower-right corner on the screen for the bitmap's display region. If the bitmap differs in size than the destination rectangle, then it is scaled (stretched) to fit into the proper region. If the values of X1 and Y1 are zero, then the bitmap is shown verbatim in whatever resolution of the disk based file (this is more like the RIP*LOAD_ICON command above). *(v2.A3)\_

The .BMP file extension does not need to be included as part of the filename. If omitted, it will automatically be appended to the filename. If an extension is provided, it will be used verbatim. _(v2.A1)_

If the width or height of the Icon would make it go off the right or bottom edge of the viewport, the bitmap will be clipped. The `<mode>` parameter defines the modes in which the Icon will be displayed on the screen. The modes are identical to the [RIP_PUT_IMAGE](#rip_put_image) and the RIP*LOAD_ICON commands, and are as follows: *(v2.A1)\_

| Mode | Description                                      | Logical |
| ---- | ------------------------------------------------ | ------- |
| 0    | Paste the image onto the port normally           | (COPY)  |
| 1    | Exclusive-OR image with one already on the port  | (XOR)   |
| 2    | Logically OR image with one already on the port  | (OR)    |
| 3    | Logically AND image with one already on the port | (AND)   |
| 4    | Paste the inverse of the image onto the port     | (NOT)   |

### Bitmap Flags

The `<flags>` parameter is a bit field. RIPtel 3.1 accepts numerical values **0..63** with these six defined bits; **values64 and above reject the command** with `Invalid flags parameter` before filename lookup, image drawing, duplication or wallpaper copying. Unknown high bits are not silently ignored. _Evidence: original validation0xc5e6 and [378,267 native bitmap checks](../research/issue-58-load-bitmap-flags.md#native-matrix-and-wallpaper-geometry)._

| Value | Operation |
| --- | --- |
| 1 | Duplicate the initially drawn/composited rectangle to another port |
| 2 | Request use/adoption of the bitmap palette for the initial draw |
| 4 | Request auto-dithering for the initial draw |
| 8 | Use `<trans_color>` as a translated key for the initial draw |
| 16 | After initial drawing and duplication, tile the resulting pixels across the current viewport |
| 32 | With16, offset alternate tile rows by half the device tile width; alone, no effect |

The initial destination rectangle determines natural size versus fitting independently of bits16/32. Palette, dither, key and put-mode processing happen during the initial draw; wallpaper copies those resulting pixels. The individual operations follow.

**Flag 1 - duplicate the initial image.** First draw/process the image on the current port, then copy its composited pixels to another port. The renderer returns its **unclipped requested device rectangle**, not the intersection of painted pixels with the viewport. `duplicate_port=0` calls the [GET_IMAGE shared helper](#rip_get_image), including its selection/protection, extra far increment and destructive same-source behavior. Explicit 1..35 equal to current skips duplication. A different explicit target is deleted if defined, then created as an offscreen bitmap of the returned rectangle's width/height and copied with COPY. An explicit port above35 skips duplication. Without flag1 the duplicate argument is ignored.

**Protected explicit target:** the initial image/palette processing has already happened when deletion checks protection. Rejection preserves the target definition/resources, clipboard pointer and current selection, skips replacement and wallpaper, and leaves the initial draw/palette effects in place. There is no DEFINE_PORT-style fallback selection to0. An independent offscreen target keeps its pixels; a screen target can share pixels affected by the initial draw. _Evidence: [original protected deletion and native caller checks](../research/issue-42-clipboard-capture-state.md#protected-explicit-load_bitmap-duplicate)._

**Completely outside the viewport:** a valid nonempty bitmap can finish the initial draw with no visible pixels and still return its full requested rectangle. Flag1 then performs normal target selection/replacement; absence of visible pixels does not preserve the previous duplicate automatically. After successful allocation the compositor can reject the outside source, leaving the new port defined with its initialized background; the caller ignores that copy failure. For requested 4×2, an explicit target is 4×2, while the clipboard helper's extra far increment allocates 5×3. Successful explicit deletion of the assigned clipboard clears its pointer and this explicit route does not reassign it; duplicate0 assigns the newly created clipboard. Protected-target rejection and actual decoder/resource/render failures retain their separate behavior. _Evidence: [original rectangle producer/consumer and native outside-image cases](../research/issue-42-clipboard-capture-state.md#completely-clipped-is-not-a-zero-size-returned-rectangle)._

**Flag 2** - This flag indicates to take the color palette in the bitmap file and activate it in the current color lookup table. This means that the color palette in the bitmap is copied into the video device's color palette (and into RIPscrip's). This means that if any graphics are already on the screen when this happens, they might change in color as soon as the bitmap is loaded (this is due to the fact that the color palette is changed). If the number of colors in the bitmap exceeds the number of colors in the active display device, then the actual color palette in use is used for the bitmap instead of the internal bitmap palette. If the number of colors in the bitmap is equal or less than the number of colors for the active video mode then the image will be displayed exactly as it was intended. If this is the case, then no dithering is necessary on the image so the dither flag (see below) parameter is ignored. If the terminal is running in a mode that doesn't allow for a color palette in the video hardware, then dithering is ignored and the color palette inside the bitmap file is ignored - this is because the system is already running in a 32K, 64K or 24-bit color mode and there are more than plenty colors to represent the bitmap perfectly. _(v2.A4)_

If this flag is omitted, then the bitmap will use the current screen's color palette. Typically this will be the default color palette for use with RIPscrip but it might be different. This means that any pixel of the bitmap that is drawn to the screen is shown in whatever actual color is the absolute closest to the color palette number corresponding to that pixel in the bitmap (dithering may still apply - see below). _(v2.A4)_

If the bitmap has no color palette (eg, 24-bit bitmaps), then this flag is ignored. _(v2.A4)_

**Flag 4** - This flag enables auto-dithering mode. This is an intelligent way of determining if dithering should be performed or not. If there are more colors in the bitmap than in the video device or if the bitmap's color palette is not used to set the video device, then dithering is used to get the image as close to the original color scheme as possible. If the bitmap's palette is committed to the video device then no dithering is necessary because the color palette in use has all (or more) of the necessary colors to display the image. 24-bit images will always enable dithering if this mode is used unless the terminal is running in 24-bit mode. Dithering slows down image drawing so it should only be used for images that really need it. _(v2.A4)_

If this flag is omitted, then no dither is performed at all. If the number of colors in the bitmap is higher than the number of colors in the display device then this will yield a lower quality image. But if there are more colors in the display device than the bitmap then the quality of the image will be close to the actual bitmap (or exact). _(v2.A4)_

**Flag 8** - Select a color of the explicitly loaded image as transparent; `<trans_color>` must be 0..255 and is translated through the current drawing palette. It does not request a same-named BMM. The original renderer generates an internal equality mask, computes the chosen put mode against the old background, retains that background at keyed pixels and uses the computed result elsewhere: `T ? D : F(S,D)`. Selection depends on depth: source bit versus zero/nonzero key for 1-bit, palette-mapped indices for 4/8-bit, exact current-palette RGB for 24-bit. The shipped 16-bit key path fails before drawing, and the shipped 32-bit classifier selects no transparent pixels. See the [complete color-key contract](../techspecs/3.0-bitmap-mask-delta.md#flag-8-is-a-separate-color-key-operation), including key translation and scaling. _Evidence: original DLL and [4,975 native checks](../research/issue-8-bmm-masks.md#full-original-renderer-with-controlled-drawing-boundary); corrects the inherited draft's blanket description._

**Flag16 - wallpaper.** After displaying the bitmap at the requested position/size and performing any flag1 duplication, repeat its **rendered device rectangle** across the **then-current port's viewport**, clipped to that viewport. The original helper copies horizontally and vertically from pixels already on the same drawing device using **COPY/SRCCOPY**, regardless of the initial `<mode>`. It does not reopen the bitmap, scale again, adopt another palette, dither again or test transparency at each repetition. If initial transparency retained background pixels inside the seed rectangle, those retained pixels are tiled too; the key is not applied to each new background. The initial requested ROP is evaluated once to form the seed, rather than repeated against each destination's old pixels.

**Flag32 - staggered rows.** This modifies flag16 only. Relative to the row containing the seed, alternate rows start **floor(tile_device_width/2)** pixels to the left of aligned rows. Both directions from the seed use the same alternating phase, including odd tile widths. With16 absent,32 is accepted and has no effect. This is an offset of existing pixel copies, not another stretch or a different palette/dither mode.

The tile starts at the renderer-returned image position, with the resulting device width/height. The wallpaper helper trims its far bounds to the viewport before repeating and rejects nonpositive/irreconcilable rectangles. A tile already covering the viewport requires no visible extra copy. This is a post-draw operation, separate from loading/scaling a bitmap to cover the viewport in one stretch. _Evidence: original `imageWallpaper()`0x3ea2e, rectangle reconciler0x3f0a6, complete wire/renderer runs and [native tile/phase grids](../research/issue-58-load-bitmap-flags.md#native-matrix-and-wallpaper-geometry)._

**Duplication precedes wallpaper.** Flag1 captures the initial image rectangle, after its palette/dither/key/ROP processing, **before** wallpaper fills the viewport. It does not capture the completed wallpapered viewport. An explicit duplicate equal to the current port skips only duplication. The clipboard route (`duplicate_port=0`) uses [GET_IMAGE](#rip_get_image); if that helper changes the current port, wallpaper re-reads and uses that new current port/viewport. The handler does not save and restore the original selection around the copy.

On renderer failure, the placeholder/error path returns before duplication and wallpaper. The later duplicate paths are not transactional: failure to delete an existing explicit duplicate returns before wallpaper; failure to create its replacement skips that copy but still reaches wallpaper. The [derivation](../research/issue-58-load-bitmap-flags.md#original-flags-and-ordering-checkpoint) records original branches and the controlled native failure cases.

The `<filename>` parameter must not contain any sub-directory or path information and must specify a valid bitmap file name. If the bitmap cannot be located or an error occurs on the disk, then a box should be displayed on screen indicating that the given bitmap could not be loaded. This visual prompt indicates that something is amiss to the end-user. The size of the box will be as big as the destination bitmap image on screen. If the X1 and Y1 are zero, then some suitable box should be drawn. _(v2.A3)_

NOTE: The 4-byte `<res>` parameter is RESERVED FOR THE FUTURE and should be set to "0000". _(v2.A4)_

A host command can also stamp a bitmap via the `$<file.BMP$` playback prefix - see [5.3 Local File Playback](5.3-local-playback.md#local-bitmap-playback---filebmp).

**Canonical example decoded.** With two-character XY fields and base36, `!|1b0000HS0Y000G000000STRIP6.BMP` means:

| Field          | Value                              |
| -------------- | ---------------------------------- |
| x0,y0          | 0,0                                |
| x1,y1          | 640,34 **world coordinates**       |
| duplicate_port | 0, ignored because flag1 is absent |
| mode           | 0/COPY                             |
| flags          | `0G`=16: wallpaper                 |
| trans_color    | 0, ignored because flag8 is absent |
| reserved       | 0                                  |
| filename       | STRIP6.BMP                         |

The original DRAGON.RIP first sets world1280×960 and creates/activates port1. STRIP6.BMP is320×17 pixels. The example draws it into the world box640×34, using the current world/device conversion, **then tiles that resulting rectangle throughout the viewport**. With a640×480 device and that2:1 world ratio, the initial rectangle is320×17 device pixels. Bit16 does not itself request that scaling, and the result is not merely a single stretched header band. _Evidence: original scene/BMP bytes, hashes and [decode](../research/issue-58-load-bitmap-flags.md#canonical-example-and-source-bytes)._

This loader (added v2.A1) supersedes [RIP_LOAD_ICON](#rip_load_icon). DBACK.FN stamps TORCH.BMP with flag8 + `trans_color` for transparent-color compositing; menu scenes place TELBUT.BMP skins with `(x1,y1)` zero for verbatim size. HLP notes the driver "Can't show compressed bitmaps" - RLE-compressed and OS/2-style BMPs are unsupported ([6.1](6.1-content-file-roles.md#windows-bmp--dib)). _Evidence: HLP; corpus (DRAGON.RIP, DBACK.FN, TELDEMOS.MNU and others)._

## RIP_COPY_BLIT

_Added in RIPscrip v2.A1._

_Copy a screen area to a new location (bit blit)_

|               |                                                |
| ------------- | ---------------------------------------------- |
| **Level**     | 1                                              |
| **Command**   | `g`                                            |
| **Arguments** | `x0:2 y0:2 x1:2 y1:2 dx0:2 dy0:2 mode:1 res:1` |

**Format:** `!|1g <x0> <y0> <x1> <y1> <dx0> <dy0> <mode> <res>` **Example:** `!|1g0000XCQO280000`

**Attributes used:** Draw Color, Back Color, Fill Style, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_copy_blit)) · HLP (`RIP_CopyBlit`) · corpus (88 uses in 6 files) - not in SyncTERM

This command is similar to the [RIP_SCROLL](#rip_scroll) command but is more generic in nature - it can move a rectangle of graphical information on the screen from one position to another - not just up or down. It does this with high-speed bit-blit operations. The rectangle contained in (x0,y0) to (x1,y1) is copied so that its upper-left corner is now at the location (dx0,dy0).

Some, part, or none of the original source image might be covered up by the moved screen data. The parts of the original image which are still on the screen (unobscured) can be cleared to some color or state if you wish by using the `<mode>` parameter (like RIP_SCROLL does). The possible settings for `<mode>` are:

| Mode | Description |
| --- | --- |
| 0 | Do nothing - leave the old graphics on the screen |
| 1 | Fill the old graphical area with the current drawing color (solid fill in COPY mode). |
| 2 | Fill the old graphical area with the current background drawing color (solid fill in COPY mode). |
| 3 | Fill the area with the current fill color (solid fill in COPY mode). Fill pattern/styles are not used for this. |
| 4 | Fill the old graphical area with the current fill style/pattern in the current fill color. |
| 5 | Erase the affected area entirely to black. |

The corpus uses it as a _within-screen_ slide primitive in the wipe/transition library (WIPE00-02.FN, DL.FN, DR.FN): the preserved example selects a 1200×960 world-coordinate slab and moves it 80 world units right in one step of a push transition. _Evidence: corpus (WIPE00.FN, WIPE01.FN, WIPE02.FN, DL.FN, DR.FN)._

## RIP_SCROLL

_This command was formerly RIP_COPY_REGION._

_Copy (scroll) screen region up/down_

|               |                                                    |
| ------------- | -------------------------------------------------- |
| **Level**     | 1                                                  |
| **Command**   | `G`                                                |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY mode:1 res:1 dest_line:2` |

**Format:** `!|1G <x0> <y0> <x1> <y1> <mode> <res> <dest_line>` **Example:** `!|1G080G140M0005`

**Attributes used:** Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.0-icons-and-bitmaps.md#rip_scroll)) · HLP (`RIP_Scroll`) · SyncTERM (ripper.c:16246 - **documentation-only stub**: full 1.54 spec comment, then a bare `break;`) - not observed in the RIPtel demo corpus

This command physically "copies" a rectangular region of the graphics screen up or down. The `<dest_line>` parameter is the Y position that is the destination scan line to receive the region. The Destination of the copy can overlap the original region, but cannot be on the same line. You cannot move the image area left or right at all. This command is designated for vertical scrolling of graphical data either up or down.

This is one of the only graphical output commands that DOES NOT adhere to the [RIP_VIEWPORT](1.3-world-view-virtual-canvas.md#rip_viewport) command. In other words, you can scroll graphical data outside the current graphical viewport (even over the text window!). However, it does adhere to the boundaries of the current drawing port. _(v2.A3)_

The `<mode>` parameter instructs the terminal what to do with the part of the source rectangle that isn't covered up by the scrolled data. You may specify several things to happen as defined by the mode values below: _(v2.A1)_

| Mode | Description |
| --- | --- |
| 0 | Do nothing - leave the old graphics on the screen |
| 1 | Fill the old graphical area with the current drawing color (solid fill in COPY mode). |
| 2 | Fill the old graphical area with the current background drawing color (solid fill in COPY mode). |
| 3 | Fill the area with the current fill color (solid fill in COPY mode). Fill pattern/styles are not used for this. |
| 4 | Fill the old graphical area with the current fill style/pattern in the current fill color. |
| 5 | Erase the affected area entirely to black. |
| 6 | Fill the affected area with the color of a pixel from one of the corners of the affected rectangle. If the image area was scrolled up, then the color is taken from the lower-right most pixel from the old graphical rectangle (left exposed). If the data is scrolled down, then the rectangle is filled in with the color of the pixel in the upper-left most pixel. This is mode is used so that if the area is a multi-colored graphic, that a suitable fill color is used. |

It is the one command SyncTERM documents in-source but does not implement - recognized and swallowed. The corpus does all of its region moving with [RIP_COPY_BLIT](#rip_copy_blit) and level-2 [RIP_PORT_COPY](7.0-drawing-ports.md#rip_port_copy) instead. _Evidence: SyncTERM (ripper.c:16246); corpus (absence)._

## Masks and transparency

The 1.54 technique of explicitly stamping a mask in AND mode and the image in OR mode remains available. The original RIPtel 3.1 image/button paths do **not** automatically fetch a BMM companion. An explicitly loaded BMM is an ordinary BMP: resolved white pixels preserve the background under AND and black pixels clear it, independent of their stored palette index. See the [bitmap-mask contract and four-pixel oracle](../techspecs/3.0-bitmap-mask-delta.md) for depths, mode order and missing/different-size cases. [RIP_LOAD_BITMAP](#rip_load_bitmap) flag 8 is a separate single-image color-key operation, used by DBACK.FN. _Evidence: [original driver routing/renderer trace and native observations](../research/issue-8-bmm-masks.md)._

_Evidence: 2.00a4; corpus (DBACK.FN)._

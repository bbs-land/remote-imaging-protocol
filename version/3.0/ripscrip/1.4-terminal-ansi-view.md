## Text Windows and Terminal Emulation

_Evidence: 2.00a4; HLP; corpus._

A text window is a screen region where raw (non-RIPscrip) text is routed, with ANSI and VT-102 emulation: colors, cursor movement, scrolling margins, wrap/chop. Up to 36 text windows are defined in the text window [data table](7.1-data-tables.md); the default is full-screen 80×25. A deactivated current window silently discards incoming text - the demos lean on `$DTW$` (deactivate text window) constantly to keep stray host text off their graphics.

The 3.0.7 driver's strings confirm a richer text-window model than the draft documents: row/column positions, wrap/chop designator, domain designator, text metric mode, write mode, and article/column bindings into the flowed-text system ("Invalid text article number", "Invalid text column number" - see [3.1 Column Text System](3.1-column-text-system.md)). _Evidence: HLP._ The separately recovered [`RIP_TEXT_METRIC`](3.0-text-output-and-fonts.md#rip_text_metric) command queries graphics-font measurements; its name does not establish a text-window mode setter.

## Byte Character Sets in RIPtel 3.1

_Evidence: original RIPtel 3.1 / driver 3.0.7 designation handlers, byte translator, SI/SO routing and reset/save consumers. [Issue #104 derivation](../research/issue-104-terminal-character-sets.md) records exact source boundaries and the explicit glyph-stage completion below. This is the byte-oriented 3.0 terminal profile; it does not revise RIPterm 1.54 or promise generic DEC terminal behavior._

### Designation, Invocation and Emulation Mode

With ANSI parsing enabled, both ANSI and VT-102 modes accept `ESC ( A`, `ESC ( B`, `ESC ( 0` to designate G0 as UK, US or special graphics, and `ESC ) A`, `ESC ) B`, `ESC ) 0` to designate G1. These controls change the selected designation without emitting a glyph or moving the cursor. Unknown designation final bytes have no designation effect. Initial G0 and G1 are both US, and initial invocation is G0.

The ANSI-versus-VT-102 choice is global client state, separate from each TW's designations. In ANSI mode the designation state is still recorded, but display bytes use the CP437 bank without UK/special translation. In VT-102 mode the invoked set's mapping below applies. Changing the emulation choice does not reset the designations or invocation; returning to VT-102 exposes the retained set again.

For this recovered RIPtel byte profile, **SI (`0x0f`) and SO (`0x0e`) do not change invocation**. In VT-102 mode they are consumed without a glyph or cursor advance. In ANSI mode they display CP437 bank glyphs `0x0f` (☼) and `0x0e` (♫), respectively, without changing invocation. The original VT-102 router calls an invocation helper that is a one-byte return; no effective SI/SO set switch is recovered. A normal stream starting at the initial state therefore keeps G0 invoked even after SO; designating G1 does not make it visible. Implementors must not silently substitute modern DEC SI/SO semantics for these rules. A separate extension providing working G1 invocation must identify that additional behavior.

Draw a translated bank identity directly: for example, special-set `d` displays bank `0x1b` (←), rather than opening a new escape sequence. Do not translate ANSI designation/CSI payload into drawing glyphs or reinterpret mapped C0-bank values as incoming controls. The original table and its chosen identities are source facts; this clean syntax/glyph boundary is an interoperability choice, not a claim that all native translated-control paths produce these results. UTF-8 remains outside this profile.

| Live `RESET(TW,0)` / TW 0 within TBL/ALL | Explicit fresh-reset profile: US/US, G0 invoked; retain global emulation choice and connection parser. [Complete live reset boundary](5.1-text-variables.md#live-text-window-reset-contract) |

| HARD / HEADER global bit 1 | Explicit [fresh TW-0 HARD profile](1.3-world-view-virtual-canvas.md#shared-hard-result): US/US, G0 invoked; retain global emulation and connection parser. Nonzero TWs are discarded even if protected; larger ESC snapshot is cleared |
| Freshly initialized TW state | US/US, G0 invoked, independently of whether ANSI or VT-102 is selected globally |

## ANSI ESC 7 and ESC 8 Snapshot

**Completed 3.0 profile:** ANSI `ESC 7` (bytes `1B 37`) saves one interpreter-owned TW snapshot; `ESC 8` (`1B 38`) restores it into the **currently selected TW**, without selecting another slot. They are available on the ordinary ANSI-enabled text path and do not require a VT-102 emulation option. Existing RIP/column-flow routing and inactive-window input discard still apply. This is separate from per-window `CSI s/u` and whole-TW backups.

The accepted [#104 evidence](../research/issue-104-terminal-character-sets.md#reset-definition-and-saved-state) establishes a complete native record copy and the live-cursor overwrite of its initial saved-coordinate bytes. The logical payload, safe ownership, protection/target rules, empty/lifetime and failure boundaries below are **explicit portable completion**; [derivation and independent vectors](../research/issue-150-ansi-esc-snapshot.md). A historical `0xf1`-byte record is not a wire/file format or permission to copy pointers, reserved bytes or undocumented fields. This profile does not change RIPscrip 1.54 or require new VT-102/flowed-text commands.

### Snapshot Payload and Other Save Operations

The interpreter owns **one optional value S**, initially absent, across TW selection. A successful ESC 7 reads the current **defined, active** window, including a protected source, and atomically replaces S with an independently owned logical copy. It leaves the source record, its CSI-saved coordinates, current index and displayed pixels unchanged. An ineligible source leaves S unchanged. Saving again replaces the one value; this is not a per-window slot or stack.

| Logical field | ESC 7 capture / ESC 8 application |
| --- | --- |
| Ordinary/extended kind; cell bounds/counts; stored bounding/display rectangles and cell metrics | Copy the logical definition by value. Restore those stored values without WORLD reprojection, automatic fitting, relocation or replacement by current user defaults |
| Logical MicroANSI font selection | Save the font descriptor/number and required logical metrics, not a native font/cache handle. Realize a compatible resource at restore |
| Definition/protection/activation flags | Defined/active source is required. Restore saved logical flags on an eligible target, with target 0 always defined and unprotected; no unused/native flag bits become new state |
| Live cursor | Capture the source live position. Restore it with the ordinary bounds clamp into the restored grid |
| CSI-saved cursor coordinates | The ESC snapshot's saved-coordinate value is **the captured live position**. ESC 7 does not retain the source's previous CSI-saved coordinates as a second independent point; ESC 8 installs the captured value into the destination's CSI-saved slots |
| ANSI foreground/background and rendition | Copy logical indexed/direct colors and all already supported rendition flags. Direct-color support is conditional on the existing terminal; no new SGR syntax or graphics color-mode change |
| Per-window terminal modes | Copy the existing wrap/chop, origin, cursor-key, insert/replace, newline and per-window keyboard modes and other already defined TW-local mode values; global RIP input lock is separate |
| Scrolling margins and explicit tab map | Copy logical values independently of later live edits |
| Requested cursor visibility and per-window shape | Copy requests; recreate presentation resources without restoring historical cursor pixels |
| G0/G1 designations and invocation | Copy per-window values. Do not change the global ANSI-versus-VT-102 choice or require that mode to be implemented |
| Fixed resident query attached to the source TW | Copy its logical value/absence as owned data; restore an independently owned value in the destination. Do not evaluate it |
| Already exposed TW-local article/column binding identifiers, including absence | Copy logical identifiers/unset values, not pointers or flowed article/column objects. Resolve supported bindings against current live resources; do not recreate objects or change global article/column selection. An implementation with no such exposed binding keeps this field absent; HLP diagnostics alone add no setter or new binding feature |

In particular, for source live cursor `(4,2)` and old CSI-saved `(1,1)`, ESC 7 leaves the source's old `(1,1)` unchanged but records `(4,2)` for both snapshot live position and its derived saved-coordinate value. ESC 8 into a different window gives that destination live `(4,2)` and CSI-saved `(4,2)` for this in-bounds example. A subsequent CSI u there uses `(4,2)`, not the source's pre-ESC 7 `(1,1)`. This follows the accepted overwrite evidence rather than assuming that every old record byte survives capture unchanged.

| State/ownership | CSI s/u | ESC 7/ESC 8 | Whole TW backup/restore |
| --- | --- | --- | --- |
| Unit | Selected window's cursor coordinates | One interpreter-owned logical TW value, applied to the selected target | Existing full family: all 36 entries |
| Geometry/font, per-window modes/colors/tabs/charset/query/flags | Not saved/restored | Payload above | Per-entry definition/state under the existing family contract |
| Live/saved cursor | CSI s writes the selected window's saved coordinates from live; CSI u moves live from that window's saved coordinates | Captured live point supplies restored live and CSI-saved value as above | Per-entry values under the existing family contract; no ESC overwrite recipe |
| Current TW index | Retained | Not captured or changed | Saved/restored by the family |
| Floating TW query | Unchanged | Excluded and unchanged | Saved/restored by the family |
| Interpreter S | Unchanged | Replaced by successful ESC 7; reusable/unconsumed by ESC 8 | Neither captured nor restored |
| Screen pixels, logical cell/history contents, other families' backups/state | Not part of these saved coordinates | Excluded | No TW contents/pixels; other families remain separate |

Also exclude connection parser/input buffers, pending escape/string syntax, font resource ownership, global client preferences/emulation/input lock, graphics PORT/STYLE/ENV/PAL selection and records, and global article/column content, pagination, flow position and selection. Already defined TW-local values are copied logically; diagnostic names do not authorize opaque native pointer/record cloning. Independent copies may use safe immutable value sharing, but later source/target edits and deletion must not mutate or invalidate S.

### Restore Target, Resources and Failure

ESC 8 with **no S**, or an **undefined, inactive or protected current target**, performs no restore, creation or selection and retains S. It does not fall back to TW 0, the original source slot, CSI u or a default record. Inactive text may already be discarded before forming an ANSI sequence; neither route bypasses that gate. Graphics PORT activation/protection is not this TW eligibility check.

For an eligible target, restore into its existing numeric slot. The saved source index is not payload or a binding to that original object. Source deletion, redefinition, live reset or a whole-TW restore therefore does not invalidate the owned snapshot. Destination 0 always remains defined/unprotected even if the source was a protected nonzero window. A nonzero destination receives saved protection; that can make a subsequent ESC 8 a protected-target no-op until separately unprotected. Normal successful capture has active state; restoring hidden cursor visibility does not disable the window's raw text path.

Resolve saved logical font/metric requirements and any supported binding identifiers against current resources. Missing/incompatible resources are a recoverable failure; do not copy an old handle, silently substitute a font, refit geometry, auto-create a flowed object, or select an article/column. A reused identifier refers to the compatible currently live resource under its ordinary identifier rules, not the original native object's address. Copy/retain owned query text and all other payload values before publication.

**Failure/publication boundary:** failed ESC 7 retains the old S, including absence. ESC 8 prepares the entire logical target/resource replacement before commit; failure retains the target definition, fixed query, selection and S without a partial record swap. A successful restore replaces the target logical state as one operation and leaves S unchanged for reuse. This explicitly chosen ESC boundary does not change COPY or whole-family restore recovery rules. No query, macro/provider, flow operation or host command executes as part of saving/restoring state.

A recognized ESC 7/ESC 8 produces no text/Boolean reply. Uninitialized/ineligible/failure cases are not deferred retries or raw sequence replay. The parser consumes a recognized escape normally; no parser prefix is saved/restored from S, and all runtime handling remains below the existing parser/session boundary without connection termination.

Changing geometry/font restores **definition/state only**: no canvas clear, glyph redraw, scroll, pixel relocation or restored logical-cell/history image. A cell-backed implementation must preserve the entry raster rather than paint blank cells or replay history due to definition replacement. Only the selected cursor overlay may be removed/recreated according to the new requests; cursor/font pixel parity is not specified.

### Snapshot Initialization and Lifetime

| Event | S state |
| --- | --- |
| New interpreter/connection session; end of that session | Absent; no implicit TW 0 or CSI-derived default |
| Successful ESC 7 | Replace S with the completed owned value |
| Failed/ineligible ESC 7 | Retain old S/absence |
| Successful, absent/ineligible or failed ESC 8 | Retain S/absence; restore never pops or consumes it |
| Ordinary w, extended b, MTW; deactivate/reactivate; selection/first use | Retain S independently of affected records |
| CSI s/u, ANSI ESC c | Retain S; these operations do not initialize it or turn it into the per-window saved cursor |
| Entry COPY/delete/redefinition; live RESET(TW), including TBL/ALL | Retain S, as required by the accepted live-reset boundary |
| Whole-TW save/restore, other families' backups/restores or backup deletion | Retain S; do not serialize/rewind/synthesize it from BASE/slots/stack. A family restore may independently change current TW under its own contract; later ESC 8 uses that current target |
| SOFT / RIP * / HEADER soft-reset flag alone | Retain S, independently of deleted TW entries and floating queries. ESC 8 cannot undo the separately cleared screen pixels |
| HARD / accepted HEADER hard-reset flag | Clear S when the hard-reset operation is accepted/applied, before fallible subsystem setup; later failure does not resurrect it. Hard takes precedence if soft is also requested |
| HEADER without hard reset, including selection-only or viewport-only actions | Retain S; only any separately requested hard reset clears it |

The lifetime/empty/failure rules are explicit portable completion, not recovered native validity bits or pointer ownership. They add no backup family, scene buffer or cross-connection cache.

## MicroANSI Fonts (`.maf`)

_Evidence: HLP (file headers)._

Terminal text is rendered from **MicroANSI** bitmap fonts shipped as `RIPscrip.maf` - header `RIPterm v2.0 MicroANSI Font File`. The format is inherited directly from RIPterm Professional 2.0, whose `RIPTERM.FNT` (preserved in the [2.x font assets](../../2.0/assets/fonts/README.md)) carries the identical header; RIPterm 2.0 additionally ran EGA 640×350 as a native video mode. RIPtel still supports 640×350 - as the default world view, for 1.54 compatibility - but treats it like any other world resolution, scaled to the display, so it needs no 350-line MicroANSI table of its own. The file carries per-resolution tables for **three display resolutions** - 640×480, 800×600, and 1024×768 - each with about five font-size subtables, so text windows keep proportion as the device resolution changes. (Text-mode geometries offered by RIPtel: 80×43, 91×43, 80×25, 91×25, 40×25.) Byte-level format details are in the [MicroANSI `.maf` techspec](../techspecs/3.3-microansi-maf-delta.md). Graphical text uses the separate font systems: BGI stroked `.CHR` vector fonts and the `.RFF` outline fonts of RIP_EXTENDED_FONT_STYLE, covered in [3.0 Text Output & Fonts](3.0-text-output-and-fonts.md).

## RIP_TEXT_WINDOW

_Evidence: 2.00a4; HLP (`RIP_TextWindow`; the five MicroANSI text modes 80x43/91x43/80x25/91x25/40x25 appear in MESSAGES.HLP); corpus (14 uses in 14 files); SyncTERM (ripper.c:14783)._

_Define the size and location of the Text Window_

|               |                                         |
| ------------- | --------------------------------------- |
| **Level**     | 0                                       |
| **Command**   | `w`                                     |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY wrap:1 size:1` |

**Format:** `!|w <x0> <y0> <x1> <y1> <wrap> <size>` **Example:** `!|w00001B0M10`

**Attributes used:** Base Math (current setting)

This command specifies the dimensions of the virtual TTY window that will display all ASCII/ANSI (non-RIPscrip) data coming across the connection. (x0,y0) defines the upper-left corner of the window in text-based character-cell coordinates. (x1,y1) defines the lower-right corner of the window (inclusive). There may be two simultaneous windows on the screen, one for TTY text, and one for the display of RIPscrip graphics (a viewport), and they may overlap.

Bytes received over the modem are first checked for RIPscrip commands. All bytes that don't conform to the RIPscrip syntax are treated as ANSI/ASCII and displayed in the TTY window (if defined). User keystrokes that are echoed by the BBS would also appear in the text window by this scheme.

### Font sizes

The text window may be deactivated, ignoring all non-RIPscrip bytes, by setting all RIP_TEXT_WINDOW parameters to zero (0). The X and Y parameters' ranges vary depending on the setting of the `<size>` parameter which governs the font size used for the output text. Valid settings for the `<size>` parameter and the ranges for X/Y values are as follows:

| Size | Font Size (\*) | X Range | Y Range | Columns | Rows |
| ---- | -------------- | ------- | ------- | ------- | ---- |
| 0    | 8x8            | 0-79    | 0-42    | 80      | 43   |
| 1    | 7x8            | 0-90    | 0-42    | 91      | 43   |
| 2    | 8x14           | 0-79    | 0-24    | 80      | 25   |
| 3    | 7x14           | 0-90    | 0-24    | 91      | 25   |
| 4    | 16x14          | 0-39    | 0-24    | 40      | 25   |

(\*) Font sizes are based on a 640x350 device resolution

The font sizes in the preceding table vary depending on the resolution that the terminal software is running under. The actual cell sizes of each font are calculated based on the number of rows and columns required. For example, at a resolution of 800x600, the cell sizes are calculated by dividing the horizontal resolution by the number of columns (800/80) which yields a cell width of 10. By doing the same thing for the same height we get 600/43 which equals 13.95348837. You obviously cannot have a fractional cell size so we round down. This gives us a cell height of 13. This gives a vertical region of 559 scan lines of text information yielding 41 extra scan lines that don't get used. This method can be used to determine the cell sizes for any arbitrary resolution. _(v2.A3)_

### Text window placement

Now that we know what the font cell sizes are, or more acurately, how to calculate them, we need to establish a standardized way to determine screen placement for text characters. RIPscrip 1.54 was based on 640x350 resolution and text placement was very straightforward. If the text window was to be defined using font #2 (8x14 under 640x350) and was to be from (10,15) to (20,24) in text coordinates, then our actual upper-left corner of the text window would be located at pixel (10x8,15x14) or (80,210). Now that we have the upper-left corner of the text window, calculating an arbitrary row/column in the text window is simple based on the cell size. _(v2.A3)_

Under resolutions other than 640x350, we need to take very special care to make the text characters appear as close to the 640x350 counterparts as possible. In order to calculate the text window's orientation as closely as possible in other resolutions, calculate the upper-left corner of the text window at 640x350 coordinates and scale those coordinates up to the actual resolution used on the terminal. This will insure that the text window is located as closely to the 640x350 counterpart as possible. As previously described, the font cell sizes can leave some "slop space" due to fractional columns/rows. This means that you cannot be pixel-for-pixel accurate with text window placement at varying resolutions. In this matter, the RIP_TEXT_WINDOW command is not truly resolution independent (see [RIP_EXTENDED_TEXT_WINDOW](#rip_extended_text_window) for a truly resolution independent way of creating text windows).

The `<wrap>` parameter applies to the horizontal dimension. If `<wrap>` is set to 1, then any text that extends beyond the right margin of the window will wrap to the next line of the window, scrolling the window up if necessary. If `<wrap>` is 0, then any text going beyond the right margin is truncated and no scrolling is performed; the cursor remains at the right margin.

When a text window is defined, its coordinates are relative to the actual screen, not the current graphical Viewport or the Device Coordinate Frame.

**NOTE:** If the text window currently being defined is identical to the currently defined text window, the cursor will not be relocated to the upper-left corner of the window. The only aspect of the text window that can be different and still be deemed "identical" is the `<wrap>` parameter. For the current and new text windows to be considered identical, the parameters `<x0>`, `<y0>`, `<x1>`, `<y1>` and `<size>` must be the same.

HEADER's [type-3 geometry/erase/caret profile](1.1-protocol-and-command-hierarchy.md#text-window-geometry-erase-and-caret-profile) is separate from ordinary definition and live RESET(TW): maximization with retained font and window kind, home position in the target, retained CSI/query/ANSI state and active/protection gates. Its erase adopts the same palette-index-0 source as e/ETW.

### Ordinary Definition State Boundary

_Evidence: 2.00a4 (identical-definition exception and per-window state); original RIPtel 3.1 / driver 3.0.7 definition, ANSI state and activation consumers. Read-only derivation: [issue #100](../research/issue-100-ordinary-text-window-state.md). This completes the 3.0 ordinary-window contract; it does not revise 1.54._

For a nonzero definition, compare the effective cell bounds and font with the current slot's stored ordinary definition. Reversed endpoint pairs are ordered first; each coordinate is then clamped to its selected font's nominal X/Y range above. The original driver reports the adjustment and continues. Thus font 2 `(10,15)` through `(20,25)` becomes `(10,15)` through `(20,24)`, an 11-column, 10-row window. The corrected placement example uses the valid final row 24; it does not add a 26th row to font 2. This normalization precedes the identical-definition test. Invalid font numbers outside 0–4 are rejected without redefining the window.

| State | Identical bounds and font, including wrap-only changes | Changed bounds or font |
| --- | --- | --- |
| Current cursor | Retained | Window-relative `(0,0)` |
| Saved ANSI cursor coordinates | Retained | `(0,0)` |
| ANSI foreground/background | Retained | ANSI light gray on black, indices 7/0; independent of graphics STYLE colors |
| Rendition | Retained | Normal intensity; bold, underline, blink and reverse flags cleared |
| Vertical scrolling margins | Retained | First through last row of the new window |
| Per-window terminal modes | Retained except requested wrap/chop | Reset: normal cursor-key mode, absolute origin, replace mode, keyboard unlocked, newline mode off; wrap/chop from this command |
| Cursor visibility | Retained | Enabled |
| Tab stops and character-set selections | Retained | Retained; defining a window is not a complete ANSI terminal reset |
| Incomplete ANSI escape/CSI parser state and collected parameters | Retained | Retained |

The ANSI parser state is interpreter state separate from the window definition. A successful `w` does not cancel an unfinished ANSI sequence; subsequent raw bytes continue it against the current window and its resulting state. This statement applies to the inherited byte-oriented ANSI/CP437 terminal. UTF-8 decoding and partial UTF-8 sequence handling are outside RIPscrip 3.0; an implementation offering that extension must specify its own decoder boundary and cannot attribute it to RIPtel.

Definition changes geometry and state without erasing, moving, restoring or repainting existing text/graphics pixels. Newly included screen space keeps the pixels already present; no background fill is selected. A terminal with a logical cell backing store must preserve this visible behavior instead of painting blank cells as a side effect of redefinition. Cursor hide/show may update the cursor overlay. Use an explicit erase operation to clear the region.

All-zero `w` deactivation hides the cursor and disables raw-text output without replacing the stored geometry or ANSI state. A subsequent nonzero `w` matching that stored definition reactivates it and retains the cursor, saved cursor, colors, rendition, margins, modes and pending ANSI parser state, apart from the requested wrap setting. A different definition follows the changed-definition column above. Discarded raw text during deactivation does not become delayed output on reactivation. A protected current text-window slot rejects both redefinition and all-zero `w`; the separate table/backup and query-dispatch contracts remain unchanged.

**NOTE:** A text window definition command is ignored if the current text window data table entry is protected! _(v2.A4)_

All 14 corpus uses set every parameter to zero (`!|w0000000000`) - TeleGrafix's own demos use the command purely to **deactivate** the text window before full-screen graphics, or define minimal windows for status text. _Evidence: corpus._

|  |  |

This RIPscrip command is a more sophisticated way of defining a text window than by using the older [RIP_TEXT_WINDOW](#rip_text_window) command. The older command doesn't permit you the luxury of creating a truly resolution independent text window - this command does and is far superior in design to the older RIPscrip 1.xx RIP_TEXT_WINDOW command. If at all possible, you should use this command instead of the older command as it provides more flexibility and more methods of interfacing with the text window via text variable query statements.

This version of a text window works by establishing a bounding rectangle that is to contain the actual text window display region. This bounding rectangle is specified just like you would in drawing a filled rectangle, by indicating the upper-left X/Y coordinates and the lower-right X/Y coordinates of the bounding rectangle. Note that the lower-right corner of the bounding rectangle is non-inclusive to the bounding rectangle region, just like with filled rectangles. See ["The Mathematics of Graphics and Coordinates"](1.2-math-and-coordinates.md#the-mathematics-of-graphics-and-coordinates) for more detailed information on this subject and why it is important.

### Extended Bounds and Validation

_Evidence: 2.00a4 §3.4.1.12 and command-shortening rule 10; read-only RIPtel 3.1 definition/fitting/font-metric consumers. [Issue #101 derivation](../research/issue-101-extended-text-window-contract.md) separates recovered rules from the explicit completion choices below._

The four coordinates are absolute WORLD coordinates relative to the screen. Convert both endpoints independently to device coordinates with the current WORLD/device scale, rounding down, then order each endpoint pair. Do not add the current graphics PORT or viewport origin, use its clipping rectangle, or add one to the far edges. The result is `[left,right) × [top,bottom)`. A rectangle with zero device width or height after conversion is rejected; a positive WORLD extent can collapse to zero during conversion. The stored bounding rectangle is not clipped to the screen before fitting. Actual drawing is limited to addressable screen pixels, independently of graphics PORT/viewport clipping.

Requested columns and rows must both be positive. Font numbers 0–4 are valid; flag 8 ignores the parsed font value, including values outside that range. A protected current TW rejects definition, including a repeated identical `b`. The final reserved field may be omitted, meaning zero, under [rule 10](1.1-protocol-and-command-hierarchy.md); if transmitted, its value is ignored in this revision and senders should use zero. Omitting it also permits shortening leading zeros in the now-final flags field as rule 10 describes. Missing other required fields is not a request for zero dimensions or implicit defaults.

**Explicit completion choices:** the portable command accepts only combinations of the six documented flags, values 0–63; reject an unsupported flag bit without changing the TW or pixels. Undocumented original-driver extensions are not enabled implicitly. Perform conversion, products, comparisons and fitting with sufficiently wide integers; do not reproduce internal 16-bit product or coordinate truncation. Invalid input fails before definition/clear. A terminal whose selected font metrics are unavailable or nonpositive must reject the definition instead of dividing by zero; this does not prescribe recovery from unrelated resource-allocation failure.

### Fitting the Text Window

**Cell metrics:** use the device cell width and height of each selected terminal font, consistently for fitting, display placement and cell queries. With a loaded MicroANSI table, these are its stored raster dimensions, not a fresh division by the nominal 80/91/40 columns and 43/25 rows. RIPtel initially computes nominal-grid floor metrics as a fallback, then replaces them with successfully loaded MAF metrics. At 1024×768 the supplied fonts are 12×17, 11×17, 12×30, 11×30 and 20×24 for fonts 0–4. In particular, font 4 is 20×24, not 25×30. See the [MAF metric table](../techspecs/3.3-microansi-maf-delta.md#the-new-resolution-set). The ordinary `w` nominal-grid/640×350 reference-origin description above does not define extended `b` fitting metrics.

**Automatic font selection, flag 8:** ignore `font_no` and start at font 4. Test the entire requested column/row count with that font's device metrics. If it fits both dimensions, stop. Otherwise follow the same directional transition table below, selecting Shrink Width, Shrink Height or Shrink Both according to the current candidate's overflow and retesting the full request after each transition. Stop at the first candidate that fits, or at `n/a`, then reduce dimensions as described below. There is no exhaustive search, area/aspect-ratio scoring or additional tie-break: the path through the table determines preference. Explicit-font selection starts at the supplied font and uses the same procedure.

Once a bounding rectangle is established, you indicate how many columns wide and how many lines tall you wish your text window to be, and also indicate the desired text font you wish to use for your window. The RIPscrip software will take your desired width, height and text font into consideration and determine if it can fit a text window inside your bounding rectangle with this font's dimensions. If it can make a text window exactly the width and height of your request, it does so - centering the text window inside the bounding rectangle as in the following diagram:

If the font number provided would make either the width or height of the text window "too large" to fit inside the bounding rectangle, then several things may happen (in the following order):

1. The font number is checked. If a narrower or shorter font is available in the RIPscrip text window system, it will be chosen, then everything will be recalculated to see if the width and/or height can now be fit inside the bounding rectangle. If it can, then this new font will be used to accomodate the request. This evaluation process is incremental in nature. If the width and/or height is too large, then the next smaller font is checked, so on and so forth. Here is the table of fonts, their row/column sizes, and which font number will be checked if the width or the height (or both) is out of range for the given bounding rectangle:

   | Font | Columns | Rows | Shrink Width | Shrink Height | Shrink Both |
   | ---- | ------- | ---- | ------------ | ------------- | ----------- |
   | 0    | 80      | 43   | 1            | n/a           | n/a         |
   | 1    | 91      | 43   | n/a          | n/a           | n/a         |
   | 2    | 80      | 25   | 3            | 0             | 1           |
   | 3    | 91      | 25   | n/a          | 1             | n/a         |
   | 4    | 40      | 25   | 2            | 0             | 0           |

   If a new font must be chosen, then you evaluate whether you need to shrink the font in the width, height or in both directions. Consult the preceding table to determine which font number to check next. If the entry specifies "n/a", then you cannot shrink the font any further and must move on to step number 2 (see below).

2. If the current candidate has `n/a` for its overflow direction and you still cannot obtain the desired height and width of your text window, you have no alternative then to reduce the width and/or height to make it fit inside the bounding rectangle. This is a last resort situation, but must be done if the text window is to fit inside the bounding rectangle. If the width is too wide, then one column will be trimmed off of the text window and then its new pixel width would be evaluated. If it still doesn't fit, you keep removing more columns, one-by-one, until you either get a window that fits, or you hit zero columns. If your bounding rectangle is so small that you can't have even a one column wide or one line tall text window then the text window is made exactly one line tall, or one column wide to accomodate the situation and the bounding box is adjusted accordingly to fit exactly the outer dimensions of the newly defined text window (albeit an incorrect one).

For the final chosen font with positive metrics `(cw,ch)` and bounding size `(BW,BH)`, the dimension-reduction step is exactly `columns = max(1, min(requested_columns, floor(BW/cw)))` and `rows = max(1, min(requested_rows, floor(BH/ch)))`. Do not reduce counts while another transition is available: every candidate is tested against the original requested counts.

**Explicit undersized-box completion:** when even one cell cannot fit on an axis, keep that axis's near edge and extend its far edge to exactly one cell beyond it. Leave the other bounding axis unchanged unless it also needs extension. The draft requires a one-cell minimum and adjusted bounding box, but does not establish this anchoring; this is the portable rule, not a claim about all original error/recovery paths. After adjustment, center the display rectangle: `display_left = left + floor((BW - columns*cw)/2)` and `display_top = top + floor((BH - rows*ch)/2)`, with exclusive far edges one full display width/height later. An odd leftover pixel stays on the right/bottom. Flag 16 clears this final adjusted bounding rectangle, including its margins, clipped only to the physical screen.

Every accepted `b`, including one identical to the previous definition, homes both live and saved cursor to window-relative `(0,0)`, resets rendition and per-window terminal modes, sets full-height scrolling margins, and sets ANSI colors to normal light gray on black (7/0). Wrap/chop is then selected by flag 1. Existing cursor visibility is retained unless flag 2 hides it; absence of flag 2 does not turn a previously hidden cursor on. The explicit tab-stop map and character-set selectors are reset, unlike changed ordinary `w`, which retains them. Incomplete ANSI parser state and global client emulation options are retained, as distinguished in the [ordinary state boundary](#ordinary-definition-state-boundary). This is a window-state reinitialization, not an ANSI parser reset. Without flag 16, definition preserves screen pixels; newly included areas are not implicitly filled. Flag 16 is applied before the final cursor display and before flag 4 deactivates the window; flag 32 protects the completed definition.

For example, using the supplied 1024×768 MAF metrics, a 40×25 automatic request in device box `[10,1010) × [20,620)` selects font 4 immediately: display size 800×600, display box `[110,910) × [20,620)`, bounding box unchanged. A 40×25 request in `[0,800) × [0,500)` overflows height with font 4 and follows 4→0, yielding 480×425 centered at `(160,37)`. A 1×1-cell request in the nonempty device box `[20,21) × [30,31)` follows the both-axis path 4→0, then expands the box to `[20,32) × [30,47)` for one 12×17 cell. These are source-derived calculations with the stated completion rule, not native pixel captures.

### Flags

The `<flags>` parameter of this command allows you to specify some extra options to control how the text window is defined and how it will operate. The available flags, which must be OR'ed togther to create a final flags "value", are as follows:

| Flag | Description |
| --- | --- |
| 1 | Enable character-wrap. If this flag is not present, then "chop" mode is in use. See the RIP_TEXT_WINDOW command for more details on this mode of text window operation. |
| 2 | Disable the cursor immediately (as if a `$COFF$` text variable were processed). This hides the cursor immediately when the text window is created (see flag 16 for more on this). This doesn't mean that text won't be displayed, it only means that you won't see a cursor in the text window when it is current and active. |
| 4 | Deactivate the text window immediately upon creation. This acts as if immediately after defining the text window, a `$DTW$` text variable command were issued. Any raw text received by the terminal would not be displayed in this text window if it is the current one. When deactivated, the cursor for this text window is hidden and any text variables requesting information about this text window will return a result indicating that the text window is deactivated. Note, that the `$INUSE(TW)$` text variable will still respond that this text window is "in use", even though it is deactivated. |
| 8 | Ignore the font number parameter. This flag gives the text window definition software the task of finding the best font to use for the text window. This alleviates the coder from having to determine the proper font to use. This makes life a bit easier in choosing fonts. |
| 16 | Erase the text window immediately after it is created. This erases the contents of the entire bounding rectangle, not just the text window display area! The area is erased to index 0 of the current graphics palette (typically black), independently of STYLE background and previous ANSI background. This operation is performed before the text window's cursor is displayed (if it is displayed at all based on flag 2), and before the text window can possibly be deactivated (via flag 4). |
| 32 | The text window is protected immediately after it is created. |

It should be noted that there are some fundamental differences in nature from the extended text window command and the older normal text window command. This one is obviously more powerful and has the benefit of being resolution independent. When working with [text variables](5.1-text-variables.md) to query the status or configuration of text windows, some text variables cannot query particular pieces of information about extended text windows (eg, `$TWX0$`, `$TWY0$`, `$TWX1$` and `$TWY1$`). The types of information that cannot be obtained are the text cell coordinates of the upper-left and lower-right corners of the extended text window - there aren't any - they're specified in graphical coordinates, not in text coordinates like with the RIP_TEXT_WINDOW command. The `$ISEXTWIN$` variable reports whether a given window is an extended one. See the [shared geometry-query table and ordinary/extended examples](5.1-text-variables.md#text-window-geometry-query-grammar): omitted TYPE requests legacy ordinary cell corners, while explicit TEXT/BOUND requests graphical edges. Only TWW/TWH(TEXT) accept the matching COLS/ROWS domain.

>
> The `<reserved>` parameter is reserved for future use in RIPscrip and should be set to "000" for compatibility with future releases of RIPscrip.

### Selection, First Use and Partial ANSI Input

_Evidence: 2.00a4 §3.4.3.10, CUR's explicit TW-default table and per-window state/protection model; bounded original selection/parser consumers. [Issue #106 derivation](../research/issue-106-text-window-selection.md) records the documentary/native distinction and explicit completion choices. This contract concerns the ordinary wire `2T` form with reserved zero and `$CUR(TW,n)$`; it does not redefine independent COPY or backup operations._

**The first-use rules differ.** Wire `2T` copies the current TW definition into an undefined nonzero destination, as its protocol entry states. `$CUR(TW,n)$` instead gives an undefined destination a fresh full-screen ordinary window using the user's default font, as CUR's own table states. Do not read CUR as an automatic first-use clone. The original driver's common low-level selector uses the latter default-window fallback even for wire `2T`; that implementation limit does not replace the explicit wire protocol's copy rule. Existing destinations use their own retained state in both forms.

**Explicit portable first-use completion:** for wire `2T`, copy the source's complete per-window logical definition/ANSI state listed below, then mark the new destination defined and **unprotected**. This specifies the otherwise incomplete meaning of “definition copied”; it is not a claim that the native fallback cloned those fields. For CUR first use, use the stated fresh defaults. A protected source can be read/left without permission changes; it does not protect a newly created destination. Selecting an already defined protected destination is allowed and does not unprotect or redefine it. The copied values are independent, not shared mutable aliases. These successful-selection rules do not add transactional guarantees for resource-allocation failures.

| State | Wire `2T` first use | `$CUR(TW,n)$` first use | Existing destination, either form |
| --- | --- | --- | --- |
| Ordinary/extended kind and cell/world/device layout | Copy kind and stored bounds/display geometry; do not refit or relocate | Ordinary full-screen nominal grid for the user's default font | Retain |
| Selected MicroANSI font | Copy | User default | Retain |
| Active/deactivated state | Copy; selecting an inactive clone does not activate it | Active | Retain; selection does not activate an inactive target |
| Live cursor and CSI-saved cursor coordinates | Copy both | Both `(0,0)` | Retain both |
| Requested cursor visibility and per-window shape | Copy requests; recreate presentation resources if needed | Visible, default per-window shape | Retain requests |
| ANSI foreground/background and rendition | Copy logical values | Normal ANSI 7/0 | Retain |
| Wrap, origin and other per-window terminal modes | Copy | User wrap preference; otherwise ordinary-definition defaults | Retain |
| Scrolling margins | Copy | Full window height | Retain |
| Explicit tab-stop map | Copy | Empty initial explicit map | Retain |
| G0/G1 designation and invocation | Copy per-window values | US/US, G0 invoked | Retain; mapping rules remain the [charset contract](#byte-character-sets-in-riptel-31) |
| Resident TW query definition | Copy an independently owned logical value; do not execute it | None | Retain |
| Definition protection | New destination unprotected; source unchanged | New destination unprotected | Retain target/source protection |

“Copy logical colors” includes optional direct ANSI color values if the implementation already supports them; this does not require any new SGR syntax or change RIP's graphics ENV color mode. Global client emulation mode, input lock, font resources and graphics palette/PORT/STYLE/ENV selections are outside this per-window copy. The larger [ESC 7/8 snapshot](#ansi-esc-7-and-esc-8-snapshot) is interpreter-owned; selection retains it without creating a per-window copy. Its saved-coordinate payload derives from the captured live point, as specified above.

An unfinished ANSI ESC/CSI/designation or **supported** ANSI string sequence belongs to the connection's terminal parser. Selection neither discards it nor stores/copies it in either window. With an active destination, subsequent raw bytes continue that same sequence and any resulting terminal operation addresses the newly current TW. This ownership rule does not require support for otherwise undocumented OSC/DCS/string sequences; if provided by an implementation, their partial input follows the same boundary. Selecting an inactive window retains the parser; the separately adopted deactivated-window input-discard rules still apply.

Selection preserves displayed screen pixels. It does not clear, scroll, relocate, redraw or restore text/graphics, and first use copies no logical cells, bitmap contents or scrollback/history. Only the visible cursor overlay changes: remove it from the departing window and present the target's requested cursor if that target is active and visible. A cell-backed implementation must not repaint a window merely because it becomes current. Other family selections and the source's logical TW state are unchanged by successful selection.

### Selection Transition Example

Use source TW 0 with an ordinary 20×10 layout, font 2, ANSI foreground/background 2/4, bold, live cursor `(7,4)`, CSI-saved cursor `(2,1)`, cursor hidden, wrap/origin enabled, margins rows 2–7 and explicit stops at columns 5/11. All geometry is already valid and no WORLD/device change occurs in this example. Byte fragments below are terminal data after RIP framing, with selection dispatched between fragments and no additional raw bytes.

| Step | Operation | Required state/result |
| --- | --- | --- |
| 1 | `! | 2T30`, destination 3 unused | TW 3 becomes an independent, unprotected clone of all listed per-window state; TW 0 retains it. Pixels/history are not copied or repainted. |
| 2 | In 3, set normal rendition and foreground 9, live cursor `(1,2)`, explicit stops at 3; protect its definition | Changes belong to 3; 0 retains its original fields. |
| 3 | `! | 2T00` | Select 0 with its original attributes/cursors/tabs. No repaint. |
| 4 | `$CUR(TW,3)$` | Select protected existing 3; its changed state and protection are retained. |
| 5 | Select 0; raw `1b 5b 33`; select existing 3; raw `31 6d` | One `ESC[31m` completes in 3, selecting its ANSI red foreground; 0's foreground stays 2. No glyph from the control sequence; other 3 state is retained. |
| 6 | `$CUR(TW,4)$`, destination 4 unused | Fresh active full-screen default-font TW 4 with normal colors/cursors and no explicit stops, unprotected. It is not a clone of protected 3. |

If the wire-copy source is a protected nonzero TW instead of slot 0, a new wire destination still receives its state without its protection. Slot 0 itself remains unprotectable. Repeating a selection of the already current defined slot does not reinitialize it, copy another slot, reset ANSI parsing or change protection.

The graphics-only demos deactivate their single text window and never switch. _Evidence: corpus._

## RIP_ERASE_WINDOW

_Evidence: 2.00a4; HLP (`RIP_EraseWindow`, plus `$ETW$` variable); SyncTERM (ripper.c:14388) - not observed in the RIPtel demo corpus._

_Clear the text-window bounding rectangle to palette index 0_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `e`      |
| **Arguments** | `<none>` |

**Format:** `!|e` **Example:** `!|e`

**Attributes used:** Base Math (N/A)

This clears the TTY text window to index 0 of the current graphics palette (typically black) and positions the live cursor at window-relative `(0,0)`. Changing STYLE background with `k` or changing ANSI background does not select this erase color. The draft's “current graphics background color (color #0)” is resolved in favor of its explicit index 0 and `Uses Back Color: NO` attribute declaration. This is the protocol rule; historical implementation paint helpers are not an alternative definition. _(2.00a4; reconciliation in [issue #101](../research/issue-101-extended-text-window-contract.md).)_

The area that is erased is actually the bounding rectangle of the text window, not only the display region inside the bounding rectangle. This is different than ANSI commands which erase the text window to a certain color. ANSI/VT-102 commands only erase the display region, not the entire bounding rectangle. _(v2.A4)_

If the text window is not in use or deactivated, then this command is ignored. If the text window and any viewports overlap, then this command will clear the overlapping viewport(s) also. _(v2.A4)_

`$ETW$` uses the same whole-bounding-box, fixed-index-0 erase and homes each target's live cursor. Both forms operate on defined, active text windows even when their TW definition is protected. Graphics PORT activation/protection and viewport clipping do not gate or clip this screen operation. Neither erase resets ANSI colors/rendition, saved cursor, scrolling margins or terminal modes. See the [erase-source comparison](#text-window-erase-sources).

The demos typically deactivate the text window outright (`$DTW$`, or `!|w0000000000`) rather than erase it. _Evidence: corpus._

## RIP_GOTOXY

_Evidence: 2.00a4; HLP (`RIP_GotoXY`, plus `$TWGOTO$` variable); SyncTERM (ripper.c:14428) - not observed in the RIPtel demo corpus._

_Move text cursor to row & column in Text Window_

|               |           |
| ------------- | --------- |
| **Level**     | 0         |
| **Command**   | `g`       |
| **Arguments** | `x:2 y:2` |

**Format:** `!|g <x> <y>` **Example:** `!|g0509`

**Attributes used:** Base Math (current setting)

This command sets the position of the text cursor in the TTY Text window, if it is active. If inactive (if the dimensions are 0,0,0,0), then this command is ignored. With ANSI origin mode off, the comparable ANSI cursor-address sequence is `ESC[row+1;column+1H`: its row precedes column and both are 1-based, whereas RIPscrip `g` supplies zero-based X then Y.

Coordinates are absolute within the full text window: X is column and Y is row, both zero-based. Clamp to `0..columns-1` and `0..rows-1`; ANSI origin mode and scrolling margins neither offset nor restrict this RIPscrip operation. It does not scroll or change margins, saved cursor or origin mode. `$TWGOTO$` follows the same positioning rule for a chosen window, with its own optional-argument syntax. TW definition protection does not prohibit cursor movement, and graphics PORT/viewport state is irrelevant. See [the macro entry](5.1-text-variables.md#twgoto).

The graphics-only demos keep their text windows deactivated and never need it. _Evidence: corpus._

## RIP_HOME

_Evidence: 2.00a4; HLP (`RIP_Home`, plus `$TWHOME$` variable); SyncTERM (ripper.c:13687) - not observed in the RIPtel demo corpus._

_Move cursor to upper-left corner of Text Window_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `H`      |
| **Arguments** | \<none\> |

**Format:** `!|H` **Example:** `!|H`

**Attributes used:** none

This command positions the text cursor to the upper-left corner in the TTY Text Window, if it is active. This uses the full-window absolute origin, independently of ANSI origin mode/scrolling margins, and is equivalent to `g` with `(0,0)`. The comparison with ANSI `ESC[1;1H` assumes ANSI origin mode is off; it is not a reason to home at a scrolling margin. An undefined/deactivated TW is a no-op; definition protection and graphics PORT/viewport state do not block movement.

## RIP_ERASE_EOL

_Evidence: 2.00a4; HLP (`RIP_EraseEOL`); SyncTERM (ripper.c:13426) - not observed in the RIPtel demo corpus._

_Erase current line from cursor to end of line_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `>`      |
| **Arguments** | `<none>` |

**Format:** `!|>` **Example:** `!|>`

**Attributes used:** Back Color, Base Math (N/A)

This command will erase the current text line in the TTY text window from the current cursor location (inclusive) to the end of the line. The erased region is filled with the current graphics background color. This differs from the ANSI command `ESC[K` which clears the area with the current ANSI background color.

The corpus never uses it, but a `$TWERASEEOL$` command-variable equivalent exists in the RIPtel help. _Evidence: HLP._

### Text-window Erase Sources

HEADER type-3 erase flags 4096/8192 explicitly adopt this contract for the whole bounding box and current graphics palette index 0, including protected active TWs and independence from graphics PORT/viewport state. The [header field/gate table](1.1-protocol-and-command-hierarchy.md#text-window-geometry-erase-and-caret-profile) specifies geometry and caret behavior separately; neither a native ANSI brush nor an inactive graphics port changes the adopted erase color.

_Evidence: 2.00a4 command attribute declarations and §5.6.13; target-TW gating corroborated by original consumers. [Issue #101 derivation](../research/issue-101-extended-text-window-contract.md)._

| Operation | Paint source | Region and cursor |
| --- | --- | --- |
| Wire `e`, `$ETW$` | Index 0 of the current graphics palette | Entire target bounding rectangle; live cursor homes |
| Extended `b`, flag 16 | Index 0 of the current graphics palette | Final adjusted bounding rectangle; definition has homed the live/saved cursor |
| Wire `>` | Current graphics STYLE background selected by `k`, resolved through the current graphics palette | Cursor cell through final cell of its display row; cursor unchanged |
| `$TWERASEEOL$`, ANSI `ESC[K` | Target TW's current ANSI background, resolved through the terminal's ANSI color mapping | Cursor cell through final cell of its display row; cursor unchanged |

The two end-of-line forms intentionally have different documented color sources; `$TWERASEEOL$` is not a color-identical alias of wire `>`. For example, with graphics palette entry 0 black, STYLE background blue and target ANSI background red, `e`/`$ETW$`/flag 16 clear black, `>` clears blue and `$TWERASEEOL$` clears red. Reprogramming palette entry 0 changes the first group's actual color; “black” is not a hardcoded RGB requirement.

Outside a successful definition's flag-16 operation, an undefined or deactivated target TW is a no-op for these erase operations. Definition protection does not prevent erasure. A deactivated graphics PORT does not suppress erasure of an active TW, and an active PORT does not enable a deactivated TW. Erase operations replace covered pixels, independently of graphics write mode, fill pattern, PORT bounds and viewport clip; they can visibly overwrite overlapping graphics/windows. End-of-line erase covers display cells only, leaving bounding margins intact. [The macro entries](5.1-text-variables.md#etw) retain their all-arguments syntax validation before effects.

## Overlapping Windows and Viewports

_Evidence: 2.00a4._

Multiple text windows and viewports may overlap freely, and no compositing occurs - everything is just pixels on the screen. Draw a circle across a text window and then scroll the window, and part of the circle scrolls with it; text written where two windows overlap is simply graphics on top of the other window. RIPscrip preserves no record of _what_ drew a pixel; the final screen state is the only truth. The full inherited discussion is in [1.3 World View & Virtual Canvas](1.3-world-view-virtual-canvas.md#viewports-and-text-windows---overlapping-issues); mouse regions are the one place ordering matters - overlapping regions are scanned most-recent-first on a click.

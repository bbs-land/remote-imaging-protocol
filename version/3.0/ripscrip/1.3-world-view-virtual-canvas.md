# 1.3 World View & Virtual Canvas

[◀ Prev: 1.2 Math & Coordinates](1.2-math-and-coordinates.md) · [Contents](README.md) · [Next: 1.4 Terminal & ANSI View ▶](1.4-terminal-ansi-view.md)

Drawing happens in [world coordinates](../../glossary.md): the world frame is the logical space, the terminal maps it onto whatever physical resolution it runs at, and the current [drawing port](../../glossary.md)'s [viewport](../../glossary.md) clips what is drawn and sets its origin - the [screen](../../glossary.md) is simply port #0.

_The 1.54 model this generalizes - a single fixed 640×350 graphics window with a clipping viewport - is [1.3 in the v1.54 reference](../../1.54/ripscrip/1.3-world-view-virtual-canvas.md); a 1.54 scene runs unchanged under 3.x because the defaults reproduce that environment exactly._

## The Port Model at a Glance

_Evidence: 2.00a4; HLP._

A drawing port is an area where graphics can be drawn. At any moment there is exactly one **current drawing port** - the port that receives graphical drawing operations. Ports come in two types:

1. **Screen (visual) drawing ports** - rectangular regions of the user's actual screen. Drawing to a screen port appears immediately. Screen ports divide the display into separate drawing areas that can be switched between at will.
2. **Offscreen bitmap drawing ports** (also called **clipboard ports**) - drawing surfaces that are not part of the visible screen. Graphics drawn to an offscreen port are invisible until copied to a screen port. Offscreen ports are used to compose scenes out of sight and reveal them whole, to cache bitmaps loaded from disk, to save screen regions under dialog boxes, and to drive transition animation.

The 3.0 driver additionally distinguishes **snapshot ports** - offscreen ports created by capturing screen contents - in its error strings ("No mouse/button fields on offscreen drawing ports"). _Evidence: HLP._

Ports live in a 36-slot [data table](7.1-data-tables.md), entries numbered 0-35. **Port 0 is always the screen** - it is the full size of the display, exists at all times, and cannot be created, deleted, or redefined (confirmed verbatim by the 3.0.7 driver's error strings "Can't delete graphics port #0" and "Can't create drawing port #0"); ports 1-35 are user-definable ("The given port number is invalid (1-35 only)"). Mouse fields, clickable buttons, text windows, and resident query expressions are screen-only and may not be placed on an offscreen port. _Evidence: 2.00a4; HLP._

Each port has its own coordinate origin - (0,0) is the upper-left corner of the port - and its own remembered drawing state, and every port has an associated **viewport**: a clipping rectangle inside the port that defines its drawing limits and shifts the drawing origin to its own upper-left corner. Anything drawn beyond the viewport's edge is truncated (clipped). By default a port's viewport is the full size of the port. So a point at (50,50) inside a viewport that starts at (40,40) inside a port that starts at (25,25) on the screen lands at screen position (25+40+50, 25+40+50) = (115,115). _Evidence: 2.00a4._

```text
╔═════════════════════════════ Screen ══╗
║ (0,0)                                 ║
║   ┌────────── Port (25,25 screen) ─┐  ║
║   │ (0,0) port                     │  ║
║   │    ┌──── Viewport (40,40) ──┐  │  ║
║   │    │ (0,0) viewport         │  │  ║
║   │    │        drawing here    │  │  ║
║   │    └────────────────────────┘  │  ║
║   └────────────────────────────────┘  ║
╚═══════════════════════════════════════╝
```

In TeleGrafix's own 3.x material the port system is the workhorse: the RIPtel demo corpus contains **9,104 uses of `2C` (RIP_PORT_COPY)** - almost all in the WIPE00-WIPE24 "wipe" transition library, which composes the next scene in an offscreen port and reveals it with sequences of narrow port-to-screen copies. Defining, deleting, switching, and copying between ports - and the port-copy scaling and viewport rules - are documented in [7.0 Drawing Ports](7.0-drawing-ports.md). _Evidence: corpus (WIPE00.FN-WIPE24.FN); HLP._

## RIP_SET_WORLD_FRAME

_Added in RIPscrip v2.A0._

_Evidence: 2.00a4; HLP (`RIP_SetWorldFrame`, plus `$WORLD$`/`$WORLDW$`/`$WORLDH$` variables); corpus (151 uses in 103 files); SyncTERM (ripper.c:14401)._

_Sets the coordinates for the World Frame_

|               |                     |
| ------------- | ------------------- |
| **Level**     | 0                   |
| **Command**   | `f`                 |
| **Arguments** | `x_dim:XY y_dim:XY` |

**Format:** `!|f <x_dim> <y_dim>` **Example:** `!|fZKQO`

**Attributes used:** Base Math (current setting)

This command sets the dimensions of the World Coordinate Frame. This Frame is the Global Coordinate Space of the RIPscrip drawing screen. It is not the exact size of the Device Frame - that is a lower level coordinate system. With this frame, you can "map" your scenes into something, say a 1024x1024 grid and let the terminal worry about mapping it into whatever device coordinates it is using (eg, 640x350, 800x600, etc). Any coordinates used for setting viewports or other such things will be specified in World Frame Coordinates. Actual drawing primitives will use the current Drawing Frame's coordinates - another level of coordinate mapping. This allows you to do things like draw full screen images inside a tinier window, leaving additional drawing space on the screen for other images.

The actual Device Coordinate Frame is not specified in the RIPscrip language anywhere - it is handled entirely by the remote terminal, because only it knows the device coordinates of the environment that it is running under (although the host can query these values from the terminal).

The `<x_dim>` parameter is how wide the drawing area is in logical coordinates. The `<y_dim>` parameter is how tall the drawing area is in logical coordinates.

**Shipped setter range:** RIPtel 3.1 accepts each dimension in **0..65535**, including zero and 32768..65535. If either exceeds 65535 it leaves the frame unchanged. The white paper’s advertised 32767 limit is not enforced here. This is the world-state setter contract; individual drawing-coordinate signedness remains command-specific. [WORLD](5.1-text-variables.md#world) has the same ordinary stored range but a different oversized-pair validation defect. _Evidence: original handler 0x1f874, active setter 0x3e9d4 and [native wire/macro matrix](../research/issue-23-environment-query-names.md#native-callback-activation-and-wire-checkpoint)._

This command is the single biggest semantic change of the 2.0/3.x era: it redefines the logical coordinate space away from 1.54's fixed 640×350, making every subsequent coordinate frame-relative. It closes the standard corpus prologue in over 100 files as `!|fZKQO` - `ZK`/`QO` decode to **1280×960**, the square-pixel MegaNum world frame recommended by the [2.00a4 RIP_HEADER discussion](../../2.0/ripscrip/1.1-protocol-and-command-hierarchy.md#rip_header) and supported by the shipped [environment header segment](1.1-protocol-and-command-hierarchy.md#rip_header). Alternate observed frames: `HSDC` = 640×480, `HR9S` = 639×352, `HRDC` = 639×480 (BLUEFADE.FN works at 640×350 and TELPORT.FN's comments then "reset our environment back to 1280x960 world coordinates"). ONLINE.RIP demonstrates the driver's argument-parsing tolerance with an inline trailing comment: `!|fZKQO                 Set world coordinats to 1280x960` _(sic)_. _Evidence: corpus._

### Translating World to Device Coordinates

To translate from World Coordinates to Device Coordinates, you need to know four things:

```text
1/2) The World Frame's dimensions (ie, x_dim and y_dim)
3/4) The dimensions of the actual display device (x_max, y_max)
```

After you have these four values, you can translate any X/Y coordinate pair in World Coordinates to Device Coordinates with the following equations:

```text
EQUATION 1 - TRANSLATE WORLD TO DEVICE COORDINATES
──────────────────────────────────────────────────

           ╔═══════════════════╤═══════════════════╗
           ║       Xw * x_max  │       Yw * y_max  ║
           ║  Xd = ──────────  │  Yd = ──────────  ║
           ║         x_dim     │         y_dim     ║
           ╚═══════════════════╧═══════════════════╝
```

Where (Xw,Yw) is a point in World Coordinates. We are solving for the point (Xd,Yd) which is in Device Coordinates. The values x_max and y_max are the physical dimensions of the display device (eg, x_max=640, y_max=350). The values x_dim and y_dim are the dimensions of the World Coordinate Frame (eg, x_dim=1000, y_dim=1000).

As an example, let's say we are drawing onto a 640x350 display device and our World Coordinate Frame is 1000x1000 logical pixels in size. If we plot a pixel at coordinates right in the middle of the screen at (500,500), here is what we would have:

```text
     500 * 640   320,000
Xd = ───────── = ─────── = 320
       1000       1000


     500 * 350   175,000
Yd = ───────── = ─────── = 175
       1000       1000
```

This gives us a final Device coordinate of (320,175) which is smack in the middle of the device screen as we wanted.

### Translating Device to World Coordinates

If we solve the above equations for Xw and Yw, we get the inverse equations - translations from Device Coordinates to World Coordinates:

```text
EQUATION 2 - TRANSLATE DEVICE TO WORLD COORDINATES
──────────────────────────────────────────────────

           ╔═══════════════════╤═══════════════════╗
           ║       Xd * x_dim  │       Yd * y_dim  ║
           ║  Xw = ──────────  │  Yw = ──────────  ║
           ║         x_max     │         y_max     ║
           ╚═══════════════════╧═══════════════════╝
```

### Precision of translation

If the World Coordinates are larger than the Device Coordinates, then when you translate World Coordinates to Device Coordinates, there will be pixel-perfect translation. This means that translation will be unambiguous - they will convert to pixel coordinates without there being any discrepency. For example, if your Device Coordinates are 640x350 and your World Coordinates are 1280x700, then a Point in World Coordinate space at (0,0) and (1,0) will both translate to the Device Coordinates (0,0) and (0,0) respectively. This is because the World Coordinate space is twice as large as the Device Coordinate space. If on the other hand the Device Coordinates were 1280x700 and the World Coordinate space were 640x350, then the World Points (0,0) and (1,0) would translate to (0,0) and (2,0) respectively. Notice that in the World Coordinates, the pixels were adjacent. But in the Device Coordinates, they are separated by a one pixel gap.

In summary, World Coordinates should always be equal to or greather than the size of the Device Coordinate Frame, otherwise disparity will exist in the translations. Since coordinate translation will almost ALWAYS be from World -> Device coordinates, everything will be fine if the World Frame has a larger resolution than the Device Frame. The same holds true for the inverse equations to translate from Device to World coordinates. If the World Coordinate Frame is larger than the Device Coordinate Frame, then any point that is translated from Device -> World Coordinates (a Mouse X/Y location for example), might not translate over precisely - skipping over pixel spaces in the World Frame - this is simply because of the precision of translation and cannot be overcome mathematically since a Mouse Pointer's location is pixel based - it doesn't have any finer locations than on pixel boundary locations (there's no such thing as a fractional pixel location in graphics hardware - only mathematically).

To maintain backward compatibility with previous versions of the RIPscrip specification, after a [RIP_RESET_WINDOWS](#rip_reset_windows) command is received, the World Coordinate Frame is defined as having the dimensions 640x350 until reset by a RIP_SET_WORLD_FRAME or [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) command.

## RIP_VIEWPORT

_Evidence: 2.00a4; HLP (`RIP_Viewport`, plus `$AVP$`/`$DVP$`/`$MVP$` variables); corpus (3 uses in IMAGES.RIP); SyncTERM (ripper.c:14725)._

_Define the size & location of the Graphics Window_

|               |                           |
| ------------- | ------------------------- |
| **Level**     | 0                         |
| **Command**   | `v`                       |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY` |

**Format:** `!|v <x0> <y0> <x1> <y1>` **Example:** `!|v00002E1M`

**Attributes used:** Port, Base Math (current setting)

This command defines the (X,Y) pixel boundaries of the RIPscrip graphics window, which will contain all RIPscrip graphics output. ASCII/ANSI text will be displayed in the current TTY window defined by the [RIP_TEXT_WINDOW](1.4-terminal-ansi-view.md#rip_text_window) command. (x0,y0) defines the upper-left corner of the graphics viewport, and (x1,y1) defines the lower-right corner (inclusive). The viewport may be deactivated by setting all parameters to zero (0). This suppresses graphical operations such as IMAGE display; it is not a universal gate on configuration commands. In RIPtel 3.1, wire [IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style) still replaces the stored image rectangle/flags while inactive, and reactivation preserves that new setting. Its IMGSTYLE macro counterpart has a separate inactive-target rejection. _Evidence: [original setter/activation/display sequence](../research/issue-21-image-style.md#integration-review-inactive-viewport-wire-setter)._

The viewport belongs to the current [drawing port](7.0-drawing-ports.md), but the shipped RIPtel 3.1 producer differs from the draft's port-relative/clamped description. It converts both supplied corners directly from world to device coordinates, normalizes their order, adds one to right/bottom for the inclusive endpoint, and stores the result as the port's viewport in its drawing context. It **does not add the screen port's origin or intersect the rectangle with port bounds**. A screen port's initial viewport is copied from its screen bounds; a later viewport definition replaces it with these directly converted values. Drawing is then clipped by that stored rectangle and by the underlying drawing surface. _Evidence: original handler 0x20f87 / helper 0x33cc6 and [producer/placement probe](../research/issue-11-pixel-pen-units.md#viewport-producer-and-screen-port-origin)._

For world 1280×960/device 640×480, viewport arguments (80,80)..(118,118) store device `[40,40,60,60)`, even on a screen port beginning at (25,25). [RIP_POINT](2.1-lines.md#rip_point) at world (2,2) then uses center (41,41); [RIP_PIXEL](2.1-lines.md#rip_pixel) has a separate omitted-origin defect and attempts (1,1). The generic port-relative composition (25+40+1,25+40+1) is not what this original viewport producer performs. An implementation restoring that composition or enforcing port-bound clipping should identify those changes as corrections to the shipped client.

Graphics displayed in the viewport are "truncated" at this rectangular border, meaning if a circle would normally extend outside one of the borders, it will be chopped, only displaying the portion of the circle that is contained inside the viewport boundaries.

Coordinates that specify the boundary of the Graphics Viewport are specified in World Coordinates. The interior area of the Viewport is then considered the Drawing Frame. The Drawing Coordinate frame are set to the same size/dimension as the World Coordinate Frame area that the viewport inhabits. For example, if you define a viewport from (100,100) to (299,299) in World Coordinates, then your Drawing Frame will be a drawing area with a resolution of 200x200 logical drawing pixels. In other words, when you set a viewport, you immediately have a 1:1 mapping of logical drawing pixels to World Coordinate Pixels. If you wish to change the X/Y Drawing Frame resolution to some other value, use the RIP_SET_DRAWING_FRAME command after setting the viewport. If you draw anything before executing this command, then the privimitives will be drawing things in the current Drawing Frame's coordinates (a sub-set of the World Coordinates). The Drawing Frame's coordinates do not take on another mapping until you actually set them with a RIP_SET_DRAWING_FRAME command. _(v2.A0)_

To re-activate a viewport that was previously deactivated, either send a correctly configured RIP_SET_VIEWPORT command, or issue a query command with a `$AVP$` [text variable](5.1-text-variables.md) (Activate ViewPort). _(v2.A4)_

_[Editor's note: the `RIP_SET_DRAWING_FRAME` command referred to in the v2.A0 paragraph above was dropped before the ALPHA 4 draft - no entry for it exists anywhere in the specification, and no trace of it appears in the 3.x evidence (HLP inventory, corpus, or SyncTERM). In practice the viewport's 1:1 world-coordinate mapping described above is the only drawing-frame behavior defined.]_

In the corpus, IMAGES.RIP uses this command to clip bitmap stamping regions, then restores the full frame with `!|v0000ZKQO`. _Evidence: corpus._

An inactive viewport retains its stored rectangle. A defined clipboard port can still supply that rectangle and its pixels to [PUT_IMAGE](4.0-icons-and-bitmaps.md#rip_put_image) while a separate active port receives the paste.

HEADER type-2 [black fill](1.1-protocol-and-command-hierarchy.md#port-bounds-reset-and-black-fill) is a full-port operation: its active viewport is an eligibility gate, and its temporary clear scope does not replace the stored viewport used by subsequent drawing. The separate geometry flags 2048/4096 maximize eligible active viewports to the same screen canvas rectangle as MVP. [MVP](5.1-text-variables.md#mvp).

### Viewport Projection Range

For a viewport definition, compute the mathematical WORLD-to-DEVICE projection of each corner using the active axis extents. For a decoded nonnegative coordinate `n`, the result is `floor(n × DEVICE / WORLD)`. Use sufficient precision for the product and final addition. Normalize the projected corners, then add one to each inclusive far coordinate to form the half-open DEVICE rectangle.

The portable `v` contract requires each of the four **final stored boundaries**, including the exclusive right and bottom, to fit the signed 32-bit DEVICE range −2,147,483,648 through 2,147,483,647. If any boundary is outside that range, reject the complete definition. The previous stored viewport and its active state remain in effect for drawings, queries and transfers. Consume the command normally and continue the stream. A range-valid rectangle is stored exactly as projected, even where it is outside the port or physical surface. Its consumers still apply their ordinary clipping. [Projection and storage derivation](../research/issue-313-viewport-projection-range.md) · [Physical storage and sample coverage](7.0-drawing-ports.md#physical-storage-and-sample-coverage).

The range check includes the final increment. An inclusive projected endpoint of 2,147,483,646 can produce an exclusive boundary of 2,147,483,647. An inclusive endpoint of 2,147,483,647 exceeds the stored range when incremented. A new rectangle also requires positive WORLD extents on both axes. The all-zero deactivation form uses its usual deactivation rule.

For example, start with active PORT 0 viewport `[10,10,20,20)` on a 640 × 480 device. Set WORLD to 1 × 480 while retaining this stored viewport. With UltraNum and XY width 5, receive `!|v00000000000G00000001`, which requests corners (0,0) through (4,194,304,1). The mathematical right coordinate is 2,684,354,560 inclusive and 2,684,354,561 exclusive. Reject the definition. After restoring WORLD to 640 × 480, the portable result of `$PORTX1(0,VIEW,DEVICE)$` is decimal `20`. A drawing sample at final DEVICE position (0,0) still lies outside the old clip. [PORTX1](5.1-text-variables.md#portx1).

## RIP_ERASE_VIEW

_Evidence: RIPtel 3.1 slot 25 and the shared erase routine. The [ALPHA 4 entry](../../2.0/ripscrip/1.3-world-view-virtual-canvas.md#rip_erase_view) preserves the earlier description. [Original handler and fill derivation](../research/issue-273-full-port-erase.md)._

_Clear the current graphics port to black_

|               |          |
| ------------- | -------- |
| **Level**     | 0        |
| **Command**   | `E`      |
| **Arguments** | `<none>` |

**Format:** `!|E` **Example:** `!|E`

**Attributes used:** current port and its activation state.

At the command delimiter, `E` clears the current port when it is defined and its viewport is active. Protected ports are eligible. The fill uses the same [full-port black-fill contract as HEADER](1.1-protocol-and-command-hierarchy.md#port-bounds-reset-and-black-fill). For a stored port rectangle B and actual backing extent S, fill B intersect S with opaque RGB (0, 0, 0). The stored viewport is the activation gate. Its bounds do not clip this operation. The fill is independent of graphics background color, palette entry 0, write mode, and fill pattern. Later palette changes leave these pixels fixed black.

A screen port clears the corresponding shared screen pixels, including pixels occupied by overlapping text windows. A bitmap port clears its own storage. Afterward, port selection, bounds, viewport, protection, graphics and text cursor positions, query definitions, image style and remembered copy pair retain their values. Subsequent drawing uses its usual viewport clip.

For example, an active screen port with B = `[10, 18) × [20, 24)` and viewport `[12, 15) × [21, 23)` clears the whole B when it lies inside the physical screen. A defined active bitmap with B = `[0, 8) × [0, 4)` and a narrower viewport clears all 32 pixels when its backing has that size. [Source and portable geometry checks](../research/issue-273-full-port-erase.md).

[`$EGW$`](5.1-text-variables.md#egw) uses the same fill on its selected ports. The text-window erase commands [`e`](1.4-terminal-ansi-view.md#rip_erase_window), [`>`](1.4-terminal-ansi-view.md#rip_erase_eol) and [`$ETW$`](5.1-text-variables.md#etw) have their own contracts.

### Outer SOFT Reset Contract

_Evidence: 2.00a4 §3.4.1.44 and RESET/backup rules; original RIPtel 3.1 / driver 3.0.7 outer reset and reached family consumers. [Issue #105 derivation](../research/issue-105-outer-soft-reset.md) distinguishes read-only evidence, earlier bounded fixtures and explicit portable clear/protection decisions. This completes the 3.0 contract and leaves 1.54 unchanged._

Wire `*` performs the drawing/SOFT reset with deletion of unprotected nonzero ports, screen clear enabled and display update enabled. It does **not** perform HARD reset or an additional “select every table zero” operation. [HEADER global bit 8](1.1-protocol-and-command-hierarchy.md#rip_header) is a separate operation; HEADER bit 2 invokes this SOFT path before the header's own subsequent operations. The old blanket zero-selection bullet was incorrect for PAL.

| Family | Current selection after `*` | Unprotected live records | Protected live records |
| --- | --- | --- | --- |
| TW | 0 | Nonzero slots discarded; 0 redefined as the ordinary default text area with the user's default MicroANSI font | Nonzero definitions survive, subject to the old-current ANSI side effect below |
| BUT | 0 | Default button styles; nonzero entries become undefined, 0 remains defined | Retain definition/protection |
| STYLE | 0 | Boot/default graphics style; nonzero entries become undefined, 0 remains defined | Retain definition/protection; see the source-limit note below |
| PAL | **Retained** | RGB values reset to boot defaults; nonzero entries become undefined, 0 remains defined | Retain RGB, definition and protection, even when current |
| PORT | 0 | Nonzero screen/offscreen ports deleted; 0 is the full physical screen with full viewport | Nonzero ports and offscreen pixels survive, with the adopted old-current image-style exception below |
| ENV | 0 | Default environment records; nonzero entries become undefined, 0 remains defined | Retain records subject to the already documented [activation write-back boundary](7.1-data-tables.md#environment-table) when departing from a protected current ENV |

Protection of a current slot does not prevent selecting a different slot. Slot 0 remains the unprotectable/defined baseline in each family. A retained current PAL can therefore become undefined after reset; `$CUR(PAL)$` still returns its original number while `$INUSE(PAL,n)$` is false. Selecting PAL 0 is a separate request. See the adopted [palette lifecycle](7.1-data-tables.md#palette-reset-lifecycle).

### Physical Screen Clear and Palette Ordering

The outer clear targets the entire physical screen canvas, independently of the previously selected screen/offscreen port, viewport origin/clip, viewport activation, STYLE background, write mode or fill pattern. The source passes literal raw color `0x00000000` to a solid **RGB-black** brush and fills the physical screen rectangle **before** resetting/uploading the palette table. It does not pass a palette-index token or resolve STYLE's background. There is therefore no selected palette supplying the clear color, and PAL selection is not switched to 0 as a side effect.

**Explicit portable display rule:** after `*`, cleared screen pixels represent RGB black `(0,0,0)`, including when the retained protected current palette has a nonblack entry 0. Do not recolor that clear from the retained palette's entry 0 or a later palette upload. This defines the visible canvas result without requiring obsolete Windows palette realization/dithering behavior. A strictly indexed backend must supply the black clear consistently with this rule; the command does not rewrite a protected palette to manufacture a black entry. Subsequent palette-index drawing continues to use the retained current PAL and may therefore draw a nonblack index 0. This clear differs from [wire `e`/`$ETW$`/extended-window flag 16](1.4-terminal-ansi-view.md#text-window-erase-sources), whose adopted protocol source is palette index 0.

The old explanation “black because the palette was just reset” gave both the wrong dependency and the wrong order. Palette reset still respects protection and current-index retention; these rules do not require native palette-device pixel parity.

### Text, Graphics, Environment and Input State

TW 0 is activated in the client’s [ordinary default text area](1.4-terminal-ansi-view.md#default-window-rows-and-scrolling) using the user’s selected default among fonts 0–4. Its live and saved cursors are `(0,0)`. Its colors become ANSI 7/0, rendition becomes normal, scrolling margins cover the full window, cursor is enabled and wrap follows the global user's wrap setting. Apply the adopted [ordinary-window geometry](1.4-terminal-ansi-view.md#rip_text_window), including device cell placement and any unused edge space. “Full-screen TW” does not mean clearing only its text-cell display region: the separate clear covers the physical canvas.

This outer sequence is separate from [live RESET(TW)](5.1-text-variables.md#live-text-window-reset-contract), whose completed slot-zero recipe uses fresh per-window defaults and has no canvas clear, departing-window ANSI reset, floating-query deletion or unconditional table-wide selection of 0.

Before discarding/selecting TW slots, the outer path performs an ANSI reset on the **old current TW**, including a protected one. That changes its ANSI colors to 7/0, clears rendition and insert mode, homes its live cursor if active, zeros its saved cursor, restores full-height scrolling margins and the default tab map. This is an allowed terminal-state operation on a protected definition, not deletion/redefinition. Its other per-window modes and charset fields are not blanket-cleared by that preliminary ANSI reset. Protected noncurrent TW records do not receive this preliminary effect. TW 0 then receives the ordinary-definition defaults described above. Its tab map is the result of the preliminary reset if it was old-current; otherwise ordinary redefinition retains TW 0's existing map.

G0/G1 and invocation are retained in TW 0 and protected surviving TWs; the ANSI-versus-VT-102 client choice and partial ANSI parser state remain separate and retained. See the precise [charset reset/save boundary](1.4-terminal-ansi-view.md#character-set-state-boundaries). Do not turn `*` into a connection-wide ANSI parser reset.

The separate [ANSI ESC 7/ESC 8 snapshot](1.4-terminal-ansi-view.md#snapshot-initialization-and-lifetime) survives SOFT as owned interpreter state, even if the original TW is deleted. A later ESC 8 does not restore the pixels cleared here. Its hard-reset/session clearing and other lifetime cases are explicitly specified there.

HEADER type-2 [PORT-0 initialization](1.1-protocol-and-command-hierarchy.md#port-zero-initialization) shares some of these local fields but is a distinct operation: full V, homed graphics cursor, image fallback and absent pair, with prior activation/query retained and no screen clear or other SOFT effects.

Graphics cursor for port 0 becomes `(0,0)`. Surviving nonzero ports retain their own graphics cursor. The full drawing reset invalidates the interpreter's outline metric snapshot, so cached width is zero until a successful new preparation; this preserves the explicit [advance/cache policy](../techspecs/2.4-outline-advance-and-cache.md#snapshot-lifecycle), rather than asserting a newly measured native cache lifetime. Active graphics STYLE 0 supplies the adopted [boot defaults](7.1-data-tables.md#initial-and-per-slot-defaults): drawing color 15, background 0, COPY, solid fill 15, solid one-pixel line, border enabled, classic font 0 at size 1, left/top justification and zero alignment flags. The classic renderer is separately initialized to that font/justification.

The remembered scene-header revision marker becomes 0. ENV 0 is selected; active WORLD becomes 640×350, Base Math 36, coordinate width two numeric characters, and indexed/palette color mode (RGB precision 0). Stored unprotected environment records receive those defaults. The already documented departing-ENV setter behavior remains scoped to environment activation; no other table's current index is stored inside ENV.

The [remembered-copy pair lifecycle](7.0-drawing-ports.md#pair-lifetime-and-port-backups) explicitly clears port zero's pair on this full drawing reset, drops deleted-port pairs and retains protected surviving nonzero pairs; viewport-only resets follow their separate preservation rule.

Mouse fields and clickable button instances are deleted, independently of whether their button-style definitions survive protection. Mouse pointer becomes the default arrow. **SOFT retains the existing HEADER scene input restrictions.** `#` / RIP_NO_MORE releases both devices. The portable explicit input resets release their respective device. [Scene input gates](1.1-protocol-and-command-hierarchy.md#scene-input-gates). Active audio is not given a stop request by SOFT; digitized sound/music remains under its normal lifecycle unless separately stopped. Clearing the screen is not an audio reset.

**Adopted image-style exception:** old-current PORT and port 0 get viewport-fallback image rectangle and image flags zero, even if the old current port is protected. Other protected surviving ports retain their image state. See the [image reset table](4.1-jpeg-images.md#defaults-and-reset-scope).

**Source limit for protected STYLE:** original outer preparation also writes border-enabled into the old current STYLE before selecting STYLE 0, bypassing its protection. The portable contract preserves the protocol's protection of STYLE configuration and does not require that additional native write. This distinction is recorded in the derivation; it does not revise the already adopted image-style or environment-activation boundaries.

### State That Survives

- The [live local playback rate](5.5-file-transfer-and-queries.md#live-playback-rate-and-env-state) and pacing remain in effect across the reset, including during local file playback.
- User/named variables and all template definitions survive; SOFT does not mean `$RESET(TV,...)$`, variable deletion or template deletion.
- All separately owned backup **base areas, numbered slots and stacks** survive for BUT, STYLE, PORT, TW, PAL, ENV, mouse fields and screen, with their stored state/pixels/protection. Live-table resets do not erase the independent backup objects. HARD reset and explicit backup-reset operations have different ownership.
- Offscreen/clipboard ports follow the live PORT protection rule: an unprotected clipboard is deleted and its assigned clipboard pointer cleared; a protected clipboard and assigned pointer survive. “Clipboard always cleared” and “all clipboard data always survives” are both incorrect. See [GET_IMAGE lifecycle](4.0-icons-and-bitmaps.md#rip_get_image).
- Global client ANSI/VT-102, communication/encoding preferences and the existing input-lock flag survive. Pending ANSI syntax is not copied into backup windows or canceled by this command.

The command does clear the floating PORT/TW query expressions, both shared hover handlers and refresh expression, as well as live mouse/button fields. The [hover lifecycle table](4.2-mouse-fields-and-pointer.md#hover-handler-and-membership-lifetime) distinguishes this full reset from field-only deletion and saved mouse-family restoration. Queries/resources owned by a deleted live entry disappear with that entry; do not infer deletion of their independent saved copies. The earlier [deferred-query dispatch contract](5.5-file-transfer-and-queries.md#rip_query) is unchanged.

## HARD Reset State and Lifetime

**Explicit portable completion:** [HEADER global bit 1](1.1-protocol-and-command-hierarchy.md#global-header-flags) and immediate [`$RESET(HARD)$`](5.1-text-variables.md#reset) invoke the same HARD reset. ALPHA 4 specifies a complete RIPscrip environment reset overriding protection and clearing saved areas; the original shared routine establishes family/clear/font ordering. The field and lifetime inventory below completes otherwise unspecified fresh-state boundaries, adopting the existing PAL and ESC-snapshot answers. [Derivation, exact source ranges and limits](../research/issue-158-hard-reset-profile.md). It specifies a successfully completed logical reset, rather than OS handles, native stale-field inheritance or RIPscrip 1.54 behavior.

**Scope choices:** fresh PORT-0 activation/cursor/query/clipboard state, the forced fresh TW-0 recipe and complete shared-query cleanup are deliberate portable completion of “complete environment reset.” They do not claim that selecting an existing native record reset every field. The metric/snapshot and fixed-RGB-black results reuse their earlier explicit contracts. The source ledger records these boundaries instead of making native DC/brush/font/allocation history visible protocol state.

The physical black result is independent of current PAL entry 0. The original clear request occurs **before** palette reset/upload; palette reset is not the cause of the clear color. Apply the existing [fixed-black color model](#physical-screen-clear-and-palette-ordering): a subsequent edit of PAL entry 0 does not recolor the cleared canvas as stored index-0 pixels. Future indexed drawing uses the then-current palette normally. Screen/ANSI cursor overlays are presentation, not surviving pre-reset scene pixels.

This table describes successful completion. Invalid HEADER/RESET syntax has its existing no-application behavior; this adds no global allocation rollback guarantee. Accepted HARD clears the larger ESC snapshot at its separately established early boundary even if later resource setup fails. Backend resources must realize the completed logical state, without exposing private handles or requiring vintage pixel/failure-path identity.

### HEADER Versus Live HARD

HEADER validates the whole command before application; when both global HARD bit 1 and SOFT bit 2 are set, HARD takes precedence. After the shared HARD operation, HEADER records its supplied revision, releases any prior scene input lock, optionally locks input again with global bit 4, then performs other requested global operations and segments in their established order. Thus revision-1 `!|h01000100` ends with marker **1**, default tables and unlocked input. A later segment may deliberately change the just-reset state. The segment-free header itself does not execute an HCL reply.

Immediate `$RESET(HARD)$` performs the shared operation with marker **0**, preserves the connection’s current scene input restrictions and uses the shared reset stages. It returns no inserted text; later literal text, variable providers and template lookups in the current response continue under the usual preprocessing/two-pass/block rules. Because template slots were cleared, a **later** lookup cannot fetch their old bytes; bytes already copied into an owned working program before HARD remain part of that program. A later explicit ordinary definition may create a new slot normally. If HARD removes the field owning the current committed action, retain that action's captured source/FIELDID until return; subsequent associated writes/redraws still require the original live owner and cannot attach to a replacement.

Pending ANSI syntax belongs to the connection parser, not the old TW record or saved ESC snapshot. With the fresh active TW 0 current, subsequent routed raw bytes complete that retained syntax against TW 0's new state. For example, pending `ESC [ 31` followed after HARD by `mZ` applies red ANSI foreground and draws Z in the new window; it does not display the pending prefix as text or restore the old window. Normal intervening routed control/newline bytes still have their ordinary effects. HARD is not an inbound-stream discard or a TCP/session restart.

## Viewports and Text Windows - Overlapping Issues

_Added in RIPscrip v2.A1; revised in v2.A3._

_Evidence: 2.00a4._

Since there are multiple text windows and [ports](7.0-drawing-ports.md) (with their viewports) allowed in the RIPscrip specification, some elaboration needs to be made on what happens if any overlap each other. Very simple, they do what they have always done - draw text, or draw graphics. For example, if a viewport overlaps a text window and you draw some graphics (say a circle) over the top of some text in a text window, and the text window subsequently scrolls, all or part of the circle could scroll with it! Now, of course, from the viewport's standpoint, the graphics are no longer what you originally sent to the viewport, but that doesn't matter - you don't preserve any of the commands you used to create the graphics - you simply draw the graphics and that's it. So with this in mind, even if multiple viewports overlap each other it doesn't matter because the final result is what's on the screen - doing things in one viewport might do some overlapping graphics in another viewport but that is alright.

If a text window overlaps another text window, the same thing happens. To a RIPscrip terminal, text is simply just a piece of graphical information that is being placed on the screen in a formatted fashion. If two text windows overlap and text is placed on an area that overlap the other window, then you will be drawing graphics (essentially) on top of another text window. The same thing as the circle example above would happen if that text window scrolled.

No compositing occurs anywhere in this model - RIPscrip preserves no record of _what_ drew a pixel; the final screen state is the only truth. Mouse regions are the one place ordering matters: overlapping regions are scanned most-recent-first on a click (see [4.2 Mouse Fields & Pointer](4.2-mouse-fields-and-pointer.md)). _Evidence: 2.00a4._

# 4.1 JPEG Images

[◀ Prev: 4.0 Icons & Bitmaps](4.0-icons-and-bitmaps.md) · [Contents](README.md) · [Next: 4.2 Mouse Fields & Pointer ▶](4.2-mouse-fields-and-pointer.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

Photographic images - a capability of the 2.0/3.x generation with no 1.54 counterpart: a host delivers a compressed image file to the terminal and displays it scaled into an **image area**, a sub-region of the current viewport established by [RIP_IMAGE_STYLE](#rip_image_style). JPEG is the only compressed image format in shipping 3.x - the ALPHA 4 draft also added GIF _(v2.A4)_, but GIF was dropped over LZW licensing before shipping, and PNG was announced but never shipped (see the [white paper](../text/RIPScrip-3.x-technical-whitepaper.txt)) - and SyncTERM's `RIPSCRIP030001` mode has no raster support at all, making JPEG display a clean 3.x-only differentiator.

_Evidence: WP (§3.7.2, GrayPEG); HLP (jpeg\_ strings; readme progressive-display note); corpus (7 shipped JPEGs, 16 references)._

_The 2.0 record is [4.1 in the v2.0 reference](../../2.0/ripscrip/4.1-jpeg-images.md); decoder profile, scaling and palette-rendering internals are in the [v2.0 JPEG techspec](../../2.0/techspecs/3.1-jpeg-images.md), and the file-role view is [6.1 Content File Roles](6.1-content-file-roles.md#jpeg-and-graypeg)._

## RIP_IMAGE

_Display a scalable photo type image_

|               |                  |
| ------------- | ---------------- |
| **Level**     | 1                |
| **Command**   | `p`              |
| **Arguments** | `res:4 filename` |

**Format:** `!|1p <res> <filename>` **Example:** `!|1p0000ASTRO.JPG`

**Attributes used:** Viewport, Port, Base Math (current setting); JPEG painting uses COPY independently of current Write Mode **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.1-jpeg-images.md#rip_image)) · HLP (`RIP_Image`; JPEG engine strings - jpegShow, LoadJPEGBuffer; the `$(FILE.JPG$` macro) · corpus (13 uses in 6 files, 16 JPEG references) - not in SyncTERM

This command displays a local JPEG file in the current port’s image area, using [RIP_IMAGE_STYLE](#rip_image_style). It does not delete that file when image-style DELETE is set. Clearing, aspect margins and painting follow the [shipped rendering policy](#clearing-aspect-margins-and-write-mode) below. _Evidence: DLL; [original presentation and cleanup derivation](../research/issue-21-image-style.md)._

Display can also be triggered by receiving an image via [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) with an image file type, or by the `$(file.JPG$` playback prefix in a host command ([5.3 Local File Playback](5.3-local-playback.md#local-jpeg-playback---filejpg)). A host can confirm JPEG capability first with [`$IFS(JPEG)$`](5.1-text-variables.md#ifs).

All JPEGs are 24-bit; the white paper notes support for the **GrayPEG** grayscale variants, and progressive ("display while downloading") rendering was advertised but noted as not working in RIPtel 3.1. _Evidence: WP (§3.7.2, GrayPEG); HLP (readme progressive-display note)._

The corpus's photo scenes (N2_PHOTO.RIP, N2_TITLE.RIP, IMAGES.RIP, FXSHWIMG.FN) cycle ASTRO/GALAXY/JUPITER/BEACH2/BRIDGE02/DUSK_SEA/FIRCLOUD JPEGs. SPECLEFX.RIP demonstrates the conditional slideshow idiom, the filename argument computed by the [macro layer](5.2-templates-and-conditionals.md) at execution time:

```text
!|1p0000<<IF $INUSE(TV,NEXT_IMG)$="0">>$-=NEXT_IMG=ASTRO.JPG$<<ENDIF>>$&NEXT_IMG$
```

- if the `NEXT_IMG` variable is unset, initialize it, then display whatever it dereferences to. FXSHWIMG.FN brackets its slow JPEG display with [RIP_SET_MOUSE_CURSOR](4.2-mouse-fields-and-pointer.md#rip_set_mouse_cursor) hourglass/arrow switches. _Evidence: corpus (SPECLEFX.RIP, FXSHWIMG.FN)._

## RIP_IMAGE_STYLE

_Alter subsequent displayed image settings_

|               |                                          |
| ------------- | ---------------------------------------- |
| **Level**     | 1                                        |
| **Command**   | `i`                                      |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY flags:4 res:12` |

**Format:** `!|1i <x0> <y0> <x1> <y1> <flags> <res>` **Example:** `!|1i1E4I80940004000000000000`

**Attributes used:** Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.1-jpeg-images.md#rip_image_style)) · HLP (`RIP_ImageStyle`; also the `$IMGSTYLE(cur,x0,y0,x1,y1)$` variable) · corpus (13 uses in 6 files) - not in SyncTERM

This command replaces the current port’s image rectangle and flags for subsequently displayed JPEGs, including local playback and received-image display. Coordinates use current world/device conversion; reversed corners are ordered. RIPtel 3.1 stores the converted far coordinates plus one. The setter accepts flags **0..63**, replaces the previous flags and rejects a larger value without changing the style. Unlike the [IMGSTYLE macro setter](5.1-text-variables.md#imgstyle), the wire handler can change a protected current port. _Evidence: original driver 0xc39a and [native style checks](../research/issue-21-image-style.md#native-style-checkpoint)._

**All-zero coordinates do not disable JPEG viewing in RIPtel 3.1.** The inherited ALPHA 4 claim that they disable viewing is not implemented by this driver: the command stores (0,0,1,1), and subsequent display reaches the decoder through a lower-level size fallback. In the full-viewport fixture this uses the physical display dimensions. Do not implement an all-zero “ignore and delete” branch as shipped behavior. A separate internal raw-zero rectangle sentinel suppresses explicit IMAGE/playback before lookup, but is not produced by all-zero IMAGE_STYLE; the client’s received-image export bypasses that guard. _Evidence: [full original presentation chain and zero-area checks](../research/issue-21-image-style.md#full-presentation-and-zero-area-checkpoint)._

The flag bits may be OR’d together:

| Value | Shipped RIPtel 3.1 effect |
| --- | --- |
| 1 | **ASPECT:** fit the image while preserving its proportions. Unoccupied margins retain their previous contents; they are not automatically blackened. |
| 2 | **DELETE:** accepted and stored, but **not acted on by JPEG presentation**. Neither an existing local JPEG shown by IMAGE/playback nor a received JPEG is deleted by this style bit. |
| 4 | **NOCLEAR:** suppress the initial black fill of the fitted image rectangle. Without it, that rectangle is filled with black, independently of current background color. |
| 8 | **USEPAL:** accepted and stored; ignored for JPEG. The inherited draft described committing a GIF palette, but this client ships no GIF decoder. |
| 16 | Wallpaper: after successful display, repeat the image-area contents across the viewport using COPY. This subsequent copying can overwrite areas outside the initially fitted image. |
| 32 | With wallpaper (16), stagger alternate rows by half the image-area width. No independent effect without 16. |

_Evidence: DLL; original JPEG consumers, wallpaper helper 0x3ea2e and [primary derivation with controlled-service limits](../research/issue-21-image-style.md). The ALPHA 4 table’s automatic-deletion, background-color and black-margin descriptions are corrected here for the recovered client; the original text editions remain unchanged._

### File deletion and received files

**None of image-style bits 2, 4 or 8 deletes a displayed or skipped JPEG in the recovered driver.** There is no distinction whereby style bit 2 deletes a newly received file but spares an explicitly displayed local file: this style bit has no deletion effect on either path. The draft’s “deleted if flag 4 or 8” sentence is therefore incorrect, and changing its numbers to 2 would still misdescribe RIPtel 3.1.

The client has a separate transfer flag that registers completed files in a temporary-file list for **later purge**. That policy is independent of image style, viewing success and the image-area rectangle; it is not deletion on completion of JPEG drawing. The inherited UU-encoded-image description also does not supply a working alternative: this driver’s encoded-stream handler is a stub. _Evidence: [original client transfer call chain, temp-list registration/purge and encoded-stream tests](../research/issue-21-image-style.md#received-file-cleanup-and-encoded-stream-checkpoint)._

### Clearing, aspect margins and write mode

JPEG rows use **COPY (SRCCOPY)**, independently of the current vector Write Mode. Unless NOCLEAR is set, the initial fill uses a **black replacement fill**, not the current background color or XOR/OR/AND mixing. With ASPECT, the driver first fits the image, then clears only that fitted rectangle. It leaves the surrounding margins unchanged. Thus **XOR + ASPECT + NOCLEAR** leaves the margins exactly as they were and copies the JPEG into the fitted rectangle; no black margins are XOR’d or otherwise combined with their previous contents. Wallpaper is a separate subsequent COPY operation when bit 16 is set.

For a display region (10,20)–(110,120), a 10×5 source fits to (10,45)–(110,95), while a 5×10 source fits to (35,20)–(85,120). Those are the black-fill rectangles when ASPECT is set and NOCLEAR is clear; with NOCLEAR, neither fill occurs. Exact JPEG decoding, sampling and Windows palette/color realization are outside these geometry/side-effect observations. _Evidence: original black-brush FillRect and SRCCOPY StretchDIBits calls, captured in the [native preparation/scan-line matrix](../research/issue-21-image-style.md#native-jpeg-preparationscan-line-checkpoint)._

### Defaults and reset scope

A default image rectangle is an internal **all-minus-one marker**, meaning “use the current viewport when displaying,” with **flags zero**. It is not a saved copy of the viewport’s dimensions. Image state belongs to each port. Reset behavior in RIPtel 3.1 is:

| Operation | Image rectangle and flags |
| --- | --- |
| RESET_WINDOWS; HEADER drawing-reset global flag 2 | Reset **the port current before reset** and **port zero** to viewport fallback and flags 0. This affects the old current port even if protected. Other protected surviving ports retain their image rectangle and flags. Unprotected nonzero ports are removed; current port ends at zero. |
| HEADER hard-reset global flag 1 | Remove nonzero ports, including protected ports; port zero has viewport fallback and flags 0. |
| HEADER without a global reset | No implicit image-style reset; any explicit port segments still perform their own documented operations. |

_Evidence: [original outer reset/header and protected-port tests](../research/issue-21-image-style.md#original-outer-resetheader-checkpoint); see also [RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) and [header flags](1.1-protocol-and-command-hierarchy.md#global-header-flags)._

The example (N2_TITLE.RIP) sets flag 4 for its inset newspaper photo. Corpus uses also appear with the reserved block omitted, e.g. `!|1i00009F6Q0004`; authors should send the full documented field widths. _Evidence: corpus (N2_TITLE.RIP)._

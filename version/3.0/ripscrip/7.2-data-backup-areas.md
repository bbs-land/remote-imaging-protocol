## Data Backup Areas

_Added in RIPscrip v2.A4._

_Evidence: 2.00a4; HLP._

A data backup area is a backup area that composes one base save area and ten data save regions for specific data table types. The data save regions are broken collectively up as a set of individually addressable data save slots (like an array in most programming languages), and a data save stack. Each data backup area can contain up to eleven separate, complete data tables of one particular type - one in the base save area, and up to ten other data tables in the data save slots or the data save stack, or in some combination of the two (save slots or stack).

The 3.0.7 driver confirms all three mechanisms directly: the `$SAVE0$`-`$SAVE9$` / `$RESTORE0$`-`$RESTORE9$` slot variables and the slot-less `$SAVE$`/`$RESTORE$` pair in RIPTEL.HLP's variable tables, stack PUSH/POP via the RIPSCRIP.HLP error strings **"No slots available for PUSH"** and **"No stack to pop"**, and per-object save/restore of button styles, graphics styles, text windows, palettes, mouse fields, environments, ports, and screens. _Evidence: HLP._

Each data backup area can store only one particular type of [data table](7.1-data-tables.md). For example, the color palette data backup area can only store color palette data tables (remember a color palette data table consists of 36 separate color palette definitions).

A data save slot is a backup area that is large enough to store an entire specific data table, or other object (graphics screen, mouse fields, etc). Each data backup area's save slots can hold one entire data table of the type designated for the data backup area. Each data save slot has a specific slot number associated with it (0-9). When the data in a data save slot is restored back to the actual RIPscrip drawing environment, that slot is deleted (cleared), providing that it isn't protected (see below).

A base save area is very similar to a data save slot, except that a base save area does not have a specific "slot number" associated with it. Unlike data save slots, when you restore a data table object from a base save area, the base save area is not cleared (ie, deleted) so it can be restored multiple times without losing the saved data (the base save area cannot be protected like data save slots can be - see below for more details).

Finally, we have stack save areas. Stack save areas are like a stack of plates - you put plates on top of the stack, and when you want one, you take one off the top of the stack. The plate at the bottom of the stack was the first plate placed on it, and to get to it, you need to take off each of the plates above it. When you place a data table onto a save stack, it is like placing a plate on top of our stack of plates. This is extremely useful (in fact, critical) to creating dialog boxes that overlap menus, and when you close the dialog box, you restore the menu's environment. The act of placing a data table onto a data save stack is called "pushing" a table onto the stack. The act of removing a table from the top of the stack is called "popping" a table from the stack. In order to remember where the "top" of the stack is (ie, how many layers are on the stack), a thing called a "stack pointer" is maintained internally which is simply a count of the number of items on the stack. Each time you add a new data table onto the stack, the pointer is increased by one (we have one more item on the stack).

Notice how there are ten different data save slots, and ten different data save stack "locations". What this means is that individually, either one of these may hold ten complete data tables. But combined, they cannot both contain more than 10 complete data tables. What this means is that you can have 4 separate tables saved in the data save slots, and 6 data tables pushed onto the stack, but then you wouldn't be able to store one more data table into an "open" data save slot, or push it onto the save stack (the slot/stack system is effectively "full"). The diagram above shows a completely empty data backup area.

Our stack system is now full. We have four items on our stack and six in our data save slots. If we tried to push another data table onto our stack, the operation would be ignored (an error because our slot/stack system is full - the 3.0 driver's "No slots available for PUSH"). If we tried to store a data table to data save slot #2 (which is currently open), it would also be ignored because the slot/stack system is full. If however, we tried to save a data table onto data save slot #3 (which is occupied), the operation would be performed providing that data save slot #3 is not protected (see below).

A stack restore (also known as a "pop") is a method of restoring a data object from the data save stack into a data table. When you perform a stack pop, the data table at the top of the stack (the entry just below the stack pointer) is removed from the stack and placed in the appropriate data table (which one is based on the type of data that is stored in the data backup area). Once the restore operation is complete, the entry in that location of the stack is deleted (cleared), and the stack pointer is decremented by one, thus making room for one more entry in the data save slot/stack system to hold a new data table. (Popping an empty stack is an error - the 3.0 driver's "No stack to pop".)

Each data backup area maintains its own stack pointer. Each backup area's stack pointer is unique and completely unrelated to the stack pointers of other backup areas. _(v2.A3)_

The base data save area is provided as a "temporary" storage location for data tables. The slot/stack system is designed for more permanent storage of tables.

All totalled, a data backup area can store eleven separate data tables, and each data table in a data backup area is of the same type of information (eg, text window, color palette, etc). If a data table has 36 separate data table entries in it, then a data backup area for that data table would hold 396 separate data table entries in it! This makes for a lot of backup storage. You cannot individually access sub-elements of a data table inside of a data backup area - you can only save/restore "entire" data tables at any one moment.

Push and pop operations are vital to the concept of multiple overlapping windows and dialog boxes in RIPscrip. When you close a window, you need to restore the background graphics, mouse regions, text windows and any other data tables that were in use at the time the dialog/window was created. What if that restored background is itself a window that is on top of some background menu? That window would also have tables pushed (the background environment). When that window closes, it will pop the information and restore the background environment's configuration.

## Protection and Restoration

_Added in RIPscrip v2.A4._

_Evidence: 2.00a4._

The way that a stack operates has been clearly outlined in the previous section. When you store a data table onto the stack, it grows by one table. When you pop a data table off of the stack, you reduce the contents of the stack by one data table (ie, that data table is deleted from the stack).

The base save area has already been described as a temporary storage location. A data table in the base save area remains in the base save area until it is either explicitly deleted, or until a hard reset of the RIPscrip environment is performed. In this manner, the base save area can be used as a source of data table copy operations many times and still read the same data table.

When you restore a data table from a data save slot back into the actual data table on the other hand, that data save slot is deleted (cleared) unless it is protected from deletion. In other words, just like individual data table entries, you can individually protect data save slots from deletion or overwriting. Only a data save slot that is actually "in use" can be protected - it is pointless to protect a data save slot that isn't holding a data table because what would you do with it? You couldn't store anything in it and you couldn't read anything from it, so this situation is not allowed.

There are only three ways of deleting or modifying a protected data save slot (two of which involve manually unprotecting the slot):

1. Explicitly unprotect the slot and then overwrite or delete it.
2. Explicitly unprotect the slot then copy the data table from it to the actual data table designed to work with that data. This deletes the contents of the slot once the copy operation is complete.
3. Perform a hard reset of the RIPscrip environment.

The base save area cannot be protected and neither can the data save stack. Protection goes against the very nature of these two backup areas.

It should be noted that when a data table is stored in the data backup area, any of the entries in that data table "retain" their protection status! This means that if you restore a data table from the backup area and put it back into action, the protection status of each entry in the table is restored as well.

You cannot protect an entire data table. This means that if you have entries in a data table that are protected and you perform a restore operation from a backup area, this will override any individual entries in the data table with those stored in the actual data table in the backup area. This is the only way that a data table entry's protection status can be bypassed.

## Individual Data Backup Areas

_Evidence: 2.00a4; HLP._

There are data backup areas for the following types of information (not all of them are normal data tables per se): _(v2.A3)_

Host commands drive these areas through the save/restore [text-variable](../../glossary.md) families in [5.1](5.1-text-variables.md#data-table-and-backup-area-text-variables) - `$SAVE$`/`$RESTORE$`, `$SAVE0$`-`$SAVE9$`/`$RESTORE0$`-`$RESTORE9$` and `$SAVEALL$`/`$RESTOREALL$` (graphics screen), `$SGS$`/`$RGS$` (graphics styles), `$SBS$`/`$RBS$` (button styles), `$STW$`/`$RTW$` (text windows), `$SCP$`/`$RCP$` (palettes), `$SMF$`/`$RMF$` (mouse fields), `$SCB$`/`$RCB$` (clipboard), `$SENV$`/`$RENV$` (environments) - plus the generic [`$COPY$`](5.1-text-variables.md#copy) and status queries [`$BACKSTAT$`](5.1-text-variables.md#backstat) and [`$INUSE$`](5.1-text-variables.md#inuse).

### Button Style Table Save Area

A backup area for an entire button style data table (all 36 button styles that may be defined). _(v2.A3)_

This backup area stores the following information: _(v2.A4)_

- The current button style data table entry number
- The actual button style data table (all 36 entries)

### Graphical Style Table Save Area

A backup area for an entire graphical style data table (all 36 graphical styles that may be defined). _(v2.A3)_

This backup area stores the following information: _(v2.A4)_

- The current graphical style data table entry number
- The actual graphical style data table (all 36 entries)

**RIPtel 3.1 scope and restore defect:** STYLE saves only the current style index and all 36 style records; it contains no port cursor/image state or environment color-mode/mouse state. Its restore reads the saved index into the current style's foreground word, then immediately overwrites that word when restoring the table. The pre-restore current style index therefore survives and is reactivated. For example, saving while style 5 is current and restoring while style 7 is current restores all records but leaves style **7** current. _Evidence: DLL; [original save/restore and native case](../research/issue-24-drawing-state-ownership.md#backups)._

### Drawing Port Table Save Area

A backup area that stores all 36 separately defined [graphical ports](7.0-drawing-ports.md) in the Port Table. Video Ports save only the specific definition of the ports. Clipboard Ports store not only the port definition, but also the graphical data that is saved inside the Clipboard Ports. _(v2.A3)_

This backup area stores the following information: _(v2.A4)_

- The current drawing port data table entry number
- The actual drawing port data table (all 36 entries)
- All offscreen/clipboard ports' actual graphical contents
- The current "floating" viewport query expression
- The current "clipboard port pointer" (see [RIP_GET_IMAGE](4.0-icons-and-bitmaps.md#rip_get_image) for more details).

The 3.0.7 driver's strings confirm port backups carry **strip-based screen bitmap data** for the stored pixels. _Evidence: HLP._

**RIPtel 3.1 cursor exception:** PORT owns and saves the image rectangle/flags, separately from STYLE; restore reinstates those image fields without touching style/environment records. Screen-port cursor X/Y are written to the backup stream, but restore reads them into a local buffer and never copies them to the port. Thus an existing screen port retains its live cursor rather than its saved cursor: saving (515,616), changing to (717,818) and restoring leaves **(717,818)**. Offscreen ports do not serialize cursor X/Y in this path. The saved current port selection and resident queries do restore. Do not infer cursor restoration from the fact that the stream contains it. _Evidence: DLL; [original serializer/restore and native screen-port case](../research/issue-24-drawing-state-ownership.md#backups)._

### Text Window Table Save Area

A backup area that stores the entire [text window](1.4-terminal-ansi-view.md) data table. This stores all 36 of the possibly defined text window configurations. Only the text window definitions are saved in these areas, not the contents of the text window(s). _(v2.A3)_

This backup area stores the following information: _(v2.A4)_

- The current text window data table entry number
- The actual text window data table (all 36 entries)
- The current "floating" text window query expression

### Color Palette Table Save Area

A backup area that stores all 36 currently defined color palettes in the color palette data table. _(v2.A3)_

This backup area stores the following information: _(v2.A4)_

- The current color palette data table entry number
- The actual color palette data table (all 36 entries)

### Mouse Field Table Save Area

A backup area that stores all currently defined simple mouse fields and mouse button fields currently active on the screen. The mouse field boundaries and any mouse button configuration data is stored. Mouse fields do not have a directly accessible data table. In other words, you cannot directly protect a specific entry in the mouse field data table. The mouse field data table is different than normal data tables in that they can have up to 128 separate table entries and are not directly accessible like other simpler data tables like graphical style data tables, etc. When a mouse button definition is restored, the graphics displayed for a button are not restored - only the internal mouse button field definitions are restored. _(v2.A3)_

This backup area stores the following information:

- The total number of mouse fields defined
- The actual mouse field data table (up to 128 entries)

### Screen Save Area

_Evidence: original RIPtel 3.1 driver; [complete serializer, wrapper, manager and native derivation](../research/issue-26-screen-backups.md). This corrects the inherited 2.00a4 capture list and SAVE recipes._

Ordinary [`SAVE`](5.1-text-variables.md#save)/[`RESTORE`](5.1-text-variables.md#restore), including numbered aliases, address only the **screen backup family**. Its capture/restore set is:

| State | SAVE captures | RESTORE does |
| --- | --- | --- |
| Graphics pixels | Bitmap of physical screen DC from **port 0**, at client-rectangle width/height, origin (0,0) | Unscaled SRCCOPY to **port 0's screen DC** at (0,0), using saved bitmap dimensions |
| Palette RGB | All **768 RGB bytes of the currently selected palette table entry**, irrespective of which port is current | Overwrites RGB bytes of the palette entry **current at restore time**, then uploads them |
| Current palette index / palette definition or protection flags | Not captured | Retained; target RGB is overwritten even if protected or undefined |
| Current port / viewports / port definitions | Not captured | Retained; no port is selected, revived, redefined or unprotected |
| Graphics-style / button-style tables | Not captured | Retained |
| Status-bar visibility | Not captured | Retained |
| Text windows, mouse fields, offscreen port contents, environments | Not captured | Retained |

The screen operation ignores the selected port's viewport and protection when choosing its **capture/restore target**: that target is port zero's screen DC. It does not restore port zero's viewport, the saved current port's viewport, all viewports, or an independent viewport setting. If port 1 was current at save and port 35 is current at restore, 35 remains current. Deleting, redefining or protecting port 1 between those operations does not change that result. Restore does not resize the canvas. The original calls are specified here; native fixtures use an unclipped indexed GDI model and do not establish exact Windows clipping/raster behavior.

#### Palette binding example

Suppose palette **5** is current at SAVE, its index 15 is red, and the screen contains pixels of index 15. Before RESTORE select palette **17**, make its index 15 green, and protect entry 17. RESTORE writes 5's saved RGB values into **17**, leaves 17 current/protected, and presents the saved pixels using that restored mapping. It neither selects palette 5 nor restores the whole palette table. Its direct RGB overwrite does not change the target's defined/protected flags. In the original private stream the palette occurs twice—an outer RGB block and the bitmap codec's included palette—and both copies target the same live palette entry, causing two uploads. Private in-memory storage need not duplicate an identical palette to reproduce the resulting state.

[`RESTOREALL`](5.1-text-variables.md#restoreall) differs because it subsequently restores the **whole palette table**: all 36 entries/flags and saved current index 5 return. The screen phase's temporary overwrite of 17 is then replaced by 17's saved table contents, and saved palette 5 becomes current. This order is observable; the combined operation is not a single atomic snapshot restore.

| Form | Destination/source and lifetime |
| --- | --- |
| `SAVE` / `SAVE(BASE)` | Replace screen base backup; reusable until replaced/deleted |
| `RESTORE` / `RESTORE(BASE)` | Restore base without consuming it |
| `SAVE(n)` / `SAVEn`, n = 0..9 | Same numbered backup; a protected existing snapshot blocks overwrite |
| `RESTORE(n)` / `RESTOREn`, n = 0..9 | Same restore followed by delete; unprotected snapshot is consumed, protected snapshot is restored and retained |
| `SAVE(PUSH)` / `RESTORE(POP)` | Per-family stack; successful POP restores and consumes the top snapshot |

Numbered aliases accept **no arguments**; all SAVE0..9 and RESTORE0..9 are registered in RIPtel 3.1. Parameter keywords are case-insensitive. Snapshot protection is separate from protection of a live palette or port. **Numeric restore requests deletion even if restoration fails**, so an unprotected snapshot can be consumed after a failed read; POP instead requires successful restoration before removing the stack entry. These action callbacks do not propagate the manager's success/failure as a value or variable error; invalid arguments do set the variable-error flag. Lower-level error reporting remains separate.

RIPtel 3.1 uses generated files in the configured engine directory, named **`%03hu%05hu.$$$`** from instance number and an incrementing counter, not RIPTERM.SAV or RIPTERM0.SAV..RIPTERM9.SAV. It closes but retains a reusable snapshot's file, unlinks on overwrite/consumption/deletion, and clears backups during normal manager teardown. These are client-owned backing files, not filenames named by the host command. A memory-backed implementation can preserve the same state/lifetime semantics without creating either the inherited RIPTERM*.SAV names or the driver's private generated files.

#### SAVEALL / RESTOREALL composition

These wrappers operate on eight independent backup families in the following **actual order**, for BASE, numbered and PUSH/POP forms:

| Order | Family | Save operation | Restore operation |
| --- | --- | --- | --- |
| 1 | Text windows | STW | RTW |
| 2 | Drawing ports, including offscreen contents | SCB | RCB |
| 3 | Mouse fields | SMF | RMF |
| 4 | Screen | SAVE | RESTORE |
| 5 | Whole palette table | SCP | RCP |
| 6 | Button styles | SBS | RBS |
| 7 | Graphics styles | SGS | RGS |
| 8 | Environments | SENV | RENV |

Numeric RESTOREALL attempts all eight restores, then all eight deletes in that same order. Base backups remain reusable. PUSH/POP use each family's independent stack. A failed/protected family does not stop subsequent families and there is no rollback; snapshot protection and consumption apply independently per family.

The **PORT** component supplies the saved current port and viewport definitions of saved defined ports, unlike screen-only SAVE. Saved definitions replace even protected live targets; a deleted saved port is redefined. Initial PORT cleanup skips protected live ports, however, and an undefined saved slot does not overwrite them, so a protected live port absent from the snapshot can survive. The [PORT cursor exception](#drawing-port-table-save-area) and [STYLE current-index defect](#graphical-style-table-save-area) still apply to RESTOREALL. Status-bar state is not added by any of these families: its owner is separate engine/host state. Thus “all” means this exact eight-family composition, not every client/UI setting.

### Environment Table Save Area

_Added in RIPscrip v2.A4._

The environment save area is a backup area to store the entire environment data table (all 36 entries). It is used for the purpose of backing up the entire environment table for later restoration.

This backup area stores the following information:

- The current environment data table entry number
- The actual environment data table (all 36 entries)

## Observed Usage in the 3.x Era

_Evidence: corpus (MENU.ENT, TEL3X2.ENT)._

TeleGrafix's own demo scenes exercise the backup system constantly - the `.ENT`/`.EXT` menu transition stubs ([6.0](6.0-writing-rip-files.md#the-script-container-family)) "Paste original screen image back" (their comment) around every menu excursion, saving the screen on entry and restoring it on exit through the screen save area's variable family.

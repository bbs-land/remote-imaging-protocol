## RIP_RECTANGLE

_Draw a rectangle in current color/line style_

|               |                           |
| ------------- | ------------------------- |
| **Level**     | 0                         |
| **Command**   | `R`                       |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY` |

**Format:** `!|R <x0> <y0> <x1> <y1>` **Example:** `!|R2020A030`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.3-shapes-and-fills.md#rip_rectangle)) · HLP (`RIP_Rectangle`) · corpus (108 uses in 12 files) · SyncTERM (ripper.c:13948)

This command draws a rectangle in the current drawing color, using the current line style, pattern and thickness. (x0,y0) and (x1,y1) are any two opposing corners of the rectangle. If x0=x1 or y0=y1 then the command will draw a single vertical or horizontal line. The rectangle interior is not filled by RIP_RECTANGLE.

## RIP_FILLED_RECTANGLE

_Added in RIPscrip v2.A2._

_Draw a filled rectangle with the current fill and optional pen border_

|               |                           |
| ------------- | ------------------------- |
| **Level**     | 0                         |
| **Command**   | `K`                       |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY` |

**Format:** `!|K <x0> <y0> <x1> <y1>` **Example:** `!|K0000ZLQP`

**Attributes used:** Draw Color, Back Color, Line Style, Fill Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.3-shapes-and-fills.md#rip_filled_rectangle)) · HLP (`RIP_FilledRectangle`) · corpus (163 uses in 13 files) · SyncTERM (ripper.c:13812)

This command fills a rectangle using the current fill style and, when [borders](#rip_set_border) are enabled, draws its border with the **current logical pen and current write mode**. RIPtel 3.1 does **not** force that border to solid COPY. (x0,y0) and (x1,y1) are any two opposing corners of the rectangle. If x0=x1 or y0=y1 then the command can draw a single line or pixel; with borders off the degenerate region draws nothing. _Evidence: original K consumer, line-pen producer and native border/ROP captures; [derivation](../research/issue-33-filled-rectangle-borders.md)._

The pen producer maps line types 0/1/2/3/4 to GDI SOLID/DOT/DASHDOT/DASH/DASHDOTDOT. Therefore a width-one dotted border keeps its dotted pen, while **custom type 4 uses fixed DASHDOTDOT rather than the stored arbitrary 16-bit custom mask** in this K path. Thickness is the stored device value described by [LINE_STYLE](2.1-lines.md#rip_line_style). GDI makes patterned CreatePen styles solid when width exceeds one; width zero requests one device pixel. This API limitation explains wide solid borders, but does not change their selected write mode. For example, K with a width-one dotted pen and XOR uses DOT plus XOR; width three uses a solid GDI pen plus XOR. _Evidence: original pen requests/selection and Microsoft's [CreatePen contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createpen); [derivation](../research/issue-33-filled-rectangle-borders.md)._

With borders enabled, ordinary line flags draw the fill first with no pen, then a border with the current pen, no fill brush and transparent pattern gaps. Line flags **exactly 1** combine fill and current pen in one pass with opaque background gaps; flags 0/2/3 take the separate-pass route. Borders off uses the fill brush with no pen. In all cases K retains the current write operation for its drawing passes and leaves stored pen/mask/write-mode state unchanged. _Evidence: complete original K execution across all five modes, line types, border states and flags; [derivation](../research/issue-33-filled-rectangle-borders.md)._

This command operates similarly to the [RIP_BAR](#rip_bar) command when borders are disabled, however the lower-left and lower-right edges of the filled rectangle obey the resolution independent method of performing fills (see [1.2 Math & Coordinates](1.2-math-and-coordinates.md) for details on how this works). _(v2.A3)_ Under that rule a filled interior fills _between_ the coordinate lines - one pixel short of the right and bottom border.

Before the rectangle is actually drawn, the (x0,y0) and (x1,y1) coordinates are "normalized". This means that they are adjusted so that they specify the upper-left and lower-right coordinates respectively. For example, if the parameters are received in the order of (50,25) and (25,75) - upper-right and lower-left respectively - they would be reorganized to be (25,25) and (50,75) before the rectangle is actually drawn. _(v2.A3)_

This is the corpus's standard full-screen background primitive. The BLUEFADE.FN example fills `(0,0)`-`(1281,961)` - one past the 1280×960 [world](../../glossary.md) frame, matching the non-inclusive lower-right convention of resolution-independent fills.

### Rounded-Rectangle Geometry

**Wire fields:** U and u each contain **five XY-width unsigned numbers**, including `rad`. Supported XY widths are 2..5 in the current base math. There is no signed negative-coordinate/radius form and no fixed two-character radius exception. For example, after selecting XY=3, all five fields occupy three characters; a two-character radius leaves an incomplete command. _Evidence: original dispatch descriptors and complete byte-parser captures at both bases/all four widths; [derivation](../research/issue-38-rounded-rectangle-geometry.md)._

For ordinary values, first normalize each opposing coordinate pair, then convert the two corners with their respective world-to-device X/Y ratios. Let the converted inclusive corner lines, after viewport origin, be `(L,T)` and `(R,B)`. The driver requests **RoundRect(L,T,R+1,B+1,2r,2r)**, where **`r=floor(rad × device_width / world_width)`**. It does not convert radius with Y, apply another aspect correction or clamp it against the rectangle before that request.

On a **640×350 world / 640×480 canvas**, radius 20 becomes **20 device pixels on both axes**, giving a 40×40 corner ellipse. World corners `(20,35)` and `(100,105)` become `(20,48)` and `(100,144)` with zero viewport origin; the request is `(20,48,101,145,40,40)`. Thus Y placement scales by 480/350 while the corner's ordinary radius stays 20. On a 1280×960 world / 640×480 canvas, radius 20 instead becomes 10 device pixels and the corner ellipse is 20×20. These are device-coordinate circles before any oversize fitting; the inherited unrestricted claim of truly circular corners is too broad.

**Oversize fitting:** the RIP driver neither rejects nor pre-clamps an oversized radius; it forwards the corner ellipse to GDI. In the ordinary compatible device-coordinate geometry, GDI fits the ellipse's absolute diameters **independently** to the available X/Y spans: `dx=min(abs(ellipse_width),R-L)`, `dy=min(abs(ellipse_height),B-T)`. Semiaxes are dx/2 and dy/2. This happens after coordinate/radius conversion and compatible-mode far-edge adjustment; it is not a common circular-radius clamp to half the smaller dimension. For example, an 8×6 span and r=5 fits to an 8×6 ellipse, rather than a circle of radius 3. Fine curved-edge rounding remains a canvas raster decision. _Evidence: original unchanged requests, Microsoft's [RoundRect diameter contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-roundrect), and separately identified [GDI conformance vectors](../research/issue-38-rounded-rectangle-geometry.md#gdi-boundary-reconciliation)._

**Zero and degenerate cases:** radius 0 requests square corners (ordinary rectangle geometry). Equal source X or Y coordinates are accepted; far+1 makes the corresponding API extent one device unit, including for u with N0. There is no RIP-level early rejection or empty-object skip; U still requests its pen, and u still requests its fill/optional pen. Do not expand a degenerate shape by the radius: fitting is constrained by its resulting span. A one-unit API box has a zero centerline span on that axis. Whether it changes a digital edge pixel depends on pen/fill rasterization. The driver ignores the drawing service's success/failure return, including oversized requests, and does not report a new RIP argument error on that basis. _Evidence: original branches and normalized/zero-extent/success/failure captures; [derivation](../research/issue-38-rounded-rectangle-geometry.md)._

**Shipped high-radius defect:** the actual request is `ellipse_width=2r` using the full converted DWORD, but `ellipse_height=2×(int16_t)(r & 65535)`. Thus r=32768 produces height -65536, r=65535 height -2, and r=65536 height 0. GDI's ellipse handling uses the magnitude for negative dimensions and treats a zero dimension as square-corner geometry; this is not a second radius unit. Modern geometry code should distinguish the normal X-world radius rule from this original truncation/sign defect. Extreme DWORD multiplication/doubling overflow is also original fixed-width arithmetic, not an additional advertised coordinate range. _Evidence: original U/u argument preparation, exhaustive WORD-radius native captures and the separately sourced [GDI boundary](../research/issue-38-rounded-rectangle-geometry.md#gdi-boundary-reconciliation)._

**Filled interior:** u uses the same converted bounds with or without its pen. There is **no extra one-pixel inset or shrink** when N0 is selected. The original K path also constructs far+1 bounds; the inherited prose about filling strictly between all coordinate lines must not be interpreted as an additional inset applied to u. The brush fills the rounded region with the established [device-context pattern phase](#fill-pattern-bitmaps). Removing the pen removes a separate border operation, not the region's geometric contour. Microsoft's [RoundRect contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-roundrect) and the bounded conformance observations establish the drawing boundary; these native probes capture requests and do not execute Windows rasterization.

For a device-space rounded contour `(0,0)`..`(8,6)` with r2, this grid distinguishes strictly interior samples from its contour. **F** samples are inside the fill region in either N state, **B** marks the straight geometric border, **.** is outside, and **?** leaves curved-edge pixel selection unspecified:

```text
      x 012345678
    y
    0   .?BBBBB?.
    1   ??FFFFF??
    2   BFFFFFFFB
    3   BFFFFFFFB
    4   BFFFFFFFB
    5   ??FFFFF??
    6   .?BBBBB?.
```

This is a geometry/interior illustration, not a Windows pixel oracle. With N0, B is not separately stroked; the grid does not promise that removing the pen paints or erases every integer sample on that contour. Exact corner scan conversion is deliberately left to the canvas. The resolved wire fields, device radius, independent oversize fitting and unmodified filled bounds are sufficient to construct the shape without choosing an unspecified RIP policy. _Evidence and inference boundaries: [complete derivation](../research/issue-38-rounded-rectangle-geometry.md)._

### Polygon counts and wire limits

**Reconstructed from RIPtel 3.1:** [RIP_POLYLINE](2.1-lines.md#rip_polyline), RIP_POLYGON and [RIP_FILLED_POLYGON](#rip_filled_polygon) consume a **two-character count in the current base math**, followed by exactly N pairs of XY-width coordinates. Increasing coordinate size changes the coordinates' widths, not the count's width.

| Base math | Largest count prefix | Supplied vertices | Open polyline segments |
| --- | --- | --- | --- |
| MegaNum (36) | `ZZ` | 1295 | 1294 |
| UltraNum (64) | `&&` | 4095 | 4094 |

The exact maximum-command prefixes are `!|J10|lZZ` and `!|J1S|l&&`, respectively, followed by 1295 or 4095 XY coordinate pairs. Replace `l` with `P` or `p` for the closed or filled commands. J's own parameter always uses MegaNum. For example, keeping default XY=2, the UltraNum command supplies 8191 numeric values (one count plus 8190 coordinates). Do not transmit a separate closing vertex unless it is intentionally part of the N supplied vertices; Polygon closes the last-to-first edge automatically, while Polyline stays open.

The historical readme/HLP advertisement of **4096 vertices** does not establish a reachable wire count. Two digits have no representation for 4096 and the original parser has no special count encoding. The original handlers actually convert **N+1** pairs from scratch storage while passing **N** to Polygon/Polyline; at the maximum UltraNum count, that is 4096 scratch conversions and 4095 drawn vertices, even for an open polyline. The extra pair comes from stale argument slots, not an implicit closing point supplied by the host. A new implementation should read exactly N pairs and validate the complete count/length relationship before drawing.

**Evidence:** original count/coordinate descriptors, byte parser, J/n handlers and l/P/p drawing consumers, including all maximum prefixes at XY widths 2–5 and a trailing-sentinel test; see the [derivation and native probe](../research/issue-13-polygon-counts.md#exact-counts-and-single-contour-closure). These are RIPtel 3.1 wire findings; they do not change the earlier editions' 512-vertex limits or require reproducing GDI rasterization.

> **NOTE:** You will get unusual effects if the lines of the polygon overlap, creating a polygon with internal "gaps". ### Multi-contour widths and aggregate limits

**Reconstructed from RIPtel 3.1:** the initial contour count C and the **first** contour's vertex count N1 each occupy **two digits** in the current base math. Every coordinate occupies XY digits. A shipped descriptor quirk makes **every later contour's vertex count occupy XY digits too**. The exact sequence is:

```text
C:2 N1:2 (x:XY y:XY repeated N1 times)
N2:XY (x:XY y:XY repeated N2 times)
...
NC:XY (x:XY y:XY repeated NC times)
```

At default XY=2, all these counts are two digits. At XY=3, however, first-contour count 3 is `03` and second-contour count 2 is `002`. For example, this exact stream gives the first contour three (1,2) pairs and the second two (1,2) pairs; the coincident points deliberately isolate parsing from rendering:

```text
!|J10|n3000|<0203001002001002001002002001002001002
```

The original parser collects at most **8193 numeric values in one command**, including all count fields. For a well-formed multi-contour command with total V vertices, use the aggregate constraint **1 + C + 2V <= 8193**. Each contour must have at least two supplied vertices. C and N1 must fit two digits; later Ni must fit XY digits. All contours share the point/argument budget.

| Base math | Maximum contours C | Count encoding | Construction reaching that maximum |
| --- | --- | --- | --- |
| MegaNum (36) | 1295 | `ZZ` | Two vertices in each contour; 6476 numbers |
| UltraNum (64) | 1638 | `Pc` | Two vertices in each contour; 8191 numbers |

These maxima are `min(base²-1, floor(8192/5))`: each minimal contour costs one count and four coordinates, in addition to the initial C. Increasing C can reduce the remaining vertex allowance. With XY=2, the maximum **aggregate** V is 4094 in MegaNum (counts 1295,1295,1295,209) or 4095 in UltraNum (counts 4093,2, or one contour of 4095). With XY>=3, MegaNum also reaches 4095, using first-contour count 2 and later-contour count 4093. All three multi-contour vertex-boundary constructions use 8193 numbers and are verified through the original parser and PolyPolygon consumer. There is no separate 4096-vertex allowance for every contour.

**Shipped malformed-input behavior:** after collecting 8193 values, RIPtel discards further numeric fields but still dispatches the collected prefix. Its contour/length guards are incomplete, and its single-contour handlers also perform the stale extra read described [above](#polygon-counts-and-wire-limits). These defects are not a safe rejection policy for oversized input. Implementations should enforce the full grammar, declared counts and aggregate budget before drawing, rather than forwarding truncated or inconsistent arrays to a renderer.

**Evidence and scope:** original dispatch slot 13, width helper 0x39de0, numeric collection branches 0x3a800/0x3a97d, and handler 0x1e80a; [complete derivation and controlled-service limits](../research/issue-13-polygon-counts.md#exact-multi-contour-grammar-and-aggregate-budget). This specifies original wire representation and reachable valid limits independently of shape-edge rasterization.

### Fill-pattern origin and scaling

**Reconstructed from RIPtel 3.1:** predefined and custom patterns tile from **(0,0) of the drawing device context**, with an **eight-device-pixel period** in each direction. Onscreen ports share the master screen drawing context; each offscreen bitmap has its own bitmap-local origin. This is the graphics drawing surface's origin, independent of where the application window sits on the desktop. Changing the port, viewport, clipping rectangle or primitive does not restart the tile within that context. World scaling converts shape coordinates to device coordinates but does not resize the 8×8 mask.

For a covered device-context pixel `(x,y)`, use `M[y mod 8] & (0x80 >> (x mod 8))`, with modulo residues 0–7. A nonzero result selects the fill color; zero selects the pen background color, subject to the current write mode. Evaluate this after world conversion and geometry placement, using the final context coordinates. [RIP_VIEWPORT's original placement behavior](1.3-world-view-virtual-canvas.md#rip_viewport) determines those coordinates; do not separately add a screen port's origin a second time. Adjacent primitives sample the same tile continuously.

For example, let a screen port start at `(2,1)` and its stored viewport start at device-context `(5,3)`, with world and device sizes both 640×480. Set custom rows `80 00 00 00 00 00 00 00` (MegaNum command `!|s3K0000000000000001`, fill-color index 1). Draw filled objects over neighboring world-coordinate ranges `x=0..8` and `x=8..16`, both spanning `y=0..8`. Their placement starts at context X=5 and X=13. Interior samples `(8,8)` and `(16,8)` both select foreground, while `(9,8)` and `(10,9)` select background. Restarting at the viewport would instead put a set bit at `(5,3)`; restarting at the port would put one at `(10,9)`. The native probe captures the original placement and unchanged brush; these sample colors follow from the context-origin rule, independently of exact shape-edge rasterization.

With a 1280×960 world on the same 640×480 device, doubling the object coordinates gives the same device placements. The mask still repeats every eight device pixels, equivalent to sixteen world units. When an offscreen bitmap is copied elsewhere, its already painted pixels move with the bitmap; the copy does not reapply a fill pattern at the destination origin.

**Evidence and limits:** the original brush builder creates a fixed 8×8 monochrome bitmap; the ordinary filled-shape paths select that brush directly into their drawing context without changing its origin. The [derivation](../research/issue-12-fill-masks.md#consumers-and-exact-phase-derivation) combines those original calls with Microsoft's [default brush-origin contract](https://learn.microsoft.com/en-us/windows/win32/gdi/brush-origin). This establishes RIPtel's default phase, rather than leaving it to a new implementation's choice; it does not claim exact Windows shape-edge rasterization or historical 1.x/2.x phase parity. The legacy [RIP_FILL defect](../techspecs/2.0-fill-defects-delta.md) remains an exception: its affected border-color branch fills solid instead of applying the pattern.

This command does not affect whether borders are enabled or disabled. See [RIP_SET_BORDER](#rip_set_border) command for details on how to alter the status of borders. _(v2.A3)_

> **NOTE:** The RIP_FILL_STYLE (predefined fill patterns) and this RIP_FILL_PATTERN (custom fill patterns) completely override each other's effects.

The example (BLUEFADE.FN) defines an alternating dither pattern (`4Q2D` = 170/85, i.e. `10101010`/`01010101`) used to blend adjacent fade bands - the workhorse of the corpus's smooth 256-color gradients.

## RIP_SET_BORDER

_Added in RIPscrip v2.A3._

_Enable or disable borders on filled objects_

|               |             |
| ------------- | ----------- |
| **Level**     | 0           |
| **Command**   | `N`         |
| **Arguments** | `borders:2` |

**Format:** `!|N <borders>` **Example:** `!|N01`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.3-shapes-and-fills.md#rip_set_border)) · HLP (`RIP_SetBorder`) · corpus (122 uses in 23 files) · SyncTERM (ripper.c:13842)

This command specifies whether borders are drawn with filled objects (eg, [RIP_FILLED_RECTANGLE](#rip_filled_rectangle), etc). This command does not affect the command [RIP_BAR](#rip_bar). When borders are enabled, the following commands will draw a border around the filled region:

- RIP_FILLED_RECTANGLE
- [RIP_FILLED_CIRCLE](#rip_filled_circle)
- [RIP_FILLED_OVAL](#rip_filled_oval)
- [RIP_PIE_SLICE](#rip_pie_slice)
- [RIP_OVAL_PIE_SLICE](#rip_oval_pie_slice)
- [RIP_FILLED_POLYGON](#rip_filled_polygon)
- [RIP_FILLED_POLY_BEZIER](#rip_filled_poly_bezier)
- [RIP_FILLED_ROUNDED_RECT](#rip_filled_rounded_rect)

The inherited ALPHA 4 draft claims all filled-object borders use COPY and that only polygon borders honor line patterns. **That blanket rule does not describe RIPtel 3.1's K path.** [RIP_FILLED_RECTANGLE](#rip_filled_rectangle) selects its current logical pen, including dotted/dashed styles at supported widths, and uses the current write mode for both fill and border. Its GDI pen mapping, custom-mask limitation, width behavior and background-gap/pass rules are specified in that command's entry. N controls whether that border is present; it does not force a solid pen or COPY. Do not derive K's rendering from the draft's generic exception list. _Evidence: original N state setter and K producer/consumer captures; [derivation](../research/issue-33-filled-rectangle-borders.md)._

Setting the `<border>` parameter to "01" enables borders around filled objects. A value of "00" indicates that borders are disabled.

When a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) or a [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) command is executed (where the environment is reset), borders are automatically enabled for backwards compatibility. Disabling borders on filled objects is new since 1.54, and carries into 3.x.

The corpus extends the documented list of affected commands: NEWCMDS.RIP and POLYPOLY.RIP toggle `N` around the new [filled skewed ovals](2.2-curves.md#rip_filled_skewed_oval), [chords](2.2-curves.md#rip_filled_oval_chord), and [poly-polygons](#rip_poly_polygon) to demonstrate "With a border / Without a border" - all the 3.x primitives obey it.

## RIP_FILL

_Flood fill screen area with current fill settings_ · **[deprecated](../techspecs/2.0-fill-defects-delta.md)**

|               |                                     |
| ------------- | ----------------------------------- |
| **Level**     | 0                                   |
| **Command**   | `F`                                 |
| **Arguments** | `x:XY y:XY border:CM` _(1.54 form)_ |

**Format:** `!|F <x> <y> <border>` **Example:** `!|F1E180F`

**Attributes used:** Back Color, Fill Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** DLL (RIPSCRIP.DLL 3.0.7 disassembly - a live flood-fill command with a border-color codepath, RIPlib `§DEAD.7`) · SyncTERM (ripper.c:13593, descriptor `2#2#2#` - implements the 1.54 flood fill) · 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.3-shapes-and-fills.md#rip_fill)) - not in the RIPSCRIP.HLP name inventory, not observed in the RIPtel demo corpus

This command performs a "flood fill" emanating from the given `<x,y>` point. The fill "oozes" in all directions up to `<border>` color, but the border itself is not changed. If the border color does not completely enclose the `<x,y>` point, the fill will continue to the edges of the viewport; if the fill point is already the border color, no fill is performed. _(1.54 semantics, never restated for 2.x or 3.x)_

**Source correction:** ordinary pie/chord paths call GDI Pie/Chord, while skewed filled variants submit Polygon contours. They do not share the claimed manual boundary flood construction; that earlier attribution is [withdrawn](../techspecs/2.0-fill-defects-delta.md). Their actual [angle and closure behavior](2.2-curves.md#angle-ordering-and-sweeps) remains command-specific.

There are a number of alternatives to using a flood fill. In fact, a large number of screens could have been drawn much more efficiently using the filled object commands listed below, than using a fill. _(v2.A2)_

# 6.2 Asset Delivery & Storage

[◀ Prev: 6.1 Content File Roles](6.1-content-file-roles.md) · [Contents](README.md) · [Next: 7.0 Drawing Ports ▶](7.0-drawing-ports.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

How a host gets content files onto the terminal and where they land: the query-then-download workflow, the block-mode extension routing table, RIPtel's per-bookmark host directory, the shared default icon directory, and the "file override" lookup order.

_The 2.0 model this carries forward is [6.2 of the v2.0 reference](../../2.0/ripscrip/6.2-asset-delivery-and-storage.md) (1.54 lineage in the [v1.54 page](../../1.54/ripscrip/6.2-asset-delivery-and-storage.md))._

## The delivery workflow

_Evidence: 2.00a4; HLP._

A well-behaved host delivers assets in two steps:

1. **Staleness check** - [RIP_FILE_QUERY](5.5-file-transfer-and-queries.md#rip_file_query) asks whether a file already exists on the terminal's disk, and (modes 02-04) its size, date and time. The host compares the response against its own copy to decide whether a download is needed at all - the host side of the 3.x resource-caching story. Terminals that store audio in a translated local format must answer as if the WAVE original were on disk ([4.5](4.5-audio-files.md)). _Evidence: 2.00a4; HLP (`RIP_FileQuery`); SyncTERM (ripper.c:16104) - not observed in the RIPtel demo corpus, whose scenes are local and have no host to answer._
2. **Download** - [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) requests a supported transfer and specifies how to use a received file. RIPtel 3.1 starts a ZMODEM receiver for codes 7 and 8 and handles the returned files after reception. Its [encoded stream command](5.5-file-transfer-and-queries.md#rip_begin_uuencode_block) is a stub. The 2.00 Alpha 4 draft describes a separate UUencoded delivery mechanism.

The recovered 3.0 [FILE_QUERY contract](5.5-file-transfer-and-queries.md#rip_file_query) distinguishes lookup misses from later open/metadata failures and reports a legacy planar icon-equivalent size for eligible ICN/HIC/MSK aliases. A direct BMP query instead reports actual file length. Compare the host resource in the requested representation; do not assume the translated cache file has that same byte length. Mode 04 uses a colon between prepared filename and size, with the exact engine/client endings defined there.

Once delivered, the host uses the assets by name - stamping icons, displaying images, playing audio, replaying scenes - with no further transmission cost, from the command stream (chapter 4) or from [host commands](../../glossary.md) via the playback prefixes ([5.3](5.3-local-playback.md)).

Mode 1 requests upload. The [capability and refusal rules](5.5-file-transfer-and-queries.md#completion-and-refusal) distinguish the draft’s cancellation sequence from the recovered client dispatch.

Housekeeping uses [`$FILEDEL(file,...)$`](5.1-text-variables.md#filedel). The host is required to name only files it created/downloaded, but the original RIPtel 3.1 driver does not track or enforce that provenance. It resolves each filename using **host directory → shared ICONS → ordered icon search path**, deleting only the first existing match. With no configured host directory, resolution begins at shared ICONS and still includes the search path. Deletion failure does not try a lower-tier duplicate, does not stop later filenames and produces no per-file result.

> **Correction to the earlier hypothesis:** FILEDEL is not host-directory-only, and the user search path is not read-only for this operation. The original callback calls ordinary resource lookup and then unlink without a creator/session check. Shared/search-path files may predate the current connection and are still eligible. Asset delivery's target-directory policy does not establish deletion scope.

Hosts should send bare filenames. The inherited “ignore path information” prose has specific parser behavior: forward slash/wildcards reject the macro expression, single backslashes are consumed as escapes (`DIR\X.BMP` becomes `DIRX.BMP`), consecutive/trailing backslashes reject, and colons remain in the filename. The [FILEDEL entry](5.1-text-variables.md#filedel) gives exact examples and status rules; the inherited generic reject-all-path-input guidance is not an account of this later parser. _Evidence: original DLL callback/helper/full lookup and [native derivation](../research/issue-20-filedel-scope.md)._

The v2.A3 revision notes announced a `RIP_FILE_DELETE` command, but no entry exists in the ALPHA 4 draft and no such command name appears in the RIPSCRIP.HLP inventory; FILEDEL is the recovered 3.x text-variable mechanism.

## Block-mode routing - the extension table

_Evidence: 2.00a4._

The draft describes this extension routing for the batch DYNAMIC file types. The [RIPtel 3.1 completion table](5.5-file-transfer-and-queries.md#file-types) gives the shipped JFIF, scene, archive and legacy-icon paths.

| Extension | COMPOSITE DYNAMIC (type 4) | ACTIVE DYNAMIC (type 5) |
| --- | --- | --- |
| `RIP` | Store in proper directory | Store **and play back** locally |
| `BMP` | Place icon in proper directory | Place icon in proper directory |
| `BMH` | Place hot icon in proper directory | Place hot icon in proper directory |
| `BMM` | Place mask icon in proper directory | Place mask icon in proper directory |
| `JPG` | Store in proper directory | Store **and display** per image settings |
| `GIF` _(v2.A4)_ | Store in proper directory | Store **and display** per image settings |

Other extensions, including `.WAV`, are stored in the host resource directory under the draft rule. The connected RIPtel 3.1 wrapper uses the host directory or its `ICONS` fallback. Its type 5 image handling recognizes JFIF JPEG.

## Where files land

_Evidence: HLP (RIPTEL.HLP "Host Directory", "Icon Search Path", "Download Directory"/"Upload Directory" topics - survey in the [techspec](../techspecs/4.0-connection-directory-model-delta.md))._

The 3.x client carries the 2.0 storage model forward intact and renames its surface. Every host-deliverable media type still flows through **one directory family** - there is no separate audio, image, or scene directory:

- The **default icon directory** (`ICONS\`) houses the whole host-deliverable media family: `.BMP`/`.BMH` icons (and legacy `.ICN`), `.JPG` images, `.WAV` sounds, and the script containers. RIPtel's installer creates `ICONS`, `FONTS`, and `Files` under the install root.
- Each **bookmark** (RIPtel's name for a dialing-directory entry) can name a per-host sub-directory - the **host directory**, the 3.x name for the connection directory (RIPterm 2.30's "System Dir", the 1.54 manual's DIR field) - configured in the bookmark editor's Advanced options. When one is specified, any icon, RIPscrip, sound, or image files sent by the host are automatically placed there. New bookmarks import their defaults from RIPtel's setup configuration, and auto-creation carries over from the DOS clients: "Many online services create their own host directories for you, without your knowledge."
- **New constraint in 3.x** - the host directory can only exist under the directory where the client is installed: "For security reasons, the host directory cannot exist in any arbitrary location on your hard drive." Directories the _host_ can populate are jailed under the install root; directories only the _user_ configures (the search path, below) may live anywhere. Implementations should preserve this property - host-influenced writes stay inside a client-owned sandbox.
- **New third lookup tier in 3.x** - the setup-level, user-configurable **icon search path**: extra directories consulted only after the two classic tiers fail, aimed at CD-ROM-distributed resource sets. Multiple directories are separated by semicolons (`C:\Windows;D:\;Icons\MyIcons`). Host deliveries do not write new files there, but [FILEDEL](5.1-text-variables.md#filedel) uses the same lookup path for deletion.
- **Fonts are the exception** - stroked, outline and terminal fonts are global client resources resolved only from the font store (`FONTS\`), never per connection ([6.1](6.1-content-file-roles.md)).
- **User file transfers stay outside the model** - ordinary Zmodem downloads land in a `Files` directory (with separate user-configurable download and upload directories), a different namespace from host-deliverable resources, exactly as in the 2.0 block-mode rule.

## Temporary Resource Lifetime

[RIP_WRITE_ICON flag bit value 1](4.0-icons-and-bitmaps.md#rip_write_icon), [RIP_PORT_WRITE flag bit value 1](7.0-drawing-ports.md#export-flags-and-filename) and the [completed-transfer temporary flag](5.5-file-transfer-and-queries.md#rip_enter_block_mode) request later cleanup through the same original instance-owned registry. RIPtel 3.1 registers an export's resolved name before attempting the write, and appends a transfer's resolved name after reception. Registration and export are independent operations. The native purge attempts removal of the registered names and then retires the list.

The recovered client invokes purge during normal disconnect cleanup and on interpreter/application teardown. A drawing or scene reset, resource lookup, clipboard reassignment, or display of a registered image does not run that purge. Directory selection affects new writes. Earlier registrations keep the resource locations resolved when they were recorded.

**Portable ownership.** Register a successful temporary export or transfer under the receiving interpreter session and the resource's resolved logical directory and name in its writable resource store. Preserve the registration across RIP resets, local scene playback and resource-directory changes within that scope. Another owner's resource is identified separately even if it uses the same basename. A later same-session replacement at an already registered resource location keeps that registration until cleanup. Export attempts that fail leave the portable registry unchanged. This avoids assigning ownership of an unrelated existing resource on a failed write.

Purge the session's registered resources on completed disconnect and when the interpreter is destroyed. For offline local playback the owning interpreter supplies that lifetime. Consume the registrations at purge and attempt removal of each resource still owned by that scope. Filesystem failures may leave a file behind. The registry can be implemented by the client's resource store. The protocol requires no client installation directory, native registry filename or host-visible cleanup message. [Original registration and purge paths](../research/issue-215-write-icon-export.md)

## Lookup order ("file override")

_Evidence: HLP (RIPTEL.HLP "Host Directory" topic)._

When a command or playback variable references a file by name, the terminal searches the **host directory first**, then the default `ICONS\` directory, then the icon search path entries in order; first hit wins, and an error is reported only after all tiers fail. RIPTEL.HLP states the order outright: the client "will look for these kinds of files in that directory first. If the file cannot be found, then it checks the ICONS\ directory. If the file still cannot be found, then [it] checks any additional search directories that you have defined." The macro layer documents the same resolution order for the local-playback prefixes (`$>FILE.RIP$`, `$)FILE.WAV$`, `$<FILE.BMP$`, `$(FILE.JPG$` - [5.3](5.3-local-playback.md)).

The point of the scheme is unchanged from 2.0: same-named assets from different hosts do not collide - each host's `MENU.BMP` resolves to that host's own copy, while genuinely shared assets can live once in `ICONS\`. The RIPterm manuals call this behavior "file override". Commands never carry path information - filenames are bare DOS-style names, and the terminal decides where they resolve. (Modern implementations should also treat lookups as case-insensitive, as the DOS originals inherently were - see the [connection directory model techspec](../techspecs/4.0-connection-directory-model-delta.md).)

## Programmatic surface

The wire command [`RIP_SWITCH_DIRECTORY`](#rip_switch_directory) selects the host/resource directory. The client API also exports `RIP_SetHostDirectory`/`RIP_GetHostDirectory`; the separately recovered [`$HOSTDIR([name])$`](5.1-text-variables.md#hostdir) callback queries or selects that directory, with **OFF** as its clear argument. Its grammar differs from this wire command’s literal `$OFF$` special case. _Evidence: DLL; HLP ([help extraction §3, §5](../research/riptel-help-extraction.md))._

## RIP_SWITCH_DIRECTORY

_Select a host directory beneath the client installation root_

|               |                              |
| ------------- | ---------------------------- |
| **Level**     | 2                            |
| **Command**   | `<esc>` (one byte, ASCII 27) |
| **Arguments** | `reserved:4 directory`       |

**Format:** `!|2\x1b <reserved> <directory>` **Example:** `!|2\x1b0000MYBBS`

`\x1b` represents a single ESC byte, not four printable characters. Explanatory spaces are omitted on the wire. The four numeric digits use current Base Math and are consumed but ignored.

**Evidence:** DLL 3.0.7, physical dispatch slot 110 (logical callback command index 121), handler RVA `0x46f66–0x47125`, host-directory setter `0x6b36`, creation path `0x3f5ff`/`0x6c430`; [derivation and original-handler/path probe](../research/issue-5-scene-headers.md). This is recovered executable syntax, replacing the former HLP-only entry.

The handler is a silent no-op when the client has not installed its host-service callback. Otherwise, it processes the name in this order:

1. Reject a literal empty argument, then trim leading/trailing whitespace and uppercase it.
2. If the normalized literal is exactly `$OFF$`, clear the selected host-directory name and return without creating a directory.
3. Otherwise expand text variables, then require at most 12 bytes. Reject exact `.` and `..`, and reject any of these characters: `\ : * ? + / " , ; > < = [ ] |`. Interior spaces are not independently rejected.
4. Store the resulting host-directory name and attempt to create `installation-root\name`. Creation failure is ignored; it does not roll back the selection.

Normalization precedes expansion. Thus a variable that expands to `$OFF$` selects a directory literally named `$OFF$`; it does not invoke the clear sentinel. A nonempty literal that becomes empty after trimming or expansion is accepted: it clears the stored name and attempts creation of the root path. Expanded text is not uppercased a second time by this handler.

The command selects a directory name beneath the installation root, not an arbitrary host-supplied path. It has no data-table slot or protection flag. The selected name participates in the [lookup order](#lookup-order-file-override) and resource-delivery model above; `$OFF$` removes that per-host selection.

[Buttons](../../glossary.md) - styled interactive controls with plain, icon (BMP), or clipboard faces, optional [hot-icon](../../glossary.md) pressed states (`.BMH`), special effects (bevel, chisel, recess, sunken), labels, hotkeys, and radio/check-box grouping. ## RIP_BUTTON_STYLE

_Button style definition_

|  |  |
| --- | --- |
| **Level** | 1 |
| **Command** | `B` |
| **Arguments** | `wid:XY hgt:XY orient:2 flags:4 size:2 dfore:2 dback:2 bright:2 dark:2 surface:2 grp_no:2 flags2:2 uline_col:2 corner_col:2 other_port:1 res:5` |

**Format:** `!|1B <wid> <hgt> <orient> <flags> <bevsize> <dfore> <dback> <bright> <dark> <surface> <grp_no> <flags2> <uline_col> <corner_col> <other_port> <res>` **Example:** `!|1B0000020PVS080F000F080700000F07000000`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.3-buttons.md#rip_button_style)) · HLP (`RIP_ButtonStyle`; limits - label ≤255 chars, hotkey ≤255, groups 0-35, types "plain, icon or snapshot") · corpus (47 uses in 18 files) · SyncTERM (ripper.c:15015)

This RIPscrip command is probably one of the most complex in the entire protocol. It defines how subsequent [RIP_BUTTON](#rip_button) commands will be interpreted. The purpose of this command is to define what a Button is and how they operate. Buttons can have many different configurations, flags, and styles. With the diversity of modes that the Button can take on, complexity is a necessary evil.

There are 36 separate button style slots that can be defined simultaneously. This command allows you to alter the current button style slot. This button style slot is used by the RIP*BUTTON command to define buttons of particular types. Button style slots can be used to avoid retransmitting button styles over and over again. *(v2.A4)\_

This command does not actually do anything visibly on the screen. Simply put, this creates an internal definition for the Button mode which will be used with RIP_BUTTON commands after the definition is created.

TeleGrafix left the positional crib for its 36-character argument block as a comment in the corpus's SHOWFONT.FN:

```text
!|! wwhhooffffssffbbBBddssgg22uuccprrrrr
```

HLP's "snapshot" button type corresponds to the 2.00a4 clipboard button. _Evidence: corpus (SHOWFONT.FN); HLP._

### Initial and Reset Style

RIPtel 3.1 starts with current button-style slot **0**, only slot **0** in use and every slot unprotected. All 36 records contain this fixed default. Selecting an undefined nonzero slot installs the same default, marks it in use, clears protection and selects it; it does not copy the previously selected style. The [state transitions below](#undefined-current-slots-and-first-use-selection) distinguish explicit definition from selection, including the inherited inconsistent metadata case.

| Field                        | Default                                 |
| ---------------------------- | --------------------------------------- |
| Width, height                | 0, 0 (dynamic sizing)                   |
| Label orientation            | 2 (CENTER)                              |
| Flags                        | 768 = PLAIN 256 + BEVEL 512             |
| Bevel size                   | 3 device pixels                         |
| Label foreground, background | 15, 0                                   |
| Bright, dark, surface        | 15, 8, 7                                |
| Group number                 | 0                                       |
| Flags 2                      | 0                                       |
| Underline, corner colors     | 15, 7                                   |
| Other-port storage           | 0; wire argument ignored by this driver |

Specific unprotected-slot reset restores these fields; zero stays in use and a nonzero slot becomes undefined. Table reset restores unprotected records and clears their nonzero in-use flags, retaining protected records. **Shipped defect:** resetting the current entry (`$RESET(BUT,CUR)$`, or the current-entry default) instead copies the default bytes into selection/in-use metadata: the records remain unchanged, current becomes zero and the first 26 in-use bytes are overwritten. It does not overwrite protection bytes. A protected current entry rejects the reset unchanged. This corrupt current-reset path must not be mistaken for a different default style. _Evidence: original initialization/selection/reset and bounded native matrices; [derivation](../research/issue-27-button-style-contract.md)._

### Undefined Current Slots and First-use Selection

A button style's **stored fields, in-use flag, protection and current index are separate state**. A specific nonzero reset can leave the current slot undefined; successful explicit definition makes it defined again. The following rules complete the earlier reset/default contract. _Evidence: ALPHA 4 current-style definition and first-use CUR rules; original RIPtel 3.1 definition, reset, selection and query consumers; [derivation and exact instruction/field references](../research/issue-112-undefined-button-style.md)._

| Operation | Stored fields / in-use / protection | Current index |
| --- | --- | --- |
| `$RESET(BUT,n)$`, unprotected nonzero n | Fixed defaults; in-use false; protection remains false | Retain, even if n was current |
| `$RESET(BUT,TBL)$` | Default unprotected records, clear their nonzero in-use flags; retain protected records and flags; slot 0 stays defined | Retain; it does **not** select 0 |
| Accepted `1B` on an unprotected current slot | Store the supplied style under the existing conversion/normalization rules; **set in-use true**, even if previously false; retain protection | Retain |
| Rejected `1B` | Retain all four state components, including a false in-use flag | Retain |
| `$CUR(BUT,n)$` with n already in use | Retain fields, in-use and protection, including a protected record | Select n, including if already current |
| `$CUR(BUT,n)$` with nonzero n not in use | Install fixed defaults; set in-use true; **clear protection** | Select n, including if already current |
| Query-only `$CUR(BUT)$` | Inspect the index without defining/defaulting any slot | Retain |
| Outer SOFT / `RIP_RESET_WINDOWS` | Perform the separately documented table reset | **Then** select 0 explicitly |

A valid `1B` does not require the selected slot to be in use, does not select/default another slot and does not leave an edited record undefined. It checks the current **protection byte independently of in-use**: a protected current slot rejects the write even if marked undefined. Invalid field/type validation likewise does not define the slot. The [existing validation rules](#validation-and-flag-precedence) and protected auto-clip exception remain unchanged. If no definition was accepted before a later explicit selection, that selection still takes the undefined-slot default branch. If a definition was accepted, the slot is now in use, so selection preserves that new style.

**Completion for inherited inconsistent metadata:** Normally an undefined slot cannot be protected. The [already documented current-reset overwrite](#initial-and-reset-style) can leave a protected record with a false in-use byte. In that case, apply the undefined-slot selection row above: replace its fields with fixed defaults, mark it in use and clear the surviving protection. This follows the original selector's first-use branch and is the explicit completion adopted here for that inconsistent state; it does not permit overwriting a **defined** protected style. Selection is not rejected merely because an undefined destination retains protection. If an overwritten in-use byte is **nonzero**, it counts as in use, so selection retains the fields and protection instead. Queries do not perform this selection or repair metadata.

For a nonzero current slot n, protection queries differ as follows:

| Slot state | `$INUSE(BUT,n)$` | `$ISPROT(BUT,n)$` | `$ISPROT(BUT,CUR)$` |
| --- | --- | --- | --- |
| Undefined, protection false | `0` | `-1` | `0` |
| Undefined, protection true (inconsistent metadata) | `0` | `-1` | `1` |
| Defined, protection false | `1` | `0` | `0` |
| Defined, protection true | `1` | `1` | `1` |

The numeric ISPROT form checks in-use before protection; CUR directly reads current protection. Neither query marks the slot in use or changes its fields. Slot 0 remains defined and unprotectable. The second row describes how to inspect such a state **if it is current**; the current-reset overwrite itself selects 0, and explicitly selecting an undefined nonzero slot immediately applies the completion above.

#### Reset, redefine and reselect example

Assume unprotected slot 5, Base Math 36, coordinate size 2 and palette color mode. Evaluate dollar expressions in a text-variable expansion context; send the `!|` lines as wire commands:

```text
$CUR(BUT,5)$
!|1B0000020074000A000F080100000F07000000
$RESET(BUT,5)$
!|1B0000020074000C000F080200000F07000000
$CUR(BUT)$:$INUSE(BUT,5)$:$ISPROT(BUT,5)$:$ISPROT(BUT,CUR)$
$CUR(BUT,5)$
!|1U0A0A2I140000<>Style B
```

Both style definitions use dynamic size 0×0, CENTER orientation, PLAIN 256 with no effects, zero group/flags 2, label background 0, bright/dark 15/8 and underline/corner 15/7. A uses label foreground 10 and surface 1; B uses foreground 12 and surface 2. The flags field `0074` is 256 in base 36, and the last six bytes are ignored other-port `0` plus reserved `00000`.

| After operation | Current | Record 5 | In use 5 | Protection 5 |
| --- | --- | --- | --- | --- |
| Initial explicit selection | 5 | Existing style if already defined, otherwise fixed defaults | True | False |
| Accepted style A | 5 | A | True | False |
| Specific reset 5 | 5 | Fixed defaults | False | False |
| Accepted style B | 5 | B | **True** | False |
| Query expression | 5 | B | True | False |
| Explicit selection of 5 again | 5 | **B retained** | True | False |
| Button creation | 5 | B | True | False |

The query expression returns **`5:1:0:0`**. The final `1U` uses **style B**, not the reset defaults, to create a plain nonmouse button labeled `Style B`. With AUTOCLIP absent, this example does not rewrite its style during rendering. Immediately after reset and before B, the same query would return **`5:0:-1:0`**. Replacing specific reset with `$RESET(BUT,TBL)$` has the same selected-slot result while additionally resetting the other unprotected slots; it still leaves current index 5. The outer SOFT reset instead selects 0 under its separate rule.

#### Selecting a protected record hidden by the inherited overwrite

Start with defined unprotected slot 7 containing a nondefault style, protect it with `$PROT(BUT,7)$`, then select an unprotected slot 0. Apply the already specified `$RESET(BUT,CUR)$` metadata overwrite. Its published default bytes leave current 0 and in-use[7]=0, while record 7 and protection[7]=1 survive. At this point `$INUSE(BUT,7)$` returns `0`, numeric `$ISPROT(BUT,7)$` returns `-1`, and `$ISPROT(BUT,CUR)$` returns `0` because current is 0.

Now `$CUR(BUT,7)$` installs **all fixed default fields**, sets in-use[7]=1, clears protection[7] and selects 7. Both ISPROT forms for that now-current slot return `0`, and a following `1U` uses the fixed default style. This is a bounded logical state example using the already published bytes; it requires no invalid memory write or reproduction of an obsolete-client failure. A protected slot whose in-use byte remains nonzero follows the defined selection row and retains its style/protection.

### Validation and Flag Precedence

The shipped style definition validates orientation **0..4**, group **0..35**, flags 2 **0..255**, the seven colors and current-style protection. A protected current style rejects an explicit definition. At least one of CLIPBOARD 1, ICON 128 or PLAIN 256 must be set; no type bit rejects the command without changing the record. More than one type bit is accepted. Other low-word flags, including combinations marked N in the compatibility tables, are retained: those tables describe applicability, not an additional definition-time rejection or normalization matrix. BEVEL absent is the exception: its stored size becomes zero. The wire `other_port` field is ignored.

Rendering chooses **ICON first, otherwise CLIPBOARD, otherwise PLAIN**. Creation checks for an existing clipboard whenever CLIPBOARD is set, even if ICON is also set and would win rendering; an undefined clipboard rejects creation. HOT applies to the icon path, and mouse interaction options require a mouse field. These retained combinations do not make a nonmouse decoration interactive. The separate rule against mixing radio and checkbox groups still applies.

For top/center/bottom labels, flags 2 LEFT 8 wins when RIGHT 16 is also set. NOFILL 32 wins over PATTERN 64: both set means no interior fill; PATTERN alone uses the current fill pattern, neither uses solid surface color. These decisions do not clear the stored flags. _Evidence: complete 65,536-value definition matrix, all flags 2 byte values and original creation/renderer captures; [derivation](../research/issue-27-button-style-contract.md)._

### Label Orientation

Every Button can have an optional text label. It can appear in several different locations compared to the Button itself. This is specified in the `<orient>` parameter. The actual text of the label is not specified with this command, it is specified when you actually create a Button (see RIP_BUTTON below). The value that `<orient>` can be is as follows:

| Value | Description of Orientation                |
| ----- | ----------------------------------------- |
| 00    | Display label above button                |
| 01    | Display label to the left of button       |
| 02    | Display label in the center of the button |
| 03    | Display label to the right of button      |
| 04    | Display label beneath the button          |

### Button Types

There are three basic "types" of Buttons. There are Icon buttons, Clipboard buttons and Plain buttons. Each of these differ in the way that they create the button's image. A description of each type is as follows: _(v1.54)_

**ICON BUTTON (flag 128)** - An Icon Button means that the actual image of the button will be created by loading a bitmap icon image from the disk and load it at the given locatino. Any special effects (see below) can be applied to the Icon to further enhance the image. The filename for the Icon is supplied with the RIP*BUTTON command, as is the Icon's upper left X/Y coordinate. Icon Buttons are always stamped in COPY mode. *(v1.54)\_

RIPtel 3.1 loads the normal `.BMP` directly. When HOT 4096 is enabled and the button is selected, it first tries the paired `.BMH` quietly; any nonzero loader error retries `.BMP`. Successful fallback clears HOT and sets INVERT in that created field, retaining the style record; failure of the normal/fallback load returns an error. All requests use the current palette with mode 2 and fixed SRCCOPY, including when the surrounding effect renderer changes its pen ROP2. See [bitmap palette handling](4.0-icons-and-bitmaps.md#rip_load_bitmap) and the bit-128 finding below. _Evidence: original caller and request captures; [derivation](../research/issue-27-button-style-contract.md)._

**CLIPBOARD BUTTON (flag 1)** - Uses the current clipboard port's viewport as the base image. An undefined clipboard rejects button creation. Although the inherited draft assigned explicit-port semantics to `<other_port>`, RIPtel 3.1 ignores that wire argument and uses the clipboard pointer. Effects can be applied to the pasted image. _Evidence: original definition, constructor and clipboard renderer; [derivation](../research/issue-27-button-style-contract.md)._

**PLAIN BUTTON (flag 256)** - A plain button is exactly that, plain. No special graphics are used to create the button. The entire button region is simply filled-in with a solid colored rectangle using the `<surface>` color. Any special effects can be further applied to enhance the button's appearance. _(v1.54)_

### Size and Color Parameters

For **PLAIN faces only**, the `<hgt>` and `<wid>` parameters provide fixed dimensions only when **both stored dimensions are nonzero**; the button command's far corner is then ignored. If either is zero, both dimensions come from the command's corners: a single positive style dimension does not independently fix that axis. An empty nonmouse plain button with no complete fixed size and both command far coordinates zero is skipped. RIPtel 3.1 converts the style dimensions from the definition-time world into device units once; creation adds those stored dimensions directly to the converted anchor. A world change after definition does not reconvert them.

With BEVEL 512, `<bevsize>` is converted once using the definition-time **X** ratio, `floor(bevsize × device_width / world_width)`, stored as a WORD, then its low byte is copied into a created button. The same device size is used on both axes. Without BEVEL the stored size is zero. See [effect coordinate units](#effect-coordinate-units) for chisel, recess, sunken and label insets. _Evidence: original B/U handlers and native scale/mixed-zero matrices; [derivation](../research/issue-27-button-style-contract.md)._

There are a large number of flag values that can be combined to achieve a great many effects. There are two flag parameters for the RIP_BUTTON_STYLE command, `<flags>` and `<flags2>`. They are detailed in the two tables that follow in this Section. You may combine any of the flags in the first table together simply by adding the "Value" of each one together and representing that number as a MegaNum.

The `<dfore>` and `<dback>` parameters are used with the text label. The `<dfore>` parameter is the foreground color for the text. It is always used to determine the color of the text label. The `<dback>` color is the color of the dropshadow (if any). This parameter is only used when you have specified the "Dropshadow" flag in the `<flags>` parameter (see below).

NOTE: There are seven (7) color parameters in this command. These parameters are ALWAYS used in Color Map mode. Direct RGB Color Mode cannot be used for these parameters. With Color Map mode, you have up to 256 separate color combinations possible for each color, providing you with a great deal of flexibility. The color parameters always use the Base Math set by the global Base Math setting. _(v2.A0)_

The `<bright>`, `<dark>` and `<surface>` parameters are used with Plain Buttons and with the Special Effects styles (see `<flags>` below). These colors represent the highlighted color, the shadowed color, and the regular surface color that is used in Special Effects. Typical color combinations for these colors might be White, Dark-Gray and Light-Gray respectively for a "chiseled steel" appearance. Each of these values can contain a two-digit value representing any valid color code that may be used in the [RIP_COLOR](2.0-color-modes-and-palettes.md#rip_color) command.

In addition to the special effects colors, are two additional colors that can be used, `<uline_color>` which is used for the color of the underline (in the text label), and `<corner_color>` which is used to display the colors of corners for things like the Bevel, Recess, etc.

The `<grp_no>` parameter determines which Button Group subsequent RIP_BUTTON commands will be associated with. Button Groups are used to maintain groups of Buttons for things like Radio Buttons and/or Checkbox Buttons. See the section on the BUTTON COMMAND for more information on these modes, and what Button Groups can offer. This value can range anywhere from 0-Z (i.e., 0-35). A live group cannot mix checkbox and radio members; conflicting creation rejects under the [grouped selection contract](#grouped-selection-and-feedback).

### Flags Field 1

The right-most five columns describe the combinations for which each flag has an effect. Use one of Plain, Icon or Clipboard for ordinary content. RIPtel 3.1 accepts multiple type bits and inapplicable flags as described in [Validation and Flag Precedence](#validation-and-flag-precedence); an N is not itself a syntax-error condition.

The following table contains the possible flag values for the `<flags>` parameter. Each of these values may be combined to achieve a "composite" group of flags. See the preceding paragraphs for a more detailed explanation of this method.

| Value | Description of Flags Field #1 | Icn | Clp | Pln | Mse | NoMse |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Button is a "Clipboard Button" | N | Y | N | Y | Y |
| 2 | Button is "Invertable" | Y | Y | Y | Y | N |
| 4 | Reset screen after button click | Y | Y | Y | Y | N |
| 8 | Display Chisel special effect | Y | Y | Y | Y | Y |
| 16 | Display Recessed special effect | Y | Y | Y | Y | Y |
| 32 | Dropshadow the label (if any) | Y | Y | Y | Y | Y |
| 64 | Auto-stamp image into Clipboard slot _(v2.A2)_ | Y | Y | Y | Y | Y |
| 128 | Button is an "Icon Button" | Y | N | N | Y | Y |
| 256 | Button is a "Plain Button" | N | N | Y | Y | Y |

The Icon Button, Clipboard button and Plain flags have already been discussed. Following, will be more discussion of the various flags used in the preceding table: _(v1.54)_

**BUTTON IS INVERTABLE (flag 2)** - This means that the button will be inverted when clicked. This flag is only useful when combined with the "Button is a Mouse Button - flag 1024) flag. Even if the button has special effects, those will be inverted as well as they are considered part of the button - all except for the Recessed effect. The recessed effect is NEVER considered part of the actual button image, and will never be part of the mouse field, button's image or anything - it is just extra graphics. _(v1.54)_

**RESET SCREEN AFTER BUTTON CLICK (flag 4)** - This flag is used when the button is considered a Mouse Button (flag 1024). What this means is that when the user clicks on the button, the screen will be reset exactly the same as a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) command will do. The reset is performed before the host command is processed (if any). _(v1.54)_

**DISPLAY CHISEL SPECIAL EFFECT (flag 8)** - This displays a special effect on-top of the button image that gives the visual impression of an indented gutter just to the inside of the button's border. The amount of indentation varies depending on the size of the button. See below for a table of indentation values for the Chisel effect. _(v1.54)_

**DISPLAY RECESSED SPECIAL EFFECT (flag 16)** - This places a recessed one-pixel bevel around the exterior of the button. It is never considered part of the button's image. Its purpose is to give the button a more 3D look by making it appear that the button is "poking through" a hole in a dialog box. This effect is accomplished by placing a black outline (one pixel wide) around the exterior of the button's image (including bevel, etc), then placing a one-pixel wide inverted bevel around the black outline. _(v1.54)_

**DROPSHADOW THE LABEL IF ANY (flag 32)** - This flag will instruct RIPscrip to place a dropshadowed version of the text label one pixel to the right and one pixel lower than the original label. This is accomplished by drawing the label first in the `<dback>` color, then drawing the label offset up-left in the `<dfore>`. _(v1.54)_

**AUTO-STAMP IMAGE INTO CLIPBOARD SLOT (flag 64)** - Subject to the same-destination guard below, after rendering the face and effects but before the label, captures the button image through the current clipboard mechanism. It excludes the recess. RIPtel 3.1 uses the existing clipboard slot or chooses the first free nonzero port; the ignored `<other_port>` field does not select a destination. On capture success it changes both the created field's flags and the **actual current style record's flags** to `(field_flags & 0x7c37) | 1`: ICON, PLAIN, CHISEL, BEVEL, AUTOCLIP and SUNKEN are cleared and CLIPBOARD is set. This write occurs **even if the current style is protected**; protection still rejects an explicit style edit. Other style fields and protection are retained. The initial recess has already been removed from the field's persistent flags, so that field-based write also removes it from the style. On capture failure, drawing returns an error and the style flags remain unchanged; earlier painting or clipboard-port work is not rolled back. Later buttons use the captured face. _Evidence: original renderer and protected/unprotected success/failure fixtures; [derivation](../research/issue-27-button-style-contract.md)._ The [auto-stamp redraw contract](#auto-stamp-geometry-and-redraw) defines the baked footprint, source crop, provider stages and same-target continuation boundary.

**BUTTON IS AN ICON BUTTON (flag 128)** - See previous discussions on button types above. _(v1.54)_

**BUTTON IS A PLAIN BUTTON (flag 256)** - See previous discussions on button types above. _(v1.54)_

**DISPLAY BEVEL SPECIAL EFFECT (flag 512)** - When this flag is active, a bevel will be drawn `<size>` pixels thick on the outside of the base image of the button. This makes the button that many pixels wider and taller in each direction. See the RIP*BUTTON for a more detailed description of the affects of the button's final size. *(v1.54)\_

**BUTTON IS A MOUSE BUTTON (flag 1024)** - When this flag is enabled, the button becomes a clickable mouse region. When this option is in use, the Invert flag and several others are available (see the preceding chart). When a button is a non-mouse button, then it is only used to draw a dialog box or an elaborate "static graphic" image of something that "looks" like a button. _(v1.54)_

**UNDERLINE HOT-KEYS IN LABEL (flag 2048)** - When this flag is active, the first occurence of the hot-key character in the button's label will be underlined using the `<uline_col>` color. Special care must be taken when underlining the character, taking into consideration if the character has a segment that goes below the "baseline" of the font. Consult the following section to determine what ASCII characters have these "descenders". Characters with descenders have the underline drawn slightly lower than for characters without them. _(v1.54)_

**MAKE ICON BUTTON USE HOT ICONS (flag 4096)** - A Hot Icon is a button that has an alternative image when the button is "depressed". Normally, when a button is an Icon button, some form of Icon File is used to create the image of the button (eg, EMAIL.BMP). When the Hot Icon flag is in use, whenever that button is depressed, rather than using the normal Icon File for the button's image, a different Icon File is used for the button's image. The filename would be the same filename as the original Icon, but with an extension of .BMH instead of .BMP. When Hot Icon is in use, the alternative Icon is stamped in COPY mode. If the file does not exist, then the original Icon's image is used, but pasted in NOT mode for the duration of the depression. _(v1.54)_

**ADJ. VERTICAL CENTERING OF LABEL (flag 8192)** - Some Labels may appear non-centered vertically when drawn using some fonts that are rather large. With this in mind, you have the option to adjust the vertical centering. What this does is take into consideration the height of any descenders of the label and calculate those into the overall height of the label before centering. If this flag is not used, then the descenders are not taken into consideration when the vertical centering is calculated. See the Font Metric tables below for more detailed information on font sizes and their associated metrics. This command has no effect if the Label orientation is LEFT or RIGHT of the button. It only applies to an orientation of TOP, BOTTOM or CENTER. _(v1.54)_

**BUTTON BELONGS TO A RADIO GROUP (flag 16384)** - At most one live radio member of a group is persistently selected. A committed pointer/keyboard activation selects its target and clears its peers; an already selected target stays selected and still processes one activation. Initial selection is visual/logical state only, with no creation-time host processing. The [grouped selection contract](#grouped-selection-and-feedback) and [associated-template lifetime](5.2-templates-and-conditionals.md#associated-template-ownership-and-lifetime) complete the inherited wording.

**DISPLAY SUNKEN SPECIAL EFFECT (flag 32768)** - When this option is enabled, a one-pixel inverted bevel is drawn exactly one pixel to the inside of the base image of the button. This and the chisel effect are the only two special effects which physically "overwrite" portions of the base button image. _(v1.54)_

### Font Metrics and Descenders

#### Classic Font Zero Labels

A `1U` button captures its effective font and size at creation, including the implicit classic font 0 after drawing defaults. For a captured classic font 0, prepare and paint the **solid DEFAULT EX outline face** from DEFAULT.RFF. Use the [shared size table, 140% face scale and device spacing](3.0-text-output-and-fonts.md#classic-font-zero-in-text-and-text_xy) with the captured size and creation WORLD. The effective DPI still comes from the device canvas and that captured WORLD. The inherited font-zero table below describes the historical bitmap metrics. The ordinary graphics character anchors from `Y`, including direction and shadow, give way to the button's own upright, horizontal label layout and flags. See the [original button measurement and draw trace](../research/issue-190-button-font-zero.md).

##### Measuring and positioning the label

1. Expand the label under the existing [button expansion contract](5.2-templates-and-conditionals.md#graphical-consumer-expansion). Measure the expanded bytes with the selected outline's per-character X advances and spacing, including the last gap. The same per-byte positions govern painting and hotkey decoration. On a full redraw use the then-current expanded label with the instance's captured font, size, WORLD and original face geometry.
2. **Portable vertical metrics:** scale the face's 750-unit baseline height and 250-unit descent separately by `Q × Dy / (72 × 1000)`, truncating in DEVICE units. Use the baseline height for the placement height, adding the descent for an above-face or center label only when flags 1 bit 8192 is set and the label contains a descender according to `low_char` below. A below-face label keeps its top offset. Use the actual baseline height to place the baseline even when the descent participates in centering.
3. For placement, convert these dimensions, label width, original face bounds and face width and height separately from DEVICE into the captured WORLD, truncating toward zero. Use the original inner face `F` as the reference. All offsets in the following table are creation-WORLD units. Use truncation toward zero for each half difference.

| Orientation | Unjustified start X | Label top Y |
| --- | --- | --- |
| 0 (above) | `left + trunc((face_width − label_width)/2)` | `top − placement_height − 5` |
| 1 (left of face) | `left − label_width − 8` | `top + trunc((face_height − placement_height)/2)` |
| 2 (center) | `left + trunc((face_width − label_width)/2)` | `top + trunc((face_height − placement_height)/2)` |
| 3 (right of face) | `right + 8` | `top + trunc((face_height − placement_height)/2)` |
| 4 (below) | `left + trunc((face_width − label_width)/2)` | `bottom + 5` |

For orientations 0, 2 and 4, apply the existing [left/right alignment and chisel insets](#effect-coordinate-units), with left winning when both bits are set. Centering can start outside the inner face when its label is wider. Convert the resulting X and Y separately back to DEVICE. Convert the WORLD baseline height back separately and add it to the converted Y. Paint from that left/baseline origin. Flag 32 selects the button-label shadow and `dback` color, and the ordinary label uses `dfore`.

##### Hotkey decoration

On an eligible mouse button with a nonzero explicit hotkey, find the first case-insensitive match in the expanded label. Flags 2 bit 2 highlights that glyph in `uline_col`. Flags 1 bit 2048 draws an underline in `uline_col`. When both bits are set, apply both effects to the same glyph. When the match is absent, the entire label uses normal foreground and there is no hotkey mark.

The decorated glyph starts at the label X plus the sum of all **spacing-adjusted** prefix steps. Let `w` be that glyph's **unspaced** DEVICE advance. Its underline occupies one pixel row at baseline +3 and the half-open X interval from the glyph start to start + `w`. The suffix starts after the matched glyph's full step, including its gap. The font-zero underline uses this baseline offset with or without a descender on that glyph. Painting stays one run, with no CHR prefix measurement or reset of spacing after the hotkey.

##### Centered label example

At WORLD and device 1024×768, RIPaint 2 `ACC.RIP` creates a 268×28 inner face and its label with these lines (MegaNum, XY width 2).

```text
!|*|fSGLC|Y00000209
!|1B7G0S0201FA030F000F080300040F07000000
!|1U0W4W00000000<>Home Phone Number<>D
```

The inner face is `[32,300)×[176,204)`. Q=22, P=109 and Dx=Dy=72. All 17 bytes have 500 design units of advance, giving 15 DEVICE pixels plus one gap each. The 272-pixel run starts at X=30, with label top Y=182 and baseline Y=198 from the 16-pixel baseline height. Clipping follows the drawing destination. The measured run stays centered even though its logical span extends two pixels past either face edge. Native ink bounds are a separate question.

For a decoration vector, change flags 1 from `01FA` to `0306` to enable underline, flags 2 from `04` to `06` to enable highlight, and the `1U` hotkey from `00` to `26` (ASCII N). The first match is the lowercase `n` in Phone. Its eight-byte prefix advances 128 pixels. Highlight it at X=158 and underline `[158,173)` at Y=201. The next glyph starts at X=174.

### Chisel Effect Insets

The Chisel effect draws a dropshadowed line around the inside of the button. How far from the borders of the button are determined by this table:

| Height of Button | X inset | Y inset |
| ---------------- | ------- | ------- |
| 0 - 11           | 1       | 1       |
| 12 - 24          | 3       | 3       |
| 25 - 39          | 4       | 4       |
| 40 - 74          | 6       | 6       |
| 75 - 149         | 7       | 5       |
| 150 - 199        | 8       | 6       |
| 200 - 249        | 10      | 7       |
| 250 - 299        | 11      | 8       |
| 300 -            | 13      | 9       |

The height and both inset columns are **device pixels**, using the face's far-minus-near device height. The 12..74 rows correct the inherited draft's Y values 2/3/5 to the shipped values **3/4/6**. _Evidence: original inset selector, all heights 0..32767 and captured chisel rectangles; [derivation](../research/issue-27-button-style-contract.md)._

### Effect Coordinate Units

| Quantity | RIPtel 3.1 coordinate rule |
| --- | --- |
| Style width/height | Converted with the definition-time X/Y ratios and stored in device units |
| Bevel thickness | Converted with the definition-time X ratio once, then copied as a device byte; same value on both axes |
| Chisel | Table selected by device face height; device insets; one-device-pixel pens |
| Sunken | One device pixel inside the face; one-device-pixel pens |
| Recess | Black frame one device pixel outside the bevel, outer inverted bevel two device pixels outside it; does not enlarge the interactive face |
| Left/right label indent | Constants in the world captured at creation, applied after converting face geometry and font metrics to that world, then converted back for output |

For a captured world width W and canvas width D, label LEFT adds **10** world units without chisel or **20** with chisel; RIGHT subtracts label width plus **9** or **19** from the far extent boundary. LEFT wins both flags. The right-edge boundary convention accounts for its one-unit difference from the draft's nominal 10/20 description. For example, at X ratios D/W of 1, 1/2 and 1/4, a left inset of 10 becomes 10, 5 and 2 device pixels for integer-aligned positive fixtures. The chisel/recess/sunken one-pixel strokes remain one device pixel at all three ratios. Default bevel 3 is already a literal device value; an explicitly defined bevel is scaled by the formula above. These rules apply at every device canvas; there is no additional hard-coded 640×350 scaling stage. _Evidence: original helpers and label coordinate consumers, native 1/2/4 ratio matrices; [derivation](../research/issue-27-button-style-contract.md)._

Following is a more complete description of the flags described in the `<flags2>` parameter: _(v1.54)_

**BUTTON IS IN A CHECK BOX GROUP (flags 2 bit 1)** - Members toggle independently and any number may be selected. A live group cannot mix checkbox and radio members. Initial selection does not process the opaque host source; both ON and OFF committed activations later process their own source once. See the [grouped selection](#grouped-selection-and-feedback) and [template ownership](5.2-templates-and-conditionals.md#associated-template-ownership-and-lifetime) rules.

**HIGHLIGHT HOTKEY CHARACTER (flag 2)** - When this flag is active, then the first occurence of the hotkey character in the label will be hilighted using the `<uline_col>` color. This gives the user a visual impression of what keystroke they need to type in order to activate the button without the mouse. _(v1.54)_

**EXPLODE (ZOOM OUT WHEN CLICKED) (flag 4)** - This optional flag is designed to "zoom out" from the button when the user clicks on it. What is generally done is a dotted rectangle is drawn initially around the button and it is repeatedly redrawn over itself in XOR mode, constantly getting larger and larger until it hits the full size of the screen. This gives the visual impression that the button is zooming out to another screen. Each time another frame of the zooming rectangle is drawn, the previous rectangle on the inside of the new one is erased by XOR drawing the same rectangle over itself again. This option does not need to be supported in order to be considered a RIPscrip terminal, although it would be nice. In other words, this is not a "make or break" feature. _(v1.54)_

**LEFT JUSTIFY LABEL (TOP/CTR/BTM) (flag 8)** - If this option is enabled, then any TOP, CENTER or BOTTOM label orientations will be left justified to the left edge of the button. The exact indentation of the label from the interior of the button's base image depends on whether the chisel effect is active. RIPtel 3.1 adds 10 creation-world units without chisel or 20 with chisel; see [effect coordinate units](#effect-coordinate-units). This option can be combined with the Adjust Vertical Centering flag only if the label orientation is CENTER. _(v1.54)_

**RIGHT JUSTIFY LABEL (TOP/CTR/BTM) (flag 16)** - If this option is enabled, then any TOP, CENTER or BOTTOM label orientations will be right justified to the right edge of the button. The exact indentation of the label from the interior of the button's base image depends on whether the chisel effect is active. RIPtel 3.1 subtracts label width plus 9 creation-world units without chisel or 19 with chisel from the far boundary; see [effect coordinate units](#effect-coordinate-units). This option can be combined with the Adjust Vertical Centering flag only if the label orientation is CENTER. _(v1.54)_

**DON'T FILL-IN BUTTON INTERIOR** - If this option is enabled and the button is a Plain Button, then the interior of the Button will not be filled in with the surface color. By default, any plain button will have its interior filled in with the surface color. Use this option if you don't want the button face to be drawn. _(v2.A0)_

**FILL-IN INTERIOR IN FILL PATTERN** - If this option is enabled in conjunction with a plain button, then the interior of the button that would normally be filled in with the surface color will instead, use the current Fill Color and Fill Pattern to fill in the interior. This allows for patterned button faces. _(v2.A0)_

## RIP_BUTTON

_Define a Mouse Button_

|               |                                                       |
| ------------- | ----------------------------------------------------- |
| **Level**     | 1                                                     |
| **Command**   | `U`                                                   |
| **Arguments** | `x0:XY y0:XY x1:XY y1:XY hotkey:2 flags:1 res:1 text` |

**Format:** `!|1U <x0> <y0> <x1> <y1> <hotkey> <flags> <res> <text>` **Example:** `!|1U2E5O747G2000<>Hotkeys<>`

**Attributes used:** Font Style, Viewport, Port (only for "non-mouse" type buttons), Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.3-buttons.md#rip_button)) · HLP (`RIP_Button`; limits label ≤255, hotkey ≤255) · corpus (75 uses in 17 files) · SyncTERM (ripper.c:16764)

This command physically creates a new Button using a previously defined [RIP_BUTTON_STYLE](#rip_button_style) in the current button style. You may have at most 128 different Mouse Buttons (you may have any number of non-Mouse Buttons). The `<slot>` parameter determines which button style slot is used to determine how this button appears. _(v2.A1)_ The ALPHA 4 draft removed the explicit `<slot>` parameters in favor of the current-style model. _(v2.A4)_

Mouse-active buttons use the [shared left-button gesture contract](4.2-mouse-fields-and-pointer.md#left-button-gesture-commitment): press captures one field, release inside commits its host action, release outside cancels, and dragging out/back updates temporary depression. The explicit mutation policy prevents overlapping/replaced/restored definitions from inheriting another instance's press. This governs pointer click actions and momentary feedback; existing keyboard/hotkey and persistent checkbox/radio rules remain separate. The optional [identity prefix](5.0-host-commands.md#identity-grammar-and-fieldid-lifetime) is parsed at the start of the full `1U` text payload before label/host splitting.

The `<x0>` and `<y0>` parameters for this command designate the upper-left corner of the Button. This (X,Y) location may not be the actual "absolute" corner position of the Button, as it may be adjusted via the Special Effects functions that are part of the RIP_BUTTON_STYLE command (see above).

The `<x1>` and `<y1>` parameters are used only for dynamic PLAIN faces. Complete nonzero stored PLAIN style dimensions ignore them. CLIPBOARD and ICON ignore both style dimensions and transmitted far coordinates entirely, including zero/reversed values; see the [per-type sizing table](#image-face-sizing-and-source-eligibility).

The (x0,y0) and (x1,y1) parameters will be modified by the following values for the different special effects:

| Effect Type | X0 Modifier | Y0 Modifier | X1 Modifier | Y1 Modifier |
| ----------- | ----------- | ----------- | ----------- | ----------- |
| Bevel       | -bevel size | -bevel size | +bevel size | +bevel size |
| Recess      | -2          | -2          | +2          | +2          |
| Sunken      | 0           | 0           | 0           | 0           |
| Chisel      | 0           | 0           | 0           | 0           |

The modifiers above use the [effect coordinate units](#effect-coordinate-units): bevel is the already converted device size, and the additional recess border remains two device pixels outside it. Chisel and sunken overwrite the face without enlarging its bounds. The recess is painted once and excluded from the persistent mouse/button image. _Evidence: original renderer/effect helpers; [derivation](../research/issue-27-button-style-contract.md)._

The `<hotkey>` parameter is only used with Mouse Buttons. It is the ASCII code for the keystroke that will activate this Button. It is represented as a two-digit MegaNum. If this character exists in the text label, and the Underline flag or hilight hotkey flag is enabled in the RIP*BUTTON_STYLE, then the character will be underlined in the label. Control codes are allowable, and a value of 255 (decimal) corresponds to "any" key. *(v1.54)\_

The `<flags>` parameter provides several different functions for each button. The possible "combinatorial" flags for this parameter are listed in the following table. Note that these values may be combined together (by adding their values) to arrive at the final flag parameter's value.

| Value | Description                                   |
| ----- | --------------------------------------------- |
| 1     | Draw button as already selected               |
| 2     | Button is "default" when \<ENTER\> is pressed |

Using a flag of 1 means that the Button is already "selected". By selected, we mean that it is already clicked and should be initially drawn as clicked. This is typically used for Radio Buttons and/or Check Boxes. This establishes the initial persistent selection and artwork under the [grouped selection contract](#grouped-selection-and-feedback). It does not parse or execute the host source. If this parameter is set to 0, then the Button will be drawn in normal, unselected mode.

### Grouped Selection and Feedback

**Explicit portable completion:** use persistent selection separately from temporary pressed artwork. Primary group exclusivity/toggling and the original selected-bit/renderer routes support the normal cases; [source boundaries and continuation choices](../research/issue-131-grouped-button-lifetime.md) distinguish this policy from native live-index behavior. The existing stable-instance pointer/keyboard commitment rules remain controlling.

| Event | Persistent selection | Feedback and host action |
| --- | --- | --- |
| Successful initial selected creation | Checkbox takes its supplied state; an initially selected radio wins over older selected peers | Render initial state; no parsing/evaluation of host source or associated definitions |
| Pointer press / drag inside | Unchanged | Target previews its proposed selected state; radio peers retain their committed state until release |
| Drag outside / outside release / canceled capture | Unchanged | Restore surviving target's committed artwork; no click host processing |
| Valid inside release | Checkbox toggles; radio selects target and deselects peers atomically | Commit once before optional full redraw/providers, then process clicked source once |
| Eligible translated key or repeat | Same state operation immediately, even for an already selected radio | One committed activation per delivery; prior pointer capture is canceled under the keyboard rule |
| Already selected radio activated | Remains selected | One host activation; no synthesized deselect/reselect cycle |
| Redraw/prompt/file/provider failure after commitment | Keep the committed state | No rollback or retry; the committed action snapshot survives optional feedback failure |

For a checkbox, pressed feedback previews the opposite of its committed state, including an ON box previewing OFF. A radio press previews selected artwork on the target without changing its peers' committed bits. Render selected state using the existing PLAIN/CLIPBOARD/ICON rules (HOT/fallback/inversion/label colors as enabled); PLAIN without a selected visual effect may look unchanged. Normal ungrouped buttons have only momentary depression; their initial selected flag is ignored as before.

Reject a `1U` with both group kinds or a kind conflicting with existing live members of that group **before painting/admission**, retaining prior fields and the current style record. A style definition may still store the accepted flag combination; this is a use-time membership constraint. Recheck after a suspended creation before admission. Ordinary ungrouped buttons do not establish a group kind. Last-member deletion releases that kind. A new selected radio commits its initial state only after successful creation rendering/admission, so failed pending creation cannot deselect an earlier field.

At activation commitment, own the clicked stable token, numeric FIELDID, raw host source and the affected peer/redraw-token list. Commit selection exactly once, rebuild existing group-owned slot bytes without providers, then perform optional redraws and the clicked host continuation. Source deletion, reset, replacement or a duplicate numeric ID cannot retarget the action or replay its selection on resume. Skip stale redraw targets; newly added fields do not acquire the old activation or run their sources. A later independently committed action may change current state; an older continuation must not restore its earlier selection afterward. Optional redraw cancellation follows the adopted NONE/transparent-empty lookup rules; a hard redraw abort also cannot undo the already committed action. No rendering path evaluates host text as a test.

### Keyboard Activation

**Explicit portable completion:** The inherited hotkey/default descriptions and original character-event paths do not fully define case/priority/translation/repeat or mutation lifetime. The following keyboard profile completes them; the [derivation](../research/issue-118-button-keyboard-activation.md) separates original input-uppercase/reverse-scan/immediate-action evidence from these choices. It does not revise pointer, payload or deferred-host contracts.

[Tab navigation](4.2-mouse-fields-and-pointer.md#tab-navigation) handles its eligible keys first, including Enter for a focused simple field or button. Ordinary hotkey lookup considers only surviving **resident mouse-active `1U` button instances**, using each instance's captured binding/default flag. Simple `1M` fields, nonmouse decorations and the current style record do not supply keyboard bindings. The pointer need not be inside the chosen button. An eligible event supplies one translated character/control **byte** in the terminal's existing CP437 byte profile, before normal forwarding. Semantic noncharacter keys (arrows/function keys, etc.) are not byte candidates; their later terminal escape-sequence encoding is not fed back byte by byte into button matching. Local shortcuts and unrepresentable/multibyte character translation remain client policy, with no new emulation mode.

| Stored hotkey / flag | Matching rule |
| --- | --- |
| `0` | No explicit keyboard binding; it does not bind NUL |
| `1..127` | Match that byte, folding ASCII `a..z` to `A..Z` on **both** key and binding |
| `128..254` | Match the exact byte; no Unicode/OEM locale case folding |
| `255` | Wildcard for any eligible byte, including NUL and byte 255; never a noncharacter event |
| Per-button flag `2` | Default candidate for translated **CR (13)** only, independent of its explicit hotkey; not an implicit LF binding |

Select one winner by class: **explicit byte match, then flag-2 CR default, then wildcard**. Within a class choose the newest surviving button. An explicit CR binding therefore beats even a newer default/wildcard; duplicate A/a, CR, default or wildcard bindings choose newest within their class. A flag-2 button can also win an explicit match through its own nonzero hotkey. This is a three-class lookup, not one scan in which a newer wildcard hides an explicit match.

A matching translated key-down/character event commits **immediately once**, without waiting for key-up. Each separately delivered repeat event performs a fresh lookup and can commit again; no extra autonomous repeat timer is required. Deliver only one translated candidate per key-down/repeat; do not count both a raw key-down and its derived character notification as two activations. Key-up never commits. Once a button wins, **consume the event**, including an empty host action or an action that later fails, deletes the button or resets the scene; it must not also enter the terminal path. Unmatched input follows the existing terminal path with its original byte/case unchanged, subject to the normal input controls. Merely defining/drawing/preselecting the button still executes no host action.

**Portable input/lifetime policy:** Pointer-only mouse disable suppresses pointer/hover interaction, not keyboard buttons. HKEYOFF disables button keyboard lookup (HKEYON enables it); unmatched input then takes its normal path. HEADER's global mouse/keyboard input lock suppresses keyboard activation **and** normal forwarding while locked under the existing lock contract. Local terminal shortcuts remain client policy. No existing viewport change deletes a resident binding merely by changing its former drawing destination.

Before a winning keyboard action starts, snapshot its stable instance, identity and unexpanded host action, then **cancel any held pointer capture**, on the same or another field, and remove its temporary feedback. The physical pointer coordinates/button state do not change; the eventual physical release cannot activate that canceled gesture or transfer it to a replacement. An unmatched/disabled keyboard lookup does not cancel a pointer capture. Give the keyboard target momentary pressed feedback and restore it only if that same instance survives; no fixed sleep, fake pointer press or deferred dereference is required. Each delivered repeat snapshots its newly chosen winner independently.

Use the same activation-time host stages, reset-before-host flag and [FIELDID snapshot/stack](5.0-host-commands.md#identity-grammar-and-fieldid-lifetime). A callback that deletes/replaces its field, applies restored definitions or invokes SOFT retains its own numeric FIELDID until return, but cleanup must not touch a deleted/replacement field. Clear pending keyboard feedback safely before replacement. X/Y/XY and mouse-button queries retain the actual last pointer position and physical state; keyboard activation supplies no synthetic center/click coordinate. Existing style/group behavior is otherwise unchanged.

#### Literal Keyboard Vectors

Assume Base Math 36, coordinate size 2, active full-screen PORT0, WORLD=DEVICE=640×480, palette mode and keyboard lookup enabled. This plain mouse style has dynamic size, no effects, and MOUSE+PLAIN flags 1280 (`00ZK`):

```text
!|1B00000200ZK000F000F080700000F07000000
!|1U0A0A1E0U1T00ID=1:<>A<>A$FIELDID$
!|1U0A141E1O2P00ID=2:<>a<>a$FIELDID$
!|1U0A1Y1E2I0000ID=3:<>Zero<>Z$FIELDID$
!|1U0A2S1E3C0D00ID=4:<>CR<>E$FIELDID$
!|1U0A3M1E460020ID=5:<>Default 1<>D$FIELDID$
!|1U0A4G1E500020ID=6:<>Default 2<>D$FIELDID$
!|1U0A5A1E5U7300ID=7:<>Any<>W$FIELDID$
```

The buttons are created oldest to newest: ID 1 hotkey A, ID 2 hotkey a, ID 3 unbound zero, ID 4 explicit CR, IDs 5/6 Enter defaults, ID 7 wildcard. Each host source is its letter followed by `$FIELDID$`.

| Input / current definitions | Result |
| --- | --- |
| A or a, all seven present | ID 2; host `a2`; event consumed |
| CR, all present | ID 4; host `E4`, ahead of newer defaults/wildcard |
| CR after deleting ID 4 | ID 6; host `D6` |
| CR after also deleting ID 6 | ID 5; host `D5` |
| CR after also deleting ID 5 | ID 7; host `W7` |
| NUL, all present | ID 7; host `W7`; ID 3 is unbound |
| NUL after deleting wildcard | Unmatched NUL follows normal input; ID 3 still does not match |
| Byte 128, all present | ID 7; if a newer explicit hotkey-128 button is added, it wins byte 128 but not byte 129 |
| Semantic Up key, all present | No button match, even if normal terminal encoding later contains ESC bytes |
| Matched callback executes `1K`/SOFT | Consume once; FIELDID remains the chosen ID during that callback; no dangling cleanup |
| Pointer press held on any field, then A wins keyboard ID 2 | Cancel pointer capture; send `a2`; later pointer release sends no click action |

A repeated delivered A event repeats lookup/commit; its key-up sends nothing. An empty/failing action still consumes A. These are explicit profile vectors, not original-client executions.

### Image Face Sizing and Source Eligibility

The inherited ALPHA 4 fixed-width/height rule explicitly applies **only to PLAIN**. The following table reconciles that documentary rule with the original natural-image consumers; source facts and explicit source/hot completion are recorded in the [derivation](../research/issue-119-image-button-sizing.md). Earlier type precedence, payload, host stages and destination hit/clipping policy remain adopted.

| Effective face | Face size before effects/destination clipping | Style width/height and command far coordinates |
| --- | --- | --- |
| PLAIN, both stored style dimensions nonzero | Those already converted device dimensions | Ignore command far coordinates |
| PLAIN, either stored dimension zero | Both dimensions from ordered WORLD corners, converted once | Both command far coordinates used; prior PLAIN omission/empty rules apply |
| CLIPBOARD | Entire source viewport's DEVICE `right-left`, `bottom-top` | Ignore all style dimensions and all far values; no plain-only zero/reversal guard |
| ICON | Decoded dimensions of the initially chosen image, scaled through creation WORLD | Ignore all style dimensions and all far values; no plain-only zero/reversal guard |

The transmitted anchor still converts once from creation WORLD and uses the effective destination viewport origin. Image sizing never reorders it with ignored far coordinates. Nonempty style sizes are not an image fitting request; neither a complete 50×40 size nor a mixed zero/nonzero pair changes image face size.

**CLIPBOARD:** Use the current clipboard source's **stored viewport extents**, in its own canvas/device coordinates, with no conversion through current WORLD. Its viewport origin selects the source crop; it does not change the destination anchor. Use the whole logical viewport size for face, label, effects and eventual hit bounds, not the physical backing intersection's size. Protection and source inactivity do not prohibit reading a defined source; changing current WORLD does not resize that viewport. The ignored `other_port` argument remains ignored.

**Explicit clipboard eligibility/padding completion:** Require a defined/readable clipboard and a positive viewport with at least some available backing pixels. Reject empty/inverted or wholly unavailable source regions before new painting/field creation. For a partially clipped source, preserve the whole viewport-sized face: copy its available intersection at offset `availableNear - viewportNear`, without stretching/recentering; fill unavailable face pixels with the current destination palette's **index 0**, using COPY semantics. This is not guaranteed RGB black and does not modify the source viewport or palette. The original paste helper is not a complete oracle for this policy. Apply the separate destination viewport/screen clip afterward, retaining whole-face effect/label geometry.

**ICON:** Let decoded positive raster dimensions be `(iw,ih)` and the captured creation WORLD be `(W,H)` on device `(D,E)`. The natural face is **`floor(iw*D/W) × floor(ih*E/H)`**; reject if either device dimension is nonpositive. It equals native device bitmap dimensions only when WORLD=DEVICE. There is no additional hard-coded 640×350 or bitmap-DPI scaling stage for button icons; a 640×350 reference applies only when that is the actual creation WORLD. Do not import the separate legacy `RIP_LOAD_ICON` scale convention.

Choose the initial image under the already adopted normal/hot/fallback rules. **Portable hot-size completion:** the first successfully selected creation image fixes the instance's face dimensions. A later normal/hot image of different decoded size is fitted to that stored face; it cannot change hit/effect/label geometry while pressed. If the button is initially selected and its hot image succeeds, that hot image may establish the initial size; a missing hot image uses the normal fallback. This adds no required load of an otherwise unused normal image and does not alter image/key/palette failure rules.

For an [auto-stamped instance](#auto-stamp-geometry-and-redraw), retain its original inner face plus a separate baked-image footprint as specified below. Creation otherwise captures logical face geometry and the WORLD reference used for later redraw. Subsequent WORLD changes, clipboard-pointer/viewport changes or normal/hot state changes do not reflow an existing button; create a new instance to choose new geometry. This does not promise frozen clipboard pixels: existing rendering may refresh content within the fixed face. BEVEL/RECESS, label units and destination clipping retain their earlier rules.

#### Auto-Stamp Geometry and Redraw

_Evidence: the primary ALPHA 4 flag-64 description, original capture/renderer/wrapper instructions and the [derivation](../research/issue-128-auto-stamp-redraw.md). Geometry/crop and continuation details labeled below are explicit portable completion; raw legacy rectangle arithmetic is not a pixel oracle._

**Documented same-destination guard:** If the selected capture target/current clipboard is also this definition's **effective drawing destination**, ignore auto-stamp **before** deleting/replacing that port, allocating a capture or applying capture-success style writes. For a mouse-active button the destination is PORT0; for a nonmouse decoration it is the captured current port. Compare those destinations, not an unrelated current port. Evaluate this guard at the capture boundary, after filename preparation and face/effect rendering but before destructive capture work, using the then-current clipboard target and the already captured destination identity. A permitted filename setter may have changed the clipboard selection. This is a skipped capture, not a pure-preflight rejection of the whole definition. The primary draft expressly requires the guard; the shared legacy capture helper alone does not implement that complete protocol rule.

A guarded definition keeps its original face type/effects and draws its label normally on that same destination. It changes neither the clipboard nor the style's auto-stamp request. **Once-only completion:** mark that instance's creation capture attempt as skipped; later redraws do not retry it merely because the clipboard changed. A new `1U` is a new definition and can try under its own state. This does not create a resident mouse field for a nonmouse decoration.

**Explicit baked-geometry completion:** When an allowed capture succeeds, retain three separate rectangles:

| Rectangle | Meaning after conversion to CLIPBOARD |
| --- | --- |
| F: original inner face | Preserve its anchor, size and captured creation WORLD/font/label-layout parameters; use F for label orientation/indentation/centering |
| H: stored hit rectangle | Preserve the adopted once-expanded, viewport/screen-clipped half-open hit geometry; do not inflate it again when capture succeeds |
| C: baked-image footprint | F expanded by the existing device BEVEL size, or F without BEVEL; includes its CHISEL/SUNKEN artwork, excludes RECESS and label |

Clearing BEVEL/CHISEL/SUNKEN prevents drawing those effects again; their already captured pixels still occupy C. Preserve the original label-inset choice as part of the captured layout, including a chisel-dependent inset; clearing a paint flag must not move that existing label. The converted CLIPBOARD tag chooses the pixel source, **not a new ordinary clipboard-button definition** whose viewport dimensions replace F/H. Capture C before label rendering, preserving its whole logical extent; copy the available effective-viewport/canvas intersection at its C-relative offset and pad unavailable image pixels with destination palette index 0 using COPY. The existing capture failure and clipboard/style side-effect rules remain adopted.

The captured source's **logical viewport/crop is `[0,Cwidth) × [0,Cheight)`**. Physical allocation capacity does not enlarge that viewport, the field or the label box. An inclusive-end helper's `(far-near)+1` gives exactly C's size when passed `(CL,CT,CR-1,CB-1)`. If a backend retains an extra allocated row/column, exclude those units from the logical viewport. They are not an additional border, bevel or image pixel. This logical crop is a portable completion, not a requirement to reproduce native allocation bookkeeping.

On every actual full redraw, read the **then-current clipboard source** from its viewport origin, one device pixel per pixel, into the same C. For a larger source, crop its right/bottom to C's size; for a smaller or partially available source, preserve top-left alignment and pad missing C pixels with destination palette index 0/COPY. Do not stretch, recenter, reapply cleared effects or move F/H. Require a defined/readable source and positive used crop with at least one available backing pixel; otherwise fail that redraw before label expansion. Reading an inactive/protected source remains permitted. Source viewport changes and padding never change label geometry. Apply destination clipping afterward without resizing any rectangle. Existing selected/inversion and label-color rules remain adopted; this crop policy introduces no new pressed-image raster rule.

**Full redraw versus pixel restoration:** The original selected and unselected wrappers both enter the common renderer. Each actual full redraw repeats a nonempty raw filename's common preparation, then reads/pastes the current clipboard image, then expands/renders a nonempty raw label with then-current variables. It loads no former ICON file and performs no second auto-stamp. The [graphical one-pass permissions, bounds, prompts and failures](5.2-templates-and-conditionals.md#graphical-consumer-expansion) apply unchanged. Merely being selected does not authorize a cached-image return that skips those providers.

| Path | Nonempty filename stage | Clipboard/capture | Nonempty label stage |
| --- | --- | --- | --- |
| Successful original auto-stamp creation | Once | Face/effects, then capture once and commit converted flags | Once after capture |
| Actual selected full redraw | Once | Read current source into C; no recapture | Once |
| Actual unselected full redraw | Once | Read current source into C; no recapture | Once |
| Ignored same-destination capture at creation | Once | Original face/effects; no capture or converted-style write | Once on original destination |
| Filename hard failure | Attempted once | No later face/source/capture stage | Skipped |
| Source eligibility/paste failure on redraw | Once | Attempted; existing partial-effect rules apply | Skipped |
| No-op input, or pixels-only undo of temporary feedback | Skipped | Optional owned-pixel restoration only | Skipped |
| Stale scene/instance/destination detected before a stage | No further providers | No further drawing | Skipped |

Empty source slots skip their individual provider stages. A successful empty label result is still one completed expansion; restoring temporary feedback is not an implicit fresh redraw. A pixel cache may optimize painting but cannot suppress the required providers of a requested full redraw. Conversely, undo-only cleanup must not re-run providers, auto-stamp or the opaque host slot.

**Destination and prompt boundary:** Replacing a different clipboard port does not change the captured drawing destination. If an implementation has already replaced its own destination before checking validity, retain any completed clipboard/style effects under the existing no-rollback rule, but **abandon the stale continuation**. A fallback to PORT0 by a helper is not a command-authorized destination transfer and cannot rebind the label or a later prompt. The documented guard prevents that case in conforming creation. External destination replacement/reset during a prompt likewise cancels the stale drawing. No extra activation, host-slot evaluation or connection termination is introduced.

The initial capture is also a [remembered-pair producer](7.0-drawing-ports.md#producers-and-publication): record only its actual nonempty successful transfer, using logical C and the logical clipboard viewport rather than extra backing capacity. The same-target ignored capture publishes nothing. Later label failure does not roll back a completed capture/pair; later face/feedback redraw copies do not publish another pair. The pair does not control this button's fixed F/H/C redraw geometry.

Its unclipped H and baked C are **`[97,123) × [47,63)`** (26×16). ### Text Payload Slots

After the [definition-time identity prefix](5.0-host-commands.md#identity-grammar-and-fieldid-lifetime) is recognized once, remove leading ASCII whitespace (space, HT, LF, VT, FF, CR) from the **remaining whole** button payload. Do not trim individual slots. The ID scan precedes that removal: a leading space before `ID=` does not create an identity through a second scan. The remaining payload must contain at least one byte; use `<>` or `<><>` for a deliberately blank decoration. _Evidence: original identity/leading-trim consumer and shared splitter; [derivation](../research/issue-116-button-payload-hit-geometry.md#exact-positional-payload-consumers)._

Split at the **first two literal `<>` byte pairs**, before filename/label/host expansion. The three positions are always **icon filename, label, host source**; only trailing delimiters may be omitted. Missing positions and zero-length fields are empty. Quotes and backslashes do not escape a delimiter at this stage, and an expansion that later inserts `<>` does not resplit the button payload. Everything after the second delimiter is one host-source field, including further `<>` pairs.

**Payload form:** `icon-field[<>label-field[<>host-source]]`

| Effective face type | First position | Second position | Third position |
| --- | --- | --- | --- |
| ICON | Required icon filename | Optional label | Optional click host source |
| CLIPBOARD | Icon position retained; use empty; the face comes from the current clipboard | Optional label | Optional click host source |
| PLAIN | Icon position retained; use empty; the face uses the plain-style rules | Optional label | Optional click host source |

The type/clipboard preconditions and ICON→CLIPBOARD→PLAIN precedence remain unchanged. A nonempty first field on a non-ICON style **does not become a label or select an icon face**; it remains subject to common filename-field validation/preparation. Do not invent a plain-button one-field label shorthand. The common source bounds are at most **127 bytes for the icon slot** and **255 bytes for the label slot**, before their ordinary rendering expansions; existing expansion/output bounds still apply afterward. No new host-source cap replaces the existing wire/storage/host-response bounds.

| Payload after identity/leading-space handling | Icon slot | Label slot | Host-source slot |
| --- | --- | --- | --- |
| `icon<>label<>host` | `icon` | `label` | `host` |
| `<>label<>host` | Empty | `label` | `host` |
| `icon<>label` or `icon<>label<>` | `icon` | `label` | Empty |
| `<>label` or `<>label<>` | Empty | `label` | Empty |
| `<><>host` | Empty | Empty | `host` |
| `icon`, `icon<>` or `icon<><>` | `icon` | Empty | Empty |
| `<>` or `<><>` | Empty | Empty | Empty |
| `<><><>` | Empty | Empty | Literal `<>`; not an omitted host field |
| `<>label<>host<>tail` | Empty | `label` | `host<>tail` |
| `Style B` | `Style B` | Empty | Empty |
| `<>Style B` | Empty | `Style B` | Empty |

Thus the earlier reset/redefinition example's corrected label command is **`!|1U0A0A2I140000<>Style B`**. Its style/current/protection sequence is unchanged; the leading delimiter places `Style B` in the label slot. An empty first slot is not sufficient for an ICON face, whose filename/image rules still apply. _Evidence: original type-independent splitter, filename/label bounds and rendering consumers; [derivation](../research/issue-116-button-payload-hit-geometry.md)._

The filename's default normal extension is `.BMP`, and the matching selected hot image is `.BMH`; omit a default extension when possible. Supplying an explicit extension preserves it under the existing file rules. The host field may contain the documented controls, variables, pick lists, templates, command segments and local playback; those belong to the host stage below, not the payload splitter.

Under RIPscrip 1.54 and earlier versions, button icon filenames ended with .ICN for normal icons, and .HIC for "Hot IcoN". Under 2.0 and later, these file extensions are different. For normal button icons, the extension .BMP is used for a standard bitmap, and .BMH is used for a "hot bitmap". _(v2.A3)_

When a button is displayed that uses an icon/bitmap, special care must be taken when dealing with hot bitmaps. If the flag is present in the button style indicating to use hot icons, then when the button is displayed as selected then the hot bitmap (.BMH) file's image is used to display the button. If that file doesn't exist, then the normal bitmap button is displayed in an inverted state. If neither of these files are present, then the RIP*BUTTON command is ignored. *(v2.A3)\_

Filename and label stages have a complete [graphical expansion and prompt-lifetime contract](5.2-templates-and-conditionals.md#graphical-consumer-expansion): raw versus working limits, provider gates, common filename preparation, label-after-capture timing, redraw and nontransactional failure. The host slot remains opaque during all of them.

### Creation and Deferred Host Validation

**Explicit portable completion of the inherited validation sentence:** “cannot be parsed” does not authorize executing or eagerly validating the stored host source while defining the button. Creation performs pure checks of numeric/style/type/clipboard/field-count constraints, the raw positional payload/field lengths and geometry. It stores the third slot as **opaque unexpanded HCL source**. It must not resolve its variables/templates, evaluate its conditionals, run active providers/delays/assignments/playback or transmit it to test whether it will succeed. This also applies to initially selected buttons. Filename and label rendering retain their separate ordinary-consumer rules; they are not a reason to expand the host slot. [Source facts and completion boundary](../research/issue-116-button-payload-hit-geometry.md#validation-versus-deferred-execution).

A pure preflight failure ignores that definition before painting or adding a resident field, retaining earlier fields and the style record. This includes an empty payload, excessive raw filename/label length, missing required ICON filename, failed existing clipboard/type/numeric constraints and the geometry failures below. Later file/font/rendering failures keep their separately documented behavior; this is not a rollback promise for effects already performed after preflight.

At a valid activation, execute the stored host source in the **then-current** field context and environment through the [adopted stages](5.2-templates-and-conditionals.md#shipped-processing-order): angle preprocessing, HCL block/template handling, and two ordinary passes on resulting responses. Honor the existing inactive-header rules, inserted-result skipping, callback gates and 4096-byte working-prefix truncation at their established points. Validate only the syntax each stage actually reaches. Do not add a raw-host scan that rejects an ordinary suffix which will be discarded or clipped before evaluation. A raw source string that looks malformed can still be a valid stored action.

| Stored third slot / setup | At definition | At activation |
| --- | --- | --- |
| `$D(1)$$-=FLAG=changed$` | Store only; no delay or assignment | Execute reached callbacks in the established order |
| `$FIELDID$` | Do not query FIELDID | Use the committed field callback's identity/lifetime rules |
| `$?3$$D(1)$`, template 3 is 4096 `X` bytes | Store only; do not expand template 3 | Insertion fills the retained working prefix; the discarded D suffix does not run |
| `$?3$$RAND("bad")$`, same template | Do not reject based on the raw ordinary suffix | The RAND suffix is clipped before its argument parser is reached |
| `$RAND("bad")$` without preceding clipping | Keep the button; no host parse yet | Normal reached dollar-argument error; no successful numeric replacement |

An activation failure does not retroactively remove the button or roll back earlier callback effects/transmissions. Normal stage error handling controls the rest of that activation. Creating, drawing or preselecting the button never commits its click action; the [press/release contract](4.2-mouse-fields-and-pointer.md#left-button-gesture-commitment) remains adopted. No native conditional constructor host-action branch is required to override the explicit protocol rule.

NOTE: The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc.. It should be set to 0 for compatibility with future releases.

### Face Extents and Input Eligibility

**Explicit portable geometry/input completion:** The source uses far-minus-near device drawing sizes but different pointer and hover edge tests. This reference adopts one positive **half-open** stored hit rectangle for all mouse fields and mouse-active buttons: `L <= x < R`, `T <= y < B`, with width `R-L`, height `B-T`. Stored R/B remain extent boundaries; do not decrement them for storage or add 1 to dimensions. Use the same predicate for press, drag feedback, release and hover. This deliberately excludes the old pointer helper's near-edge tolerance and inclusive hover far edge; exact native raster/input parity is not claimed. [Evidence and policy boundary](../research/issue-116-button-payload-hit-geometry.md#geometry-source-facts-and-explicit-input-policy).

For **effective PLAIN** dynamic `1U`, order each WORLD corner pair first, then convert once and add the effective viewport origin under the existing rules. Reversed corners are accepted by reordering, not by interpreting negative dimensions. If both stored style dimensions are nonzero, the command's far coordinates remain ignored; if either is zero, use the command's corners for both axes. For PLAIN only, both far coordinates zero without a complete fixed size are omitted/empty geometry, not a full-viewport shorthand. Image faces use their independent natural sizing and must not be suppressed by that guard. Reject a nonpositive **device face** width/height, including a positive WORLD span that collapses under conversion, **before** effects can inflate it into a clickable line. This positive-area/empty guard is the portable completion; original degenerate recovery paths are not required.

Keep the existing per-type face sizing and effect geometry. The interaction rectangle includes the effective BEVEL expansion; CHISEL/SUNKEN do not enlarge it and the extra RECESS is excluded from the persistent hit bounds. Exact stroke/bitmap ink need not equal that logical rectangle. Clip painting under the existing renderer rules; clipping must not stretch/recenter the face or change its original size/effect calculations.

**Effective-destination policy:** Mouse-active `1U` and simple `1M` use **PORT0's viewport** and physical screen for creation/input eligibility, regardless of an unrelated current offscreen/other port's activation. Nonmouse decorations retain their current-port destination. If the effective destination viewport is inactive, or has no positive intersection with its canvas, ignore the new definition. For mouse geometry, intersect the interaction rectangle with PORT0's viewport and the screen as half-open extents:

```text
L = max(interactionLeft, viewportLeft, 0)
T = max(interactionTop, viewportTop, 0)
R = min(interactionRight, viewportRight, screenWidth)
B = min(interactionBottom, viewportBottom, screenHeight)
```

If `R <= L` or `B <= T`, there is no resident field and no painting/hover/click/host action from that definition; it consumes no mouse-region slot and does not disturb older fields. A merely touching edge is empty. Partial clipping stores only the visible/input intersection, with no hit tolerance across a viewport/screen edge. A skipped definition is not resurrected when the viewport is reactivated. These effective-destination, empty/intersection and no-phantom-field rules are explicit completion, not a claim that the original current-port gate implements them all.

Creation clipping and the stored global hit rectangle are snapshots. Later viewport movement or deactivation does not relocate/reclip/delete already defined fields or retarget a held gesture. Explicit field deletion/reset/restore and global input controls keep their own rules. This follows the [stable field-instance gesture policy](4.2-mouse-fields-and-pointer.md#left-button-gesture-commitment).

For an active screen/viewport containing these rectangles, with WORLD equal to DEVICE, no effects unless stated, and all coordinates in device units:

| Case | Result |
| --- | --- |
| Dynamic face `(10,20)..(30,40)` | Size 20×20; `(10,20)` and `(29,39)` hit, `(30,20)` and `(10,40)` do not |
| Dynamic corners `(30,40)..(10,20)` | Reorder to the same 20×20 face |
| Equal X or equal Y after conversion | Ignore before effect expansion, even with BEVEL set |
| Positive WORLD span converts to equal device edges | Ignore as zero device area |
| Complete fixed size 20×10 at `(10,20)` | Far edge `(30,30)`; transmitted reversed/equal far corners are ignored |
| Face `(10,20)..(30,40)`, BEVEL 3 | Interaction `[7,33) × [17,43)` before clipping; RECESS adds no hit area |
| Same beveled face, viewport `[12,28) × [18,39)` | Store hit `[12,28) × [18,39)`; `(28,20)` and `(15,39)` are outside |
| Interaction starts at viewport's exclusive right/bottom edge | Empty intersection; no new field/painting |
| PORT0 viewport inactive, or field wholly clipped by it | No new mouse field or painting, including when another port is current and active |

### The shipped 3.x button aesthetic

The 3.x corpus shows how TeleGrafix itself built buttons: rather than 1.54-style chiseled plain buttons, scenes stamp **bitmap skins** with [RIP_LOAD_BITMAP](4.0-icons-and-bitmaps.md#rip_load_bitmap) (TELBUT.BMP, RADIONEW.BMP, CHECKBOX.BMP) and lay `1U` buttons or [`1M` mouse fields](4.2-mouse-fields-and-pointer.md#rip_mouse) over them; the corresponding `.BMH` files on disk are the pre-rendered **highlight-state** variants automatically shown while a hot-icon button is depressed (they are never named in any script - pairing is by filename convention; see [6.1](6.1-content-file-roles.md#bmh---button-highlight-variants)). `1B` + `1U` with empty `<><>` blocks also serve as pure chisel-frame decorations. The example above is a plain radio-group demo button whose host command is empty - its behavior comes from the button-style flags. _Evidence: corpus (ICONS/\*.BMH pairs; BUTTONS.RIP, TELDEMOS.MNU)._

## RIP_SWITCH_BUTTON_STYLE

_Switches to a new button style_

_Added in RIPscrip v2.A4._

|               |                |
| ------------- | -------------- |
| **Level**     | 2              |
| **Command**   | `B`            |
| **Arguments** | `bstyle_num:2` |

**Format:** `!|2B <bstyle_num>` **Example:** `!|2B04`

**Attributes used:** Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.3-buttons.md#rip_switch_button_style)) · HLP (`RIP_SwitchButtonStyle`; button-style slots 0-35, `$SBS$`/`$RBS$` backup variables) - not observed in the RIPtel demo corpus, not in SyncTERM

This command physically switches the currently active button style. Any subsequent button operations will use this new button style.

You are allowed up to 36 separate button styles to switch between. Possible button style slot numbers are from 0-35 (0-Z).

When a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) or the global drawing-reset flag of [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) is executed, then all unprotected button style slots are reset to the default button style. Also, the current button style is reset to button style number 0.

The demos simply re-send [RIP_BUTTON_STYLE](#rip_button_style) before each button group instead of switching slots. _Evidence: corpus (absence)._

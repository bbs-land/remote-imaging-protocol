## Angle ordering and sweeps

**Reconstructed from RIPtel 3.1:** the shipped driver has command-specific angle contracts. Angles are nonnegative degree values, zero at the right and increasing counterclockwise. The angle fields remain two digits in the current base math (0–1295 MegaNum or 0–4095 UltraNum), independent of XY coordinate width. Both increasing and decreasing raw pairs are accepted; the inherited assertion that start must be greater than or equal to end is incorrect.

| Commands | Actual angle policy |
| --- | --- |
| A, V, I, i, _ | Reduce start/end separately to endpoint rays; discard raw turn count. For different rays the API follows the counterclockwise arc, wrapping through zero when necessary. |
| O | Ignores its angle fields and draws a complete ellipse. It is not a V alias in this driver. |
| ], +, [ | Apply the span normalizer below and traverse S..E inclusively. |
| C, G, o, &, - | Complete circle/ellipse primitives, with no start/end fields. |

For A/V/I/i/_, the driver compares computed integer ray endpoints before issuing an arc operation. Equal endpoints give a zero-length line for A/V, a **center-to-edge radial contour for I/i**, and no drawing for _. The protocol draws that radial outline only with N1, using the filled-border COPY rule; N0 supplies no outline contribution. Original-client call observations do not create an N0 exception. Thus a zero-length angular interval is not a uniform empty command across the family. The [exact ray rule and API boundary](../techspecs/2.1-arc-consumer-contract.md#axis-aligned-endpoint-rays) also explain radius-dependent quantization and the distinction between equal integer endpoints and equal projected rays.

The following cases distinguish the contracts for positive radii. “Zero span” in the skewed column means one generated arc sample; + closes that sample and [ also appends the center, so it does not promise an empty border.

| Raw start..end | A/V | I/i | _ | Normalized skewed S..E / span |
| --- | --- | --- | --- | --- |
| 0..0 | Zero-length line | Radial line | No draw | 0..0 / 0 |
| 90..90 | Zero-length line | Radial line | No draw | 90..90 / 0 |
| 270..90 | Counterclockwise half arc through zero | Half pie | Half chord | 270..450 / 180 |
| 0..360 | Zero-length line | Radial line | No draw | 0..360 / 360 |
| 360..0 | Zero-length line | Radial line | No draw | 360..360 / 0 |
| 450..810 | Zero-length line | Radial line | No draw | 90..450 / 360 |
| 0..720 | Zero-length line | Radial line | No draw | 0..360 / 360 |
| 450..450 | Zero-length line | Radial line | No draw | 90..450 / 360 |
| 0..719 | Quantized endpoint-ray operation; raw turns lost | Same ray reduction, with pie closure | Same ray reduction, with chord closure | 0..719 / 719 |

O draws the full ellipse in every row. The inherited text's 0..360-full assertion describes documented intent, but contradicts the original A/V code path; the same raw pair also does not produce a filled ellipse through I/i/_. A renderer that repairs these whole-turn cases follows that intent while differing from RIPtel 3.1. The full-shape commands C/O/G/o/&/- provide an explicit full figure without relying on arc endpoint coincidence.

A 360-degree pie/chord has **no universal ellipse-only boundary guarantee** in the original driver. The raw full-turn I/i cases above draw only a radial line, and _ draws nothing. A full normalized + contour closes back onto its first point without an interior chord; a full normalized [ contour still includes its center and internal radial edges. These are original construction decisions, separate from pixel-edge reproduction. The [consumer contract](../techspecs/2.1-arc-consumer-contract.md#skewed-contour-construction) records the exact point sequences and the native probe.

### Skewed arc span normalization

For ]/+/[, preserve the raw pair until this algorithm runs. All divisions and remainders below are integer operations on nonnegative values. It returns S≤E and a positive-or-zero span E−S; it does not clamp every span to one turn.

```text
S = raw_start; E = raw_end
if S <= 360 and E <= 360:
    if S > E: E += 360
else if S < E:
    k = S / 360
    S -= 360*k; E -= 360*k
    if E >= 720: E = 360 + (E-360) % 360
else:
    k = E / 360
    S -= 360*k; E -= 360*k
    d = S-E
    if d > 360: S -= 360*((d-1)/360)
    if S >= 360: S -= 360
    E += 360
```

This preserves the shipped discontinuities: equal 450..450 becomes a full turn, while equal 90..90 stays zero; 0..719 retains nearly two turns, while 0..720 becomes one. Original generation visits S,S+1,…,E, including both endpoints. Multiple traversal remains part of the contour and can affect polygon overlap and repeated outline writes; a renderer that collapses every span >=360 to one ellipse changes that behavior.

**Evidence:** unchanged driver handlers and original normalizer 0x138e8, verified over all 4096² raw angle pairs; original axis-aligned endpoints verified across every angle, both endpoint positions, radii 2/40/200 and both border settings. [Derivation and reproducible native probe](../research/issue-14-arc-sweeps.md); [numerical ray/topology contract](../techspecs/2.1-arc-consumer-contract.md). The fixture captures original calls without executing Windows rasterization or asserting earlier-client parity.

**Original RIPtel behavior:** this command consumes both angle fields but ignores their values, drawing the complete ellipse centered at (x,y). ## RIP_ARC

_Draw circular arc in current color/line thickness_

|               |                                             |
| ------------- | ------------------------------------------- |
| **Level**     | 0                                           |
| **Command**   | `A`                                         |
| **Arguments** | `x:XY y:XY start_ang:2 end_ang:2 radius:XY` |

**Format:** `!|A <x> <y> <start_ang> <end_ang> <radius>` **Example:** `!|A1E18003G0T`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/2.2-curves.md#rip_arc)) · HLP (`RIP_Arc`) · SyncTERM (ripper.c:13470) - not observed in the RIPtel demo corpus

This command draws a circular arc, or a segment of a circle. Drawing begins at `<start_ang>` and terminates at `<end_ang>`. The angles are represented starting at zero for the 3 o'clock position and increasing counterclockwise through a full circle to 360:

```text
     90°
      │
180°──┼──0°
      │
     270°
```

For distinct endpoint rays the arc proceeds counterclockwise, accepting increasing or wrapped decreasing pairs. The [shared angle contract](#angle-ordering-and-sweeps) defines endpoint reduction and the original whole-turn exceptions; 0..360 reaches a zero-length line instead of a full circle in RIPtel 3.1. This command recognizes aspect ratios like the circle command does. It does not take advantage of line patterns but does comply with line thickness.

Equal computed integer endpoints reach a zero-length line call. This does not establish a common empty-angle rule for the filled or skewed variants; see the [case table](#angle-ordering-and-sweeps).

The radius is considered to be in the horizontal direction for the purpose of aspect ratio calculations. _(v2.A3)_

Both angles may exceed 360 within their two-digit range. Either raw ordering is accepted; [the original angle policy](#angle-ordering-and-sweeps) determines wrapping and whole-turn behavior.

SyncTERM version-gates a 1.54 bug-compatibility quirk after arc drawing (a stale line-pattern register clobber), fixed in its 3.0 mode - evidence that 1.54 and 3.x arc behavior were treated as distinct contracts.

## The Skewed-Oval Family - 3.x Census Discoveries

_Evidence: corpus (NEWCMDS.RIP, SHAPES.RIP); see the [script census](../../3.0/research/riptel-script-census.md)._

The six commands below exist in no published specification - not 1.54, not 2.00a4. They were recovered from the RIPtel demo corpus, where NEWCMDS.RIP demonstrates each new primitive over a coordinate grid with TeleGrafix's own naming comments ("Show RIP*SKEWED_OVAL", "Show a RIP_SKEWED_OVAL_PIE_SLICE", …), making the canonical names verbatim TeleGrafix. They add what the 1.54/2.0 [RIP_OVAL](#rip_oval) family cannot do: ellipses whose axes are **rotated to an arbitrary angle**. Original dispatch and point-generation instructions now establish the widths and degree units; see the [angle derivation](../research/issue-14-arc-sweeps.md). The filled members honor [RIP_SET_BORDER](2.3-shapes-and-fills.md#rip_set_border) like the documented filled primitives - NEWCMDS.RIP demos each "With a border" and "Without a border". None of these commands appear in the RIPSCRIP.HLP name inventory or in SyncTERM. The filled members of the family stay on this page with their outline siblings, as the 3.x record groups them.

## RIP_BEZIER

_Draw a cubic Bézier curve_

|               |                                                         |
| ------------- | ------------------------------------------------------- |
| **Level**     | 0                                                       |
| **Command**   | `Z`                                                     |
| **Arguments** | `x1:XY y1:XY x2:XY y2:XY x3:XY y3:XY x4:XY y4:XY cnt:2` |

**Format:** `!|Z <x1> <y1> <x2> <y2> <x3> <y3> <x4> <y4> <cnt>` **Example:** `!|ZCSIYDBIYDVIZEEJ014`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** original RIPtel 3.1 driver 3.0.7, handlers 0x19f7b / 0x2cc30 and integer generator 0x2c9e0; [derivation and native probe](../research/issue-15-bezier-contracts.md). The earlier [2.0 draft description](../../2.0/ripscrip/2.2-curves.md#rip_bezier) explains the geometry, but its equation typo, B-spline terminology, floating-point implementation claim and subdivision wording do not describe this shipped driver accurately.

The curve starts at (x1,y1) and ends at (x4,y4). The intermediate control points (x2,y2) and (x3,y3) pull its shape and usually do not lie on the curve. Its ideal cubic Bernstein equations are:

```text
X(t) = X1*(1-t)^3 + 3*X2*t*(1-t)^2 + 3*X3*t^2*(1-t) + X4*t^3
Y(t) = Y1*(1-t)^3 + 3*Y2*t*(1-t)^2 + 3*Y3*t^2*(1-t) + Y4*t^3
0 <= t <= 1
```

This is a cubic Bézier curve. The final terms use **X4/Y4**, giving the fourth point at t=1. The shipped driver evaluates three levels of integer linear interpolation (de Casteljau), rather than using the draft's claimed double floating-point implementation. See the [numerical consumer contract](../techspecs/2.2-bezier-consumer-contract.md) for exact fixed-point arithmetic and truncation.

`cnt` is always a **two-digit numeral in the current base**, independently of XY width: 0..1295 in base 36, or 0..4095 in base 64. **Use at least 2.** RIPtel forwards 0/1 to Polyline without a command-level rejection; these counts cannot draw a curve. For N>=2, it submits **N points and N-1 connecting edges**, not N straight segments or N+1 points. It generates the start, samples at **t=i/N for i=1..N-2**, then the endpoint at t=1. Thus N=2 is a straight endpoint-to-endpoint line, and the normal `(N-1)/N` sample is missing. The example's `14` means **40 points** in base 36.

The driver converts each control point from world to device coordinates with integer truncation **before** evaluating the curve. It then uses eight fractional bits, truncating signed division at each interpolation and flooring fractional device coordinates at output; it does not evaluate a floating-point world curve and round each final point. Z has no additional poly-Bézier expansion-budget reduction: its maximum encoded N is 4095. These are exact original consumer semantics; captured drawing calls do not establish Windows pixel rasterization or historical XOR join defects.

## RIP_POLY_BEZIER

_Added in RIPscrip v2.A1._

_Draw a chain of cubic Bézier curves and lines, closed_

|               |                                    |
| ------------- | ---------------------------------- |
| **Level**     | 0                                  |
| **Command**   | `z`                                |
| **Arguments** | `num:2 count:2 [type:1 record]...` |

**Format:** `!|z <num> <count> [<type> <record>]...` **Example:** See the annotated original below.

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** original special byte parser, handlers 0x1e449 / 0x2cda0, type-class table 0x7ef48, and complete SHAPES.RIP samples; [derivation](../research/issue-15-bezier-contracts.md).

The header contains **only `num` and `count`**, each fixed width 2 in the current base. There is **no separate `x_base y_base` header pair** in the shipped 3.0 grammar. The first typed record supplies the first point. This corrects the inherited [2.0 draft layout](../../2.0/ripscrip/2.2-curves.md#rip_poly_bezier); it is not a special second grammar for the census examples.

### Typed records

`num` is the number of records, including the terminal record, and must be at least 1. Each record begins with one literal digit. All coordinates have the active XY width and current base; they are absolute world coordinates.

| Type digits | Following fields | Rendering meaning |
| --- | --- | --- |
| `0`, `3`, `4` | `x:XY y:XY` | A point on the connected outline; a straight edge leads to the next record's start |
| `1`, `2`, `5`, `6` | `x:XY y:XY cx1:XY cy1:XY cx2:XY cy2:XY` | Cubic start P0=(x,y), controls P1/P2, endpoint P3 taken from the **next record's first pair** |

All three point types render identically; all four curve types render identically. The draft calls 1 “smooth” and 2 “jointed” as authoring distinctions, but this renderer neither synthesizes missing controls nor enforces a smooth join. Types 3..6 are accepted directly on the wire, including 5/6 in the shipped demos.

For a **last curve record**, z takes P3 from the **first record's first pair**. A **last point record** need not repeat that first pair: the closed polygon consumer adds the final straight edge. The command does not append a separate closure vertex. This same closure rule applies to filled [`x`](2.3-shapes-and-fills.md#rip_filled_poly_bezier). Only open [`t`](#rip_poly_bezier_line) prohibits a terminal curve.

### Counts, limits and rejection

`count` is the requested point count **per curve**, using the same sampling as [`Z`](#rip_bezier). Let C be the number of curve records and L the number of point records, so `num=C+L`. The complete decoded input occupies **2+7*C+3*L numeric values**, including both headers and every type. This must fit the original parser's **8193-value** collection capacity; each header is also bounded by its two-digit encoding. For example, no more than 1170 all-curve records fit, while base-64 permits 2730 all-point records. This input limit is separate from the generated limit below.

If C>0 and count is zero, RIPtel rejects the whole primitive without drawing. If C=0, count is unused and may be zero. For C>0, calculate the effective N as follows:

```text
N = count
if C*N + L + 1 > 4095:
    N = floor((4094 - L) / C)
if N == 0:
    reject whole primitive
submitted_points = C*N + L
```

Thus **4094 is the maximum actual submitted point count**, not 4096, and reduction applies uniformly to every curve. For example, two curves and one point requested at 2047 use N=2046 and submit 4093 points. Each curve's N-point output includes its next record's start when N>=2; that following record also supplies its own start, so join duplicates are retained. N=1 contributes only the curve start to the submitted array. The generator's extra scratch endpoint for N=1 is not an additional drawn point.

Invalid types, incomplete records or disagreement with `num` reject the whole primitive; they do not draw a prefix or silently omit a bad terminal record. Most common-consumer failures are silent, while `num=0` reports “Too few segments”. Oversized numeric input is truncated by the byte parser and rejected when its resulting vector fails validation. See the [consumer contract](../techspecs/2.2-bezier-consumer-contract.md) for the exact numerical and capacity boundaries.

### Annotated original z example

The first z at physical line 70 of the original **SHAPES.RIP** is complete below. The file sets `J10` (base 36) and `n2000` (XY width 2). The census's 60-character preview truncates its tail; the original payload is valid.

```text
!|z081428KGC8KESASF85CGF8E4F8BCGC5DKGCEOGCE4GW5DKHGD0I0BWI06ASI0BWGWASFS09OGW09OI008KI0
```

| Field / record | Exact grouped bytes | Decoded world coordinates |
| --- | --- | --- |
| Header | `08 14` | 8 records, requested N=40 |
| 1: curve | `2 8K GC 8K ES AS F8` | Start (308,588); controls (308,532), (388,548) |
| 2: curve | `5 CG F8 E4 F8 BC GC` | Start (448,548); controls (508,548), (408,588) |
| 3: curve | `5 DK GC EO GC E4 GW` | Start (488,588); controls (528,588), (508,608) |
| 4: curve | `5 DK HG D0 I0 BW I0` | Start (488,628); controls (468,648), (428,648) |
| 5: curve | `6 AS I0 BW GW AS FS` | Start (388,648); controls (428,608), (388,568) |
| 6: point | `0 9O GW` | (348,608) |
| 7: point | `0 9O I0` | (348,648) |
| 8: point | `0 8K I0` | (308,648) |

Each curve ends at the next listed start. The last point closes straight to (308,588). C=5 and L=3 produce **203 submitted points** without budget reduction. The original parser produces 46 numbers, exactly `2+7*5+3*3`; the apparent `28 KG` header and invalid type `C` arise only from applying the draft's nonexistent base-point header. Artifact identity and native vectors are preserved in the [research note](../research/issue-15-bezier-contracts.md).

## RIP_POLY_BEZIER_LINE

_Added in RIPscrip v2.A2._

_Draw a chain of cubic Bézier curves and lines, open_

|               |                                    |
| ------------- | ---------------------------------- |
| **Level**     | 0                                  |
| **Command**   | `t`                                |
| **Arguments** | `num:2 count:2 [type:1 record]...` |

**Format:** `!|t <num> <count> [<type> <record>]...` **Example:** `!|t03142JA62HA62JEA66HUA6JGA6HCEE0JCEG`

**Attributes used:** Draw Color, Back Color, Line Style, Write Mode, Viewport, Port, Base Math (current setting) **Evidence:** original handlers 0x1e4a4 / 0x2cda0, mode-2 terminal check 0x2ce98, and original CURVES/SHAPES samples; [derivation](../research/issue-15-bezier-contracts.md).

Use the [same header, typed records, sampling and limits as z](#rip_poly_bezier). The outline remains open. Its **last record must be a point type 0/3/4**; a terminal curve type 1/2/5/6 causes rejection of the **entire command**, without a drawing call. The help string “The last segment of a poly-bezier cannot be a curve” applies to this open form, not to closed z or filled x. No terminal point is required to repeat the first point, and t adds no closing edge.

The original example decodes as follows; it too has no separate base-point header:

```text
03 14                         # 3 records, N=40 in base 36
2 JA 62 HA 62 JE A6            # start (694,218), controls (622,218),(698,366)
6 HU A6 JG A6 HC EE            # start (642,366), controls (700,366),(624,518)
0 JC EG                       # terminal point (696,520)
```

The two cubics end at (642,366) and (696,520), respectively. C=2, L=1 gives **81 submitted points**. The original parser produces the 19-number vector `3,40,2,694,218,622,218,698,366,6,642,366,700,366,624,518,0,696,520`.

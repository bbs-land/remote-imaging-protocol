# Bitmap masks and color-key compositing in RIPtel 3.1

[◀ Prev: Fill Defects](2.0-fill-defects-delta.md) · [Contents](README.md) · [Next: FastFont Additions ▶](3.2-fastfont-additions.md)

This is the RIPtel 3.1 / RIPscrip driver 3.0.7 delta to the [inherited Windows BMP icon formats](../../2.0/techspecs/3.0-icon-formats.md). It resolves [issue #8](https://github.com/bbs-land/remote-imaging-protocol/issues/8) from the unchanged shipped driver; the [derivation and reproducible native probe](../research/issue-8-bmm-masks.md) distinguish original instructions from controlled drawing services. These findings do not establish behavior in earlier RIPterm clients.

## A BMM is an explicitly loaded BMP

**The client does not automatically load a same-named BMM alongside an image.** The bitmap loader, legacy icon loader, local bitmap playback and icon-button renderer pass one image filename to the common BMP renderer. Buttons choose the normal BMP or hot BMH; they do not fetch an attached BMM. An explicitly supplied MSK extension is normalized to BMM. BMM is a filename role for a mask raster used by explicit stamping, with the ordinary BMP decoder and put modes; it has no special Boolean pixel interpretation. _Evidence: DLL filename/renderer/button audit in the [research note](../research/issue-8-bmm-masks.md#completed-routing-audit)._

The recovered distributions contain no BMM sample. That absence does not require a guessed 1-bit or nonzero-index mask rule: the original executable supplies the loading/compositing contract. A BMM may use the same profiled uncompressed Windows BMP depths as an ordinary image:

| Depth | Ordinary load, flag 8 clear | Color-key load, flag 8 set |
| --- | --- | --- |
| 1 | Supported; two RGB palette entries determine displayed colors | Compares source bits to zero/nonzero translated key |
| 4 | Supported; expanded to 8-bit, then palette-mapped | Compares mapped indices after expansion |
| 8 | Supported; palette-mapped | Compares mapped indices |
| 16 | Supported; BI_RGB RGB555 | Rejected by the original mask creator; image is not drawn |
| 24 | Supported; BGR triples | Exact equality to the translated key's current palette RGB |
| 32 | Supported; BI_RGB BGR plus unused high byte | Shipped classifier defect: ordinary RGB keys select no transparent pixels |

The verified format profile is a 14-byte BMP file header followed by a 40-byte BITMAPINFOHEADER, one plane, BI_RGB (compression 0), a contiguous RGBQUAD table for indexed depths, and positive-height, bottom-up rows padded to four bytes. Use the inherited format page for those layouts. This table extends its depth coverage for this client; it does not promise OS/2, compressed, extended-header, top-down or arbitrary malformed BMP handling. The 32-bit high byte is not an alpha channel. _Evidence: original reader/expansion/remapping/display and all six depth fixtures, [full renderer observations](../research/issue-8-bmm-masks.md#full-original-renderer-with-controlled-drawing-boundary); standard BI_RGB packing is defined by Microsoft's [GDI header reference](https://learn.microsoft.com/en-us/previous-versions/dd183376%28v%3Dvs.85%29)._

## Put modes and manual mask polarity

Let `D` be the existing destination pixel and `S` the decoded source pixel after palette processing and placement/scaling. Logical operations apply to the rendered color components, with NOT limited to the destination color width. There is no universal test that a stored bit/index is nonzero and therefore transparent. On a true-color RGB surface the five modes are:

| Mode | Operation  | Result, flag 8 clear |
| ---- | ---------- | -------------------- |
| 0    | COPY       | `S`                  |
| 1    | XOR        | `S ^ D`              |
| 2    | OR         | `S OR D`             |
| 3    | AND        | `S & D`              |
| 4    | NOT-source | `~S`                 |

For an indexed BMM, the palette-resolved color matters to these raster operations. With palette entry 0 = white and entry 1 = black, AND preserves the destination where the stored pixel is **0**, and clears it where it is **1**. Reversing the palette reverses that outcome. The bitmap renderer supplies DIB_RGB_COLORS and the requested ROP; a device's palette realization can affect its actual colors. These formulas describe RGB raster semantics, not XOR of raw file indices. _Evidence: original mode mappings 0xc816–0xc854 / 0xcd5a–0xcd95, original display call 0x4e77b–0x4e7a8, native inverted-palette fixtures; Microsoft's [StretchDIBits contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-stretchdibits) defines that API boundary._

For manual two-image transparency, explicitly load a mask `M` in AND mode, then explicitly load an image `S` in OR mode at the same intended placement. The result is `(D & M) OR S`: use white mask pixels and black source pixels in the parts to preserve; use black mask pixels where the image should overwrite. This convention works at any profiled depth capable of representing the required colors; it is not a dedicated 1-bit file requirement.

If the second explicit image uses another mode, it operates on the destination left by the first command. After an AND mask, the results are COPY `S`, XOR `S ^ (D & M)`, OR `S OR (D & M)`, AND `S & (D & M)`, NOT `~S`. The extension never changes this sequence. _Evidence: common original renderer and [two-load pixel oracle](#four-pixel-independent-oracle)._

## Dimensions and missing files

There is no mask/image pair whose dimensions are validated together. A same-name BMM that is absent, differently sized or malformed has no effect if it is never referenced. An explicitly loaded BMM uses its own image dimensions and the command's ordinary target rectangle, scaling and clipping rules. If two manual stamps have different extents, each affects its own extent in command order; the client neither rejects the pair nor resizes the BMM to an otherwise unspecified companion image.

An explicitly requested missing BMM follows ordinary bitmap failure handling: the image command's failed file lookup takes the missing-image placeholder path, or suspends if retrieval is pending. If the downstream reader cannot open the requested file, rendering fails before drawing its pixels and the caller handles that ordinary load error. There is no implicit all-transparent or all-opaque fallback mask. _Evidence: original lookup branches 0xc789–0xc811 / 0xccb2–0xcd3a and renderer 0x4a441–0x4a475; native missing-file and independent-size fixtures in the [derivation](../research/issue-8-bmm-masks.md#full-original-renderer-with-controlled-drawing-boundary)._

## Flag 8 is a separate color-key operation

[RIP_LOAD_BITMAP](../ripscrip/4.0-icons-and-bitmaps.md#rip_load_bitmap) flag 8 applies to the **explicitly loaded file**, including a BMM. It does not enable a companion-file lookup. Without it, the renderer receives the negative no-key sentinel; with it, the command validates `trans_color` as an index in **0..255** and translates it through the current drawing palette. It is not an RGB value or necessarily an index into the file's palette.

For precise RIPtel compatibility, let `N` be the current palette's direct-index limit (normal initialized profile 236; other initialized profiles 2 or 16). A key below `N` is unchanged. Otherwise look up that key's current drawing-palette RGB and choose the nearest of its 256 entries by squared RGB distance: stop at the first exact match; absent an exact match, a later equal-distance minimum replaces an earlier one. This yields the translated index `K`. The original drawing palette uses its stored component values for that distance calculation. _Evidence: original validator 0x44385, translation 0x16140 and nearest-color routine 0x16070, [translation probes](../research/issue-8-bmm-masks.md#color-key-input-and-palette-translation)._

Transparency selection is then depth-dependent:

- **1-bit:** source bit 0 matches when `K == 0`; source bit 1 matches when `K != 0`. The file's palette RGB does not enter this equality test, even though it determines visible raster colors.
- **4/8-bit:** the 4-bit raster is expanded to 8-bit, then each file palette color is mapped to the nearest current output-palette entry before testing the resulting pixel index against `K`. Thus a file pixel numbered 0 can become output index 255. Duplicated or quantized colors can collapse different indices. This is equality of the resulting indices, not a generic nonzero test.
- **24-bit:** fetch current output palette entry `K`, then compare the source B/G/R components exactly to that entry. A merely nearby RGB color is not transparent.
- **16-bit:** mask creation fails as an unknown color format, so the color-key load fails before drawing.
- **32-bit:** the shipped classifier never marks a pixel for a normal byte-valued RGB key, including matching black or white. Exact historical compatibility retains this defect; substituting the 24-bit comparator changes the client behavior.

The renderer constructs this equality mask internally, scales it to the image's target geometry, captures the old background, forms the requested `F(S,D)` intermediate, retains background at selected transparent pixels, and copies the merged result to the target. If `T` is the resulting internal selection, final output is **`T ? D : F(S,D)`**, for all five put modes, including NOT. Thus keyed pixels preserve the original background even under XOR, OR, AND or NOT. The mask creator's selector 1 means retain background, selector 0 means use the computed pixel; those internal selector bytes are not BMM file pixels. Arbitrary scaling filters and device palette quantization remain properties of the drawing boundary. _Evidence: original renderer 0x4a5e9–0x4a868, classifiers 0x49ba0–0x49f81, merge 0x49f90 and native complete keyed-mode fixtures in the [derivation](../research/issue-8-bmm-masks.md#full-original-renderer-with-controlled-drawing-boundary)._

If flag 8 is explicitly set on a manually loaded BMM, apply this color-key selection to that stamp too; subsequent image loads use their own mode/key independently. There is no additional file-mask stage. When [duplicate-port flag 1](../ripscrip/4.0-icons-and-bitmaps.md#bitmap-flags) is also requested, it copies the resulting displayed image, including the background that showed through, as described by that command.

## Four-pixel independent oracle

Start with a four-pixel RGB destination, each pixel **RGB(12,34,56)** (hexadecimal components). Both files below are 4×1, one plane, BI_RGB with a 40-byte info header, zero reserved fields, positive height, and conventional four-byte row alignment; other optional info-header fields may be zero.

- **MASK.BMM:** 1-bit BMP, file size 66, pixel offset 62. Palette entries are `FF FF FF 00` (index 0 white) and `00 00 00 00` (index 1 black). Its single padded raster row is **`50 00 00 00`**, yielding indices 0,1,0,1 from most-significant bit first.
- **SOURCE.BMP:** 24-bit BMP, file size 66, pixel offset 54, no palette. Its single BGR row is **`00 00 00 0F F0 F0 00 00 00 F0 0F 0F`**: black, RGB(F0,F0,0F), black, RGB(0F,0F,F0).

Load MASK.BMM with mode 3 (AND), then SOURCE.BMP with mode 2 (OR), with flag 8 clear and identical target rectangles. With XY width 2 and base 36, the explicit commands are:

```text
!|1b000004010300000000MASK.BMM
!|1b000004010200000000SOURCE.BMP
```

| Pixel x | Stored mask index | Mask RGB | After AND mask | After OR source |
| --- | --- | --- | --- | --- |
| 0 | 0 | FFFFFF | 123456 | **123456 retained** |
| 1 | 1 | 000000 | 000000 | **F0F00F overwritten** |
| 2 | 0 | FFFFFF | 123456 | **123456 retained** |
| 3 | 1 | 000000 | 000000 | **0F0FF0 overwritten** |

A rule that treats nonzero mask index as transparent predicts the opposite retained pixels. The probe also checks that each explicit load opens only its named file, detecting an unwanted companion-file lookup. Loading MASK.BMM alone in COPY mode produces white, black, white, black with no implicit transparency. The native original-renderer probe exercises these cases with controlled RGB drawing services, without using a recovered BMM sample or a peer implementation as its oracle. _Evidence: [probe and reproduction limits](../research/issue-8-bmm-masks.md#full-original-renderer-with-controlled-drawing-boundary)._

# 2.2 Bézier consumer contract

## Standing and scope

This documents RIPtel 3.1's RIPscrip 3.0.7 integer Bézier generation and the arrays its drawing consumers actually submit. The [language reference](../ripscrip/2.2-curves.md#rip_bezier) defines Z and the recovered z/t/x wire grammar. The [derivation](../research/issue-15-bezier-contracts.md) identifies the original DLL, hashes, RVAs, reproducible native probe and controlled services. These findings describe this shipped driver, without claiming an earlier client's numeric kernel or Windows rasterization parity.

## Ideal geometry and conversion order

For four control points P0..P3, the ideal curve is the cubic Bernstein polynomial `(1-t)^3*P0 + 3*t*(1-t)^2*P1 + 3*t^2*(1-t)*P2 + t^3*P3`. Three rounds of linear interpolation give that polynomial directly. P0/P3 are endpoints; P1/P2 are intermediate controls. This corrects the inherited X*4/Y*4 typographical error and generic B-spline label.

RIPtel first converts the four world control points to device coordinates through original **0x31084**, then samples those integer controls. For ordinary nonnegative, non-overflowing inputs, conversion is `floor(x*device_width/world_width)` and equivalently for y; no final sample can recover a fractional control position discarded here. The poly consumer takes a cubic endpoint from the next record's first pair, or the first record for a terminal closed cubic, and zero-extends that converted endpoint's low 16 bits before calling the generator. Standalone Z passes its converted controls directly. Point-class records are stored as zero-extended low-16-bit device coordinates.

## Original integer interpolation

Generator **0x2c9e0** uses signed 32-bit arithmetic with eight fractional bits. For an interior sample i/N, evaluate each axis independently. `wrap32` retains the low 32 bits and interprets them as signed, `trunc0` is signed division toward zero, and `signed16` retains the low 16 bits and interprets them as signed:

```text
q[j] = wrap32(P[j] << 8), j=0..3
for level = 3,2,1:
    for j = 0..level-1:
        difference = wrap32(q[j+1] - q[j])
        product = wrap32(difference * i)
        q[j] = wrap32(q[j] + trunc0(product / N))
output = signed16(floor(q[0] / 256))
```

The original first level accumulates i times each fixed difference rather than multiplying anew; modular arithmetic makes the expression above equivalent. The probe also covers extreme signed-16-bit controls where intermediate products wrap, so floating-point interpolation plus one final rounding is not an exact substitute. The first output is P0's input integer directly; the final output is P3 narrowed to signed 16 bits. Interior outputs use the fixed-point sequence above. Bounds are accumulated from generated outputs, rather than the ideal curve's extrema.

## Written and submitted counts

For N>=2, the generator writes **N points**:

```text
P0,
fixed-point samples at i/N for i=1..N-2,
P3
```

The expected `(N-1)/N` sample is missing. With N=2 only endpoints are generated. A unit-scale example with controls `(0,0),(0,0),(0,0),(64,0)` and N=4 yields **(0,0), (1,0), (8,0), (64,0)**, omitting (27,0) at t=3/4. This observed historical sampling defect is separate from the valid ideal cubic equation.

For N=0/1 the generator skips all interior division and still writes two scratch endpoints. Standalone Z forwards the requested N to Polyline: zero/one submitted points cannot draw a curve under that API's two-point minimum. It does not reject or replace N. Its full two-digit base-64 range reaches 4095 submitted points.

The poly consumer rejects zero N if any cubic is present. With N=1, each cubic advances its output index by only one; the extra written scratch endpoint may be overwritten by the next record, or lie outside the submitted array for a final cubic. Thus one cubic contributes only its start to drawing at N=1. Point records contribute one point each. For N>=2, a cubic includes the next record's start as its endpoint, then that record supplies its start again: join duplicates remain in the submitted array.

## Expansion budget and topology

For C cubic records and L point records, the common poly consumer checks `C*N + L + 1 <= 4095`. If exceeded, it sets **N=floor((4094-L)/C)** for every cubic, rejecting if this becomes zero. The resulting submitted count is **C\*N+L**, so the maximum is **4094**, often slightly lower because the shared N is integral. The original 80,000-byte workspace allocation does not define this usable limit.

| C    | L   | Requested N | Effective N | Submitted points |
| ---- | --- | ----------- | ----------- | ---------------- |
| 1    | 0   | 4095        | 4094        | 4094             |
| 1    | 1   | 4095        | 4093        | 4094             |
| 2    | 1   | 2047        | 2046        | 4093             |
| 5    | 3   | 40          | 40          | 203              |
| 1170 | 0   | 40          | 3           | 3510             |

Input collection remains independently bounded by **8193 numbers**, including headers and type digits. The [record grammar and rejection rules](../ripscrip/2.2-curves.md#counts-limits-and-rejection) specify its accounting; an input count is not permission to expand to `num*count` points.

Open t rejects a terminal cubic before any drawing. Closed z and filled x permit a terminal cubic and use the first record's start as its P3. A terminal point need not explicitly return to the start. z/x submit Polygon contours and t submits Polyline; this consumer appends no extra closure vertex. Polygon provides the final straight closing edge when needed. Fill/border passes preserve that array and count; the native fixture captures arguments and pass counts without emulating GDI pixels.

## Verification boundary

`run/riptel-bezier-probe DLL [ORIGINAL_CORPUS_FILE]` executes the original byte parser, state setters, numeric generator, common validation/expansion, world conversion and standalone handler. It tests all encoded base-64 counts 0..4095, selected negative/fractional/overflow profiles, both bases, all XY widths, seven record types, all modes and borders, input truncation, generated reduction, malformed-vector rejection and original corpus vectors. Host framing/state, memory services, object selection and GDI calls are controlled. The source DLL stays byte-exact, no GUI is started, and temporary executables are removed automatically.

# FastFont Additions (.RFF / atf.cfg)

[◀ Prev: Bitmap Masks](3.0-bitmap-mask-delta.md) · [Contents](README.md) · [Next: MicroANSI Delta ▶](3.3-microansi-maf-delta.md)

The Atech FastFont base format is documented in the 2.0 techspec [FastFont Outline Fonts (.FF1 / .RFF)](../../2.0/techspecs/3.2-fastfont-fonts.md); this page documents RIPtel 3.1’s added families/catalog and the recovered client’s rendering contract. Identical font bytes do not by themselves prove identical rendering in earlier clients.

Files referenced live in `~/src/rip-tools/artifacts/RIPtel/FONTS/` and byte-exact in [`version/3.0/assets/fonts/`](../../3.0/assets/fonts/README.md); all integers little-endian.

## Carried-over families - byte-identical

RIPtel 3.1 ships the five RIPterm 2.30 families unchanged. Every one is **md5-identical** to its RIPterm 2.30 counterpart (verified `~/src/rip-tools/artifacts/RIPtel/FONTS/*.RFF` vs `~/src/rip-tools/artifacts/ripterm-2.30/extracted/FONTS/*.RFF`):

| Family      | md5 (both copies)                  |
| ----------- | ---------------------------------- |
| COBB.RFF    | `d19dadc63c43d826df2ce1320f1e1324` |
| DEFAULT.RFF | `a1ce1aac2b65a0f23e1c358ecb952b15` |
| DIXON.RFF   | `1edaf8f0df33fb47b524915697ffbbc4` |
| MARIN.RFF   | `f4701a707a28ac6cf053890646f4c0f7` |
| SYMBOL.RFF  | `db84594fc82f99ecbf4e420e1e698721` |

Nothing about the base format changed - the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#rff-header-54-bytes) applies verbatim to all eight RIPtel files, including the [decoded glyph-outline encoding](../../2.0/techspecs/3.2-fastfont-fonts.md#glyph-record) (moveto/lineto/cubic-curveto opcode stream): the three added families were part of the decode's verification corpus and every one of their 224 glyph records parses strictly and renders correctly (e.g. BRUSH's script `e`).

## The three added families

RIPtel adds **BRUSH**, **EUREKA**, and **OAKLAND** (file dates April 17, 1997 - the carried five are dated April 18-19, 1997, the same conversion batch as the RIPterm 2.30 `.RFF` reformat). All three conform exactly to the documented `.RFF` header: signature bytes `10 00 02 02 2E 00 36 00 02 04 98 44` at 0x10, `&T` sentinel at 0x34, 224 glyphs from character 32, 1000 units/em, 10 style records of 46 bytes at 0x36, glyph section at 0x202 opening `01 00` + u16 pointer to 0x212. Per-family header metrics (offsets per the [2.0 header table](../../2.0/techspecs/3.2-fastfont-fonts.md#rff-header-54-bytes)):

| Family | Size | Trailer offset (u32@0x00) | bbox ymax | bbox xmax | bbox ymin | bbox xmin | Base handle | Kerning pairs |
| --- | --: | --- | --: | --: | --: | --: | --- | --: |
| BRUSH.RFF | 87,155 | 0x1544D | 305 | 1184 | -767 | -159 | 0x03B4 | 7 |
| EUREKA.RFF | 70,789 | 0x1145B | 358 | 1093 | -952 | -36 | 0x0024 | 8 |
| OAKLAND.RFF | 64,213 | 0xFA7F | 250 | 1249 | -894 | -127 | 0x0017 | 19 |

(Sample kerning pairs - BRUSH: `FL` -61, `GL` -76, `PL` -76, `ZA` -45, `gb` -91, `gd` -51, `gh` -96; EUREKA: `AV` -86, `Av` -96, `VA` -76, `yd` -86 …; OAKLAND: `VA` -137, `WA` -107, `AV` -102, `yd` -122 … - all in 1/1000 em, read at each file's trailer offset.)

BRUSH's trailer offset exceeds 16 bits (0x1544D) - direct confirmation of the 2.0 page's observation that widening the trailer offset from u16 to u32 was a motive for the `.FF1` → `.RFF` reformat: BRUSH could not have shipped as an `.FF1`.

### Style tables

Each added family carries the standard 10 records (base + Th/Cn/Wd/Ex at 85/75/125/150% + Hollow versions), same 46-byte record format, same engine-parameter block `XX 0F 05 F8 1E 14 00 00` with the hollow flag at XX. Decoded from BRUSH.RFF at 0x36 (EUREKA/OAKLAND identical in structure):

| #   | Handle | Flags | Scale % | Name       |
| --- | ------ | ----- | ------: | ---------- |
| 0   | 0x03B4 | 0x00  |     100 | `Brush`    |
| 1   | 0x03B3 | 0x01  |      85 | `Brush TH` |
| 2   | 0x03B2 | 0x02  |      75 | `Brush CN` |
| 3   | 0x03B1 | 0x04  |     125 | `Brush WD` |
| 4   | 0x03B0 | 0x08  |     150 | `Brush EX` |
| 5   | 0x03AF | 0x10  |     100 | `Brush HO` |
| 6   | 0x03AE | 0x11  |      85 | `Brush HT` |
| 7   | 0x03AD | 0x12  |      75 | `Brush HC` |
| 8   | 0x03AC | 0x14  |     125 | `Brush HW` |
| 9   | 0x03AB | 0x18  |     150 | `Brush HE` |

One telling difference: the added families spell the non-hollow style suffixes in **upper case** (`Brush TH`, `Eureka CN`, `Oakland WD`, `… EX`, `… HO`) where the carried five use title case (`Cobb Th`, `Marin Cn`, `… Wd`, `… Ex`, `… Ho`) - evidence of a different converter run, and proof that clients must match [RIP_EXTENDED_FONT_STYLE](../ripscrip/3.0-text-output-and-fonts.md#rip_extended_font_style) style names **case-insensitively** (the demo corpus already selects `marin`/`dixon`/`cobb` in lower case). EUREKA's and OAKLAND's handle sequences are ascending and non-contiguous (EUREKA 0x24, 0x25, 0x2D, 0x2E, 0x2F, 0x30, 0x31, 0x3B, 0x3D, 0x3E; OAKLAND 0x17, 0x87-0x8F) unlike the carried families' descending runs - the handles are engine-assigned and carry no cross-file meaning, exactly as the 2.0 page states.

### Trailer difference - no copyright section

The carried five end with `…[kerning record][separator B7 BC BA AB BE][COPR: + copyright text]` as documented (except SYMBOL, whose trailer offset is bogus and whose tail is truncated glyph data - a shipped Atech defect carried into RIPtel byte-identical, see the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#symbol-tail-corruption-shipped-defect)). The three added families end differently: the 5-byte separator comes **before** the kerning record (immediately preceding the trailer offset), the kerning record runs to exact end-of-file, and there is **no `COPR:` section at all** - no Atech copyright, no TeleGrafix copyright (verified: `COPR:` absent from all three files; BRUSH's kern record at 0x1544D is tag=1, totalLen=38 = 10 + 7×4, ending at 87,155 = EOF). The leaked PostScript tokens inside BRUSH ([research triage §1](../../3.0/research/riptel-binary-formats.md)) suggest these were converted from Type 1 sources by Atech's AllType converter in 1997, with the tool configured or versioned differently from the 1991-copyright batch.

## RIPtel 3.1 rendering contract

These are observations of RIPtel 3.1’s original RIPscrip 3.0.7 driver, with distinguishing synthetic glyphs executed by the original Atech rasterizer. They specify fill, outline filtering, drawing order and byte indexing; exact hinting, scan-conversion boundary pixels and host color realization are outside scope. [The primary derivation](../research/issue-22-fastfont-rendering.md) records original instructions, unchanged artifact hashes, copied-font mutations, controlled-service limits and reproducible probes. This does not assign unverified behavior to RIPterm 2.x merely because its files have the same format.

### Global bounds and spacing reference

The [corrected shared field map](../../2.0/techspecs/3.2-fastfont-fonts.md#global-bounding-box-and-header-copies) applies to all eight RFFs. The four metrics words +0x16/+0x18/+0x1A/+0x1C are signed **xmin/ymin/xmax/ymax** in y-down font units. The RFF header repeats them in reverse order at 0x1C/0x1E/0x20/0x22. The earlier labels calling xmax an ascender and ymax a width metric were incorrect; the three-family header table above now names coordinate bounds.

The original metric consumer transforms the rectangle's four corners and derives realized bounds. Spacing flag `0x0400` uses the realized **horizontal span `xmax - xmin`**, after font realization/orientation; it does not read one global header word as a width or substitute the maximum glyph advance. This preserves the [existing spacing adjustment](../ripscrip/3.0-text-output-and-fonts.md#size-rotation-baseline-and-spacing).

For MARIN, raw bounds (-78,-916)..(1059,250) have design width 1137 and height 1166. At 90 points/72 DPI with upright base style, ideal scaling by 0.09 gives X bounds -7.02..95.31 and, after the engine's Y-axis conversion, Y bounds -22.5..82.44. That explains the axis assignment in the previously measured **(-7,-22)..(95,82)** realized rectangle; it is not a new hinting or exact-rounding guarantee. For that recorded instance, `0x0400` uses width **102** device units. The ordinary F advance remains the separately converted 50 device units, as established by the [prior oracle](../research/issue-3-extended-font-style.md#unmodified-font-engine-rotation-oracle).

This correction uses read-only bytes and original instruction tracing; it does not rerun the prior native/GUI experiments or reopen their rendering conclusions. [Field/signedness derivation](../research/issue-82-rff-global-bounds.md).

### Solid contours

Use **nonzero winding** for the glyph’s filled interior. Same-direction nested contours leave the center filled; an opposite-direction inner contour cuts a counter. Duplicate same-direction contours remain filled; reversing the complete glyph preserves the result. Same-direction overlapping contours fill their overlap. Opposite duplicate contours cancel interior coverage, although the original scan converter still paints boundary pixels. Thus even-odd parity is incorrect, and an idealized cancellation of every edge pixel is also not a shipped pixel oracle.

_Evidence: original rasterizer with eight distinguishing contour records at six sizes; same-direction nested, duplicate, single and completely reversed cases have identical complete solid bitmaps. [Original-engine matrix](../research/issue-22-fastfont-rendering.md#original-engine-and-synthetic-font-checkpoint)._

### Hollow width and horizontal styles

Hollow is an outline made with an engine-selected **device-space bitmap stamp**. Its nominal diameter changes in discrete steps with font size and DPI and is capped. It is not the current graphical line thickness, a separate drawing-pen setting, or a constant-width em stroke. Horizontal style percentage scales the glyph geometry **without multiplying this stamp diameter**.

For the shipped files, calculate the hollow stamp index as follows:

```text
P = whole point size realized by the engine
    (tenths-of-a-point request + 5) / 10, integer division
    (the ordinary wire font-size field already specifies whole points)
D = X DPI for engine orientations 0/2, Y DPI for orientations 1/3
C = 2 normally, 4 when the BOLD face modifier is active
q = u16(floor(u16(C * D) * u16(P) / 7200))
k = min(q, 4) normally
    max(1, min(q, 7)) with BOLD
nominal stamp diameter = k + 1 device pixels
```

`u16` retains the low 16 bits, matching the original intermediate/return arithmetic. DPI is the driver’s world-to-device font DPI, not necessarily physical monitor DPI; see [size and rotation](../ripscrip/3.0-text-output-and-fonts.md#size-rotation-baseline-and-spacing). ITALIC alone does not change this diameter. The original metrics bytes **+0x12=4** and **+0x13=2**, previously listed together as constant 0x0204, supply the bold and ordinary hollow strengths. All eight recovered RFF files have those values. The hollow flag remains the style record’s byte +4; this is separate from the strength bytes.

At 72×72 DPI without BOLD:

| Point size | Filter index | Nominal stamp diameter |
| ---------- | ------------ | ---------------------- |
| 25         | 0            | 1 pixel                |
| 50         | 1            | 2 pixels               |
| 90         | 1            | 2 pixels               |
| 120        | 2            | 3 pixels               |
| 200        | 4            | 5 pixels               |
| 250        | 4            | 5 pixels, capped       |

The same diameters apply to Ho/HT/HC/HW/HE at horizontal percentages 100/85/75/125/150. For example, expanding a 90-point hollow style to 150% widens its glyph coordinates while retaining a nominal two-pixel stamp. Under BOLD, the larger coefficient and 1..7 index range instead allow nominal diameters 2..8 pixels.

“Nominal diameter” identifies the selected stamp, not an invariant count of covered pixels on every cross-section or an exact circular-pen/join rule. The first three stamps are 1×1, 2×2 and 3×3 squares; four- and five-pixel stamps have shortened corner rows. Clipping, scan stepping and the original glyph-cache path can affect observed edge pixels. A geometric implementation should keep the device-space outline width independent of the glyph’s horizontal percentage rather than scaling an already stroked glyph image.

_Evidence: original realization/representation construction 0x51eb0 / 0x56340, bitmap tables 0x85120 / 0x85160, actual selected-stamp captures and **1,440 anisotropic-DPI/orientation/face/width-style cases**. [Complete formula and validation](../research/issue-22-fastfont-rendering.md#completed-adapter-and-filter-scope-validation)._

### Overlapping glyphs and write mode

**Protocol boundary:** WRITE_MODE includes graphics text. The native fixed-copy observations below are historical client behavior, not an exception for a conforming implementation. The [drawing contract](../../2.0/techspecs/2.3-drawing-composition.md#operations-and-operands) defines the required color operation; it does not prescribe how a font renderer groups overlapping glyph coverage.

The driver rasterizes and presents **one glyph at a time**, clears its glyph buffer, then processes the next glyph. With shadow enabled, each glyph’s shadow copy precedes its foreground copy. There is no whole-text coverage-union stage.

In RIPtel 3.1, ordinary FastFont **glyph ink uses masked replacement**, independently of the current vector Write Mode. The original presenter uses a fixed bitmap operation that copies the selected foreground brush at ink pixels and preserves destination at non-ink pixels. Selecting XOR, OR, AND or NOT does not replace that operation with the named vector mode. Consequently two overlapping glyphs in XOR mode retain foreground ink at the overlap; they do not cancel. This is a statement about glyph bitmap presentation, not a claim that every text decoration shares its implementation.

_Evidence: original renderer loop 0x41568–0x42665, per-glyph presenter 0x40660 and fixed BitBlt operation 0xb8074a; all 256 masks at two overlapping positions after each of five original write-mode settings. [Native compositor checks and service-model limits](../research/issue-22-fastfont-rendering.md#native-renderer-compositor-and-slot-checkpoints)._

### Character bytes and raw font slots

The ordinary drawing path uses **raw unsigned byte codes**, without CP437-to-Windows-ANSI conversion, Unicode decoding or a special SYMBOL remap. For a file whose first code is 32 and count is 224, byte `c` selects table slot **`c - 32`** when 32 ≤ c ≤ 255. High bytes are not signed negative indices.

| Input byte | Raw character code | Glyph/advance table slot |
| ---------- | ------------------ | ------------------------ |
| 0x20       | 32                 | 0                        |
| 0x7F       | 127                | 95                       |
| 0x80       | 128                | 96                       |
| 0x82       | 130                | 98                       |
| 0xFF       | 255                | 223                      |

This indexing is identical for Marin and SYMBOL; the glyph artwork at a slot is face-specific. Do not apply Windows’ SYMBOL charset transformation or a CP437→CP1252 table before indexing the original file. A Unicode-facing renderer needs an explicit application-level conversion to the intended **wire byte**, then this byte-to-slot rule; UTF-8 is not decoded by this glyph path. NUL terminates the original C string. Codes below the font’s first character have no table entry; damaged SYMBOL tail records still need the existing [bounds checks](../../2.0/techspecs/3.2-fastfont-fonts.md#symbol-tail-corruption-shipped-defect).

_Evidence: all bytes 1..255 through original ordinary adapter and renderer, all 65,536 unsigned word codes through original cache range/index logic, and every raw slot through original relative-offset lookup. [Adapter and slot derivation](../research/issue-22-fastfont-rendering.md#completed-adapter-and-filter-scope-validation)._

## `atf.cfg` - the regenerated catalog

RIPtel's `FONTS/atf.cfg` (4,470 bytes) uses the same scheme as the RIPterm 2.30 `ATF.CFG` (684 bytes) documented on the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#atfcfg---the-engines-font-catalog-cache), but where the RIPterm 2.30 file is the stale FF1-era cache carried forward, RIPtel's is **freshly generated against the eight shipped `.RFF` files**. Byte-verified layout (both generations):

```text
0x00  u16  differs per file: 0x218E (RIPterm 2.30), 0x2654 (RIPtel) - meaning unverified
           (not a constant magic; not a simple byte-sum checksum of the content)
0x02  u16  fileCount     (RIPterm 2.30: 5; RIPtel: 8)
0x04  u16  totalStyles   (RIPterm 2.30: 6; RIPtel: 80)
0x06  u32  0
0x0A  fileCount × 78-byte entries:
        char[14]  filename, NUL-padded ("BRUSH.RFF" … "SYMBOL.RFF", alphabetical)
        u16       index of this font's first record in the style list
                  (RIPtel: 0, 10, 20, … 70; RIPterm 2.30: 0, 1, 3, 4, 5)
        u32       0
        byte[54]  verbatim copy of the font file's 0x00-0x35 header
        byte[4]   zero padding
then, at fileSize - 48 × totalStyles  (= 0x0A + 78 × fileCount - 4; RIPtel 0x276, RIPterm 2.30 0x18C):
      totalStyles × { u16 fileIndex, 46-byte style record }
        fileIndex = 0-based index of the owning file entry
        style record = the 46-byte format from the .RFF files, carrying the true
        engine handle from the source file; name padding is uninitialized memory
      … ending exactly at end-of-file (no trailing bytes)
```

The style-pair area's start overlaps the last file entry's zero padding by two bytes - the first pair's `fileIndex` is 0, indistinguishable from padding, which is why earlier decodes framed the records at the wrong offset (the [2.0 page's layout block](../../2.0/techspecs/3.2-fastfont-fonts.md#atfcfg---the-engines-font-catalog-cache) was corrected to this framing alongside this page).

Verified against the RIPtel file: all 8 header copies are byte-identical to the shipped files' first 54 bytes; all 80 records carry the exact handles, flags, scales, and names from the eight `.RFF` style tables (including the upper-case suffixes of the three added families); the `fileIndex` words read 0×10, 1×10, … 7×10 in file order. The catalog also preserves the DEFAULT quirk documented on the 2.0 page: record 24 ("DEFAULT Ex") has scale 0x8C = **140%** where every other family's Ex is 150% - the FF1-conversion fingerprint, carried through RIPtel's regenerated cache.

Delta summary vs the RIPterm 2.30 file: `fileCount` 5 → 8, `totalStyles` 6 → 80 (the RIPterm 2.30 cache lists only the base faces its `.FF1` sources contained, plus "DEFAULT EX"; RIPtel's lists all 10 synthesized styles per family), filenames `*.FF1` → `*.RFF`, cached header copies FF1-format → RFF-format (with `&T` sentinel), and the u16 at 0x00 changes value. The file is machine-written by the client and safe to regenerate, as before.

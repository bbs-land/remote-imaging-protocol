# Arc Consumer Contract

[◀ Prev: Fill Defects (delta)](2.0-fill-defects-delta.md) · [Contents](README.md) · [Next: Bézier Consumer Contract ▶](2.2-bezier-consumer-contract.md)

The [language reference](../ripscrip/2.2-curves.md#angle-ordering-and-sweeps) gives the command-specific angle policy. This page specifies the original RIPtel 3.1 numerical ray calculation and contour construction, so an implementor can adapt them to a geometric renderer without guessing from the inherited start/end prose. It describes driver 3.0.7; earlier clients' rendering is not established by these traces. Source identity, original instructions and controlled-service boundaries are in the [derivation](../research/issue-14-arc-sweeps.md).

## Axis-aligned endpoint rays

A/V/I/i/_ reduce each nonnegative input angle independently: values greater than 360 become `angle % 360`; 360 itself remains 360. Raw angular differences and turn counts are discarded. The actual result is an endpoint-ray pair, rather than a stored sweep.

Let R be the converted circular radius for A/I or the larger converted ellipse radius for V/i/_. The original five-degree sine table at RVA 0x76118 is:

```text
T = [0,871,1736,2588,3420,4226,5000,5736,6428,7071,
     7660,8191,8660,9063,9397,9659,9848,9962,10000]
```

For normalized angle a and positive R, integer division below truncates toward zero. Add the resulting `(dx,dy)` to the converted center. Device Y increases downward.

| Angle range   | dx                      | dy                      |
| ------------- | ----------------------- | ----------------------- |
| 0 ≤ a ≤ 90    | `R*T[(90-a)/5]/10000`   | `-R*T[a/5]/10000`       |
| 90 < a ≤ 180  | `-R*T[(a-90)/5]/10000`  | `-R*T[(180-a)/5]/10000` |
| 180 < a ≤ 270 | `-R*T[(270-a)/5]/10000` | `R*T[(a-180)/5]/10000`  |
| 270 < a ≤ 360 | `R*T[(a-270)/5]/10000`  | `R*T[(360-a)/5]/10000`  |

The signed expressions mean negate the positive quotient, not unsigned wraparound. This approximation affects the ray, not just final edge pixels: with R=40, angles 0 and 1 produce `(40,0)` and `(39,0)`, different integer points on the same ray. The native probe verifies this table/rule against every angle 0–4095, in each endpoint position, at radii 2, 40 and 200, through all six axis-aligned handlers and both border settings.

Compare the two **integer endpoint coordinates before projecting onto the ellipse**. The following table records original native calls for topology; apply the protocol N/operation rule immediately below it:

| Consumer | Identical integer endpoints | Different integer endpoints |
| --- | --- | --- |
| A / V | MoveToEx(endpoint), LineTo(same endpoint) | GDI Arc |
| I / i | MoveToEx(center), LineTo(endpoint), including with borders disabled | GDI Pie |
| _ | No draw call | GDI Chord |
| O | Ignores the two angle fields and draws a complete ellipse for positive radii | Same |

**Protocol operation:** I/i radial contours have no fill area. N1 draws that outline using solid COPY and current thickness/Draw Color; N0 suppresses it. The historical unconditional LineTo call is not an N0 requirement. A nonempty I/i/_ region uses current W for fill and, with N1, a solid COPY outline afterward. This also governs a full Pie's internal radius. See the [composition contract](2.3-drawing-composition.md).

For a geometric adapter, Arc/Pie/Chord use the intersections of the center-to-endpoint rays with the ellipse and advance counterclockwise. This is a **radial-bearing** construction; converting to ellipse parameter angles may be necessary for a renderer whose arc API uses parametric angles. Microsoft's [Arc](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-arc), [Pie](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-pie) and [Chord](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-chord) contracts define that boundary. Their complete-ellipse cases do not override the driver's earlier identical-integer-endpoint branches. Consequently 0..360 and 450..810 do not reach a full-ellipse GDI call in A/V/I/i/_.

For a kernel using ellipse-parameter angles, a nonzero ray vector `(dx,dy)` maps to `theta = atan2(-dy/ry, dx/rx)` in degrees modulo 360, with positive device radii rx/ry. The counterclockwise span between distinct curve intersections is `(theta_end-theta_start) mod 360`; the API's coincident-intersection/full-ellipse cases apply when that span is zero. Apply the driver's integer-endpoint shortcuts **before** this conversion. Pie center closure and chord endpoint closure remain separate topology operations. A ray collapsed to the center by integer quantization remains an API degeneracy, outside a claim of exact pixel reproduction.

Different integer endpoints can project to the same point on the ellipse. Retain that distinction when adapting the GDI calls: Arc/Chord document a complete ellipse for coincident curve endpoints, while [Microsoft's Pie remarks](https://learn.microsoft.com/en-us/cpp/mfc/reference/cdc-class?view=msvc-170#pie) describe a complete ellipse with an internal radial stroke for equal endpoints. The probe captures original arguments and branch choices; it does not execute Windows' rasterizer. Exact pixel coverage, pen caps, invalidation extents and radius-zero degeneracy are separate from this angle contract.

## Skewed contour construction

]/+/[ use the [order-dependent span normalizer](../ripscrip/2.2-curves.md#skewed-arc-span-normalization), rather than the axis-aligned ray reduction. Original generator 0x10160 visits every integer parameter angle from S to E **inclusively**, using the ellipse radii and rotation. The resulting arc-sample count is E−S+1, including one sample for a zero span. This is an ellipse-parameter traversal, followed by rotation; it is not the GDI radial-bearing calculation above.

| Consumer | Points supplied to the drawing call |
| --- | --- |
| ] | Arc samples only, passed to Polyline |
| + | Arc samples, then first sample again, passed to Polygon |
| [ | Arc samples, then center, then first sample again, passed to Polygon |

Closure is unconditional. For a full normalized turn the last arc sample already equals the first. + therefore adds a zero-length closing edge; [ still appends the center and produces center-to-edge segments inside the complete contour. With borders enabled those segments participate in the actual border path. A zero-span [ similarly supplies a degenerate radial contour rather than a uniform empty operation. Both border settings are verified through the original handlers.

The full-figure &/- commands also call the generator for 0..360, but submit **360 points** to Polygon and let it close the contour; they do not forward the duplicate final sample. Native checks cover both border settings and rotations 0/90/450 degrees.

Spans greater than 360 retain multiple traversal in the sample sequence. Reducing them to a single full ellipse can change polygon overlap/fill and repeated outline write effects. The original normalizer's 0..719 and 0..720 discontinuity is therefore observable independently of exact edge rasterization.

## Coordinate evaluation and rotation

For the reconstructed skewed family, convert center and radii from world to device units **before rotation**. Convert rx with X scale and ry with Y scale. Add the selected viewport's device origin to the center once; do not scale that origin or add a screen-port origin a second time. With device radii Rx/Ry, positive rotation r and parameter t, the geometric interpretation is:

```text
u = Rx * cos(t); v = Ry * sin(t)
x = center_x + u*cos(r) - v*sin(r)
y = center_y - (u*sin(r) + v*cos(r))
```

Device Y increases downward, so positive r rotates counterclockwise on screen. Rotation is of the already converted device ellipse, not a world ellipse that is scaled afterward. For world 1280×960/device 640×960, center (100,80), viewport origin (5,7), radii (20,10), r=90 and t=0, the result is **(55,77)**. Rotating in world space before scaling would produce (55,67), a different contour. Exact edge rasterization remains unspecified.

### Reproducible Q14 numeric profile

The above geometry and preserved parameter traversal are the reconstructed contract. The original client's **Q14 sampling profile** below is supplied for implementations that need its actual quantized point list. Published protocol documentation does not require these particular one-unit trig approximations; an ideal geometric renderer need not reproduce them. A renderer claiming this numeric profile must use its constants and staged rounding, rather than call floating-point sin/cos and round once at the end.

The [complete tables and vectors](data/skewed-ellipse-q14.json) contain separate 360-entry sine and cosine arrays with scale Q=16384. Source: unchanged DLL SHA-256 `83d71b358492b15bcfd3773c30a52784881a3a49a5b6e9029d986b3cba1fd5e8`; sine RVA 0x7b638/file 0x79c38, cosine RVA 0x7b098/file 0x79698. Each array is 1,440 bytes encoding 360 little-endian signed int32 values; their raw-byte hashes are in the JSON. The JSON integers are a transcription of those arrays, not a generated ideal-trig approximation. In particular S[30]=8191 and S[330]=-8192, while C[60]=C[300]=8192: do not derive cosine by shifting the sine array.

Use table indices modulo 360. Let floorQ(z)=floor(z/16384), including **toward negative infinity** for negative z. Given already converted center/radii:

```text
u = floorQ(Rx * C[t])
v = floorQ(Ry * S[t])
x = center_x + floorQ(u*C[r] - v*S[r])
y = center_y - floorQ(u*S[r] + v*C[r])
```

There are two rounding stages. The two radius products are shifted separately; each rotation dot-product is summed/subtracted **before** its shift. Do not shift both rotation products separately. Original generator 0x10160, arithmetic 0x10201–0x1023f, establishes that order; producer calls 0x1fb40/0x1fb51 establish conversion before generation, with the viewport-origin addition between them and 0x1fbb0. The [derivation](../research/issues-74-76-drawing-contract.md) records the instruction/data boundaries without executing the client.

| Device center | Device radii | r   | t   | Profile point |
| ------------- | ------------ | --- | --- | ------------- |
| (10,20)       | (6,3)        | 0   | 0   | (16,20)       |
| (10,20)       | (6,3)        | 0   | 90  | (10,17)       |
| (10,20)       | (6,3)        | 0   | 180 | (4,20)        |
| (10,20)       | (6,3)        | 0   | 270 | (10,23)       |
| (10,20)       | (6,3)        | 90  | 0   | (10,14)       |
| (100,80)      | (13,7)       | 30  | 30  | (108,72)      |
| (100,80)      | (13,7)       | 30  | 330 | (111,78)      |
| (100,80)      | (13,7)       | 390 | 390 | (108,72)      |
| (0,0)         | (131072,3)   | 0   | 0   | (131072,0)    |

For the (13,7),30,30 row, the first stage gives u=11 and v=3; the second gives offsets (8,-8). This distinguishes staged rounding from a single final floating-point rounding.

Evaluate products/sums in sufficiently wide signed arithmetic (64-bit intermediates suffice for 32-bit coordinates and these coefficients). The profile defines floor divisions and table lookup, not signed 32 wraparound or a historical bounding-box accumulator limit. For Rx=131072, r=t=0, center 0, the wide result is (131072,0). Native overflow reproduction is an optional client-emulation concern outside protocol conformance. An implementation's supported coordinate/allocation limits must not silently redefine an overflowing product as another geometric shape.

### Geometry is not a drawing-pass exception

The [drawing-composition delta](2.3-drawing-composition.md) defines the operation on these contours: standalone &/] strokes use W; filled -/+/[ use W for the region and COPY for the optional patterned border. Their raw generated point count does not by itself count pixel writes. Zero-length duplicate closure edges and ordinary joins do not automatically add contributions; genuine repeated traversal does. Existing integer-ray/native-call observations above describe historical topology and do not override N0 suppression or the protocol's border operation.

## Affine Ellipse Contours

These contours serve the [five affine ellipse commands](../ripscrip/2.2-curves.md#affine-ellipse-commands). Coordinates name the center C, conjugate radius endpoints A/B and, where supplied, ray endpoints S/E. Apply the X and Y WORLD-to-device ratios independently to every coordinate pair before deriving any vector. Truncate the projected coordinates to integers. These primitives use projected port-space positions directly and clip to the selected viewport. The viewport origin supplies no translation to these contours.

### Ring and Direction

If both projected A and B equal C, return the open one-point run `[C]`. Otherwise order the radius endpoints by integer polar angle. Given `(dx,dy) = endpoint - C`, use 90 for vertical up and 270 for vertical down or the zero vector. For nonzero dx compute `a = atan(-dy/dx) × 180/π` in degrees. Truncate a toward zero, then add 180 when dx is negative, or 360 when dx is positive and a is negative. If B has the smaller angle, swap A and B. A tie preserves input order.

Compute `U = A - C` and `V = B - C` after ordering. Form the 72 points in increasing `t = 0,5,…,355` using the separate [Q14 cosine and sine arrays](data/skewed-ellipse-q14.json). For each axis component:

```text
P[t/5] = C + floor((U * cosQ14[t] + V * sinQ14[t]) / 16384)
```

Sum the two products before taking the signed shift. A whole ellipse returns this 72-point path with closed topology, including the edge from P[71] to P[0]. No duplicate endpoint is required. With collinear radii or a single zero radius, use the same samples and later ray selection. The integer contour controls the resulting stroke and any enclosed area.

Within the ordinary signed-device range the above formula is the shipped sample arithmetic. The DLL uses 32-bit products and sums, followed by an arithmetic shift and sign extension of the low 16 bits of each shifted offset and each center coordinate. Those width rules describe the original numeric path for callers reproducing large coordinates. The one-point early return copies the projected C directly.

### Partial Contours

For a projected ray endpoint equal to C, use the ordered A for the start ray or ordered B for the end ray. This substitution occurs after ordering. An interior point and an exterior point on the same forward ray both give its direction. For each ray, visit segments `P[i] → P[(i+1) mod 72]` in order starting at i=0.

Solve the intersection of the segment's line and the ray's line. Skip parallel lines, including collinear lines and zero-length segments. Truncate the intersection X and Y toward zero **before** checking inclusion. Keep the first integer point within the segment's inclusive X/Y bounds and on the ray's forward side in both axes. To implement that test, an increasing or zero ray component requires the corresponding hit coordinate to be at or above C's coordinate, and a decreasing component requires it to be at or below C's. There is no circular distance comparison or requirement that S/E themselves lie on the ring.

Let the selected hits be Hs and He, with segment indices i and j. Apply the original fallback rules in order:

1. If the start ray misses, set Hs=P[0] and i=0.
2. If the end ray misses, set He=P[71] and set **i=71**, retaining Hs. Keep j absent.
3. If Hs equals He, return the full 72-point closed ring. This is also the result for different rays that quantize to identical hits.
4. Otherwise start the run at Hs. If j is present and i differs from j, append ring vertices from P[(i+1) mod 72] forward through P[j], with wrapping. If the two indices agree, append those vertices on a full wrap only when He precedes Hs in that segment's direction. Compare X on nonvertical segments and Y on vertical segments. If j is absent, append no ring vertices.
5. Append He. The arc returns this open run. Pie appends C and the first point and returns closed. Chord appends the first point and returns closed.

Keep repeated points in the run. A one-point result has no polygon or line segment. A two-point result remains a segment, and a closed contour with no enclosed samples has an empty interior. The [portable presentation rules](2.3-drawing-composition.md#affine-ellipse-composition) handle the selected stroke or fill.

## Filled-curve implementation correction

The original I/i/_ helpers call GDI Pie/Chord, and the skewed filled handlers submit Polygon contours. Their traced paths do not flood-fill an arc-plus-radii boundary. This corrects this repository's earlier adoption of RIPlib's `§BUG.6` as a demonstrated RIPtel leak; the [fill-defect record](../../2.0/techspecs/2.1-fill-defects.md#bug6---withdrawn-piechord-flood-leak-attribution) preserves the correction and scope. It does not prove an older RIPterm binary or every display driver free of rendering defects.
